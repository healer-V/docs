# 技术方向知识目录生成规范

知识目录是知识范围、理解依赖和文章职责的表达。生成目录时，必须先说明读者需要掌握什么、哪些知识相互依赖、每篇文章负责什么，再决定章节和文件数量。

本规范服务于“从 0 系统学习一门语言或技术”的核心定位。目录必须以初学者的理解依赖为依据，从当前技术的基础知识和基本用法逐步展开到机制、应用与进阶实践，并兼顾学习后的查阅和复用；完整性以声明范围内的知识和能力闭环判断。

| 项目 | 约定 |
|------|------|
| 适用任务 | 规划某个技术方向、创建模块蓝图、规划章节与逐篇大纲、全文重构模块目录 |
| 核心交付 | 一份可评审的方向或模块蓝图，包含范围、来源、知识项、依赖、目录、职责卡、覆盖矩阵及验证计划 |
| 前置规范 | [知识体系与方向分类规范](./knowledge-system.md) |
| 配套正文规范 | [技术文章生成与验收规范](../article/article-generation.md) |
| 蓝图存放 | 已确认的蓝图放在 `standards/blueprints/<方向>/<模块>.md`；模板见[模块蓝图模板](../templates/module-blueprint-template.md) |
| 可复用指令 | [目录规划指令](../prompts/directory.md) |

## 一、任务范围与输入契约

### 1. 先确定“方向”的层级

“后端”“Java”“Java 并发”属于不同规划层级。生成前必须判断用户要的是领域地图、完整技术模块还是已有模块内的局部主题，不能默认把它们都扩成一整套技术百科。

| 层级 | 典型对象 | 规划责任 | 交付边界 |
|------|----------|----------|----------|
| 知识领域 | 前端、后端、AI 应用工程 | 明确领域中的技术模块、能力分工和跨模块依赖 | 先交付领域蓝图；选定模块后分别补齐知识项和文章职责 |
| 技术模块 | Java、React、MySQL、Docker | 围绕一个明确对象建立完整知识体系 | 按本规范交付模块级完整蓝图 |
| 模块内主题 | Java 并发、React Hooks | 在既有蓝图内补足一组相邻知识 | 只调整受影响的章节、职责与依赖 |

领域蓝图不能冒充所有模块已经完成的逐篇目录。确需一次规划多个模块时，必须逐个完成模块契约与覆盖分析，并明确各自成熟度；未经分析的模块只作为候选，不生成伪完整的章节列表。

### 2. 必须获得的任务信息

先读取用户输入、已有蓝图和仓库上下文。能够从已确认资料唯一确定的字段直接复用；涉及实质范围或主版本的歧义时，只询问最关键的问题，同时继续不依赖该答案的现状审计。

| 字段 | 必须明确的内容 | 缺失时的处理 |
|------|----------------|--------------|
| 方向名称与层级 | 具体技术对象；领域、模块或局部主题 | 结合现有目录解释判断依据，仍存在重大歧义时确认 |
| 任务类型 | 新建、全文重构、目录规划或局部补足 | 默认只规划，不将规划要求扩大为全文重写 |
| 目标读者 | 通用基础、当前方向起点、使用场景 | 默认对目标语言或技术零基础；语言入门不默认掌握其他语言，跨技术必要前置须声明深度与学习入口 |
| 目标能力 | 读者最终能够执行和判断的具体事情 | 转成可验证的能力描述，避免“全面掌握”等空话 |
| 主版本 | 主技术、运行环境和关键依赖 | 优先复用已确认蓝图；不能自行用“最新”代替版本 |
| 维护线 | 是否需要旧版本维护与迁移内容 | 根据用户与已有项目约束确定，不默认复制第二套基础教程 |
| 目标目录 | 拟使用的模块位置与已有路径 | 优先复用；新路径标记为规划路径 |
| 范围排除 | 明确不讲什么，以及由谁负责 | 依据主方向和目标能力划定 |
| 修改权限 | 是否涉及改名、移动、导航和站内引用更新 | 目录设计本身不授权实施这些变更 |
| 验证条件 | 可用运行时、服务、示例环境和检查入口 | 记录可验证范围与核心障碍，不编造可执行性 |

在当前项目中，已确认的模块蓝图保存到 `standards/blueprints/<方向>/<模块>.md`，规划草稿与评审记录保存到本地 `superpowers/`（不提交到远程）；具体技术文章按已确定的模块位置落入项目。其他项目使用其自身明确的输出规则。

### 3. 模块教学契约

蓝图首先定义模块边界。

| 字段 | 要求 |
|------|------|
| 模块名称 | 与目标目录和导航定位一致 |
| 主知识方向 | 从知识方向分类中选择一个并说明依据 |
| 辅助知识方向 | 仅列完成目标所需的方向，没有则明确写“无” |
| 读者基线 | 默认具备的通用知识和当前方向的起点 |
| 主版本基线 | 技术、运行环境和关键依赖版本 |
| 最终能力 | 读者完成模块后能够执行和判断的具体事情 |
| 前置知识 | 由其他模块负责完整讲解的内容及目标链接 |
| 范围排除 | 当前模块明确不讲的主题和归属位置 |
| 事实来源 | 官方规范、文档、仓库、发布说明和验证方式 |

最终能力必须使用可判断的描述，例如“能够根据执行计划判断索引是否生效”，不能只写“深入理解性能优化”。

## 二、现状与事实来源

### 1. 目录规划前的检查顺序

现状检查必须覆盖实际文件与配置。文件存在只说明有资产，不能直接判断它已经承担了相应知识职责。

1. 读取适用的 AGENTS.md 和分层文档规范索引，并按任务路由读取对应规范。
2. 查看工作区状态，记录与目标模块重叠的已暂存、未暂存和未跟踪内容。
3. 读取目标模块真实目录、已有文章及相邻内容，了解实际范围和深度。
4. 对照 nav、sidebar、模块首页和正文引用，区分真实目标与规划条目。
5. 查阅既有蓝图、样板评审、交付记录及已确认的版本约束。
6. 建立主版本官方资料清单，并核对可用示例验证环境。

对需要判定“已覆盖”的知识项，必须阅读对应正文并检查深度和证据；抽样只能用于初步识别，不得推断整个模块已经完成。全篇核对尚未完成的内容记录为未审计，不纳入已完成统计。

对已确定在重构时重新编写的模块，旧正文及其资源保留，但不再评估旧稿覆盖率、建立复用映射或挂载到新目录。目录清理只调整展示与关联，不隐含删除旧文件；重构时按已确认目录重新编写。

### 2. 来源与版本规则

知识清单至少同时参考方向覆盖模型、主版本官方资料、现有内容与真实工程目标。官方目录和旧 sidebar 都是输入，不能直接作为最终教学目录。

| 来源 | 主要作用 | 约束 |
|------|----------|------|
| 官方规范与标准 | 明确语言、协议、语义与限制 | 记录对应版本或生效范围 |
| 官方文档 | 明确 API、配置与对象模型 | 链接到具体页面，不使用搜索结果页 |
| 官方仓库与发布说明 | 核对实现边界、版本变化与迁移 | 区分稳定接口与内部实现 |
| 实际执行与测试 | 证明示例、错误和状态变化 | 记录环境、入口和实际观察结果 |
| 现有文章与案例 | 判断已有覆盖、重复与工程需求 | 内容结论仍需核对，不能因文件已存在就当成事实 |

每项核心技术结论必须具有可追溯依据。无法确定主版本、核心接口或兼容关系时，将受影响内容列为阻断项，不能把推测写成已确认知识。资料不可获取时可以交付标明边界的规划草案，但不能宣称蓝图已具备正文生成条件。

## 三、按知识方向检查覆盖

### 1. 方向覆盖模型

每个模块选择一个主方向，必要时增加辅助方向。下表用于检查适用知识，不规定章节名称、数量或机械顺序；不适用项必须写明理由。

| 主方向 | 必须检查的知识范围 | 重点边界 |
|--------|--------------------|----------|
| 编程语言 | 环境与入口；词法、变量和常量；类型、表达式与转换；控制流；函数或方法；数据与对象；模块与错误；运行机制；构建、调试、测试与版本演进 | 当前语言自身的语法和类型必须建立；语言不存在的能力不得硬补 |
| 框架与类库 | 宿主平台；安装与入口；核心对象与模型；专用语法；核心 API；生命周期与运行机制；组合设计；测试、性能、安全及生态集成 | 不重新系统讲解宿主语言的全部基础 |
| 数据库与存储 | 环境与连接；数据模型与类型；定义、读写、查询；约束、索引和数据组织；事务、一致性与并发；驱动集成；性能与权限；备份恢复和升级 | 数据库语义与应用层封装分开负责 |
| 工程化工具 | 安装、输入与产物；配置、任务和依赖图；常用操作；扩展机制；调试与产物验证；缓存、性能、安全与版本 | 命令、输入、产物和失败证据形成闭环 |
| 基础设施与平台 | 资源对象；生命周期；配置与操作；网络与存储；身份、权限与隔离；日志、指标和状态；容量、高可用及恢复 | 需要说明操作条件、风险和恢复验证 |
| 协议与 Web API | 参与角色；消息或对象模型；状态与时序；调用规则与事件；错误与关闭；安全边界；性能兼容；调试方式 | 以交互、状态变化和观察证据解释行为 |
| 架构与方法 | 问题与约束；角色、所有权和边界；交互与状态；关键机制与失败传播；决策取舍；演进、验证和反模式 | 必须有具体场景、成本和采用条件 |
| AI 工程 | 模型接口和限制；上下文、结构化输出和知识检索；应用与工作流；工具、状态和人工控制；质量评测；安全边界；成本、延迟与运行 | 围绕 AI 应用生命周期组织，辅助方向不各自扩写成完整教程 |

例如 Java 的变量与类型属于当前方向基础，不能因为读者学过其他语言而省略 Java 的具体规则；React 可以将 JavaScript 作为前置知识，但必须解释 JSX、组件、数据流及框架运行模型。这是规划边界示例，不是完整技术目录。

### 2. 当前方向基础与外部前置

完整性只在已经声明的范围内判断。以“读者零基础”为由无限扩写其他方向，会造成重复与失去主线。

| 类别 | 当前模块必须做什么 | 当前模块的展开边界 |
|------|--------------------|--------------------|
| 当前方向基础 | 从可理解起点建立概念、规则和必要示例 | 不得用“前置知识”逃避本模块责任 |
| 跨方向前置 | 明确要求深度和有效资料位置 | 只保留当前主题所需的最小说明 |
| 生态与集成 | 解释完成目标所需的接入边界 | 不复制依赖产品的全部教程 |
| 工程与生产 | 根据模块能力目标提供测试、诊断或恢复知识 | 不把所有技术都扩成统一的“生产篇” |
| 版本差异 | 指明主线行为和维护线的差异归属 | 不把新版本行为套用到旧版本 |

外部前置若缺少站内文章，可引用准确的官方资料，或把站内补建项列入规划清单。不能创建指向不存在文件的正文链接来填补前置关系。

## 四、知识项、依赖与覆盖

### 1. 知识项的最小字段

知识项用于判断覆盖责任，不等于标题，也不要求一项对应一篇文章。粒度应能独立判断“有没有讲清且达到目标深度”。

| 字段 | 填写要求 |
|------|----------|
| 知识项 ID | 模块内唯一、可稳定引用；目录重排时保留对应关系 |
| 名称 | 一个具体规则、API、机制、状态变化或设计判断 |
| 分类 | 基础、核心能力、机制、组合设计、工程、质量、生产或演进 |
| 前置 ID | 真正必需的内部知识项；外部前置明确写出模块与主题 |
| 来源 ID | 指向已核对的来源及适用版本 |
| 目标深度 | 认识、使用、解释、设计或诊断 |
| 必要证据 | 代码、配置、命令、输出、状态图、日志、指标、案例或决策表 |
| 主讲文章 | 负责完整解释的唯一文章 ID |
| 覆盖状态 | 已覆盖、部分覆盖、未覆盖或不适用；未审计时单列核对状态 |

“React Hooks”通常不足以作为唯一的覆盖责任单位；但把每个形参名都拆成独立知识项也失去意义。划分时检查它是否对应独立使用规则、行为或判断。

### 2. 知识项来源

知识项至少从以下来源交叉生成：

- 当前知识方向覆盖模型；
- 主版本官方文档或规范的主题范围；
- 现有模块文件和 sidebar；
- 真实使用所需的工程、质量和生产能力；
- 已知版本差异、常见失败和迁移风险。

现有目录只能作为输入证据，不能作为完整性基准。官方目录也不能直接复制为教程目录，需要根据读者基线和知识依赖重新组织。

### 3. 依赖与排序

依赖只表达理解或使用的必要条件。主题相似、作者习惯和文件创建时间不能自动变成前置依赖。

| 检查 | 必须满足的要求 |
|------|----------------|
| 依赖有效 | 所有内部 ID 存在，外部依赖有明确归属与访问方式 |
| 原因明确 | 能说明缺少该知识后无法理解或执行的具体内容 |
| 无循环 | 不存在直接或间接循环；出现循环时重新划定概念层次或文章边界 |
| 顺序一致 | 目录顺序符合依赖；必要基础位于依赖它的能力之前 |
| 同层排序 | 无直接依赖时，按使用频率、认知负担或统一业务过程排序并说明理由 |
| 跨模块引用 | 保留最小上下文和主讲链接，避免相互要求先读完整模块 |

### 4. 覆盖矩阵与完成口径

蓝图必须同时证明知识有归属、最终能力有支撑。仅有目录树或文章总数不算完成。

| 矩阵 | 必须包含的列 | 规划通过条件 |
|------|--------------|--------------|
| 知识覆盖矩阵 | 知识项 ID、归属章节、主讲文章、目标深度、证据、正文覆盖状态 | 适用知识项均有唯一归属，排除项有理由 |
| 能力覆盖矩阵 | 最终能力、支撑知识项、负责文章、验证方式、当前状态 | 每个声明能力都有知识和验证支撑 |

**规划归属完整与正文已经完成是两个状态。** 新建模块的正文可以全部是“未覆盖”，但每项责任必须规划明确；不能把计划中的代码和验证写成已执行。模块最终验收时，必需知识项仍部分覆盖或未覆盖，就不能判定完整。

## 五、章节组织与逐篇职责

### 1. 聚合章节的规则

依赖检查通过后，按共同对象模型、目标能力或执行链路聚合章节。章节数量从知识边界产生，不预设“必须十章”或“每章五篇”。

| 章节字段 | 要求 |
|----------|------|
| 章节名称 | 准确、精简地概括共同技术主题，保留必要限定，避免冗长解释与“核心知识”“高级内容”等空泛名称 |
| 章节目标 | 明确该章建立的模型或能力 |
| 包含知识项 | 列出当前章节拥有的知识项 ID |
| 前置章节 | 仅列真实必要前置，并说明依赖原因 |
| 排除范围 | 易混入但由其他章节负责的内容 |
| 统一场景 | 需要连续示例时，确定业务对象、字段、端口和状态命名 |
| 验证方式 | 如何证明本章的知识与能力闭环 |

概述不提前展开全部 API 和工程细节；工程内容不能替代基础与机制。对比、迁移和速查放在读者理解对应对象之后，必要的版本环境说明放在实际入口附近。

### 2. 拆分与合并文章

每篇文章只回答一个主要问题，同时具备必要上下文和证据。文章长短是复核信号，不能按固定字数机械切分。

| 情况 | 处理要求 |
|------|----------|
| 同时回答多个独立问题 | 按主要问题拆分，并重新核对依赖 |
| 不同部分需要完全不同的验证环境 | 评估拆分为各自可复现的文章 |
| 基础语法、机制和排障各自形成完整论述 | 分配不同主文章类型，不挤入一篇 |
| 一个主题只有定义和一两条事实 | 合并到上级或相关小节，避免一知识点一空壳文章 |
| 多个知识项共同构成不可分割的状态变化 | 保持在一个可解释闭环内 |
| 两篇文章重复概念、示例和边界 | 确定唯一主讲，另一篇缩为必要上下文和引用 |
| 文章必须借用另一篇完整正文才能理解 | 补足最小上下文，或重新判断是否应该合并 |

文章篇幅不设置统一字数、段落数或行数门槛，只能触发复查。代码块超过10行必须折叠是展示要求，不是删减内容或拆分文章的依据。

### 3. 每篇文章必须有职责卡

目录中的每一篇正式规划文章都要填写职责卡，不得仅输出编号、标题与一句“介绍相关知识”。职责卡是正文生成的输入，放在蓝图中，不作为普通文章开头的教学模板。

| 字段组 | 必填内容 |
|--------|----------|
| 身份 | 文章 ID、标题、规划文件路径、所属章节 |
| 唯一问题 | 一个明确问句，说明读者通过本文要解决什么 |
| 知识归属 | 主讲知识项、引用知识项、必要前置、容易重复的主讲位置 |
| 内容类型 | 一个主类型，最多一个辅助类型 |
| 范围与深度 | 必须覆盖、明确不覆盖、目标深度、版本边界 |
| 证据 | 业务场景、核心示例或其他证据、必要环境与触发入口 |
| 可观察结果 | 读者应观察到什么、该结果证明什么 |
| 失败边界 | 错误、反例或不适用条件，以及判断方法 |
| 核验 | 来源、计划验证方式、当前实际验证状态 |

正文类型与证据要求按配套[技术文章生成与验收规范](../article/article-generation.md)执行。

职责卡中的示例按业务场景、知识规则、必要环境和预期结果描述，不引用仓库示例目录、既有源码入口或跨章脚本。目录、蓝图与公开交付记录同样不得提供该目录的内容入口；每篇所需的最小实现由对应正文完整给出。

示例结构按文章职责选择：独立程序使用文件名，包、访问控制、模块系统和构建主题才规划必需的目录关系。不要给所有基础文章套用统一的多层工程路径。

### 4. 目录命名

章节名称概括共同的技术对象或能力，文章标题概括具体负责的问题，均优先使用“技术对象 + 必要限定”的短语。完整知识清单、范围解释和能力目标放入章节职责与文章职责卡，不在名称中逐项堆叠；职责卡可以用完整问句描述问题，标题使用准确、精简的概括。

目录、职责卡与 sidebar 对同一主题的命名必须保持一致的含义。子项可以省略父级已经明确的范围，但文章标题应能在搜索结果中独立识别。保留必要术语、版本与问题边界，删除无信息量的修饰，不为缩短而生造缩写或改成空泛名称，也不设置统一字数上限。

名称冗长时先精简措辞；仅当实际包含多个独立问题时，才按职责重新组织章节或文章，不按标题长度机械拆分。命名示例与详细检查见[正文组织与表达规范](../writing/content-organization.md)“标题命名”。调整已有名称时，仍须核对标题、导航与站内锚点引用，不根据显示名称自动改动文件路径。

## 六、文件结构与导航约束

### 1. 章节与文件编号

当前项目新建或全文重构技术模块时，采用“模块目录 → 独立章节文件夹 → 文章文件”的结构。历史平铺目录只在相应模块获准治理时迁移。

| 对象 | 必须遵守的规则 |
|------|----------------|
| 模块位置 | 复用已经确认的领域和模块路径，不因视觉分组变化自动移动源码 |
| 章节文件夹 | 两位连续编号加英文主题，如 `01-language-foundation` |
| 文章文件 | 每章独立从 `01` 连续编号，英文名称准确表达主题 |
| 编号意义 | 表达依赖与阅读顺序，不表达创建时间 |
| 章节名称 | 使用实际技术职责，不机械复制统一基础、核心、进阶模板 |
| 模块首页 | 可以保留或规划独立 `index.md`，不占章节文章序号；未创建前不加入正式链接 |
| 图片 | 放到所属文章同级的 `images/` 目录，引用使用相对路径 |
| 改名或移动 | 先搜索引用，设计 sidebar、正文链接与锚点引用的更新方案；旧 URL 和旧锚点直接作废，不生成兼容页或隐藏锚点 |

以下只是说明编号重置的结构示意，不是 Java 的完整知识目录，也不表示需要创建这些文件。真实目录必须由知识项与依赖分析得到。

```text
content/backend/04-java/
├── 01-language-foundation/
│   ├── 01-overview.md
│   └── 02-java-platform.md
└── 02-language-syntax/
    ├── 01-variables.md
    └── 02-data-types.md
```

参照既有模块的层级规则时，以规范要求为准；历史工作区中正在迁移的重复编号或中间目录不能成为新目录的合规依据。

### 2. 规划目录与正式导航

规划可以描述未来文件，可点击的正式导航必须落到真实内容。公开目录只展示章节、编号和文章标题；未编写文章使用无链接文本，由目录页统一说明规划性质，不逐项追加状态，也不挂载旧稿参考入口。

| 对象 | 允许的状态 | 使用要求 |
|------|------------|----------|
| 蓝图目录树 | 章节、文章与目标路径 | 规划性质统一说明，不添加旧稿状态 |
| 章节与文章规划表 | 有完整职责的未来条目 | 文件尚未创建时使用无链接标题 |
| 正式 nav、sidebar | 已存在的有效目标；获准展示的规划条目使用纯文本 | 正文完成并通过对应验收后接入链接，不增加旧稿子入口 |
| 模块首页开放范围 | 真实已开放内容 | 不能以计划数量冒充完成数量 |
| 目录调整清单 | 当前路径、目标路径、引用影响、更新范围 | 先评审，后按授权范围实施；不作为旧地址跳转表 |

目录规划完成只交付蓝图与影响清单，不创建空壳正文，不批量改名，不更新正式导航。用户另行明确授权的操作，仍需满足当前任务的阶段门禁。

## 七、既有模块整理

### 1. 通用整理流程

整理技术模块时，按以下顺序执行：

| 顺序 | 步骤 | 处理原则 |
|------|------|----------|
| 1 | 查看真实目录 | 确认实际 Markdown 文件，不只读取 sidebar |
| 2 | 检查导航配置 | 对比文件、sidebar、导航和页面链接 |
| 3 | 判断知识闭环 | 按基础、机制、能力、实践和参考检查缺口 |
| 4 | 重排学习路径 | 按理解依赖排序，不按文件创建时间排序 |
| 5 | 复用已有文件 | 能复用现有路径时不随意重命名 |
| 6 | 规划新增内容 | 明确文件名、主题边界和导航位置 |
| 7 | 验证完整性 | 检查编号、链接、sidebar 和构建结果 |

### 2. 推荐知识模型

| 模块类型 | 推荐组织方式 |
|----------|--------------|
| 基础语言类 | 概述 → 语法基础 → 核心机制 → 常用 API → 进阶特性 → 工程实践 → 规范参考 |
| 框架类 | 概述 → 项目创建 → 核心语法 → 组件、状态、路由 → 原理 → 工程实践 → 性能与部署 |
| 工程化工具类 | 概述 → 安装配置 → 核心概念 → 常用场景 → 插件扩展 → 优化 → 最佳实践 |
| 浏览器与 Web API 类 | 概述 → 基础模型 → 核心 API → 事件与异步 → 安全限制 → 性能 → 兼容性参考 |

::: warning 导航占位
正常内容维护不得向 sidebar 添加指向不存在文件的链接。只有任务明确要求先规划知识目录时，才可以设计待建设条目，并且必须明确标记其状态。
:::

公开目录和 sidebar 只展示章节、编号与文章标题，不添加“待核对”“现有稿”“旧稿参考”等标记，也不在规划文章下挂载旧稿入口。尚未编写的文章保留无链接标题，规划性质在模块目录页统一说明，不逐项追加状态文字。旧正文及其资源默认保留，但不参与新目录映射、覆盖核对或导航生成；重构时按已确认目录重新编写。不得因旧文不再收录到目录而删除文件，删除必须另有明确授权。

## 八、交付结构与执行流程

### 1. 模块蓝图的完整交付包

可以使用下列结构组织规划文档，也可以按项目模板排版，但不能遗漏责任信息。领域级任务交付模块地图与跨模块关系；模块级任务必须完成全部适用项。

| 顺序 | 交付部分 | 必须能回答的问题 |
|-----:|----------|------------------|
| 1 | 任务及现状 | 规划哪一层，现有内容是什么，允许改变什么 |
| 2 | 模块契约 | 面向谁、以什么版本、最终能做什么 |
| 3 | 方向模型与边界 | 哪些适用，哪些是前置，哪些明确排除 |
| 4 | 版本与来源清单 | 核心事实从何而来，对应什么版本 |
| 5 | 知识项清单 | 必须掌握哪些具体规则、能力和机制 |
| 6 | 依赖关系及排序理由 | 为什么先讲 A 再讲 B，有无循环 |
| 7 | 章节目录与职责 | 各章围绕什么对象或能力，边界是什么 |
| 8 | 逐篇职责卡 | 每篇解决什么，如何证明讲清楚 |
| 9 | 知识与能力覆盖矩阵 | 是否有遗漏、重复主讲和无验证能力 |
| 10 | 样板选择 | 哪篇能校准主要深度、证据与边界 |
| 11 | 文件、导航和调整清单 | 拟改变哪些路径和引用，哪些站内入口需要同步更新 |
| 12 | 验证计划与评审结果 | 哪些已经确认，哪些仍阻断进入正文 |

输出必须填入实际内容。模板字段未替换、来源留空、以“按需补充”替代核心范围，都不算合格交付。

### 2. 分阶段执行

阶段确认用于锁定影响范围和质量标准。复用已有有效确认，不能因续写下一章而反复要求重新确认整个蓝图。

1. 完成任务建档、现状审计、读者与版本界定。
2. 完成知识项、依赖、职责和覆盖分析，再输出目录。
3. 自检蓝图，修复漏项、循环、重复主讲与粒度问题。
4. 将完整可评审蓝图交给用户确认；确认前不写目标模块正文。
5. 蓝图确认后生成并验证样板文章，记录样板评审结果。
6. 样板确认后，按章节执行配套正文规范；蓝图未发生实质改变时连续推进已授权范围。

“样板可以代表后续文章”必须有理由。默认一篇；若模块含证据形式显著不同的主文章类型，可在蓝图中提出第二篇样板及原因，按既有规则确认。

### 3. 蓝图验收与失败处理

验收使用硬性门禁。目录漂亮、编号连续或文章数量足够，不能抵消事实、依赖或职责问题。

| 编号 | 门禁 | 不通过的典型情况 |
|------|------|------------------|
| D01 | 范围清楚 | 领域地图与单模块教程混用 |
| D02 | 版本与来源明确 | “最新版”、来源缺失、不同版本混为默认行为 |
| D03 | 方向覆盖成立 | 语言缺本身基础；框架重复宿主语言全套语法 |
| D04 | 知识责任唯一 | 必需项无归属，或多篇同时完整主讲 |
| D05 | 依赖可解释 | 存在循环、无效 ID 或按创建时间排序 |
| D06 | 粒度与命名合理 | 只有标题、多个独立问题拼成一篇、机械按字数切分；章节或文章名称冗长空泛、与实际范围不符，或精简后丢失必要限定 |
| D07 | 能力可验证 | 声称能诊断但没有对应知识和证据方案 |
| D08 | 工程边界明确 | 拟新增与现有文件混淆、受影响站内引用没有更新方案 |
| D09 | 样板选择有效 | 只选最简单概述，不能校准主要难度 |
| D10 | 状态真实 | 把规划当完成，把未运行当已验证 |

失败项必须给出问题、证据、影响和修复动作。未获得来源或必要输入时，明确草案状态及受影响范围；不要编造结论，也不要将不相关工作一并停止。
