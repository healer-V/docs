# 知识体系与方向分类规范

知识方向分类决定教程需要覆盖哪些基础、机制和实践。AI 不得把一份通用知识清单套用到所有模块，也不得在框架教程中重新生成宿主语言的完整基础教程。

## 一、教程定位

系统教程定位为帮助读者从 0 系统学习一门语言或技术的学习文档，默认面向尚未学习过当前语言或技术的读者。模块应从当前方向的基础知识开始，先让读者理解核心概念并独立完成基本任务，再逐步达到模块声明的解释、设计和诊断能力。

语言入门应讲清必要的编程基本概念，不默认读者已经掌握另一门编程语言。框架、工具等技术所需的跨方向基础必须明确声明要求深度，并提供有效学习入口。术语、规则和操作应在需要它们的位置解释，避免要求初学者依靠猜测补齐知识。

| 内容类别 | 定义 | 处理要求 |
|----------|------|----------|
| 跨方向前置知识 | 由其他知识方向负责完整讲解的基础 | 在模块蓝图中列明并引用，不在当前模块重复系统展开 |
| 当前方向基础知识 | 理解当前技术不可绕过的概念、语法或对象 | 必须进入知识项清单并按零基础组织 |
| 当前方向核心能力 | 当前技术提供的主要 API、功能或配置 | 必须说明使用方式、边界和结果 |
| 工程与生态扩展 | 使核心能力进入真实项目所需的集成内容 | 在核心知识之后按依赖组织并说明边界 |
| 生产与演进内容 | 性能、安全、诊断、恢复、版本与迁移 | 根据知识方向和教程目标判断适用范围 |

“从 0”以目标语言或技术为边界。React 可以要求读者具备 JavaScript、HTML 和 CSS 基础，同时必须从基础讲解 JSX、组件和数据流；Java 语言教程则必须覆盖环境准备、第一个程序、变量、类型和控制流等自身基础。当前方向的基础知识不得作为默认已掌握的前置条件。

## 二、方向识别流程

规划模块前按以下顺序识别知识方向：

1. 确定模块主要交付的是语言能力、框架能力、数据能力、工具能力、平台运维能力、协议能力、架构决策还是 AI 工程能力；
2. 选择一个主方向，主方向决定知识项检查范围和章节主线；
3. 仅在完成模块目标确实需要时选择辅助方向；
4. 明确辅助方向中哪些内容需要最小讲解，哪些内容只作为前置引用；
5. 在模块蓝图中记录分类依据，禁止仅根据目录名称猜测。

无法确定主方向时不得生成目录。混合模块也必须具有一个清晰主线，不能把多个方向的完整教程拼接在同一模块中。

## 三、方向覆盖模型

方向覆盖模型提供知识检查范围，不直接规定最终章节数量和名称。具体知识项必须结合主版本官方资料生成。

### 1. 编程语言

适用于 Java、JavaScript、TypeScript、Python、Go 等语言及其直接运行模型。

| 层次 | 应检查的内容 |
|------|----------------|
| 环境与程序入口 | 工具链、源文件、程序结构、编译或解释、执行命令和首个结果 |
| 词法与基础语法 | 标识符、关键字、注释、变量、常量、字面量和作用域 |
| 类型与表达式 | 类型系统、基本与复合类型、转换、运算符、表达式和空值模型 |
| 控制与抽象 | 分支、循环、函数或方法、参数、返回值、闭包或对应抽象 |
| 数据与对象模型 | 数组、集合、对象、类、接口、继承、组合或语言对应能力 |
| 模块与错误 | 包、模块、依赖、可见性、异常或错误传播 |
| 运行机制 | 内存、调用、并发、异步、编译优化或运行时行为 |
| 工程实践 | 构建、测试、调试、代码质量、性能和版本演进 |

不是所有语言都具有类、异常或线程。不存在的语言能力必须标记为不适用，不得为了模板完整虚构对应章节。

### 2. 框架与类库

适用于 React、Vue、Spring Boot、Django 等建立在宿主语言或平台之上的开发框架。

| 层次 | 应检查的内容 |
|------|----------------|
| 前置平台 | 宿主语言、运行环境、浏览器或服务端平台要求，只声明必要基线 |
| 环境与入口 | 安装、版本、初始化、入口、最小运行结果和开发工具 |
| 框架心智模型 | 框架解决的问题、核心对象、职责边界和数据或控制模型 |
| 框架专用表达 | JSX、模板、注解、配置 DSL 等当前框架特有表达 |
| 核心能力 | 组件、依赖注入、路由、状态、请求、生命周期或框架对应 API |
| 运行机制 | 初始化、更新、调度、渲染、调用链、扩展点和失败传播 |
| 组合与设计 | 职责拆分、复用、状态归属、模块组织和常用模式 |
| 工程实践 | 测试、构建、性能、安全、可访问性、部署和生态选型 |

框架教程不得重新系统讲解宿主语言的标识符、变量、通用类型和控制流。正文使用到必要的语言特性时，只解释与当前框架行为直接相关的部分，并引用语言模块。

### 3. 数据库与存储

适用于 MySQL、PostgreSQL、Redis、文档数据库和搜索存储系统。

| 层次 | 应检查的内容 |
|------|----------------|
| 环境与连接 | 服务、客户端、连接、认证、数据库或命名空间 |
| 数据模型 | 表、字段、键、文档、键值、数据类型、空值和约束 |
| 操作语言 | 定义、写入、查询、过滤、排序、聚合、函数和批量操作 |
| 数据组织 | 模式设计、范式或反范式、索引、分区和数据生命周期 |
| 一致性与并发 | 事务、隔离、锁、并发冲突、持久化和复制 |
| 访问与集成 | 驱动、连接池、参数绑定、迁移和应用层边界 |
| 性能与安全 | 执行计划、慢查询、容量、权限、审计和注入防护 |
| 运维与恢复 | 监控、备份、恢复、高可用、故障处理和版本升级 |

数据库中的“数据类型”是存储与查询模型的一部分，不等同于编程语言类型系统。两者需要在集成文章中解释映射，不能合并为同一基础章节。

### 4. 工程化工具

适用于 Vite、Webpack、Jenkins、构建系统和持续交付工具。

| 层次 | 应检查的内容 |
|------|----------------|
| 安装与输入输出 | 版本、运行环境、输入文件、输出产物和最小命令 |
| 核心模型 | 配置、任务、依赖图、流水线、阶段和缓存 |
| 常用能力 | 开发、构建、转换、打包、发布或工具对应操作 |
| 扩展机制 | 插件、Loader、Hook、任务扩展和自定义配置 |
| 调试与验证 | 日志、分析报告、产物检查、失败定位和可重复构建 |
| 优化与治理 | 性能、缓存、安全、环境隔离、凭据和版本管理 |

工具教程以真实输入、命令、产物和失败输出为核心，不能只罗列配置项。

### 5. 基础设施与平台

适用于 Linux、Docker、Kubernetes、Nginx 等运行和交付平台。

| 层次 | 应检查的内容 |
|------|----------------|
| 资源与对象 | 进程、容器、工作负载、配置、网络、存储或平台对象 |
| 生命周期 | 创建、启动、运行、变更、停止、删除和恢复 |
| 配置与操作 | 配置文件、命令、权限、环境和自动化入口 |
| 网络与存储 | 地址、路由、名称解析、卷、持久化和数据边界 |
| 安全与隔离 | 身份、权限、密钥、隔离、供应链和审计 |
| 可观测与诊断 | 日志、指标、事件、状态、容量和故障证据 |
| 高可用与恢复 | 副本、调度、滚动变更、备份、回滚和灾难恢复 |

基础设施教程必须说明操作风险、恢复方式和验证证据，不得只提供成功路径命令。

### 6. 协议与 Web API

适用于 HTTP、WebSocket、DOM、浏览器事件和标准 Web API。

| 层次 | 应检查的内容 |
|------|----------------|
| 参与角色与对象 | 客户端、服务端、文档、节点、连接、消息或标准对象 |
| 数据与消息模型 | 字段、方法、状态码、帧、事件、参数和返回值 |
| 状态与时序 | 建立、发送、处理、更新、关闭、失败和重试 |
| API 与使用规则 | 调用方式、事件、限制、错误和最小示例 |
| 安全边界 | 同源、权限、认证、加密、注入和数据暴露 |
| 性能与兼容性 | 缓存、连接、调度、浏览器差异、标准版本和降级 |
| 调试方式 | 网络面板、协议日志、事件观察和可复现请求 |

### 7. 架构与方法

适用于微服务、DDD、事件驱动、分层架构和架构决策方法。

| 层次 | 应检查的内容 |
|------|----------------|
| 问题与约束 | 方案试图解决的问题、前提、成本和不适用场景 |
| 角色与边界 | 参与角色、职责、所有权、服务或领域边界 |
| 交互与状态 | 调用、消息、状态变化、数据所有权和失败传播 |
| 关键机制 | 通信、一致性、治理、弹性、安全和可观测性 |
| 决策与取舍 | 候选方案、比较维度、组织约束和回退条件 |
| 演进与验证 | 迁移路径、架构指标、故障演练、决策记录和反模式 |

架构教程必须通过具体场景、状态或决策证据解释取舍，不能退化为概念和优缺点列表。

### 8. AI 工程

适用于模型接入、Prompt、RAG、Agent、评测、安全和 LLMOps。

| 层次 | 应检查的内容 |
|------|----------------|
| 模型与接口 | 模型能力、Token、上下文、输入输出、流式调用和限制 |
| 上下文与知识 | Prompt、结构化输出、Embedding、检索、切分和引用 |
| 应用与工作流 | 对话、RAG、工具调用、Agent、状态和人工审批 |
| 质量与评测 | 数据集、指标、回归、事实性、鲁棒性和人工评审 |
| 安全与治理 | 权限、提示注入、数据边界、审计和内容风险 |
| 运行与成本 | 延迟、重试、限流、缓存、可观测性、成本和部署 |

AI 工程通常组合协议、数据、架构和工程化知识，但主线必须围绕 AI 应用生命周期，不能把辅助方向分别扩写成完整教程。

## 四、版本基线

每个模块必须明确一个主版本基线。

| 项目 | 要求 |
|------|------|
| 主版本 | 正文默认行为只以该版本为准 |
| 运行环境 | 记录运行时、操作系统、浏览器或服务依赖的必要版本 |
| 依赖版本 | 示例使用的关键框架、驱动和工具版本必须兼容 |
| 差异处理 | 重要版本差异集中放在版本说明、对比或迁移文章中 |
| 历史版本 | 只在解释当前行为或迁移风险时出现 |
| 新版本 | 不使用最新 API 反推旧版本默认行为 |

同一篇普通文章不得在没有明确分区的情况下混写多个版本。版本差异会改变核心示例时，应拆分版本模块或独立迁移文章。

## 五、事实来源

知识项清单生成前必须建立来源清单。

| 来源层级 | 使用原则 |
|----------|----------|
| 官方规范与标准 | 语言、协议和兼容性结论的首选依据 |
| 官方文档 | API、配置、版本和推荐实践的首选依据 |
| 官方仓库与发布说明 | 实现边界、变更、弃用和迁移结论的依据 |
| 实际运行与测试 | 示例输出、错误表现和行为验证的依据 |
| 权威补充资料 | 官方资料没有覆盖工程取舍时补充，必须说明其适用边界 |

无法确认的内容必须从“已确认知识项”中移出并记录为阻塞项。不得用模型记忆、非官方摘要或虚构运行结果代替关键证据。

## 六、完整性判断

教程完整性按以下顺序判断：

1. 当前方向覆盖模型中的适用内容已经转化为知识项；
2. 主版本官方资料中的核心主题已经映射到知识项；
3. 每个知识项具有唯一正文归属；
4. 知识点依赖能够形成无循环的有序路径；
5. 读者最终能力覆盖模块教学契约；
6. 不适用项和排除项具有明确理由；
7. 工程、质量和生产内容与模块目标相称，没有机械补章。

标题数量、文章字数、代码块数量和固定章节模板都不能单独证明教程完整。
