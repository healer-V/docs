# 技术文章生成与验收规范

一篇合格的技术文章必须回答一个明确问题，给出准确结论，并提供与文章类型相符的解释、证据、使用边界和验证方式。标题数量、字数、代码块数量与生成完成状态，不能代替内容完成度。

本规范服务于“从 0 系统学习一门语言或技术”的核心定位，兼顾长期复用和对外分享。文章应从职责卡声明的读者起点讲起，及时解释必要术语、规则和操作，使初学者能够理解当前主题、判断适用条件，并复现声明为可执行的示例。

文章可以引用明确声明的前置知识，但当前主题的讲解与示例必须能脱离对话记录、文档仓库及其他文章全文理解和复现。基础文章应先讲清基本用法和可观察结果，再按理解需要展开机制与边界；进阶文章应建立在已明确的前置知识上，不重复整套入门内容。

| 项目 | 约定 |
|------|------|
| 适用任务 | 单篇新建、单篇全文重写、已确认模块内逐章生成、历史文章局部修改 |
| 主要输入 | 当前任务、模块蓝图、文章职责卡、相邻文章、主版本资料、可用验证环境 |
| 主要输出 | 正文、必要资源或示例、职责覆盖及验证记录、精确变更范围 |
| 目录前置规范 | [技术方向知识目录生成规范](./knowledge-directory-generation.md) |
| 与项目规则的关系 | 本文是现有规则的执行用汇编；正文仍须遵守仓库和目标目录的原始规范 |
| 约束优先级 | 当前用户明确要求 → 最近目录的 AGENTS.md → 仓库 AGENTS.md → 知识体系、模块蓝图等专业规范 → 本执行规范；文章服从这些约束内的已确认蓝图 |
| 版本 | 执行规范 v1.7，修订日期 2026-09-24；新增阅读路径、注意力层级和操作证据相邻规则，沿用从 0 系统学习、示例独立复现、仓库示例目录禁引、标题命名、文字容器和长代码折叠规则 |
| 维护入口 | 本仓库中的当前文件为持续维护版本；分析目录中的同名整理稿保留为日期快照 |

## 一、生成范围与前置条件

### 1. 按任务类型执行

先确定修改范围，再决定需要哪些输入与门禁。局部修正不能自动扩大为整篇重排，单篇任务也不能变成全模块重构。

| 任务类型 | 必须具备的条件 | 范围约束 |
|----------|----------------|----------|
| 新建技术模块正文 | 模块蓝图已确认，按流程先完成样板并确认 | 样板未确认前不批量写其余正文 |
| 单篇新建 | 文章职责明确，依据确认的职责卡或既有蓝图唯一确定 | 无蓝图时至少先明确职责卡，不擅自扩展模块 |
| 单篇全文重写 | 已读取全文与相邻内容，重写职责明确 | 将该篇整体迁移到当前规范，同步更新受影响站内引用 |
| 逐章生成 | 蓝图、样板与当前批次范围已确认 | 默认以一章为最大批次，必要时缩小 |
| 历史局部修改 | 已读取被修改内容及上下文 | 只要求新增和直接影响内容合规，不顺带治理无关段落 |

已有明确授权、有效蓝图和样板确认可以复用。只在主版本、知识责任、章节范围等发生实质变化时重新确认受影响部分，不逐篇重复询问同一个已确认问题。

### 2. 写作前必须完成的检查

每次编辑以磁盘上的当前内容为准。对于已有用户改动，应保留其意图并最小修改，不用历史版本覆盖当前工作。

1. 读取适用 AGENTS.md、分层规范及当前文章类型的内容契约。
2. 查看 Git 状态，明确本次允许新增、修改、移动和删除的文件。
3. 读取蓝图、职责卡、目标全文、相邻文章、模块首页和相关导航。
4. 核对主讲知识、必要前置、范围排除与可能重复的完整讲解位置。
5. 核对技术版本、官方来源、关键依赖和实际验证入口。
6. 确定主文章类型、必要证据、示例类型和交付时应达到的深度。
7. 阅读项目的[扩展语法示例](../../content/articles/blog/02-vitepress-markdown.md)与[Markdown 语法指南](../../content/articles/tools/02-markdown-guide.md)，核对已支持的文字容器、代码组与强调语法；按本规范选择具体用途。
8. 按第四节先建立主问题与子问题的关系，判断哪些内容需要独立小节，哪些保留为连续解释、表格或提示；已有文章先核对实际内容，再决定是否调整层级。

当前项目的规范和分析产物默认保存到 `D:\01-KnowDocs\Codex分析文档归属`；技术正文保存到已确定的模块路径。不要把用于评审的职责卡和过程记录机械插入普通技术正文。

## 二、单篇文章职责契约

### 1. 必须明确的字段

职责卡约束文章的唯一问题、主讲责任和证据。来自蓝图的职责卡可以直接复用，不为满足模板而另写一份相互不一致的定义。

| 字段 | 要求 |
|------|------|
| 文章身份 | 文章 ID、文件路径、标题、所属模块与章节 |
| 唯一问题 | 用一个明确问句说明本篇解决什么 |
| 前置知识 | 当前主题需要的最小知识及真实主讲位置 |
| 主讲知识项 | 本文必须完整讲解的知识项 ID |
| 引用知识项 | 其他文章负责的知识及最小引用边界 |
| 类型与深度 | 一个主类型，最多一个辅助类型；明确认识、使用、解释、设计或诊断 |
| 必须覆盖 | 具体定义、规则、API、机制、决策或故障链路 |
| 明确不覆盖 | 相邻文章负责的内容与本次排除范围 |
| 版本 | 主技术、运行环境、依赖范围及差异归属 |
| 证据与验证 | 场景、示例、入口、预期观察、失败边界与实际核验方式 |
| 来源与重复 | 关键结论来源，以及容易重复主题的唯一主讲文章 |

文章标题与唯一问题必须一致。例如，标题承担“接入”或“排障”职责时，正文不能停留在概念介绍。发现现有职责不足以容纳必要内容时，先说明具体缺口并修订受影响职责，不能临时塞入多个无关主题。

### 2. 内容深度的判定

深度用读者能够做出的动作判断。高深度不等于篇幅更长，也不意味着每篇都要包含全部层次。

| 深度 | 达到标准的表现 | 常见证据 |
|------|----------------|----------|
| 认识 | 能定义对象、关系、适用场景与边界 | 场景、关系表、对照或反例 |
| 使用 | 能正确调用、配置或操作，并判断结果 | 最小实现、入口和可观察输出 |
| 解释 | 能说明触发、执行过程、关键状态及行为原因 | 时序、状态变化、日志、可观察代码 |
| 设计 | 能根据约束比较方案、确定边界并验证选择 | 决策矩阵、设计案例、迁移或回退条件 |
| 诊断 | 能从现象取证、定位原因、修复、恢复并预防 | 命令、测试、日志、指标和恢复验证 |

## 三、按文章类型选择内容与证据

### 1. 七类主文章契约

先确定文章类型，再决定证据和示例形式。不能让所有文章都使用统一的“概念、优势、实践、总结”模板。

| 主类型 | 必须讲清楚 | 最低证据要求 | 不合格表现 |
|--------|------------|--------------|------------|
| 基础概念 | 定义、核心对象、关系、适用边界、收益与成本、常见误解 | 真实场景、关系图、状态变化、决策表或反例至少一种 | 只有术语定义和优缺点列表 |
| 语法与 API | 语法或签名、参数、返回值、约束、状态影响、版本和错误用法 | 最小使用片段、触发方式、可观察结果；说明能否独立执行 | 只列 API 名称或参数表 |
| 运行机制 | 参与对象、触发条件、执行过程、关键状态、失败传播与使用约束 | 时序或状态图、明确伪代码、配置、日志、指标或可观察代码至少一种 | 只堆内部名词与源码字段 |
| 接入教程 | 环境、版本、依赖、配置、核心实现、入口、输出与常见失败 | 一条可按说明复现的完整链路 | 零散代码拼接，没有依赖、入口或结果 |
| 设计与实践 | 具体场景、候选方案、比较维度、约束、取舍、实施与回退 | 决策矩阵、对照案例、迁移案例或反例 | 没有条件的“最佳实践” |
| 测试与排障 | 前置条件、现象、诊断顺序、证据、根因、修复、恢复及预防 | 可执行测试、命令、日志、指标、故障注入或诊断输出 | 只有检查清单和原因猜测 |
| 速查与参考 | 参数或命令、返回值、限制、版本范围与来源 | 关键项最小用法或指向完整讲解的有效链接 | 高密度表格缺少边界和真实用法 |

主类型为设计并不意味着可以省略实际实现承诺。标题或摘要明确承诺“使用、接入、实现、测试、排障、实践、部署”的目标时，必须提供与该目标相称的可执行示例；纯架构选型可用场景、决策和迁移证据，但不能冒充实现教程。

### 2. 内部框架与历史版本的附加约束

这两类情况叠加在主文章类型之上，不改变文章只回答一个主要问题的要求。

| 情况 | 约束 |
|------|------|
| 企业内部框架 | 只展示已有源码、文档或运行证据支持的概念、注解、模块与调用方式 |
| 内部行为无法确认 | 明确列出未知边界；抽象说明标为伪代码，不编造内部接口、配置键或协议 |
| 维护旧版本 | 明确适用版本，把默认行为与升级差异分开 |
| 同篇包含版本差异 | 分区标明版本；差异改变核心示例时，按职责拆成独立迁移或版本文章 |
| 来源与已有正文冲突 | 回到主版本官方资料或源码证据核对，记录修订影响 |

## 四、正文组织与小节完整性

### 1. 直接进入技术主题

一级标题后直接说明当前知识的定义、语法、API 或问题。不先写课程安排，也不统一声明“所有代码都是局部示例”。必要前置条件放在实际使用它的示例或机制附近。

| 应避免的写法 | 对应处理 |
|--------------|----------|
| “上一篇已经学习……本篇将要介绍……” | 直接说明当前概念或问题，导航交给目录和页面组件 |
| 固定增加“学习目标、学习方法、实践任务、验收标准” | 按具体技术主题组织；必要检查跟随对应知识 |
| “核心知识、理解与应用、其他内容”作为空泛标题 | 使用对象、机制、API 或问题名称 |
| 用表格、流程图、代码块重复展示本文目录 | 删除文章目录复述；真实执行流程和数据流可以保留 |
| 开篇声明“依赖均已导入、代码不代表完整工程” | 在每个局部片段附近明确缺失上下文 |
| 正文用“下一篇、下一章”衔接 | 使用有意义的知识引用，或由 sidebar 和文章切换组件表达顺序 |

模块首页、知识目录页和专用布局页可以按用途展示章节和阅读入口；该豁免不能扩展成所有普通文章都展示课程路线。

### 2. 讲解顺序与段落节奏

动笔前先在工作记录中设计读者判断路径，不把这份规划直接写进正文。路径至少回答：读者带着什么问题进入、需要先建立哪个核心模型、沿哪些主问题推进、用什么证据确认理解，以及最终怎样判断适用边界。

| 规划对象 | 必须明确的内容 | 失败信号 |
|----------|----------------|----------|
| 入口问题 | 一个真实场景、错误判断或操作结果 | 开篇只有定义清单或课程说明 |
| 核心模型 | 对象关系、状态、时序或决策依据 | 后文术语很多，却没有共同解释框架 |
| 主问题 | 二级标题共同回答唯一学习问题 | 同级标题抽象层次混乱或只是知识点枚举 |
| 子问题 | 需要专属解释、证据或失败边界的从属问题 | 全篇只有平铺二级标题，或三级标题只是编号列表 |
| 证据路径 | 示例、输出、场景或反例如何证明结论 | 代码和表格出现后没有结果解释 |
| 收束方式 | 验收、判断案例、反例或恢复复测 | 结尾机械复述目录或突然结束 |

不同主文章类型按[单篇文档内容契约](./article-contracts.md)第四节选择默认判断路径。生成正文时可以调整标题名称和数量，但不能丢失主类型要求的证据与边界。

文章必须按读者的理解依赖组织内容。必要概念、符号和使用条件应在首次使用前或使用处解释；有前后依赖的操作按实际执行顺序排列，不能让读者先复制代码，再到末尾发现缺失的环境条件。

| 内容关系 | 默认组织方式 | 应避免的问题 |
|----------|--------------|--------------|
| 概念与用法 | 先建立最小定义，再说明规则和用法 | 先堆术语或API，读到后半篇才知道对象是什么 |
| 正常与异常 | 通常先给正常行为，再紧跟容易误用的边界与失败 | 成功代码与关键限制相隔多节 |
| 现象与诊断 | 先说明现象和条件，再按证据推进定位与恢复 | 先列一串原因，却没有判断依据 |
| 示例与结论 | 用途在示例前，观察结果与解释紧跟示例 | 只有代码、日志或“运行成功”，没有结论 |

操作、测试和排障内容需要先规划相邻的操作单元。每个单元包含当前目标与条件、命令或动作、预期结果、结果解释和就近失败处理；不要求把这些名称写成标题，但不允许把命令放在前半篇、输出放在后半篇，再把失败说明统一堆到文章末尾。

每个段落只推进一个中心意思。解释性段落通常可用2～5个相互衔接的句子完成；这只是写作建议，不是字数或句数门禁。出现过长段落时，优先检查是否混入多个主题，再按语义分段，不机械地每句话换行。

独立知识要点应达到读者能够理解和判断的深度，不能连续用“一句定义或结论”代替讲解。需要解释的要点应补充必要的原因、机制、用法、边界或证据；只需简短说明的并列事实可以合并为正文、列表或表格，不为凑段落扩写常识。

### 3. 论述必须形成闭环

小节先给结论或定义，再说明必要的机制、原因、使用方式、适用边界、示例或判断方法。不同要素自然组合，不需要每个要素建立一个标题。

| 内容要素 | 写作要求 |
|----------|----------|
| 结论 | 准确回答当前问题，限定成立条件 |
| 原因与机制 | 解释行为为何产生、由哪些对象或状态决定 |
| 使用方式 | 给出正确操作和必要参数，说明选择依据 |
| 证据 | 直接支撑当前结论，避免无关的大工程或泛化案例 |
| 结果解释 | 说明输出、状态、日志或指标证明了什么 |
| 边界与反例 | 说明何时失效、不适用或出现错误，以及如何判断 |

概念性文章可以通过场景和关系形成闭环；接入与排障文章需要执行或诊断链路。不能为了“完整”重复结论、堆同义句或机械增加篇幅。

### 4. 空小节与骨架化小节的处理

标题表示需要独立论述的主题，不是带编号的列表项。所有新增或全文重写文章必须检查每个二级、三级和四级标题；只有二级标题的文章同样需要完整性审查。

| 发现情况 | 必须采取的动作 |
|----------|----------------|
| 标题下没有正文 | 补充实质内容、合并或删除 |
| 只有一个普通正文句，且无有效结构化内容 | 判断是否需要独立论述；需要则展开机制、边界或证据，否则合并 |
| 连续三个及以上小节只有定义或结论 | 重新组织该部分，合并并列事实，不逐项灌水扩写 |
| 引导语后有表格、步骤、代码或容器 | 检查结构化内容是否提供有效信息，引导语是否说明用途 |
| 多段长文字反复表达同一观点 | 去除重复，补足缺失的机制、判断或证据 |

完整性扫描按“列出候选 → 人工语义判断 → 扩展、合并或删除 → 复查”的顺序执行。脚本只能发现候选，不能用字数阈值自动判定合格，更不能自动填充无意义内容。

### 5. 表达形式与阅读负担

正文、表格、列表和提示容器应各自承担适合的内容。可读性来自清晰的信息关系，不以表格数量、加粗数量或换行密度判断。

| 形式 | 适用内容 | 约束 |
|------|----------|------|
| 连贯正文 | 定义、因果、机制、推导和取舍 | 解释前后关系，不拆成彼此孤立的短句 |
| 表格 | 参数、同维度比较、输入输出和错误映射 | 单元格保持可扫描，复杂原因移到对应正文，不把长文章塞进表格 |
| 有序列表 | 安装、调用、诊断和恢复步骤 | 每步说明动作，必要时给出条件与检查结果，不省略影响后续操作的步骤 |
| 无序列表 | 无先后依赖的并列事实或检查项 | 避免用一句话知识清单替代核心讲解；复杂项目可用多句完整说明 |
| 提示容器 | 需要特别注意的条件、限制或判断 | 紧邻受影响内容，不连续堆叠容器代替正文 |
| 加粗与行内代码 | 关键结论、限制、API、参数和文件名 | 不整段加粗；代码标记只用于有明确技术含义的文本 |

术语和缩写首次出现时给出足够理解当前句的解释，避免连续引入未定义名词。数值写明单位、范围和必要默认值；“它、该对象、上述配置”等指代必须能在附近唯一确定。需要查阅其他文章时链接到对应主讲位置，当前文章仍保留理解本节所需的最小上下文。

### 6. 文字容器与阅读层次

文字容器是正文的信息层次之一，必须在写作和验收时主动选择。只折叠代码、增加标题或拆短段落，不能证明文章已经具备阅读重点。读者快速浏览时，应能辨认适用条件、关键判断、正确做法和容易出错的边界；随后通过相邻正文理解原因与机制。

| 信息类型 | 统一写法 | 应包含的信息 | 放置位置 |
|----------|----------|--------------|----------|
| 环境与版本前提、场景条件 | `::: info 具体条件` | 哪个环境或假设成立、影响哪项用法 | 相关示例或机制使用前 |
| 可复用结论、操作建议 | `::: tip 具体判断` | 推荐做法、成立条件和必要原因 | 规则讲解或结果之后，形成可检索的判断 |
| 常见误解、兼容限制、失败边界 | `::: warning 具体误区` | 容易误判什么、为何失效、正确处理 | 紧邻受影响用法；必要限制放在操作前 |
| 数据损坏、安全或不可逆操作 | `::: danger 具体后果` | 触发条件、实际后果、预防或恢复要求 | 危险操作之前 |
| 长代码、完整输出、补充推导 | `::: details 对象与用途` | 完整证据或可选深入内容 | 保留核心解释后，再折叠细节 |
| 原始问题或外部原话 | 普通块引用 `>` | 明确问题身份或真实出处 | 分析所引用内容的附近 |

有适用信息时必须使用相应文字容器，不能让整篇长期只有普通段落和代码块。具体数量由内容决定；没有数据或安全风险时不要硬加 `danger`，也不要为了让每节看起来一致而机械添加同一种提示。项目示例页同时演示 GitHub Alert；普通技术文章按 AGENTS.md 统一使用上述原生容器，同一篇不混用两套提示语法。

一个容器承载一个明确判断及必要解释，可以组合两段文字、短列表或小表格。标题不能只写“提示”“注意”或“核心知识”；正文不能只保留一句口号，也不能把整节包起来后省略正常论述。必要前提、警告和核心结论保持展开，不能和完整实现一起藏进 `details`。

例如，金额测试的独立期望属于可复用判断，适合在断言讲解之后强调：

::: tip 期望值应由业务规则独立确定
订单总额的期望值先按输入与业务规则确定，再与被测对象返回值比较。不要在断言里完整复制被测计算过程，否则实现与测试可能同时保留同一种错误。
:::

同一个示例中的发现规则属于失败边界，放在测试执行说明附近更容易被看到：

::: warning 构建成功仍可能没有运行任何测试
测试类命名、目录或筛选条件错误会使测试集合为空。运行后同时检查退出码、测试数量和报告；只有明确要求无测试的模块，才可以接受零测试构建。
:::

这两个容器各自承担判断与处理，原理、完整用法和证据仍由相邻正文展开。不要在多个容器中反复复述同一结论，也不以分割线、表情、徽章或荧光标记代替信息组织。

交付前必须按二级标题逐节检查阅读层次：定位连续长段落、成串的短句清单，以及被埋住的前提和风险；重新组织为连贯解释、语义容器、步骤或对照。查看实际渲染后，确认关闭长代码仍能顺着正文读懂问题、机制和结果。

### 7. 根据知识关系建立标题层级

标题层级表达主问题与子问题的关系。写作前先从职责卡确定本文的主要问题，再判断内部是否包含需要分别解释的规则、机制、操作或失败路径。该判断属于写作过程，不在普通文章开头插入目录树或规划表。

| 内容关系 | 组织方式 | 成立条件 |
|----------|----------|----------|
| 本文内部的主要问题 | 二级标题 | 各部分共同回答文章唯一问题，同级标题处于相近的抽象层次 |
| 主问题内的独立子问题 | 三级标题 | 能说明与父主题的关系，并有专属解释、示例、状态推导或判断依据 |
| 子问题内仍需单独定位的机制或分支 | 四级标题 | 确有独立查阅价值，合在原小节会混淆条件或执行过程；不因篇幅长自动增加 |
| 一个规则的简短条件、参数或提醒 | 正文、表格、列表或语义容器 | 不需要独立论述，不把一句话提升为标题 |
| 连贯的短流程或范围很窄的主题 | 保留浅层结构 | 当前标题已经准确区分问题，段落和证据足以支撑声明深度 |

增加小节前必须能够回答：它独立解决什么问题，为什么属于这个父主题，有哪些专属内容，以及拆开后是否方便理解或定位。仅有新标题而没有对应论述，不得视为有效拆分；同义改写、重复示例和从相邻文章搬来的内容也不能充当支撑。

必要的重组可以合并平级标题、把规则归入父主题、拆开混在一起的机制，或者只补充解释而保留标题。父节先给出必要的共同模型，子节再说明各自差异；不要在父节和子节重复同一段定义。无需为每个父节补齐相同数量的子节，也不为“定义、原因、示例、总结”统一设置四个标题。

::: warning 层级数量不作为质量指标
不规定每篇必须有三级或四级标题，不设置标题数量、字数或层级比例配额，也不因为某篇只有二级标题就判定不合格。已有三级标题的文章仍可能把不同机制混在一起；浅层结构是否适当，必须结合职责、实际内容和读者要解决的问题判断。
:::

### 8. 同时复审层级缺失与内容深度

结构复审必须同时检查“已有小节是否空薄”和“必要子主题是否没有建立”。脚本没有发现空小节，不代表文章已完整；相关术语出现在正文、表格或容器中，也不等于已经达到职责卡要求的使用、解释或诊断深度。

| 复审信号 | 必须核对的问题 | 可采用的修订 |
|----------|----------------|--------------|
| 全篇仅有二级标题 | 是否只是一个窄问题，还是把模型、具体机制和操作细节全部平铺 | 保留并说明理由，或按真实从属关系重组 |
| 一个标题同时列出多个概念 | 它们是否共同组成一个必要比较，还是各有独立机制和边界 | 保留对照，或分别展开；不按“与”“和”的字面机械拆分 |
| 核心机制只有一段或一行表格 | 读者能否解释过程、预测行为并判断错误 | 补充缺失的状态、因果、适用条件或最小证据；是否增加标题另行判断 |
| 大段完整代码承担全部说明 | 关闭折叠后是否还能理解关键过程与结果 | 在相关知识处补充关键机制解释，保留完整实现和入口 |
| 子节之间不断互相引用 | 是否拆散了本应连续理解的一条推导或操作 | 合并或调整顺序，减少不必要层级 |
| 文章出现多个宽泛父标题 | 是否只是用“基础、进阶、实践”等词把旧标题整体降级 | 回到具体技术问题命名和分组，删除没有内容职责的父层 |

新建与全文重写在动笔前完成语义大纲判断，写完后将职责卡中的必讲内容逐项对应到正文解释和证据。批量治理对每篇记录“保留结构、重组层级、补足解释”中实际采用的处理及理由，可以组合；记录放在治理报告中，不把审阅说明写入技术正文。

调整标题时检查实际生成的锚点，同步修正全部受影响站内引用。旧标题锚点直接作废，不添加隐藏标签保留旧锚点；页面目录应反映新的真实层级。工程检查只能证明格式与链接有效，不能替代上述语义判断。

### 9. 标题命名

章节名称、文章标题和二至四级标题必须**准确概括、表达精简**。先确定技术对象和实际范围，再删除不影响识别的修饰与解释；同一含义能够清楚表达时，选择更短的名称。目录与 sidebar 中的展示名称遵循同一原则。

| 检查项 | 命名要求 |
|--------|----------|
| 技术对象 | 读者能直接识别正在讲解的概念、API、机制或问题，标题与实际内容范围一致 |
| 表达形式 | 优先使用“技术对象 + 必要限定”的短语；问题型标题可以保留简短问句，不把职责卡的完整问题机械照抄成标题 |
| 解释位置 | 背景、原因、步骤细节与完整结论放在节首正文，不把标题写成长句式摘要或逐项罗列全部知识点 |
| 必要限定 | 保留影响含义的对象、场景、版本和差异；标准术语与 API 名称保持准确，不为缩短而截断或生造缩写 |
| 上下文 | 小节可以省略父标题已经明确且不会产生歧义的范围；文章标题仍应能在搜索结果中独立识别主题 |
| 冗余措辞 | 删除无信息量的“关于……的介绍”“相关知识”“全面详解”“从入门到精通”等套话，不用“核心”“其他”等空泛词代替技术主题 |

以下示例只展示命名调整；实际修改前必须核对正文范围，不能仅凭标题猜测内容。

| 用途 | 冗长表达 | 精简表达 |
|------|----------|----------|
| 章节名称 | Java 语言中的面向对象编程相关知识 | 面向对象 |
| 文章标题 | Java 变量的声明、常量的定义以及变量的作用域规则 | Java 变量、常量与作用域 |
| 小节标题 | invokeExact 的返回上下文也是调用点类型 | invokeExact 调用点返回类型 |

不设置统一字数上限，也不要求标题等长。较长标题应检查能否去掉赘词；必要的技术限定可以保留。多个并列主题若共同构成比较或完整机制，可以合并命名；若实际承载独立问题，再按职责调整范围，不为缩短标题增加层级或拆分文章。

标题缩短后必须复核含义、术语与正文职责，按第八小节更新受影响锚点引用；文章标题仍需与 Frontmatter 的 `title` 一致。

## 五、示例与验证契约

### 1. 明确示例类型

每个示例在出现处说明用途和执行边界。局部片段可以帮助理解，但不能代替文章承诺的完整接入或排障链路。

| 示例类型 | 必须说明 |
|----------|----------|
| 完整示例 | 环境、必要文件、依赖、入口、结果与失败处理，按说明可独立运行 |
| 局部代码 | 所属文件、已具备的上下文、省略什么以及是否依赖完整实现 |
| 配置片段 | 配置文件的完整相对路径、所属环境和生效方式 |
| 伪代码 | 明确写“伪代码”，使用 text 或明确的伪代码标识，不使用真实语言标识伪装程序 |
| 错误示例 | 现象、原因、定位证据与正确处理，不能只贴报错 |
| 命令 | 实际执行 shell、工作目录、前置服务、权限和预期作用 |
| 输出 | 区分实际输出、预期格式示意与局部摘录，不虚构运行结果 |

### 2. 最小可复现链路

接入、API 操作教程、测试与排障文档至少包含一条与主题直接相关的最小闭环。链路可以分散在连续小节，但必须采用一致的业务对象、字段、端口和版本。

| 顺序 | 要素 | 必须包含的信息 |
|-----:|------|----------------|
| 1 | 前置条件 | 运行环境、适用版本、必要服务和准备动作 |
| 2 | 依赖与配置 | 需要安装什么、配置在哪个文件、哪些设置影响当前行为 |
| 3 | 核心实现 | 直接解决当前问题的代码，说明省略的非核心上下文 |
| 4 | 执行入口 | 启动、调用、测试、页面操作或故障触发方式 |
| 5 | 预期观察 | 返回值、文件、状态、DOM、日志或指标，以及观察重点 |
| 6 | 失败与恢复 | 至少一个必要错误或边界，给出现象、原因、证据与处理 |
| 7 | 验证结论 | 示例证明什么，哪些生产能力仍未覆盖 |

同章可以复用业务场景、命名与规则，每篇必须给出当前示例所需的代码、配置、入口与结果。场景连续不等于代码依赖；不能只给示例工程链接，也不能要求读者凭“上一篇代码”猜出缺失部分。

::: warning 读者只能看到当前文档
示例不能依赖文档仓库的目录、配套源码、其他章节工程或作者机器上的既有文件。把仓库路径改成短路径仍不足以独立运行：被调用的自定义类、测试方法、初始化数据、父级构建配置和执行脚本也必须在当前文档中给出。

不得在文档中引用仓库示例目录（如 `example`、`examples`）及其内容入口。此要求覆盖正文、代码注释、目录树、命令、链接、折叠标题、公开蓝图和交付记录；不能改写成“源码见配套目录”继续引导读者取用。按当前知识设计独立的最小示例，所需实现直接在本篇展示。
:::

按以下规则建立独立示例：

| 对象 | 必须满足的要求 |
|------|----------------|
| 示例起点 | 使用读者自行新建的空目录，明确从哪里创建文件、在哪个目录执行；不要求克隆文档仓库 |
| 文件位置 | 单文件示例直接使用 `OrderApp.java`；构建工具确需分层时才使用 `src/main/java/order/OrderApp.java`。先说明由读者创建，不写成仓库内已存在的文件 |
| 包与目录层级 | Java 独立单文件示例省略无关包声明和多层源码目录；包、访问控制、反射、模块系统或构建主题需要结构时，使用 `order`、`order.model` 等简短业务包名，并解释保留理由 |
| 代码上下文 | 给齐当前闭环所需的导入、类型、字段、辅助方法和输入数据；局部解释片段对应的最小完整实现应在本篇可见 |
| 构建依赖 | 使用 Maven、Gradle 或外部库时，给出本篇可用的完整最小配置和版本；不能暗中继承另一个工程的父 POM、BOM、配置文件或脚本 |
| 工具脚本 | 可以要求先安装已注明版本的公开工具；使用 Wrapper 时在本篇说明生成步骤，不假定脚本已经存在 |
| 执行与输出 | 命令只能引用本篇创建的文件、明确安装的工具和本篇启动的服务；输出与实际展示的代码一致 |
| 本地文件和故障目标 | 在操作前给出创建数据、启动目标、获取进程号和恢复的方法；不直接引用作者已有日志、进程、数据库或编译产物 |
| 工程结构主题 | 只有目录、包、构建和多模块本身就是讲解对象时，展示与主题直接相关的最小示例结构；该结构由本文创建，与文档站目录无关 |
| 验证记录 | 公开记录说明验证环境、场景、结果和边界，不列仓库示例目录、源码入口或从该目录取用文件的命令 |

优先缩小为与当前问题直接相关的独立程序或测试，不为补齐依赖而搬入整章工程。超过10行仍折叠，前提、关键逻辑和结果判断留在折叠外。

修改路径时，必须同时核对包声明、导入、反射使用的类型名、编译与启动命令、输出、断点和失败处理。验收还要查看实际页面，不能只按仓库路径扫描，也不能排除包路径后宣称示例目录已全部清理。

### 3. 实际验证与不可验证边界

验证记录必须对应当前文章中的实际代码和版本。修改核心逻辑、依赖、文件组织或预期输出后，重新验证受影响链路；不将旧记录自动视为仍然有效。独立性验证必须从空目录只提取当前文档展示的文件并执行说明中的命令，不能复制仓库工程补齐缺失内容。

| 验证状态 | 可以作出的结论 | 交付要求 |
|----------|----------------|----------|
| 实际运行或测试通过 | 已观察到当前环境下的行为 | 记录入口、环境、结果与覆盖边界 |
| 仅编译通过 | 静态语法、类型或构建检查通过 | 明确未验证运行行为，不声称请求或事务成功 |
| 局部片段核对 | 片段支持某个机制或用法说明 | 标注依赖上下文，不能声称独立可运行 |
| 伪代码分析 | 用于解释控制流或状态关系 | 不给出冒充实测的终端结果 |
| 无法验证 | 当前存在环境、依赖或证据限制 | 记录具体原因和影响；核心结论依赖该结果时不得验收通过 |

预期输出格式可以用于解释观察对象，但必须明确它是预期或示意。接口响应若为 JSON，使用 json 代码块；普通日志和终端输出使用 text。不能只写“运行成功”或把推测输出写成执行证据。

### 4. 示例安全、命名与源码注释

示例使用真实业务语义和非敏感演示数据，不使用真实账号、密钥、客户数据、生产地址或内部仓库地址。脱敏或演示数据应说明性质，不能用它证明生产效果。

| 对象 | 注释与命名要求 |
|------|----------------|
| 所有新增函数、方法和回调 | 至少说明职责或触发场景，明确返回值；无返回值说明副作用 |
| 多入参函数 | 使用对应语言的文档注释，逐个解释参数含义、约束或边界，并解释返回值 |
| 复杂分支 | 说明业务约束、选择原因和失败边界 |
| 兼容与异常兜底 | 说明适用版本、触发条件及为何需要兼容 |
| 魔法值 | 说明来源、业务含义与允许范围 |
| 省略内容 | 显式说明省略了哪些上下文及其对运行的影响 |
| 标识符 | 使用业务语义明确的名称，避免 foo、bar、test123 等无意义名称 |

注释优先解释原因和边界，保持文件已有风格，没有局部风格时使用中文。简单赋值不逐行翻译；但简单函数也不能省略职责、返回值或副作用说明。

## 六、Markdown 与 VitePress 格式

### 1. Frontmatter 与标题

普通技术文章必须以合法 YAML Frontmatter 开始，并在结束分隔符与正文之间保留一个空行。title 与正文唯一一级标题完全一致。

| 字段或层级 | 格式 | 约束 |
|------------|------|------|
| title | 明确的文章标题 | 必填，与唯一一级标题一致 |
| tags | 稳定技术词的数组 | 可选，最多 4 个 |
| excerpt | 描述问题与核心内容 | 建议 50～120 字，避免空泛承诺 |
| date | YYYY-MM-DD | 可选，不能代替技术核验日期 |
| featured | true | 仅精选文章使用，不能批量默认开启 |
| 一级标题 | `# 文章标题` | 唯一，不编号 |
| 二级标题 | `## 一、具体主题` | 中文数字连续编号 |
| 三级标题 | `### 1. 具体主题` | 每个二级标题内从 1 重新连续编号 |
| 四级标题 | `#### 1.1 具体主题` | 按项目规则，在每个三级标题内从 1.1 重新连续编号 |

标题按层级递进，不从二级跳到四级，原则上不超过四级。代码块内的井号不参与 Markdown 标题检查。README、模块首页、导航页和专用布局页按项目豁免处理，不为形式合规破坏页面功能。

### 2. 代码、表格与提示容器

格式服务于理解。参数和对比适合表格，操作适合有序步骤，单一事实保留为正文，不把所有文字机械表格化。

| 对象 | 规则 |
|------|------|
| 代码围栏 | 必须有语言标识，纯文本用 text，命令按实际 shell 标记 |
| 代码前说明 | 写清用途、执行条件或观察目标 |
| 示例文件位置 | 在代码上方或首行注释标明相对于本篇示例目录的路径，如 `src/services/order-service.ts`，并说明由读者创建 |
| 代码后说明 | 解释返回值、状态变化、失败或边界，不重复逐行代码 |
| 表格与列表 | 前后保留合理空行，列数一致；操作有序，并列内容无序 |
| 提示容器 | 使用 VitePress 的 info、tip、warning、danger、details；按第四节匹配文字语义，不混用 GitHub Alert 语法 |
| 容器标题 | 明确用途，例如兼容限制、正确实践或诊断输出 |
| 折叠内容 | 超过10行的代码块必须使用details，核心概念、条件、关键逻辑解释与结果判断在折叠外可见 |
| code-group | 同一目标有不同语言、框架或包管理器实现时使用；任一代码块超过10行时折叠整个代码组 |
| 高亮 | 只高亮关键代码，不大面积标注 |

以下是围栏与章节关系的格式模板，不是任何技术的完整文章结构。方括号字段需要在实际任务中替换；是否保留每个标题仍由内容职责决定。

::: details 查看文章结构的 Markdown 模板

````markdown
---
title: "[与正文一级标题一致]"
tags:
  - "[稳定技术词]"
excerpt: "[用 50～120 字说明文章解决的问题及核心内容]"
---

[直接说明当前知识、API 或问题，不写课程式引导。]

[给出该部分结论及必要上下文。]

### 1. [确实需要独立展开的主题]

[解释机制、条件或用法，并在需要时提供证据。]

[说明以下输出的触发方式、实际或示意性质和观察对象。]

```text
[当前主题相关的输出；实际交付必须替换并说明验证状态。]
```

[解释结果支持的结论与适用边界。]
````

### 3. 超过10行的代码块必须折叠

单个围栏代码块的内容超过10行时，必须用 `::: details 具体标题` 和 `:::` 包裹，默认保持折叠。VitePress 的正确容器名称是 `details`，不能写成 `::: detail`。这条规则适用于核心代码、完整源码、配置、命令、日志、结构化响应及展示语法的模板，不因它属于关键示例而豁免。

| 判定项 | 执行规则 |
|--------|----------|
| 行数口径 | 计算代码块内的实际内容行，包含注释、空行和文件路径注释，不包含首尾围栏；末尾普通换行不额外计行 |
| 长度边界 | 10行以内默认展开；11行及以上必须折叠，不压缩到同一行规避计数 |
| 折叠粒度 | 通常一份文件、一个连续示例或一次诊断输出一个details；不折叠整篇或整个讲解章节，不嵌套多层details |
| 折叠标题 | 写清文件、对象或用途，如“查看订单校验完整实现”，不能只写“查看详情” |
| 代码组 | 任一代码块超过10行时，用一个details包裹整个code-group；外层用四个冒号，内层用三个冒号，分别闭合 |
| 语法模板 | 围栏内若展示单独的:::结束行，外层details也使用四个冒号包裹，避免模板内容提前闭合容器 |
| 折叠外信息 | 保留用途、必要条件、关键逻辑解释、结果与判断依据；折叠代码后仍能读懂主论述 |
| 局部讲解 | 确需解释关键逻辑时，可展示不超过10行且语义完整的局部片段，明确省略上下文并保留完整实现 |
| 禁止规避 | 不删除必要注释，不把多条语句压为一行，不把连续代码机械切成多个短块 |
| 一致性 | 完整实现只保留一个权威版本，局部片段与它一致；折叠不能替代编译、执行或结果验证 |

下面展示长响应代码块的包裹方式。JSON是用于说明排版的订单响应示意，不是实测接口结果；外层Markdown围栏本身也超过10行，因此本规范将写法示例一并折叠。由于演示文本含有三个冒号的结束行，外层实际使用四个冒号界定折叠范围。

### 4. 链接、图片与语言

链接与媒体是论述的一部分，必须可访问并与当前主题相关。复制规范到其他位置时，调整相对链接，不能保留失效路径。

| 对象 | 要求 |
|------|------|
| 站内文档 | 使用相对路径，链接到真实存在的文件，文字描述目标知识 |
| 外部来源 | 链接到具体官方资料，版本与所支撑结论对应 |
| 锚点 | 修改标题时同步更新站内锚点引用，旧锚点直接作废，不添加隐藏兼容标签 |
| 图片目录 | 文档同级 images 目录，使用相对引用 |
| alt | 说明图片内容或观察对象，不能为空或只写“图片” |
| 截图 | 裁剪到相关区域，去除敏感数据，前后说明用途与观察重点 |
| 术语 | 保留 React、Promise、WebSocket 等稳定英文写法；中文译名、大小写统一 |
| 表达 | 简洁准确，不用“显而易见、非常简单”等代替解释，不用“可能、大概”代替必要核验 |

不确定内容应精确标明“哪一项未确认、缺少什么证据、影响什么结论”。合理的版本或环境不确定性可以记录，禁止含糊掩盖未核验事实。

## 七、逐章生成与历史修改

### 1. 每批的执行顺序

同章统一版本、场景和术语；每篇保持独立理解所需的上下文。默认按章推进，复杂验证场景可以缩小批次。

1. 读取当前蓝图、样板校准项、章节职责和文章职责卡。
2. 确认前置知识已有可用引用，并重新读取当前文件与工作区改动。
3. 先设计入口问题、核心模型、主问题、子问题、证据路径和收束方式；操作类内容同时规划证据相邻的操作单元，再生成当前文章，核对职责、类型、来源和示例一致性；不套用统一层级。
4. 验证核心示例，检查所有新增函数的注释与返回说明。
5. 检查讲解顺序、必要子主题缺失、主讲深度、长段落、单句要点与空小节；逐节整理文字容器与阅读重点，扫描超过10行的代码块及折叠外解释，逐项修订。
6. 检查当前篇与相邻文章的重复主讲和知识遗漏。
7. 当前篇通过后推进下一篇；整章结束时核对覆盖矩阵、术语和统一场景。
8. 在当前授权范围内更新必要导航与引用，执行受影响的工程检查并记录证据。

发现核心事实冲突、职责漂移或缺少前置时，修复受影响范围后继续。不要边批量扩写边假定蓝图问题会自行消失。

### 2. 变更与恢复规则

范围变化需要明确影响，常规文字修正无需反复审批。历史治理保留用户改动，并使当前站内引用指向有效页面与锚点；旧地址和旧锚点直接作废。

| 情况 | 处理方式 |
|------|----------|
| 不改变职责的措辞或示例修正 | 在授权范围内直接处理，验证受影响内容 |
| 新增核心知识、章节或改变版本 | 修订蓝图与职责，确认受影响范围后实施 |
| 相邻文章重复 | 明确主讲文章，其余保留最小说明和有效引用 |
| 旧文件仅局部修订 | 不全篇格式化，不顺带改名或重排导航 |
| 全文重写旧文件 | 整体迁移到现行规范，并更新受影响站内引用 |
| 工作中断后续写 | 从蓝图版本、已完成篇目、验证记录与当前 Git 状态恢复 |
| 需要启动验证服务 | 先检查现有项目服务和端口，优先复用；临时服务结束后清理或明确告知 |

“文件已生成”不能作为续写依据中的完成标识。只有通过职责、内容、示例及必要工程检查的篇目才记录为完成。

## 八、交付验收与结果记录

### 1. 单篇硬性门禁

所有适用门禁必须通过。任何一项核心事实、验证或范围失败，都不能靠更长文章或更多表格抵消。

| 编号 | 验收项 | 通过标准 |
|------|--------|----------|
| A01 | 职责与边界 | 唯一问题清楚，主讲知识覆盖，未扩展排除范围 |
| A02 | 事实与版本 | 核心结论有依据，主版本一致，差异明确 |
| A03 | 类型与深度 | 满足当前类型的必需内容与目标能力 |
| A04 | 组织与小节完整性 | 入口问题、核心模型、主问题、证据和收束形成连续判断路径；层级表达真实从属关系，既检查已有小节，也检查必要子主题缺失，无人为加层、平铺堆叠、空薄小节或重复；核心主题有解释与证据支撑 |
| A05 | 示例链路 | 从本篇定义的空目录出发，依赖、实现、入口、结果与失败边界闭合；目录层级有知识或工具依据，没有仓库示例目录引用及隐式文件依赖；代码、命令和页面展示一致 |
| A06 | 验证真实性 | 已运行、仅编译、局部、伪代码和未验证状态准确 |
| A07 | 代码注释 | 新增函数、方法和回调有职责与返回说明；多入参有完整文档注释 |
| A08 | 格式与表达 | 结构合法，各级标题准确精简、必要限定完整；正文、步骤、表格、容器和折叠内容职责清楚，没有连续大型表格或装饰性分层；操作的命令、结果、解释与失败处理相邻；超过10行代码默认折叠，核心解释可见，无课程式模板填充 |
| A09 | 链接与资源 | 相对链接、图片与必要锚点有效，无敏感内容 |
| A10 | 跨篇一致性 | 知识主讲唯一，版本、术语、场景与相邻内容一致 |
| A11 | 工程验证 | 当前修改所需的构建、导航与页面检查通过 |
| A12 | 修改范围 | 没有覆盖用户改动或引入无关改名、删除和重构 |

### 2. 检查方法与工程范围

机器检查识别格式与引用问题，语义检查识别讲解是否成立。两者都要保留真实结果，不能用“构建成功”替代内容与示例验收。

| 检查层次 | 检查内容 | 执行原则 |
|----------|----------|----------|
| 结构检查 | Frontmatter、唯一一级标题、标题编号、代码语言、表格和容器闭合；长代码行数与details祖先关系 | 解析Markdown与实际渲染；围栏中的标题不参与正文计数，11行起必须折叠 |
| 完整性扫描 | 讲解顺序、段落主题、文字容器、单句要点、二至四级小节及折叠外解释 | 浅层结构和混合主题仅列为候选；逐节人工核对实际关系，不按数量自动加层或填充 |
| 语义审校 | 标题准确性与简洁度、主问题与子问题、必要主题缺失、核心解释、边界、主讲责任和证据对应 | 对照职责卡、来源与相邻正文；精简措辞时保留必要限定，说明结构与内容调整的依据 |
| 示例验证 | 仓库示例目录引用扫描，以及编译、测试、实际调用和空目录复现 | 扫描正文、注释、目录树、命令、链接与公开记录；只使用当前文档给出的文件、依赖、版本和入口完成复现 |
| 链接与资源 | 当前站内文件、导航目标、图片与锚点 | 检查新增和直接修改的范围，目录迁移要扩展到全部引用 |
| 构建与页面 | VitePress 配置、导航、扩展语法和共享主题改变 | 必须执行对应构建；共享配置按现有多单元运行手册验证 |
| 变更检查 | 实际新增、修改、移动、删除文件及用户原有变更 | 交付前与当前任务范围对照 |

命令从当前 package.json、项目脚本和运行手册读取，不凭习惯编造 `pnpm build` 或不存在的检查命令。普通低影响文字修正不新增与实现逐行对应的测试；需要的内容检查、示例验证和既有工程门禁仍然执行。

### 3. 交付说明必须记录的事实

正文应呈现读者需要的结论与验证边界；详细执行记录可以写在交付说明或模块验收文件中，不把维护流水账堆入每篇文章。

| 项目 | 必须报告的内容 |
|------|----------------|
| 文件范围 | 新增、修改、移动、删除哪些文件 |
| 内容职责 | 对应文章 ID、主讲知识项和目标深度是否达到 |
| 版本与来源 | 采用什么基线，核对了哪些关键依据 |
| 示例验证 | 实际命令、工作目录、环境、退出结果与关键观察；未执行则如实说明 |
| 内容检查 | 语义层级及保留或调整理由、目标深度的解释与证据、讲解顺序、骨架化候选、文字容器、长代码折叠和示例一致性的处理结果 |
| 工程检查 | 实际执行的格式、链接、导航、构建或页面检查及结果 |
| 未完成事项 | 具体原因、影响范围和继续所需条件，没有则写无 |

核心门禁失败时可以交付修订草案与准确的未完成说明，但不能称为已验收文章。未明确获得用户授权，不执行提交、推送、远端 MR/PR、发布或部署；现有项目的更具体 Git 规则继续生效。

## 九、可直接复用的生成指令

### 1. 生成或全文重写单篇文章

以下为任务模板，方括号字段是用户输入，不是允许遗留在最终正文中的占位。运行环境或版本未知时，执行者先查已有资料，必要时精确确认。

::: details 查看单篇文章生成指令

```text
请依据《技术文章生成与验收规范》，完成以下技术文章。

任务输入：
- 文章主题与唯一问题：[填写]
- 任务类型：[单篇新建 / 全文重写 / 局部修改]
- 目标文件：[填写路径]
- 所属模块及主版本：[填写，或请从已确认蓝图核对]
- 模块蓝图：[填写路径或无]
- 文章职责卡：[填写路径或文章 ID；不存在时先明确职责]
- 目标读者与深度：[填写]
- 主文章类型：[填写，或依据唯一问题判断]
- 必须覆盖与不覆盖：[填写或从职责卡读取]
- 现有样板与相关示例：[填写路径或无]
- 验证环境：[填写可用条件，或先检查本地环境]

执行要求：
1. 先读取适用规则、目标全文、相邻文章、相关导航、蓝图和 Git 状态。
2. 在开始正文前确认职责和证据，判断主问题与子问题关系；只有独立问题、专属内容和定位价值成立时才增加标题，不规定层级数量。
3. 章节名称与各级标题准确精简，保留技术对象和必要限定，解释放正文；一级标题后直接进入技术主题，不生成课程式开场、目录复述或预告。
4. 按理解依赖组织内容；结合项目语法指南，以info、tip、warning、danger呈现需要关注的前提、建议、误区和风险，保持原理讲解连贯。
5. 按文章类型提供有效证据；接入、操作、测试和排障必须形成最小闭环。
6. 示例以读者新建的空目录为起点，给齐本篇所需代码、依赖、数据和命令；路径只描述本篇创建的文件。正文、注释、命令和公开记录不得引用仓库示例目录或提供其内容入口。新增函数和回调有职责、参数约束及返回说明。
   单文件示例直接使用文件名；仅为包机制、模块或构建约定保留必要层级。路径变化同步代码、命令、输出与排错说明，并检查实际页面。
7. 从空目录只提取当前文档的内容，实际验证核心示例，如实区分运行、仅编译、局部、伪代码与未验证状态。
8. 超过10行的代码块使用带具体标题的 ::: details 容器包裹，以 ::: 结束；注释和空行计入行数，核心解释和结果留在折叠外。
9. 同时检查已有小节空薄和必要子主题缺失，按职责核对解释深度；检查格式、锚点引用、长代码折叠、重复归属与工程结果。
10. 修复发现的问题后交付正文、精确变更范围与 A01—A12 验收结果。
11. 保留用户已有改动，不扩大到其他文章或远端发布。

不要只交付写作提纲；核心验证无法完成时明确影响，不声称文章已验收。
```

:::

### 2. 按已确认蓝图续写一个章节

以下指令复用已确认的蓝图和样板，不重新规划全模块，也不批量跳过逐篇验收。

::: details 查看逐章续写指令

```text
请依据《技术文章生成与验收规范》，继续完成已确认蓝图中的指定章节。

输入：
- 模块蓝图与版本：[填写路径及版本]
- 已确认样板与校准记录：[填写路径]
- 当前章节：[填写章节 ID]
- 当前完成记录：[填写路径，或先读取实际文件与验收结果]
- 本次范围：[填写需要生成或修订的文章 ID]

先核对已有确认、当前正文、工作区改动和前置知识。
逐篇按职责卡生成、核对来源、执行必要示例、扫描薄弱小节并完成验收。
每篇示例从读者自建空目录独立复现，给齐所需文件、依赖和入口，不依赖文档仓库、其他章节源码或未展示的脚本。
正文、注释、目录树、命令和公开记录不得引用仓库示例目录或提供其内容入口。
独立单文件示例直接使用文件名，必要的包和构建目录使用简短业务命名；核对代码、命令、输出及实际页面，不能只检查路径关键词。
先判断知识从属关系，再选择标题层级；保留适当的浅层结构，不为一致外观增加子节。
章节名称与各级标题准确精简，删除赘词，保留技术对象和必要限定，不按统一字数截断。
逐篇检查必要子主题是否被埋在段落、表格或长代码中，补足职责要求的解释与证据。
按知识依赖讲解，拆分多主题长段落，完整解释独立要点；超过10行的代码块必须使用details折叠。
逐节整理文字信息层次；有适用内容时必须使用info、tip、warning或danger，不以代码折叠代替阅读重点。
折叠外保留关键解释和结果，不能通过删注释、压缩代码或机械拆块规避。
一篇通过后再推进下一篇；本章结束后检查知识覆盖、重复、版本和统一场景。
需要修改核心范围、版本或知识主讲时，先修订受影响蓝图并说明原因。

交付本章正文、知识项覆盖结果、真实验证记录和必要导航变更。
不要因文件存在就跳过验收，不要把未运行示例标成成功，不要重写已通过且不受影响的文章。
```

:::

### 3. 审查并修复一篇薄弱文章

以下指令用于局部质量提升，默认保留文章既有职责和路径。

::: details 查看薄弱文章修订指令

```text
请按《技术文章生成与验收规范》检查并修复文章 [填写文件路径]。

先读取全文、职责和相邻内容，再列出有具体位置与依据的问题：
职责偏移、定义堆砌、空小节或骨架化小节、机制缺失、无效示例、版本冲突、
不完整错误处理、重复主讲、函数注释不足、链接或格式问题。
同时检查理解顺序、长段落、连续单句要点，以及超过10行代码是否在默认折叠的details中。
核对文字容器的语义、标题、位置和解释完整性，修复长文只有普通段落与代码块的问题。
检查示例是否暗中依赖文档仓库、其他章节工程、已有辅助类或构建脚本；从空目录只用本篇内容复现，补齐当前问题所需的最小上下文。
清除正文、注释、目录树、命令、链接和相关公开记录中的仓库示例目录引用及内容入口；不能只改路径或改写为“源码见配套目录”。
复审主问题与子问题关系，既检查已有小节，也检查必要子主题缺失；保留合理浅层结构，不按标题数量判断深度。
检查标题是否准确精简，将冗长解释移到正文，保留必要限定，不为缩短标题生造缩写或改变职责。
必要时重组层级或补足机制、边界和证据，记录真实理由；修改标题须同步更新受影响站内锚点引用。
检查折叠外是否保留用途、关键解释与结果，禁止删除必要注释或机械拆块规避行数规则。

在当前文章职责内直接修复；需要改变模块范围、主版本或移动文件时先提出影响说明。
不要为了凑篇幅加同义句，不统一套课程模板，不对无关段落进行全篇格式化。
修复后重新检查实际受影响的内容、示例和工程结果，交付问题处理表与剩余边界。
```
