# 系统教程分阶段生成流程

新建或全文重构技术模块必须采用分阶段生成。阶段门禁用于在低成本时发现知识范围、目录和样板问题，禁止跳过确认直接批量生成整个模块。

## 一、流程总览

| 阶段 | 核心问题 | 主要输出 | 是否需要用户确认 |
|------|----------|----------|------------------|
| 0. 任务建档 | 当前要处理什么，依据和边界是什么 | 任务范围、现状审计、版本与来源 | 范围存在歧义时需要 |
| 1. 模块蓝图 | 应讲什么，为什么这样排序 | 知识项、依赖、目录、职责卡和覆盖矩阵 | 必须 |
| 2. 样板校准 | 一篇合格正文应达到什么标准 | 样板文章和样板评审记录 | 必须 |
| 3. 逐章生成 | 如何稳定生成剩余正文 | 当前章节正文、资源和章节检查结果 | 蓝图未变化时按章推进 |
| 4. 整体验收 | 模块是否完整、一致且可构建 | 验收报告和未验证项 | 作为最终交付依据 |

单篇文章任务不要求机械执行完整模块流程，但必须具有可确定的文章职责，并执行文章契约和质量门禁。

## 二、阶段 0：任务建档

### 1. 输入检查

开始前必须读取：

- 用户需求及当前会话中的明确约束；
- 根目录和目标目录适用的 `AGENTS.md`；
- 目标模块真实文件、相邻模块和 sidebar；
- 仓库内相关链接、现有设计稿和计划；
- Git 状态及与目标范围重叠的用户改动；
- 主版本官方资料和可用验证环境。

### 2. 输出内容

任务建档至少记录：

| 字段 | 内容 |
|------|------|
| 任务类型 | 新建模块、全文重构、单篇新建、单篇重写、局部修改、目录规划或批量治理 |
| 修改范围 | 目录、文件、sidebar、链接和资源 |
| 非目标 | 本次明确不处理的模块和历史问题 |
| 现状问题 | 已通过文件和内容证据确认的问题 |
| 工作区风险 | 与用户已有改动重叠的位置 |
| 资料范围 | 主版本官方资料和验证入口 |

### 3. 阶段门禁

范围、目标读者、主版本或修改权限不明确，且不同选择会实质改变结果时，必须请求用户确认。能够通过仓库和官方资料确定的事实不得反复询问用户。

## 三、阶段 1：模块蓝图

### 1. 执行动作

1. 使用[知识体系规范](./knowledge-system.md)识别主方向和必要辅助方向；
2. 明确当前方向基础、跨方向前置知识和范围排除；
3. 根据主版本官方资料生成知识项清单；
4. 建立知识依赖并检查循环、漏项和重复；
5. 根据依赖聚合章节和文章；
6. 为每篇文章生成职责卡；
7. 建立知识覆盖矩阵和能力覆盖矩阵；
8. 选择样板文章并制定验证方案。

完整字段和判断规则以[模块蓝图规范](./module-blueprint.md)为准，输出使用[模块蓝图模板](./templates/module-blueprint-template.md)。

### 2. 用户评审内容

蓝图评审应聚焦：

- 知识方向和版本是否正确；
- 基础内容是否属于当前方向；
- 知识项是否完整且没有无关扩张；
- 章节顺序是否符合依赖；
- 单篇边界是否清晰；
- 最终能力和验证方式是否符合预期；
- 样板文章能否代表后续正文质量。

### 3. 阶段门禁

未获得用户明确确认前，不得创建目标模块正文、批量改名或更新正式 sidebar。蓝图文件本身可以作为评审产物写入项目约定的设计目录。

## 四、阶段 2：样板校准

### 1. 样板选择

默认选择一篇样板。样板应同时满足：

- 属于模块主方向；
- 能体现主要内容深度；
- 包含具有代表性的证据或示例；
- 不是仅有概念总览的最简单文章；
- 能暴露版本、术语、代码风格和边界问题。

模块包含差异显著的文章类型，且单篇样板无法验证另一类型的核心要求时，可以在蓝图阶段增加第二篇样板。增加理由和样板类型必须由用户确认。

### 2. 执行动作

1. 根据职责卡完成样板全文；
2. 实际执行或验证核心示例；
3. 检查方向边界、内容深度和文章粒度；
4. 使用[样板评审模板](./templates/sample-review-template.md)记录结果；
5. 将发现的通用问题修正到蓝图、职责卡或生成约束中。

### 3. 阶段门禁

样板未获得用户明确确认时，不得批量生成其余正文。样板需要修改时，必须先完成修订和重新评审，不能一边批量写作一边假定样板问题会自动消失。

## 五、阶段 3：逐章生成

### 1. 批次单位

默认以一个章节为最大批次。章节较大或包含高风险示例时，应缩小到一组职责相近的文章。不得一次性生成整个模块后再统一检查。

### 2. 单章执行顺序

```text
读取章节职责与文章职责卡
→ 核对前置章节状态
→ 按文章顺序生成正文
→ 逐篇执行内容与示例检查
→ 执行章节级重复和遗漏检查
→ 更新必要的 sidebar 与链接
→ 当前章通过后进入下一章
```

每次编辑前必须重新读取目标文件现状，避免覆盖用户在批量生成期间产生的新改动。

### 3. 内容漂移处理

| 情况 | 处理方式 |
|------|----------|
| 发现蓝图遗漏的重要知识 | 暂停当前批次，补充知识项、依赖和职责卡，重新确认受影响范围 |
| 文章范围超过职责卡 | 拆分、调整归属或删除无关内容，不直接扩写 |
| 相邻文章重复 | 确定唯一主讲文章，其他文章保留最小说明和链接 |
| 统一场景无法支撑当前主题 | 在章节蓝图中调整场景，不临时使用无关示例 |
| 官方结论与蓝图不一致 | 以主版本官方证据为准，修订蓝图并记录影响 |

### 4. 章节完成条件

- 本章所有职责卡中的知识项已经覆盖；
- 没有跨篇重复完整讲解；
- 术语、版本、场景、字段和命名一致；
- 核心示例已经按声明状态验证；
- 当前章节链接和 sidebar 指向真实文件；
- 章节级质量门禁通过。

## 六、阶段 4：整体验收

整体验收使用[质量门禁](./quality-gates.md)，至少输出：

| 交付项 | 内容 |
|--------|------|
| 知识覆盖结果 | 知识项和最终能力的完成状态 |
| 顺序与边界结果 | 依赖、文章归属、重复和排除项检查 |
| 事实与版本结果 | 主版本、官方来源和版本差异检查 |
| 示例验证结果 | 已运行、仅编译、局部示例和未验证项 |
| 工程验证结果 | Frontmatter、标题、链接、sidebar 和 VitePress 构建 |
| 变更范围 | 新增、修改、移动和删除文件 |
| 剩余风险 | 无法验证内容及其影响，不使用空泛风险描述 |

存在硬性门禁失败时，不得将任务标记为完成。

## 七、正文连续性

系统性和顺序性由以下结构表达：

- 知识项依赖关系；
- 章节和文章编号；
- sidebar 的嵌套与顺序；
- 当前文章中必要的前置知识链接；
- 同章统一场景和术语。

正文不使用“上一篇已经完成”“接下来学习”“下一篇继续”等元叙述。文章必须能够独立说明自己的核心结论和最小上下文。

## 八、变更与版本管理

- 蓝图确认后的实质变更必须记录原因和影响范围；
- 局部措辞、示例数据和不改变职责的修正不需要重新评审整个蓝图；
- 新增章节、改变主版本、改变知识方向或重新分配核心知识项必须重新确认；
- 未经用户明确指示，不执行 `git push`、发布、部署或创建远程 MR/PR；
- Git 提交只包含当前任务文件，不得带入用户其他已暂存或未暂存改动。
