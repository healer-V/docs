# 模块蓝图与目录规划规范

模块蓝图是新建或全文重构技术模块的正文依据。AI 必须先证明知识范围和依赖关系完整，再把知识项聚合为章节和文章；不得从通用目录模板、现有文件数量或 sidebar 外观直接反推知识体系。

## 一、蓝图前置检查

创建蓝图前必须完成以下只读检查：

1. 读取根目录和目标目录适用的 `AGENTS.md`；
2. 读取[知识体系与方向分类规范](./knowledge-system.md)；
3. 检查目标目录中的真实 Markdown 文件；
4. 检查对应 sidebar、导航和仓库内链接；
5. 查看 Git 状态并识别用户已有改动；
6. 确定任务是新建模块、全文重构还是目录治理；
7. 收集主版本官方资料和可用验证环境。

只读取 sidebar 而不检查真实文件，或者只根据文件名推断内容，都不能进入蓝图设计。

## 二、模块教学契约

蓝图首先定义模块边界。

| 字段 | 要求 |
|------|------|
| 模块名称 | 与目标目录和导航定位一致 |
| 主知识方向 | 从知识方向分类中选择一个并说明依据 |
| 辅助知识方向 | 仅列完成目标所需的方向，没有则明确写“无” |
| 读者基线 | 默认具备的通用知识和当前方向的起点 |
| 主版本基线 | 技术、运行环境和关键依赖版本 |
| 最终能力 | 读者完成模块后能够执行和判断的具体事情 |
| 前置知识 | 由其他模块负责完整讲解的内容及目标链接 |
| 范围排除 | 当前模块明确不讲的主题和归属位置 |
| 事实来源 | 官方规范、文档、仓库、发布说明和验证方式 |

最终能力必须使用可判断的描述，例如“能够根据执行计划判断索引是否生效”，不能只写“深入理解性能优化”。

## 三、知识项清单

知识项是目录规划的最小责任单位，不等于最终标题。一个知识项应表达能够独立判断覆盖状态的技术事实、能力或机制。

### 1. 知识项字段

| 字段 | 要求 |
|------|------|
| ID | 在模块中唯一，建议使用方向缩写和连续编号 |
| 名称 | 使用具体技术名称，不使用“其他”“高级内容”等表述 |
| 分类 | 当前方向基础、核心能力、运行机制、组合设计、工程、质量、生产或演进 |
| 前置 ID | 仅引用模块内真正存在理解依赖的知识项 |
| 来源 | 对应官方资料或实际验证入口 |
| 目标深度 | 认识、使用、解释、设计或诊断 |
| 证据 | 关系图、代码、配置、命令、输出、日志、指标、案例或决策表 |
| 归属文章 | 负责完整讲解该知识项的唯一文章 ID |
| 状态 | 已覆盖、部分覆盖、未覆盖或不适用 |

知识项粒度应服务于覆盖和归属判断。把“React Hooks”作为一个知识项过于宽泛；把每个参数名拆成独立知识项又过细。合理粒度通常对应一个独立规则、API、状态变化或设计判断。

### 2. 知识项来源

知识项至少从以下来源交叉生成：

- 当前知识方向覆盖模型；
- 主版本官方文档或规范的主题范围；
- 现有模块文件和 sidebar；
- 真实使用所需的工程、质量和生产能力；
- 已知版本差异、常见失败和迁移风险。

现有目录只能作为输入证据，不能作为完整性基准。官方目录也不能直接复制为教程目录，需要根据读者基线和知识依赖重新组织。

## 四、知识依赖

依赖关系只表达“理解 B 必须先掌握 A”，不表达简单的推荐顺序或主题相似性。

| 检查项 | 要求 |
|--------|------|
| 依赖存在 | 所有前置 ID 都能在当前模块或前置模块中找到 |
| 依赖必要 | 删除前置知识后，读者确实无法正确理解当前知识 |
| 无循环 | 不存在 A 依赖 B、B 又直接或间接依赖 A |
| 顺序可解释 | 章节和文章顺序能够由依赖与教学目标解释 |
| 前置外置 | 宿主语言等跨模块知识只作为前置引用，不复制进当前知识项 |

同一层级且没有直接依赖的知识项，可以按使用频率、认知负担、业务流程或官方稳定性排序，但蓝图必须说明所用依据。

## 五、章节聚合

知识项依赖检查通过后，才能聚合章节。

### 1. 聚合原则

- 同章知识项应共享心智模型、目标能力或运行链路；
- 一章应具有能够准确命名的技术职责，章节名称精简概括共同主题，保留必要限定，不堆砌知识清单或冗长解释；
- 章节顺序优先服从知识依赖，再考虑业务使用顺序；
- 当前方向基础必须在依赖它的核心能力之前；
- 工程与生产内容不能提前替代基础与机制讲解；
- 对比、迁移和速查内容放在读者具备相应对象知识之后；
- 章节数量由知识边界决定，不设置统一数量目标。

### 2. 章节职责

每章必须声明：

| 字段 | 说明 |
|------|------|
| 章节目标 | 本章建立的能力或心智模型 |
| 前置章节 | 理解本章不可缺少的前置内容 |
| 包含知识项 | 本章负责的知识点 ID |
| 排除内容 | 容易混入但属于其他章节的主题 |
| 统一场景 | 需要连续示例时采用的业务对象和命名 |
| 章节验证 | 如何判断本章内容已经形成闭环 |

“基础知识”“核心知识”“高级内容”等名称不能单独作为章节职责，必须说明具体技术主题。

## 六、文章拆分

章节确定后，再将知识项分配到文章。

### 1. 拆分条件

出现以下任一情况时，应拆分为多篇文章：

- 同时回答两个以上相互独立的学习问题；
- 不同部分需要不同的验证环境或证据形式；
- 同时承担基础语法、运行机制和生产排障等多个主类型；
- 某个部分脱离当前文章后能够独立形成完整教程；
- 标题必须依靠多个相互独立的技术主题才能描述范围，且这些主题不构成必要比较或完整机制；
- 一部分内容的前置依赖明显多于文章其他部分。

文章过长是复查信号，不是机械拆分条件。拆分后若每篇都无法形成独立结论和验证，则说明拆分不合理。

### 2. 合并条件

出现以下情况时，应合并或重新组织：

- 主题只有简短定义，不能形成独立学习结果；
- 多篇文章重复同一概念、示例和边界；
- 拆分后必须依赖其他文章正文才能理解基本结论；
- 多个知识项共同构成同一次不可分割的状态变化或操作闭环。

## 七、文章职责卡

每篇文章必须使用[文章职责卡模板](./templates/article-responsibility-card-template.md)明确边界。

| 字段 | 要求 |
|------|------|
| 文章 ID | 与章节顺序和文件编号对应 |
| 标题 | 准确、精简地概括唯一学习问题，保留技术对象和必要限定，不机械照抄完整问句；命名细则见[文章生成规范](./article-generation.md)第四节 |
| 唯一学习问题 | 能够用一句明确问句表达 |
| 前置主题 | 使用文章 ID 或知识项 ID 表达 |
| 主类型 | 从文章契约定义的七类中选择一个 |
| 辅助类型 | 最多一个，没有则明确写“无” |
| 必须覆盖 | 当前文章拥有完整讲解责任的知识项 |
| 明确不覆盖 | 由其他文章负责或不在模块范围的内容 |
| 目标深度 | 认识、使用、解释、设计或诊断 |
| 证据形式 | 用于证明结论的代码、输出、图、日志或案例 |
| 验证结果 | 读者可以观察或判断的具体结果 |
| 重复归属 | 重叠知识的主讲位置和当前文章引用方式 |

知识项只能有一个完整归属文章。其他文章需要使用该知识时，只保留理解当前主题所需的最小说明，并通过相对链接引用主讲文章。

## 八、覆盖矩阵

蓝图必须同时提供知识覆盖矩阵和能力覆盖矩阵。

### 1. 知识覆盖矩阵

| 知识项 ID | 知识项 | 归属章节 | 归属文章 | 深度 | 证据 | 状态 |
|-----------|--------|----------|----------|------|------|------|

矩阵中不得存在无文章归属的适用知识项，也不得存在被两篇文章同时标记为完整讲解的知识项。

### 2. 能力覆盖矩阵

| 最终能力 | 支撑知识项 | 负责文章 | 验证方式 | 状态 |
|----------|------------|----------|----------|------|

最终能力没有对应知识项和验证方式时，模块教学契约尚未闭合。

## 九、蓝图评审门禁

蓝图必须满足以下条件后才能请求用户确认：

- 主方向、辅助方向和分类依据明确；
- 主版本、依赖版本和来源清单完整；
- 前置知识与当前方向基础没有混用；
- 适用知识项没有遗漏、重复归属或循环依赖；
- 章节顺序能够由依赖关系解释；
- 章节名称与文章标题准确精简，与实际职责一致，没有为了缩短而删除必要限定或生造缩写；
- 每篇文章具有职责卡且只解决一个问题；
- 覆盖矩阵能够映射到模块最终能力；
- 样板文章选择能够代表主要内容难度和证据要求；
- 目录、文件、sidebar 和链接迁移范围明确；
- 没有创建指向不存在正文的正式 sidebar 链接。

用户确认蓝图后，正文生成必须以该版本蓝图为准。后续发现重要漏项时，先修订蓝图并重新确认受影响范围。
