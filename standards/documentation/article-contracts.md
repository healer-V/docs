# 单篇文档内容契约

单篇文章必须服从模块蓝图中的职责卡。本规范定义不同文章类型如何形成完整论证，但不强制所有文章使用相同标题结构。

## 一、通用职责

每篇文章必须满足以下要求：

1. 只解决职责卡声明的唯一学习问题；
2. 一级标题后直接说明当前概念、问题、API 或场景；
3. 先给出核心结论，再解释原因、机制或操作方式；
4. 使用与主文章类型匹配的证据；
5. 解释示例结果证明了什么；
6. 说明必要的适用边界、错误表现或判断方法；
7. 遵守根目录 `AGENTS.md` 的 Frontmatter、标题、代码、链接和注释规则；
8. 按理解依赖或诊断顺序组织内容，段落围绕一个中心意思，不以大段文字堆砌或连续单句要点代替完整解释。
9. 主动整理文字信息层次；需要关注的环境前提、关键建议、常见误区与风险必须用匹配的文字容器表达，不能仅靠代码折叠组织整篇阅读。
10. 按主问题与子问题的实际关系组织标题；仅当子主题需要独立解释并有专属内容时增加层级，保留适当的浅层结构，不以标题数量判断深度。
11. 文章标题与各级小节标题准确、精简地概括实际内容，优先使用技术对象与必要限定组成的短语；解释放正文，保留标准术语和问题边界，不按统一字数截断。详细命名要求见[文章生成规范](./article-generation.md)第四节。

文章可以有一个辅助类型，例如以“接入教程”为主、以“测试与排障”为辅，但辅助内容不能改变文章的唯一学习问题。

## 二、文章类型

### 1. 基础概念

基础概念文章负责建立对象、关系和边界。

| 必须包含 | 可选增强 | 不合格表现 |
|----------|----------|------------|
| 明确定义、核心对象、对象关系、适用边界、真实场景、常见误解 | 关系图、状态变化、决策表、反例 | 只给术语定义和优缺点列表 |

概述文章应建立模块或主题的整体心智模型，但不得变成文章目录、学习路线或后续章节预告。

### 2. 语法与 API

语法与 API 文章负责让读者正确使用并判断调用结果。

| 必须包含 | 必须证据 | 不合格表现 |
|----------|----------|------------|
| 语法或签名、参数、返回值、规则、状态影响、版本边界、错误用法 | 最小代码、调用方式和真实预期输出 | 只有 API 名称、参数表或孤立代码片段 |

语言语法必须解释类型、作用域或执行语义中与当前主题直接相关的规则；框架 API 不得借示例重新展开宿主语言的完整基础教程。

### 3. 运行机制

运行机制文章负责解释行为为何发生，以及读者如何观察该行为。

| 必须包含 | 必须证据 | 不合格表现 |
|----------|----------|------------|
| 参与对象、执行阶段、关键状态、触发条件、失败传播、对使用方式的约束 | 时序图、状态图、伪代码、关键日志、指标或可观察代码中的至少一种 | 只罗列内部名词或源码字段 |

内部实现细节只有在能够解释公开行为时才进入正文。私有字段和未稳定接口不得作为业务用法。

### 4. 接入教程

接入教程负责形成一条可复现的最小闭环。

| 必须包含 | 必须证据 | 不合格表现 |
|----------|----------|------------|
| 环境与版本、依赖、配置、核心实现、执行入口、预期结果、常见失败和处理 | 可以按步骤执行的代码、命令和输出 | 只有概念、零散配置或“运行成功” |

依赖、配置、代码、命令和输出必须使用一致的项目名、端口、字段和版本。无法运行时必须明确未验证部分和原因。

### 5. 设计与实践

设计与实践文章负责帮助读者在约束下作出选择。

| 必须包含 | 必须证据 | 不合格表现 |
|----------|----------|------------|
| 具体场景、约束、候选方案、比较维度、取舍、实施方式、验证和回退条件 | 决策矩阵、对照案例、迁移案例或反例 | 脱离场景罗列优缺点和最佳实践 |

“最佳实践”必须说明适用条件和不适用条件，不能把偏好写成普遍事实。

### 6. 测试与排障

测试与排障文章负责建立基于证据的诊断闭环。

| 必须包含 | 必须证据 | 不合格表现 |
|----------|----------|------------|
| 前置条件、现象、观察点、诊断步骤、定位证据、根因、修复、恢复或回滚、预防 | 测试代码、命令、日志、指标、故障注入或诊断输出 | 只有检查清单、原因猜测或成功路径 |

错误示例必须同时说明错误表现、产生原因、定位证据和正确处理，不能只展示报错文本。

### 7. 速查与参考

速查与参考文章负责提供高密度、可检索的准确资料。

| 必须包含 | 必须证据 | 不合格表现 |
|----------|----------|------------|
| 参数、命令、返回值、限制、版本范围和来源 | 关键项的最小示例或负责完整讲解的有效链接 | 只有表格，没有版本、限制和用法 |

速查文章不负责重新解释全部机制，但不能省略会导致错误使用的关键限制。

## 三、目标深度

职责卡必须声明目标深度。

| 深度 | 完成标准 | 常用文章类型 |
|------|----------|--------------|
| 认识 | 能说明定义、对象关系和适用边界 | 基础概念、速查 |
| 使用 | 能正确调用、配置或操作并判断结果 | 语法与 API、接入教程 |
| 解释 | 能解释执行过程、状态变化和行为差异 | 运行机制 |
| 设计 | 能根据场景与约束选择和实施方案 | 设计与实践 |
| 诊断 | 能根据证据定位、修复并恢复问题 | 测试与排障 |

目标深度不是文章固定标签。一篇运行机制文章可以要求读者达到“解释”，其最小示例仍需要支持“使用”；但不得因此扩展成完整接入教程。

## 四、内容闭环

文章不强制使用固定标题，但整体内容必须形成以下闭环：

```text
当前问题或概念
→ 核心结论
→ 原因、机制或使用规则
→ 示例或证据
→ 结果解释
→ 边界、错误或判断方法
```

不同要素可以使用正文、表格、代码、图、日志或 VitePress 容器表达。标题只用于独立主题，不得把闭环中的每个步骤机械创建为一个小节。

### 1. 公共阅读骨架

闭环还必须形成一条可以连续跟随的读者判断路径。公共骨架统一信息职责，不要求文章使用相同标题：

```text
问题或场景
→ 核心模型
→ 分层解释
→ 示例或操作证据
→ 失败分支
→ 判断边界
```

一级标题后的二至四个短段落直接建立问题、核心判断和必要边界。复杂主题先给出足以承载后续内容的关系、状态、时序或决策模型，再展开具体规则；不能先连续罗列术语，让读者到文章后半部分才理解对象之间的关系。

文章结尾根据类型使用判断案例、反例、恢复复测或验收结果收束，说明当前证据证明了什么、没有证明什么。不得机械复述目录或使用后续章节预告代替结论。

### 2. 类型对应的判断路径

文章主类型决定正文的默认推进方式：

| 文章类型 | 默认判断路径 |
|----------|--------------|
| 基础概念 | 真实问题 → 核心定义 → 对象关系 → 关键差异 → 场景判断 → 边界与反例 |
| 语法与 API | 使用目标 → 语法或签名 → 参数与规则 → 调用结果 → 错误用法 → 版本边界 |
| 运行机制 | 行为现象 → 参与对象 → 正常过程 → 状态变化 → 失败传播 → 观察方式 |
| 接入教程 | 最终结果 → 前置检查 → 分阶段操作与验证 → 失败处理 → 恢复或最终验收 |
| 设计与实践 | 具体场景 → 约束 → 候选方案 → 取舍 → 实施 → 验证与回退 |
| 测试与排障 | 故障现象 → 现场保护 → 分层证据 → 分支收敛 → 修复或回退 → 恢复复测 |
| 速查与参考 | 适用版本 → 查询维度 → 参数或命令 → 最小用法 → 限制与完整资料入口 |

默认路径可以按职责删减或合并，但不能改变主类型应交付的证据。例如概念文章不需要伪造操作步骤，教程文章不能只用关系图代替可执行闭环。

### 3. 操作单元的证据相邻性

操作、测试和排障内容按“目标与条件 → 命令或动作 → 预期结果 → 结果解释 → 失败处理”组织为相邻单元。不同要素可以使用段落、步骤、代码和容器表达，不把这些名称机械设置为标题。

命令与输出之间只插入理解执行所必需的说明。结果解释紧跟输出，明确观察项证明的状态；最可能发生的失败及处理放在当前步骤附近，不能把全部限制集中到文章末尾，迫使读者执行后才发现前置条件不成立。

### 4. 注意力层级

读者只浏览标题、各节首段和提示容器时，应能还原文章的主要判断路径。页面元素按职责分工：

- 正文承担定义、因果、机制和结论推导；
- 有序列表承担有前后依赖的操作与诊断；
- 表格只承担稳定的同维度比较、参数和状态查询；
- 提示容器只突出一个关键条件、建议、误区或风险；
- `details` 只收起完整长代码、补充证据和次要细节；
- 标题只承担确实需要独立解释和定位的主问题与子问题。

出现连续大型表格、同一节反复切换表达形式、命令与解释相隔多个小节，或者纯文字连续超过一个主要主题时，必须重新设计信息关系。不能用更多表格、容器、加粗或标题制造虚假的内容层次。

## 五、示例契约

### 1. 示例选择

- 示例必须直接证明当前文章的核心结论；
- 同章文章优先复用统一业务场景、对象和命名；
- 每篇保留理解和执行当前示例所需的最小上下文；
- 示例不得依赖“上一篇代码”、文档仓库目录、其他章节工程或未展示的辅助文件才能运行；
- 在本篇定义读者新建的示例目录，给齐当前闭环所需代码、依赖、输入数据与命令；文件位置相对于该目录，不能要求读者先查看仓库结构；
- 正文、注释、目录树、命令、链接及相关公开记录不得引用仓库示例目录或提供其内容入口；按当前知识设计独立示例，不能只改路径或使用“源码见配套目录”等说明；
- 单文件示例直接使用文件名；仅在知识机制或工具要求成立时保留必要包与目录层级，采用简短业务命名；修改路径同步代码、导入、命令、输出及失败说明；
- 不展示与当前知识无关的完整工程和配置；
- 不使用生产地址、真实账号、密钥、内部仓库地址和客户数据。

### 2. 示例结果

示例后必须说明观察对象和预期变化，例如返回值、DOM、状态、日志、指标、文件产物或数据库记录。普通终端输出使用 `text`，结构化响应使用对应语言标识。

“运行成功”“效果如下”但没有真实结果和观察重点，不能视为验证。

### 3. 示例验证

独立性验收从空目录只提取当前文档中的文件，并执行本篇说明中的命令。仓库内维护示例通过测试，只能作为补充证据，不能证明当前文档没有遗漏依赖。

| 示例状态 | 文档处理 |
|----------|----------|
| 已实际执行 | 记录执行环境、入口和与正文一致的结果 |
| 可编译但未运行 | 说明只完成编译检查以及未覆盖的运行行为 |
| 局部代码 | 明确省略上下文和不能独立运行的边界 |
| 伪代码 | 使用 `text` 或明确的伪代码标识，不冒充真实语言程序 |
| 无法验证 | 记录原因并阻止依赖该结果的核心结论进入已完成状态 |

### 4. 示例展示与长代码折叠

超过10行的围栏代码块必须放入默认折叠的 `::: details 具体标题` 容器，以 `:::` 结束。内容行数包含注释和空行，不包含首尾围栏；末尾普通换行不额外计行。代码、配置、命令和输出都适用，完整核心示例也不能豁免。代码组及语法模板按[技术文章生成与验收规范](./article-generation.md)的同一口径处理。

用途、必要条件、关键逻辑解释和结果判断保留在折叠外，让读者不展开长代码也能理解主论述。需要解释局部代码时，可以展示不超过10行且具有独立语义的片段，保留完整实现并核对两者一致；不能通过删注释、压缩语句或机械拆块规避规则。折叠不改变示例类型、可运行性和验证责任。

## 六、文章粒度

### 1. 必须复查拆分的信号

- 同时回答两个以上独立问题；
- 不同部分需要完全不同的验证环境；
- 同时承担多个主文章类型；
- 一部分内容可以独立形成完整教程；
- 标题包含多个并列且可独立学习的技术主题；
- 内容需要大量重复解释不同的前置知识。

### 2. 必须复查合并的信号

- 标题下只有一条定义或结论；
- 多篇文章重复同一组概念和示例；
- 拆分后的文章不能独立形成内容闭环；
- 多个知识点共同构成一次不可分割的调用或状态变化。

文章篇幅不设置统一字数、段落数或行数门槛。篇幅只能触发复查，不能代替对学习问题、证据和依赖的判断；代码块超过10行必须折叠是展示要求，不是删减内容或拆分文章的依据。

## 七、正文表达

正文应直接、准确地讲解当前技术事实和操作目标。禁止固定生成以下课程式内容：

- 学习目标；
- 本章或本文学习路线；
- 前文回顾；
- 下一篇预告；
- 与技术主题无关的实践任务；
- 机械重复正文的总结；
- 使用表格、流程图或代码块重复展示文章目录。

需要说明前置条件时，将条件放到实际使用它的示例或机制附近。需要引用其他知识时，使用有意义的相对链接，不用叙事话术维持连续性。

连贯讲解使用正文，同维度比较使用表格，操作过程使用有序列表，并列事实使用无序列表。复杂机制不能压缩成一个表格单元格，独立要点也不能只用一句定义带过；可以简短表达的事实不强制扩写。段落转换应体现因果、条件或步骤关系，不靠连续标题和空行制造结构。

术语与缩写在首次使用处给出必要解释，数值标明单位与边界，代词能就近找到明确对象。关键限制贴近受影响的用法，示例解释紧跟示例；加粗和提示容器只突出需要特别注意的信息，不代替论述。

文字容器按 `info`（前提与中性说明）、`tip`（建议与判断）、`warning`（误区与限制）、`danger`（安全、数据和不可逆风险）选择。标题直接指出对象和结论，内容保留条件、原因或处理方式；必要前提和风险放在操作之前。一个容器只承载一个判断，不套住整节，不连续堆叠；原理和推导保持连贯正文。长文逐节检查阅读重点，具体示例与验收方式见[文章生成规范](./article-generation.md)。

## 八、交付前自检

- [ ] 唯一学习问题与正文一致；
- [ ] 主文章类型和证据形式匹配；
- [ ] 达到职责卡声明的目标深度；
- [ ] 标题体现真实知识关系，没有为了外观统一增加层级；保留浅层结构或重组的理由明确；
- [ ] 各级标题准确精简，无冗长解释或空泛修饰；必要技术对象、版本和问题边界没有因缩短而丢失；
- [ ] 同时检查已有小节空薄和必要子主题缺失，主讲机制没有被一行表格、提示或完整代码代替；
- [ ] 必须覆盖和明确不覆盖的边界得到遵守；
- [ ] 示例前有用途，示例后有结果和观察重点；
- [ ] 只看本篇即可创建所需文件并运行核心示例，没有文档仓库路径、跨章源码、隐式辅助类或未给出创建方法的脚本依赖；
- [ ] 正文及相关公开记录没有仓库示例目录引用、源码入口或取用说明；
- [ ] 至少说明一个必要边界、错误表现或判断方法；
- [ ] 没有骨架化小节和机械扩写；
- [ ] 讲解顺序符合依赖，段落只推进一个中心意思，无多主题长段落和连续单句知识要点；
- [ ] 表格、列表和正文选择恰当，术语、单位和指代清楚；
