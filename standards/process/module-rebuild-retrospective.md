# 技术模块重建复盘：HTML 案例

2026-11-14 完成的 HTML 模块重建，把 12 篇平铺旧文整理为 7 章 40 篇，并接入 sidebar 与构建链路。这次重建留下了可复用的判断：哪些内容该压缩、章节按什么聚合、相邻主题如何避免重复主讲、样板为什么选最难写的一篇，以及章节验收中哪些条件值得写成脚本。

本文件记录这些取舍和偏差，供后续模块重建参考。它是案例复盘，不新增规范：目录、流程、门禁和文章形状仍以[目录规划](../knowledge/directory-planning.md)、[阶段流程](./workflow.md)、[质量门禁](./quality-gates.md)和[知识文档生成范式](../article/knowledge-document-paradigm.md)为准。HTML 的章数、篇数和主题顺序不能当作模板复制。

记录的边界：章节验收记录覆盖第 1—4 章，第 5—7 章只有蓝图状态、文章产物与构建结果，没有同格式的验收记录。因此下文关于验收的细节以第 1—4 章为准。

## 一、结果与关键判断

| 项目 | 结果 |
|------|------|
| 模块 | `content/frontend/01-html/` |
| 规模 | 7 章 40 篇；章节目录从 `01-foundation/` 到 `07-related-web-apis/` |
| 起点 | 12 篇平铺旧文、2 篇历史样板和旧 sidebar，没有章节层级 |
| 设计文件 | [HTML 目录设计](../blueprints/frontend/01-html.md) |
| 样板 | A01-05 元素嵌套与内容模型 |
| 章节记录 | 2026-11-14 的第 1—4 章验收记录，保存在本地 `superpowers/reviews/` |
| 结果 | 40 篇接入导航；旧稿最终移除；单元构建与浏览器回归通过 |

复盘后可以确认三个判断。第一，模块质量问题主要在蓝图阶段决定：背景是否压缩、章节按什么聚合、相邻主题归谁主讲，写正文时再调整成本很高。第二，写作阶段的主要风险不是内容太少，而是范围漂移和示例不可复现，职责卡与独立示例分别约束这两件事。第三，验收阶段能机械判定的条件应当写成脚本，人工目视只负责脚本覆盖不到的表达与排版。

## 二、模块级设计

### 1. 背景压缩为一篇概述

HTML 的起源、用途、与 CSS 和 JavaScript 的分工、HTML5 与现行标准的关系，全部放进 A01-01《HTML 概述》，没有另设“发展史”或“版本演进”章。零基础读者首先需要知道这门技术解决什么问题、在页面里处于什么位置；年表和组织史不帮助建立这个定位，却会占用建立语法与文档结构的时间。

历史差异仍然保留，但只在需要判断“某个写法是不是 HTML5 新增”时引用，并明确历史资料只用于归属核对，不作为现行行为依据。这个处理适合“历史本身不是学习目标”的技术；如果某门技术的历史争议直接影响当前写法，就应另设文章，不能为了压缩而省略。

### 2. 章节按能力递进，不按版本史切分

第 1—3 章建立基础：语法与文档结构、常用内容元素、表单。第 4—6 章按 HTML5 的能力类别展开：语义元素与属性增强、表单增强、多媒体与图形。第 7 章收相关 Web API。章节顺序表达的是理解依赖和可完成的任务，不是标准发布的先后。

这样切分还带来两个约束。HTML5 章节只讲相对 HTML4 的新增和变化，不重新教授基础；同时不把今天的所有能力都称为“HTML5 新增”。如果按版本号分章，这两条都很难守住，读者会在不同章节读到同一套标签规则。

### 3. 每章先写四项契约

蓝图里每章都写能力目标、必要前置、排除范围和验证方式。能力目标回答“学完能做什么”，必要前置说明依赖哪一章的哪些知识，排除范围阻止章节膨胀，验证方式决定这一章需要什么形态的示例。

四项写不出来，通常说明这一章还没有设计好。例如表单基础章的能力是建立控件、状态、字段条目和请求编码的关系，排除数据库、认证和生产上传；验证方式就自然是标签、键盘、状态、重置与本地接收证据，而不是再写一套业务表单。

### 4. 相邻主题先定唯一主讲

蓝图里有一张相邻主题表，为容易重复的内容指定唯一主讲文章，并写明其他文章的使用边界：

| 相邻主题 | 唯一主讲 | 其他文章的使用边界 |
|----------|----------|--------------------|
| 属性书写、全局属性与增强全局属性 | A01-03、A01-06、A04-03 | 语法篇只讲书写与取值；基础与增强全局属性分别讲用途 |
| 合法结构与容错解析 | A01-05、A01-10 | 内容模型讲作者应如何写；解析篇讲浏览器如何处理错误结构 |
| 资源接入与 URL | A01-09、A02-04 | 头部文章完成当前资源接入；路径篇完整解释文档基准 |
| 控件状态与提交条目 | A03-04、A03-05 | 状态篇讲默认值、重置与禁用；提交篇讲字段是否参与请求 |
| 输入类型、提示与校验 | A05-01、A05-02、A05-05 | 类型讲数据含义；属性讲提示与提交；校验讲规则、时机与绕过 |
| SVG 与 Canvas | A06-05、A06-04 | SVG 讲矢量节点与 HTML 集成；Canvas 讲位图与绘制 |
| 可拖动声明与拖放过程 | A04-03、A07-02 | 属性篇只讲声明；API 篇讲事件、数据与目标接收 |

重复教学首先是目录问题，不是写作问题。等写到第三篇才发现“这个属性前面讲过”，已经产生了不一致的解释。把归属和边界提前写死，正文只需引用，不需要重复定义。

### 5. 职责卡固定九个字段

每篇文章的职责卡包含身份与路径、唯一问题、知识归属、类型与深度、必须覆盖、明确不覆盖、证据与观察、失败边界、核验。字段不是为了填表完整，而是各自防一种失败：

| 字段 | 防的问题 |
|------|----------|
| 身份与路径 | 章节调整后路径漂移、sidebar 挂错 |
| 唯一问题 | 一篇里出现第二个主题，标题无法收敛 |
| 知识归属 | 同一知识项被两篇重复主讲 |
| 类型与深度 | 概念文章写成 API 清单，或入门文章讲到引擎实现 |
| 必须覆盖与明确不覆盖 | 范围膨胀，或关键规则缺失 |
| 证据与观察 | 示例形式与文章类型不匹配 |
| 失败边界 | 只写成功路径，读者不知道写错会怎样 |
| 核验 | 没有环境、版本和未验证范围的记录 |

### 6. 来源表带范围与核对日期

来源清单为每条资料写明支撑范围和核对日期。历史差异说明只用于核对归属，规范正文用于现行行为，检查器文档只用于工具能力。这样在写作时能判断“这条结论该引哪一类资料”，也避免把草案、历史说明或工具文档当成现行规则。

## 三、样板选择

### 1. 选高风险篇目，不选最好写的

HTML 的样板是 A01-05《元素嵌套与内容模型》，不是概述。它同时具备三个特征：规则密集、依赖浏览器的容错行为、需要合法与非法两种结构对照。这类文章最容易暴露术语是否准确、规则是否讲清、示例是否能证明结论、失败分支是否可复现。概述写得顺，不能证明这套写法能承载规则型内容。

### 2. 样板要证明四件事

样板评审实际检查的是：概念与规则是否先于属性表；完整文件能否独立运行；故意写错的结构能否被检查器和浏览器观察区分；验证记录是否写明环境与未验证范围。四项都成立，才说明这套深度和文风可以复制到其余文章。

### 3. 确认后的批量边界

样板确认后，后续章节按职责卡和样板深度生成，不再逐篇重复请求同一种确认。出现实质偏离——新增知识项、改变文章类型、扩张范围——才回到用户确认。这样既保持批量效率，也不会把“已确认样板”当成“任何改动都无需说明”。

## 四、章节生成与验收

### 1. 独立示例保留三份记录

每章在本地保留三组核验材料：正常示例、故意构造的错误、修复后的结果，分别写入 `verification.json`。分成三份而不是只留成功结果，是为了证明检查器确实能发现错误、修复确实解决了问题。读者拿到文章时看到的是结论，维护者需要看到结论是怎么被验证的。

### 2. 交叉复核

章内文章分组轮换复核，root 再抽查完整正文。作者不复核自己的文章，避免“按自己的理解检查自己的解释”。复核不是重写，重点看事实、范围、重复主讲和示例入口是否与职责卡一致。

### 3. 章节门禁写成脚本

本地 `work/html-generation/accept-chapter.py` 把章节验收条件写成断言：严格检查退出码为 0、每篇两个视口、无横向溢出、代码折叠默认关闭、构建页数匹配、无高亮回退、三份核验记录存在。通过后才更新导航与覆盖状态，并记录当章文件哈希。

脚本化的价值在于条件不会因为“这章看起来没问题”而放松。视口数量、折叠状态和构建日志都属于人工容易漏看、机器容易判断的项目。表达质量、术语准确性和示例是否真的说明问题，仍然要靠评审。

### 4. 问题向前修复并回查

第 2 章验收时发现第 1 章的一处 SVG 代码围栏语言标错，修复后重新检查并构建第 1 章，而不是留到模块结束。批量生成必须有回查机制：后写的文章会暴露前文的约定问题，发现后应立即回到受影响章节，不能只在新文章里改。

### 5. 外部限制不绕过

在线 Nu 检查器返回 429 时，改用官方本地 Nu 26.11.9 完成全部合法、错误和修复检查，没有跳过检查或伪造结果。无法验证的场景单独记录：文件选择器的原生取消、真实定位权限、完整屏幕阅读器都没有被写成已验证。验收记录的价值来自它同时说明“测了什么”和“没测什么”。

## 五、容易复发的偏差

| 偏差 | 本次的表现或风险 | 处理 |
|------|------------------|------|
| 按版本史分章 | 容易把 HTML4 与 HTML5 拆成两套重复教程 | 按能力聚合，版本差异只在需要处解释 |
| 背景膨胀 | 起源、组织史、版本年表挤占基础篇幅 | 压缩为一篇概述，历史资料只作归属核对 |
| 相邻主题重复主讲 | 属性、URL、控件状态在多篇反复定义 | 蓝图阶段建立唯一主讲与使用边界表 |
| 样板选最好写的 | 概述通过不能证明规则型文章可承载 | 选规则密集、有失败分支的篇目 |
| 示例共享业务 | 跨篇依赖文件，读者无法单篇复现 | 每篇从空目录给齐文件与入口 |
| 只记录成功路径 | 检查器是否有效、修复是否成立都无证据 | 正常、错误、修复三份记录分开保存 |
| 验收与工程脱节 | 内容检查通过，构建或渲染仍有问题 | 章节门禁同时断言内容、构建与视口 |
| 工具失败就跳过 | 在线检查不可用时省略检查 | 改用官方本地工具，保留未测说明 |
| 旧稿处理时机失当 | 过早删除丢失对照，过晚保留造成死链 | 迁移期保留，章节验收后接入导航，模块完成再移除 |
| 把规模和目录当模板 | 其他模块照搬七章四十篇 | 只复用判断方法，章数篇数由知识依赖决定 |

## 六、复用清单

### 1. 设计阶段

- 审计现有文件、体量、sidebar、顶栏、正文引用与旧 URL；
- 写清读者起点、外部前置与明确排除项；
- 判断背景能否压缩为一篇，历史是否只是归属问题；
- 为每章写出能力目标、必要前置、排除范围与验证方式；
- 建立相邻主题的唯一主讲与使用边界表；
- 为每篇写职责卡，确认唯一问题与知识归属；
- 给来源表标注支撑范围与核对日期；
- 选择规则密集、有失败分支的篇目作为样板。

### 2. 写作阶段

- 每篇从读者新建的空目录复现，不共享业务与跨篇文件；
- 先搭最小示例并实际运行，再按观察结果写正文；
- 分别保留正常、故意错误与修复三组记录；
- 超长代码折叠，容器承担判断，验证记录写明环境与边界；
- 每章结束执行内容检查与单元构建，发现问题回查受影响章节。

### 3. 验收阶段

- 严格检查 0 错误 0 警告；
- 每篇至少两个视口，无横向溢出，代码折叠默认关闭；
- 构建页数符合预期，无代码高亮回退；
- 三份核验记录存在，导航与覆盖状态已同步；
- 记录当章文件哈希，列出未验证的浏览器、设备与场景。
