# 正文生成指令

以下指令配合[技术文章生成与验收规范](../article/article-generation.md)使用，方括号字段在实际任务中替换。

## 一、生成或全文重写单篇文章

以下为任务模板，方括号字段是用户输入，不是允许遗留在最终正文中的占位。运行环境或版本未知时，执行者先查已有资料，必要时精确确认。

::: details 查看单篇文章生成指令

```text
请依据《技术文章生成与验收规范》，完成以下技术文章。

任务输入：
- 文章主题与唯一问题：[填写]
- 任务类型：[单篇新建 / 全文重写 / 局部修改]
- 目标文件：[填写路径]
- 所属模块及主版本：[填写，或请从已确认蓝图核对]
- 模块蓝图：[填写路径或无]
- 文章职责卡：[填写路径或文章 ID；不存在时先明确职责]
- 目标读者与深度：[填写]
- 主文章类型：[填写，或依据唯一问题判断]
- 必须覆盖与不覆盖：[填写或从职责卡读取]
- 现有样板与相关示例：[填写路径或无]
- 验证环境：[填写可用条件，或先检查本地环境]

执行要求：
1. 先读取适用规则、目标全文、相邻文章、相关导航、蓝图和 Git 状态。
2. 在开始正文前确认职责和证据，判断主问题与子问题关系；只有独立问题、专属内容和定位价值成立时才增加标题，不规定层级数量。
3. 章节名称与各级标题准确精简，保留技术对象和必要限定，解释放正文；一级标题后直接进入技术主题，不生成课程式开场、目录复述或预告。
4. 按理解依赖组织内容；结合项目语法指南，以info、tip、warning、danger呈现需要关注的前提、建议、误区和风险，保持原理讲解连贯。
5. 按文章类型提供有效证据；接入、操作、测试和排障必须形成最小闭环。
6. 示例以读者新建的空目录为起点，给齐本篇所需代码、依赖、数据和命令；路径只描述本篇创建的文件。正文、注释、命令和公开记录不得引用仓库示例目录或提供其内容入口。新增函数和回调有职责、参数约束及返回说明。
   单文件示例直接使用文件名；仅为包机制、模块或构建约定保留必要层级。路径变化同步代码、命令、输出与排错说明，并检查实际页面。
7. 从空目录只提取当前文档的内容，实际验证核心示例，如实区分运行、仅编译、局部、伪代码与未验证状态。
8. 超过10行的代码块使用带具体标题的 ::: details 容器包裹，以 ::: 结束；注释和空行计入行数，核心解释和结果留在折叠外。
9. 同时检查已有小节空薄和必要子主题缺失，按职责核对解释深度；检查格式、锚点引用、长代码折叠、重复归属与工程结果。
10. 修复发现的问题后交付正文、精确变更范围与 A01—A12 验收结果。
11. 保留用户已有改动，不扩大到其他文章或远端发布。

不要只交付写作提纲；核心验证无法完成时明确影响，不声称文章已验收。
```

:::

## 二、按已确认蓝图续写一个章节

以下指令复用已确认的蓝图和样板，不重新规划全模块，也不批量跳过逐篇验收。

::: details 查看逐章续写指令

```text
请依据《技术文章生成与验收规范》，继续完成已确认蓝图中的指定章节。

输入：
- 模块蓝图与版本：[填写路径及版本]
- 已确认样板与校准记录：[填写路径]
- 当前章节：[填写章节 ID]
- 当前完成记录：[填写路径，或先读取实际文件与验收结果]
- 本次范围：[填写需要生成或修订的文章 ID]

先核对已有确认、当前正文、工作区改动和前置知识。
逐篇按职责卡生成、核对来源、执行必要示例、扫描薄弱小节并完成验收。
每篇示例从读者自建空目录独立复现，给齐所需文件、依赖和入口，不依赖文档仓库、其他章节源码或未展示的脚本。
正文、注释、目录树、命令和公开记录不得引用仓库示例目录或提供其内容入口。
独立单文件示例直接使用文件名，必要的包和构建目录使用简短业务命名；核对代码、命令、输出及实际页面，不能只检查路径关键词。
先判断知识从属关系，再选择标题层级；保留适当的浅层结构，不为一致外观增加子节。
章节名称与各级标题准确精简，删除赘词，保留技术对象和必要限定，不按统一字数截断。
逐篇检查必要子主题是否被埋在段落、表格或长代码中，补足职责要求的解释与证据。
按知识依赖讲解，拆分多主题长段落，完整解释独立要点；超过10行的代码块必须使用details折叠。
逐节整理文字信息层次；有适用内容时必须使用info、tip、warning或danger，不以代码折叠代替阅读重点。
折叠外保留关键解释和结果，不能通过删注释、压缩代码或机械拆块规避。
一篇通过后再推进下一篇；本章结束后检查知识覆盖、重复、版本和统一场景。
需要修改核心范围、版本或知识主讲时，先修订受影响蓝图并说明原因。

交付本章正文、知识项覆盖结果、真实验证记录和必要导航变更。
不要因文件存在就跳过验收，不要把未运行示例标成成功，不要重写已通过且不受影响的文章。
```

:::

## 三、审查并修复一篇薄弱文章

以下指令用于局部质量提升，默认保留文章既有职责和路径。

::: details 查看薄弱文章修订指令

```text
请按《技术文章生成与验收规范》检查并修复文章 [填写文件路径]。

先读取全文、职责和相邻内容，再列出有具体位置与依据的问题：
职责偏移、定义堆砌、空小节或骨架化小节、机制缺失、无效示例、版本冲突、
不完整错误处理、重复主讲、函数注释不足、链接或格式问题。
同时检查理解顺序、长段落、连续单句要点，以及超过10行代码是否在默认折叠的details中。
核对文字容器的语义、标题、位置和解释完整性，修复长文只有普通段落与代码块的问题。
检查示例是否暗中依赖文档仓库、其他章节工程、已有辅助类或构建脚本；从空目录只用本篇内容复现，补齐当前问题所需的最小上下文。
清除正文、注释、目录树、命令、链接和相关公开记录中的仓库示例目录引用及内容入口；不能只改路径或改写为“源码见配套目录”。
复审主问题与子问题关系，既检查已有小节，也检查必要子主题缺失；保留合理浅层结构，不按标题数量判断深度。
检查标题是否准确精简，将冗长解释移到正文，保留必要限定，不为缩短标题生造缩写或改变职责。
必要时重组层级或补足机制、边界和证据，记录真实理由；修改标题须同步更新受影响站内锚点引用。
检查折叠外是否保留用途、关键解释与结果，禁止删除必要注释或机械拆块规避行数规则。

在当前文章职责内直接修复；需要改变模块范围、主版本或移动文件时先提出影响说明。
不要为了凑篇幅加同义句，不统一套课程模板，不对无关段落进行全篇格式化。
修复后重新检查实际受影响的内容、示例和工程结果，交付问题处理表与剩余边界。
```

:::
