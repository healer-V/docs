# 知识文档生成范式

这份范式来自本项目已定稿的 HTML 章节，用于回答一个具体问题：拿到一个知识点后，按什么顺序把它写成读者能读懂、能复现、能判断对错的文章。它约束的是生成过程与文章形状，不替代已有的格式、示例和验收细则。

后续在本项目中生成知识文档时，默认按本范式执行。用户在当前任务中的明确要求、根目录 `AGENTS.md`、[技术文章生成与验收规范](./article-generation.md)和模块蓝图优先；本范式与它们冲突时，以更高优先级的要求为准。

::: info 本范式的边界
本范式适用于技术知识文章、章节正文和模块内的学习文档，不适用于根目录说明、导航页、友链页和自动生成文件。具体的 Frontmatter、标题编号、代码折叠和链接规则仍以[Markdown 与 VitePress 格式规范](../writing/markdown-format.md)为准；知识项范围和文章职责仍以模块蓝图为准。
:::

## 一、范式的定位

### 1. 解决什么问题

知识文档常见的问题不是“没写内容”，而是内容没有形成判断路径：先列名词，再列属性，最后贴一段无法独立运行的代码；读者知道有哪些词，却不知道什么时候用、写错会怎样、如何确认结果。

本范式要求每篇文章都围绕一个可回答的问题组织，并让读者沿着“这是什么、为什么这样、怎么使用、怎样观察、错了怎么办”的顺序建立能力。篇幅、标题数和代码量都不是完成标准。

### 2. 与现有规范的分工

| 层次 | 负责内容 | 本范式如何处理 |
|------|----------|----------------|
| 根目录 `AGENTS.md` | 项目定位、任务路由、硬性规则 | 遵守，不改写 |
| [文章生成规范](./article-generation.md) | 职责契约、文章类型、验收门禁 | 引用，不重复定义 |
| [写作三件套](../writing/content-organization.md) | 正文组织、格式、示例细则 | 引用，不另立格式规则 |
| 模块蓝图 | 知识范围、章节、文章职责、版本 | 按卡执行，不擅自扩张 |
| 本范式 | 从输入到成文的默认顺序与文章形状 | 统一生成节奏和判断标准 |
| [正文模板](../templates/article-template.md) | 整篇骨架与知识单元卡片 | 作为输出形状直接使用 |

### 3. 一条总原则

**先确定读者要能判断什么，再决定写什么；每个知识点都要落到机制、用法、观察和边界四件事上。**

“机制”回答为什么这样设计、在哪个阶段起作用；“用法”回答在什么元素、属性、参数或命令上怎样写；“观察”回答从哪里看到结果；“边界”回答什么情况下不适用、写错会怎样。四件事缺一项，知识点就还没有讲完。

## 二、生成前的判断

### 1. 五类输入必须先确认

| 输入 | 要确认的内容 | 缺失时的后果 |
|------|--------------|--------------|
| 当前任务 | 新建、全文重写、局部修改还是批量治理 | 容易扩大范围或重排无关内容 |
| 模块蓝图 | 文章 ID、唯一问题、主讲知识、前置与不覆盖 | 主题漂移、重复主讲或遗漏前置 |
| 读者起点 | 已学什么、当前文章允许默认什么 | 把本模块应讲的基础转嫁给读者 |
| 版本与来源 | 主版本、运行环境、官方资料、时效边界 | 把历史写法当成现行规则 |
| 验证环境 | 能否实际运行、可观察什么、缺什么 | 把预期结果写成实测结果 |

开始编辑前还要查看工作区状态，识别并保留用户已有改动。不要用历史版本覆盖磁盘上的当前内容，也不要把“文件已存在”当成“文章已完成”。

### 2. 先选文章类型，再选证据

| 文章类型 | 主体回答 | 最低证据 | 常见收尾 |
|----------|----------|----------|----------|
| 概念与结构 | 对象是什么、由哪些部分组成、如何区分 | 场景、关系表、状态变化或反例 | 误判表、边界说明 |
| 语法与 API | 语法、参数、属性、返回值、约束 | 最小片段、完整示例、可观察结果 | 错误用法、版本边界 |
| 操作与接入 | 从环境到结果的完整链路 | 空目录可复现的文件、命令、入口 | 失败表、恢复步骤 |
| 测试与排障 | 现象、证据、根因、修复、预防 | 故障注入、日志、读数、复测 | 诊断顺序、未覆盖边界 |
| 设计与实践 | 场景、候选方案、取舍、回退 | 决策矩阵、对照案例 | 适用条件、不适用条件 |

概念文章可以不包含可运行示例，但必须用场景、关系或反例建立判断，并明确说明“本篇没有运行示例”。操作类文章不能只给代码片段，必须给入口、预期结果和失败处理。

### 3. 把“不覆盖”写在开始之前

写作前用一句话列出本篇不负责的内容，并指向真正的主讲文章。这样可以在写作中及时发现范围膨胀：出现第二个独立问题时，先判断它是否应拆成另一篇，而不是继续加三级标题。

## 三、整篇骨架

### 1. 开篇二至四段建立模型

一级标题后直接进入技术主题。开篇说明当前对象是什么、解决什么问题、核心机制或分类、适用边界；不写“学习目标”“本章将介绍”“上一篇”“下一篇”或文章目录复述。

开篇的任务是让读者知道“接下来要解决哪一个问题”，不是把全文摘要提前抄一遍。需要交代范围时，用一句 `info` 容器指向相邻文章，不展开成课程路线。

### 2. 二级标题按主问题划分

每个 `##` 承担一个主问题，例如“属性写在开始标签的哪里”“布尔属性为什么不能用 false 关闭”“浏览器如何恢复错误结构”。主问题之间按理解依赖排列：先建立概念，再讲规则，再进入组合使用和失败判断。

不要套用“概述、原理、用法、实践、总结”的固定序列。概念文章可以按“对象—关系—边界”展开；语法文章可以按“位置—取值—状态—错误”展开；操作文章可以按“准备—实现—观察—排错”展开。

### 3. 三级标题拆开需要独立定位的子问题

当一个主问题下出现多个可分别定位的知识点时，用 `###` 拆开。三级标题应使用具体技术对象或判断，不用“基本介绍”“注意事项”“补充说明”这类无法定位的标题。

四级标题只用于同一子问题下的并列细节，例如一组取值或一组对照项；原则上不超过四级。层级表达真实的从属关系，不为了视觉整齐给每段都加标题。

### 4. 收尾给出判断工具

结尾使用失败表、反例、决策表或验证记录，说明当前证据证明了什么、没有证明什么。不要用“通过本文的学习”“在实际开发中我们应该”这类总结套话。

| 位置 | 应该出现 | 不应该出现 |
|------|----------|------------|
| 开篇 | 对象、问题、核心模型、范围 | 学习目标、课程安排、目录复述 |
| 主体 | 主问题、子问题、机制、示例、观察 | 关键词清单、同义反复、无边界结论 |
| 收尾 | 失败表、验证记录、未覆盖边界 | 口号式总结、重复正文 |

::: tip 篇幅是结果，不是目标
已定稿的基础章节常见形状是 4～6 个二级主问题、8～20 个三级知识单元、200～400 行。这个区间只用于自查内容密度：明显偏短时检查是否缺少机制或边界，明显偏长时检查是否混入了另一篇文章的职责。它不是字数配额，也不能反过来要求每篇凑到相同长度。
:::

## 四、知识单元的五段式

一个三级标题下通常按五段组织：结论、状态表、最小示例、预期观察、失败边界。内容较少时可以合并段落，但不能缺少“为什么”和“写错会怎样”。具体卡片形状见[技术文章正文模板](../templates/article-template.md)第三节。

### 1. 结论必须带机制或后果

结论用一至三句说明它是什么、为什么这样设计、写错会影响什么。只把标题换一种说法，不算结论。

| 不合格 | 合格 |
|--------|------|
| `scope` 用于设置表头范围。 | `scope="col"` 告诉辅助技术这个表头作用于整列；只把文字加粗不会建立这种关系。 |
| `disabled` 用于禁用输入。 | `disabled` 是布尔属性，存在即禁用；写成 `disabled="false"` 仍然是禁用，因为属性仍然存在。 |
| UTF-8 是一种编码。 | UTF-8 规定字符如何写成字节；把 GBK 字节按 UTF-8 解码，就会得到乱码。 |

### 2. 状态表承担同维度查询

表格用于比较取值、行为、默认值和版本状态。属性表还要说明属性属于哪个元素、在什么场景使用；涉及废弃或版本差异时，必须有状态列或统一的版本说明。

原因、时序和取舍写在表格前后的正文里，不塞进单元格。连续多个表格之间要有解释，不能把文章变成表格拼接。

### 3. 最小示例说明入口和上下文

完整示例从读者新建的空目录出发，给齐文件名、保存编码、依赖、入口和预期结果。局部片段要说明它属于哪个文件、依赖哪些前置内容、省略了什么。

示例中的关键属性要有注释，注释写在元素前、代码块上方或独立行；不能把注释塞进开始标签的属性之间，破坏源码结构。

### 4. 预期观察必须可核对

“运行成功”“显示正常”不是观察项。应写成具体的页面结果、面板读数、命令输出、网络状态或校验器报告。观察项最好能与前面的机制一一对应：改哪个属性，哪个读数或结构应该变化。

### 5. 失败边界给出恢复路径

至少说明一种错误写法或失败条件：读者看到什么现象，用什么证据定位，改哪里，如何复测。错误示例不能只贴报错文本，也不能把“浏览器还能显示”当成“写法正确”。

| 五段 | 必须回答 | 缺失信号 |
|------|----------|----------|
| 结论 | 是什么、为什么、写错会怎样 | 只复述标题或只有形容词 |
| 状态表 | 有哪些取值、各自改变什么、是否现行 | 只列名称和描述，没有边界 |
| 最小示例 | 在哪个文件、从哪里进入、省略了什么 | 无法独立运行或依赖仓库示例 |
| 预期观察 | 页面、面板、命令或校验器应给出什么 | 只有“成功”“正常” |
| 失败边界 | 现象、证据、修复、复测 | 只贴报错，或把限制堆到文末 |

## 五、示例与证据

### 1. 空目录闭环

示例的默认起点是读者新建的空目录。正文给出本篇需要的文件、依赖、数据和命令；不引用仓库的 `example`、`examples` 目录，也不引用其他章节的工程或未展示的辅助脚本。

单文件示例直接使用文件名；只有包机制、模块或构建约定需要层级时，才保留最小目录。路径变化时同步修改代码、命令、输出和排错说明。

### 2. 完整示例与局部片段分工

一篇至少有一条与主题直接相关的最小闭环；其余知识点使用局部片段。完整示例负责证明链路可运行，局部片段负责聚焦某个属性或语法，不要求每个知识点都配一套完整工程。

### 3. 观察项选择客观证据

优先选择可重复读取的证据：`document.title`、`document.characterSet`、`getComputedStyle(...).direction`、Network 状态、命令退出结果、校验器报告。主观描述只能作为辅助，不能作为唯一证据。

### 4. 验证记录写清四件事

| 项目 | 记录内容 |
|------|----------|
| 时间与环境 | 日期、操作系统、浏览器或运行时版本 |
| 入口 | 从哪个文件、命令或页面开始 |
| 实际观察 | 看到了什么、读到了什么、与预期是否一致 |
| 未验证边界 | 没有覆盖的浏览器、设备、版本或场景 |

验证记录不是“已测试”三个字。没有实际运行时，应明确写“未运行”“仅静态检查”或“局部核对”，不能把预期结果写成实测结果。

### 5. 无法验证时保留诚实的边界

| 证据状态 | 可以怎样写 | 不能怎样写 |
|----------|------------|------------|
| 实际运行 | 写明环境、入口和观察结果 | 省略环境，暗示所有版本一致 |
| 仅编译或静态检查 | 说明检查命令和通过范围 | 称为“运行验证” |
| 局部核对 | 说明核对了哪一部分 | 称为“完整链路已验证” |
| 未验证或示意 | 明确标注“未验证”“示意” | 编造输出、版本或来源 |

## 六、阅读层次与容器

### 1. 容器是判断的路标

`info`、`tip`、`warning`、`danger` 和 `details` 用来突出不同性质的判断，不用来替代正文。使用前先问：这段内容是需要先知道的范围、可复用的经验、容易犯的错误，还是有风险的操作？

| 容器 | 适合放 | 不适合放 |
|------|--------|----------|
| `info` | 范围、前提、与相邻文章的分工 | 大段定义和完整推导 |
| `tip` | 可复用的判断顺序、经验法则 | 必须执行的硬性要求 |
| `warning` | 常见误区、错误写法的后果 | 普通补充说明 |
| `danger` | 数据丢失、安全风险、不可逆操作 | 一般格式提醒 |
| `details` | 超过 10 行的完整代码、长表格、可选细节 | 核心结论和必须看到的解释 |

### 2. 容器之间保留正文

每个二级主问题下使用一至两个容器通常足够。容器之间要有解释性正文，不能连续堆叠；连续三个容器会让读者分不清哪一个是重点，也会把文章切成碎片。

### 3. 表格与代码各司其职

表格适合同维度对比：取值、行为、默认值、版本状态。因果关系、执行顺序和取舍判断放在正文里。代码注释解释关键属性或步骤，不重复代码字面意思；超过 10 行的代码放入带具体标题的 `::: details`，折叠外保留用途、关键逻辑和结果判断。

## 七、章节批量生成节奏

### 1. 默认一章一批

按章推进，同章统一版本、术语和场景。每篇先通过职责、内容、示例和格式检查，再进入下一篇；不要边批量扩写边假定前面的问题会自行消失。

### 2. 单篇循环

1. 读取蓝图、职责卡、目标全文、相邻文章、sidebar 和工作区状态。
2. 确定唯一问题、读者起点、证据路径和不覆盖范围。
3. 先列主问题与子问题，再写开篇和知识单元；不先套标题模板。
4. 写完示例后实际验证，记录环境、入口和观察。
5. 检查空薄小节、必要子主题缺失、容器节奏、长代码折叠和重复主讲。
6. 运行当前范围的内容检查；涉及配置、导航或扩展语法时执行构建。
7. 通过后再写下一篇。

### 3. 章末横向检查

整章结束时统一核对：术语是否一致，版本是否一致，示例场景是否冲突，知识主讲是否唯一，前置链接是否有效，sidebar 是否有孤立页面。发现重复时保留一个主讲位置，其余改为最小上下文和链接。

### 4. 旧稿治理

旧稿处理先做引用审计，再决定归档或删除。更新 sidebar、蓝图和站内链接后，旧地址和旧锚点直接作废，不建立跳转。删除或移出 `content/` 后必须重新构建，确认没有死链和孤立页面。

| 情况 | 处理 |
|------|------|
| 旧稿已被新结构完全覆盖 | 移出 `content/`，归档到不参与构建的本地目录 |
| 旧稿仍有未被覆盖的主题 | 先保留或拆出该主题，再处理其余部分 |
| 旧稿仍被正文引用 | 先更新引用到新主讲位置，再移除旧稿 |
| 只是局部修改旧稿 | 不借机全篇格式化或批量改名 |

## 八、交付判定与不合格模式

### 1. 四类证据缺一不可

| 证据类别 | 要证明什么 | 典型记录 |
|----------|------------|----------|
| 内容 | 职责覆盖、机制清楚、边界完整 | 主问题与子问题、知识项覆盖 |
| 示例 | 读者能从空目录复现 | 文件、命令、入口、实际输出 |
| 格式 | 标题、容器、表格、代码折叠合规 | `docs:check` 结果 |
| 工程 | 页面能构建、导航和链接有效 | 构建结果、页面检查 |

“构建成功”不能替代内容与示例验收；“示例能跑”也不能替代格式和链接检查。

### 2. 常见不合格模式

| 模式 | 为什么不合格 | 修正方向 |
|------|--------------|----------|
| 术语表加优缺点清单 | 没有机制和使用判断 | 补场景、关系、边界和反例 |
| API 或属性逐条罗列 | 读者不知道如何组合使用 | 按问题组织，补最小示例和观察 |
| 示例引用仓库目录 | 读者无法独立复现 | 改为空目录闭环，给齐文件 |
| 只写“运行成功” | 没有可核对证据 | 补页面、读数、命令或网络结果 |
| 错误示例只贴报错 | 没有定位和恢复 | 补现象、证据、修复、复测 |
| 连续堆叠容器 | 阅读重点反而模糊 | 容器之间恢复解释性正文 |
| 每篇都用同一套标题 | 层级不表达真实从属关系 | 按主问题与子问题重新组织 |
| 用总结套话收尾 | 没有增加判断信息 | 改为失败表、验证记录或边界 |
| 未验证却写实测 | 事实不可信 | 标注未验证或补做验证 |
| 为凑篇幅加同义句 | 信息密度下降 | 删减，回到机制和证据 |

### 3. 交付说明至少包含

- 新增、修改、移动、删除了哪些文件；
- 对应文章 ID、主讲知识和目标深度；
- 实际运行了什么、在哪个环境、看到什么结果；
- 哪些内容没有验证，原因和影响是什么；
- 执行了哪些内容检查、构建或链接检查。

未经用户明确授权，不提交、推送、发布或部署。

## 九、HTML 定稿样本的校准点

### 1. 样本位置

HTML 表格文章是当前范式的定稿样本：`content/frontend/01-html/02-content-elements/06-tables.md`。它以 5 个二级主问题、14 个三级知识单元和 17 个容器，讲清 `scope`、`headers`、`colspan`、`rowspan`、废弃表现属性和完整表格结构，并给出 `stock.html`、观察表、失败表和验证记录。

HTML 第一章的 01～10 篇已统一到这一结构，覆盖概念、语法、文档结构、全局属性、字符引用、编码、资源引用和解析检查。两者共同说明，这套形状不只适用于表格。

### 2. 从样本提炼的五条

1. **先概念后属性**：先说明这个对象解决什么问题，再列属性和取值；不把属性表当成文章开头。
2. **每个属性四问**：它是什么、为什么需要、在哪个元素上怎样写、写错会怎样；四问不齐，属性就没有讲完。
3. **完整示例加局部片段**：完整文件证明链路，局部片段聚焦规则；两者都说明入口和观察。
4. **容器承担判断**：范围用 `info`，经验用 `tip`，误区用 `warning`，长代码用 `details`；容器之间保留正文。
5. **验证记录写边界**：写明环境、日期、实际观察和未验证范围，不把“页面能显示”当成全部验收。

### 3. 不要机械复制

不要复制样本的标题数量、容器数量或代码行数，也不要把所有主题都写成 HTML 元素文章。概念文章可以没有可运行示例，但必须用场景、关系或反例建立判断，并明确标注没有运行示例；操作文章必须有闭环，不能只给片段。

::: warning 范式不是填空模板
本范式规定的是判断顺序和证据要求，不是一套可以机械填写的段落模板。标题必须来自当前主题的真实问题，示例必须来自当前环境可复现的链路；为了对齐样本而增加空洞小节，反而违反范式。
:::

## 十、交付前自检

格式项按[正文模板](../templates/article-template.md)第八节逐项检查；本节只列范式级判断：

- [ ] 文章只回答一个主要问题，标题与 `title`、一级标题一致；
- [ ] 开篇直接进入对象、问题和核心模型，没有课程式开场；
- [ ] 每个二级主问题下按子问题使用三级标题，层级表达真实从属关系；
- [ ] 每个知识单元都有机制或后果，不是同义改写；
- [ ] 属性、参数或 API 表说明了含义、取值、使用方式和版本状态；
- [ ] 至少有一条从空目录出发的完整链路，入口、观察和失败处理齐全；
- [ ] 容器使用有明确目的，容器之间有正文，没有连续堆叠；
- [ ] 超过 10 行的代码已折叠，折叠外保留用途、关键逻辑和结果判断；
- [ ] 验证记录写明环境、日期、实际观察和未验证边界；
- [ ] 旧稿、链接和 sidebar 已按当前范围处理，没有死链或孤立页面。

完成这些检查，才可以把文章标记为“已写并验证”。仅完成正文、仅通过构建或仅生成文件，都不等于交付完成。
