# 正文组织与表达规范

本规范负责“每篇文章怎样讲清楚”：讲解顺序、论述闭环、信息密度、阅读层次和标题设计。Markdown 语法格式见[Markdown 与 VitePress 格式规范](./markdown-format.md)，示例与验证见[示例与验证规范](./code-examples.md)。

## 一、直接进入技术主题

一级标题后直接说明当前知识的定义、语法、API 或问题。不先写课程安排，也不统一声明“所有代码都是局部示例”。必要前置条件放在实际使用它的示例或机制附近。

| 应避免的写法 | 对应处理 |
|--------------|----------|
| “上一篇已经学习……本篇将要介绍……” | 直接说明当前概念或问题，导航交给目录和页面组件 |
| 固定增加“学习目标、学习方法、实践任务、验收标准” | 按具体技术主题组织；必要检查跟随对应知识 |
| “核心知识、理解与应用、其他内容”作为空泛标题 | 使用对象、机制、API 或问题名称 |
| 用表格、流程图、代码块重复展示本文目录 | 删除文章目录复述；真实执行流程和数据流可以保留 |
| 开篇声明“依赖均已导入、代码不代表完整工程” | 在每个局部片段附近明确缺失上下文 |
| 正文用“下一篇、下一章”衔接 | 使用有意义的知识引用，或由 sidebar 和文章切换组件表达顺序 |

模块首页、知识目录页和专用布局页可以按用途展示章节和阅读入口；该豁免不能扩展成所有普通文章都展示课程路线。

## 二、讲解顺序与段落节奏

动笔前先在工作记录中设计读者判断路径，不把这份规划直接写进正文。路径至少回答：读者带着什么问题进入、需要先建立哪个核心模型、沿哪些主问题推进、用什么证据确认理解，以及最终怎样判断适用边界。

| 规划对象 | 必须明确的内容 | 失败信号 |
|----------|----------------|----------|
| 入口问题 | 一个真实场景、错误判断或操作结果 | 开篇只有定义清单或课程说明 |
| 核心模型 | 对象关系、状态、时序或决策依据 | 后文术语很多，却没有共同解释框架 |
| 主问题 | 二级标题共同回答唯一学习问题 | 同级标题抽象层次混乱或只是知识点枚举 |
| 子问题 | 需要专属解释、证据或失败边界的从属问题 | 全篇只有平铺二级标题，或三级标题只是编号列表 |
| 证据路径 | 示例、输出、场景或反例如何证明结论 | 代码和表格出现后没有结果解释 |
| 收束方式 | 验收、判断案例、反例或恢复复测 | 结尾机械复述目录或突然结束 |

不同主文章类型按本文“内容闭环”中的类型判断路径推进。生成正文时可以调整标题名称和数量，但不能丢失主类型要求的证据与边界。

文章必须按读者的理解依赖组织内容。必要概念、符号和使用条件应在首次使用前或使用处解释；有前后依赖的操作按实际执行顺序排列，不能让读者先复制代码，再到末尾发现缺失的环境条件。

| 内容关系 | 默认组织方式 | 应避免的问题 |
|----------|--------------|--------------|
| 概念与用法 | 先建立最小定义，再说明规则和用法 | 先堆术语或API，读到后半篇才知道对象是什么 |
| 正常与异常 | 通常先给正常行为，再紧跟容易误用的边界与失败 | 成功代码与关键限制相隔多节 |
| 现象与诊断 | 先说明现象和条件，再按证据推进定位与恢复 | 先列一串原因，却没有判断依据 |
| 示例与结论 | 用途在示例前，观察结果与解释紧跟示例 | 只有代码、日志或“运行成功”，没有结论 |

操作、测试和排障内容需要先规划相邻的操作单元。每个单元包含当前目标与条件、命令或动作、预期结果、结果解释和就近失败处理；不要求把这些名称写成标题，但不允许把命令放在前半篇、输出放在后半篇，再把失败说明统一堆到文章末尾。

每个段落只推进一个中心意思。解释性段落通常可用2～5个相互衔接的句子完成；这只是写作建议，不是字数或句数门禁。出现过长段落时，优先检查是否混入多个主题，再按语义分段，不机械地每句话换行。

独立知识要点应达到读者能够理解和判断的深度，不能连续用“一句定义或结论”代替讲解。需要解释的要点应补充必要的原因、机制、用法、边界或证据；只需简短说明的并列事实可以合并为正文、列表或表格，不为凑段落扩写常识。

## 三、内容闭环与阅读路径

文章不强制使用固定标题，但整体内容必须形成以下闭环：

```text
当前问题或概念
→ 核心结论
→ 原因、机制或使用规则
→ 示例或证据
→ 结果解释
→ 边界、错误或判断方法
```

不同要素可以使用正文、表格、代码、图、日志或 VitePress 容器表达。标题只用于独立主题，不得把闭环中的每个步骤机械创建为一个小节。

### 1. 公共阅读骨架

闭环还必须形成一条可以连续跟随的读者判断路径。公共骨架统一信息职责，不要求文章使用相同标题：

```text
问题或场景
→ 核心模型
→ 分层解释
→ 示例或操作证据
→ 失败分支
→ 判断边界
```

一级标题后的二至四个短段落直接建立问题、核心判断和必要边界。复杂主题先给出足以承载后续内容的关系、状态、时序或决策模型，再展开具体规则；不能先连续罗列术语，让读者到文章后半部分才理解对象之间的关系。

文章结尾根据类型使用判断案例、反例、恢复复测或验收结果收束，说明当前证据证明了什么、没有证明什么。不得机械复述目录或使用后续章节预告代替结论。

### 2. 类型对应的判断路径

文章主类型决定正文的默认推进方式：

| 文章类型 | 默认判断路径 |
|----------|--------------|
| 基础概念 | 真实问题 → 核心定义 → 对象关系 → 关键差异 → 场景判断 → 边界与反例 |
| 语法与 API | 使用目标 → 语法或签名 → 参数与规则 → 调用结果 → 错误用法 → 版本边界 |
| 运行机制 | 行为现象 → 参与对象 → 正常过程 → 状态变化 → 失败传播 → 观察方式 |
| 接入教程 | 最终结果 → 前置检查 → 分阶段操作与验证 → 失败处理 → 恢复或最终验收 |
| 设计与实践 | 具体场景 → 约束 → 候选方案 → 取舍 → 实施 → 验证与回退 |
| 测试与排障 | 故障现象 → 现场保护 → 分层证据 → 分支收敛 → 修复或回退 → 恢复复测 |
| 速查与参考 | 适用版本 → 查询维度 → 参数或命令 → 最小用法 → 限制与完整资料入口 |

默认路径可以按职责删减或合并，但不能改变主类型应交付的证据。例如概念文章不需要伪造操作步骤，教程文章不能只用关系图代替可执行闭环。

### 3. 操作单元的证据相邻性

操作、测试和排障内容按“目标与条件 → 命令或动作 → 预期结果 → 结果解释 → 失败处理”组织为相邻单元。不同要素可以使用段落、步骤、代码和容器表达，不把这些名称机械设置为标题。

命令与输出之间只插入理解执行所必需的说明。结果解释紧跟输出，明确观察项证明的状态；最可能发生的失败及处理放在当前步骤附近，不能把全部限制集中到文章末尾，迫使读者执行后才发现前置条件不成立。

### 4. 注意力层级

读者只浏览标题、各节首段和提示容器时，应能还原文章的主要判断路径。页面元素按职责分工：

- 正文承担定义、因果、机制和结论推导；
- 有序列表承担有前后依赖的操作与诊断；
- 表格只承担稳定的同维度比较、参数和状态查询；
- 提示容器只突出一个关键条件、建议、误区或风险；
- `details` 只收起完整长代码、补充证据和次要细节；
- 标题只承担确实需要独立解释和定位的主问题与子问题。

出现连续大型表格、同一节反复切换表达形式、命令与解释相隔多个小节，或者纯文字连续超过一个主要主题时，必须重新设计信息关系。不能用更多表格、容器、加粗或标题制造虚假的内容层次。

### 5. 论述要素

小节先给结论或定义，再说明必要的机制、原因、使用方式、适用边界、示例或判断方法。不同要素自然组合，不需要每个要素建立一个标题。

| 内容要素 | 写作要求 |
|----------|----------|
| 结论 | 准确回答当前问题，限定成立条件 |
| 原因与机制 | 解释行为为何产生、由哪些对象或状态决定 |
| 使用方式 | 给出正确操作和必要参数，说明选择依据 |
| 证据 | 直接支撑当前结论，避免无关的大工程或泛化案例 |
| 结果解释 | 说明输出、状态、日志或指标证明了什么 |
| 边界与反例 | 说明何时失效、不适用或出现错误，以及如何判断 |

概念性文章可以通过场景和关系形成闭环；接入与排障文章需要执行或诊断链路。不能为了“完整”重复结论、堆同义句或机械增加篇幅。

## 四、空小节与骨架化小节的处理

标题表示需要独立论述的主题，不是带编号的列表项。所有新增或全文重写文章必须检查每个二级、三级和四级标题；只有二级标题的文章同样需要完整性审查。

| 发现情况 | 必须采取的动作 |
|----------|----------------|
| 标题下没有正文 | 补充实质内容、合并或删除 |
| 只有一个普通正文句，且无有效结构化内容 | 判断是否需要独立论述；需要则展开机制、边界或证据，否则合并 |
| 连续三个及以上小节只有定义或结论 | 重新组织该部分，合并并列事实，不逐项灌水扩写 |
| 引导语后有表格、步骤、代码或容器 | 检查结构化内容是否提供有效信息，引导语是否说明用途 |
| 多段长文字反复表达同一观点 | 去除重复，补足缺失的机制、判断或证据 |

完整性扫描按“列出候选 → 人工语义判断 → 扩展、合并或删除 → 复查”的顺序执行。脚本只能发现候选，不能用字数阈值自动判定合格，更不能自动填充无意义内容。

## 五、信息密度与空话判定

正文中的每个句子都必须让读者多掌握一条可以使用或验证的信息：规则、机制、成立条件、取值、反例、观察方法或判断依据。句子通顺、篇幅很长、要点很多，都不代表文章有内容；删掉某句话后读者能做出的判断没有减少，这句话就是空话。

### 1. 空话的常见形态

下表的原句取自 HTML 旧稿，用于识别同类写法。它们的共同问题是只给结论或评价，不给读者判断依据。

| 形态 | 识别特征 | 原句示例 | 处理方式 |
|------|----------|----------|----------|
| 关键词式断言清单 | 连续多条“**关键词**：一句断言”，每条既无条件也无证据 | “**非编程语言**：是一种标记语言，不是编程语言” | 删除清单，只保留后文会用到的判断，并用示例说明 |
| 收益口号 | 只写“更好的 SEO”“提高可维护性”“跨平台”，不说明产生机制和成立条件 | “**改善SEO**：搜索引擎可以更好地理解页面内容，提高搜索排名” | 改成可观察的机制和结果；无法证明的收益直接删除 |
| 定义复述 | 用同义词重复标题，或用术语解释术语 | “**head头部**：包含元数据信息” | 说明它包含哪些内容、浏览器怎样使用、写错有什么后果 |
| 无关背景 | 版本年表、发展史、发明者，读者完成当前任务不需要 | “**HTML 1.0**：1993年，第一个HTML规范” | 删除；只保留影响当前写法的历史事实 |
| 无依据评价 | “非常重要”“功能强大”“最佳实践”，没有比较对象和依据 | “语义化是Web开发中的重要概念” | 删除形容词，补充比较条件或证据 |
| 收尾套话 | “在实际开发中，我们应该……”“通过本文的学习，我们了解了……” | “通过不断学习和实践，我们可以提高自己的语义化HTML编写能力” | 改用判断案例、反例或验收结果收束 |
| 拼接摘要 | `excerpt` 由正文列表首句拼接而成 | “HyperText Markup Language：超文本标记语言 Web页面的结构基础：……” | 重写为一句话，说明文章解决的问题和核心内容 |

### 2. 自检与改写

写完每个小节后按以下顺序检查，并直接修改正文：

1. **删除测试**：遮住一句话，判断读者是否失去了一条可执行或可验证的信息。没有失去，就删除这句话。
2. **追问依据**：对保留的结论，追问“为什么成立”“什么条件下不成立”“读者怎样亲眼看到”。正文至少回答其中一个，涉及浏览器、工具或运行时行为的结论必须在附近给出示例、输出或规范来源。
3. **替换抽象收益**：把“更好的 X”改写为“在什么条件下，哪个对象出现什么可观察变化”。
4. **复查篇幅**：删除空话后文章变短是正常结果，不为恢复篇幅而补同义句。

改写的标准是读者能够据此做出判断，而不是换一种说法重复结论：

| 空话 | 改写后的信息 |
|------|--------------|
| “**DOCTYPE声明**：定义文档类型” | 缺少 `<!DOCTYPE html>` 时，Chromium 的 `document.compatMode` 从 `CSS1Compat` 变为 `BackCompat`，页面进入怪异模式；表格单元格不再继承 `body` 上设置的字号 |
| “**改善SEO**：搜索引擎可以更好地理解页面内容” | `<button>` 在无障碍树中表现为 `button "提交报名"`，可以用 Tab 聚焦并用 Enter 或空格触发；外观相同的 `<div>` 只是一段文本，键盘无法到达 |
| “**跨平台**：在任何支持HTML的浏览器中都能运行” | 浏览器按 HTML 标准的解析规则修复错误标记，所以页面能显示不代表源码正确；缺少 `</strong>` 会让后续段落也变成粗体，需要用检查器确认 |

### 3. 列表的使用条件

列表适合承载每一项都足够具体的并列事实，例如带取值、条件或可执行命令的参数说明。连续三条以上“**关键词**：短句”的列表，若各项只是名称加一句评价，必须改写为正文、对照表或示例。

`pnpm docs:check` 会把这类列表报告为 `filler-list` 警告。警告只表示候选位置：每一项都给出具体取值、条件或行为的参考列表可以保留；只有断言没有依据的列表必须改写，不能通过把句子加长到阈值以上规避检查。

## 六、表达形式与阅读负担

正文、表格、列表和提示容器应各自承担适合的内容。可读性来自清晰的信息关系，不以表格数量、加粗数量或换行密度判断。

| 形式 | 适用内容 | 约束 |
|------|----------|------|
| 连贯正文 | 定义、因果、机制、推导和取舍 | 解释前后关系，不拆成彼此孤立的短句 |
| 表格 | 参数、同维度比较、输入输出和错误映射 | 单元格保持可扫描，复杂原因移到对应正文，不把长文章塞进表格 |
| 有序列表 | 安装、调用、诊断和恢复步骤 | 每步说明动作，必要时给出条件与检查结果，不省略影响后续操作的步骤 |
| 无序列表 | 无先后依赖的并列事实或检查项 | 避免用一句话知识清单替代核心讲解；复杂项目可用多句完整说明 |
| 提示容器 | 需要特别注意的条件、限制或判断 | 紧邻受影响内容，不连续堆叠容器代替正文 |
| 加粗与行内代码 | 关键结论、限制、API、参数和文件名 | 不整段加粗；代码标记只用于有明确技术含义的文本 |

术语和缩写首次出现时给出足够理解当前句的解释，避免连续引入未定义名词。数值写明单位、范围和必要默认值；“它、该对象、上述配置”等指代必须能在附近唯一确定。需要查阅其他文章时链接到对应主讲位置，当前文章仍保留理解本节所需的最小上下文。

概念、示例、注意事项和总结之间应有清晰的过渡关系。段落转换体现因果、条件或步骤关系，不靠连续标题和空行制造结构。

## 七、文字容器与阅读层次

文字容器是正文的信息层次之一，必须在写作和验收时主动选择。只折叠代码、增加标题或拆短段落，不能证明文章已经具备阅读重点。读者快速浏览时，应能辨认适用条件、关键判断、正确做法和容易出错的边界；随后通过相邻正文理解原因与机制。

| 信息类型 | 统一写法 | 应包含的信息 | 放置位置 |
|----------|----------|--------------|----------|
| 环境与版本前提、场景条件 | `::: info 具体条件` | 哪个环境或假设成立、影响哪项用法 | 相关示例或机制使用前 |
| 可复用结论、操作建议 | `::: tip 具体判断` | 推荐做法、成立条件和必要原因 | 规则讲解或结果之后，形成可检索的判断 |
| 常见误解、兼容限制、失败边界 | `::: warning 具体误区` | 容易误判什么、为何失效、正确处理 | 紧邻受影响用法；必要限制放在操作前 |
| 数据损坏、安全或不可逆操作 | `::: danger 具体后果` | 触发条件、实际后果、预防或恢复要求 | 危险操作之前 |
| 长代码、完整输出、补充推导 | `::: details 对象与用途` | 完整证据或可选深入内容 | 保留核心解释后，再折叠细节 |
| 原始问题或外部原话 | 普通块引用 `>` | 明确问题身份或真实出处 | 分析所引用内容的附近 |

有适用信息时必须使用相应文字容器，不能让整篇长期只有普通段落和代码块。具体数量由内容决定；没有数据或安全风险时不要硬加 `danger`，也不要为了让每节看起来一致而机械添加同一种提示。项目示例页同时演示 GitHub Alert；普通技术文章按 AGENTS.md 统一使用上述原生容器，同一篇不混用两套提示语法。

一个容器承载一个明确判断及必要解释，可以组合两段文字、短列表或小表格。标题不能只写“提示”“注意”或“核心知识”；正文不能只保留一句口号，也不能把整节包起来后省略正常论述。必要前提、警告和核心结论保持展开，不能和完整实现一起藏进 `details`。

例如，金额测试的独立期望属于可复用判断，适合在断言讲解之后强调：

::: tip 期望值应由业务规则独立确定
订单总额的期望值先按输入与业务规则确定，再与被测对象返回值比较。不要在断言里完整复制被测计算过程，否则实现与测试可能同时保留同一种错误。
:::

同一个示例中的发现规则属于失败边界，放在测试执行说明附近更容易被看到：

::: warning 构建成功仍可能没有运行任何测试
测试类命名、目录或筛选条件错误会使测试集合为空。运行后同时检查退出码、测试数量和报告；只有明确要求无测试的模块，才可以接受零测试构建。
:::

这两个容器各自承担判断与处理，原理、完整用法和证据仍由相邻正文展开。不要在多个容器中反复复述同一结论，也不以分割线、表情、徽章或荧光标记代替信息组织。

交付前必须按二级标题逐节检查阅读层次：定位连续长段落、成串的短句清单，以及被埋住的前提和风险；重新组织为连贯解释、语义容器、步骤或对照。查看实际渲染后，确认关闭长代码仍能顺着正文读懂问题、机制和结果。

## 八、根据知识关系建立标题层级

标题层级表达主问题与子问题的关系。写作前先从职责卡确定本文的主要问题，再判断内部是否包含需要分别解释的规则、机制、操作或失败路径。该判断属于写作过程，不在普通文章开头插入目录树或规划表。

| 内容关系 | 组织方式 | 成立条件 |
|----------|----------|----------|
| 本文内部的主要问题 | 二级标题 | 各部分共同回答文章唯一问题，同级标题处于相近的抽象层次 |
| 主问题内的独立子问题 | 三级标题 | 能说明与父主题的关系，并有专属解释、示例、状态推导或判断依据 |
| 子问题内仍需单独定位的机制或分支 | 四级标题 | 确有独立查阅价值，合在原小节会混淆条件或执行过程；不因篇幅长自动增加 |
| 一个规则的简短条件、参数或提醒 | 正文、表格、列表或语义容器 | 不需要独立论述，不把一句话提升为标题 |
| 连贯的短流程或范围很窄的主题 | 保留浅层结构 | 当前标题已经准确区分问题，段落和证据足以支撑声明深度 |

增加小节前必须能够回答：它独立解决什么问题，为什么属于这个父主题，有哪些专属内容，以及拆开后是否方便理解或定位。仅有新标题而没有对应论述，不得视为有效拆分；同义改写、重复示例和从相邻文章搬来的内容也不能充当支撑。

必要的重组可以合并平级标题、把规则归入父主题、拆开混在一起的机制，或者只补充解释而保留标题。父节先给出必要的共同模型，子节再说明各自差异；不要在父节和子节重复同一段定义。无需为每个父节补齐相同数量的子节，也不为“定义、原因、示例、总结”统一设置四个标题。

::: warning 层级数量不作为质量指标
不规定每篇必须有三级或四级标题，不设置标题数量、字数或层级比例配额，也不因为某篇只有二级标题就判定不合格。已有三级标题的文章仍可能把不同机制混在一起；浅层结构是否适当，必须结合职责、实际内容和读者要解决的问题判断。
:::

## 九、同时复审层级缺失与内容深度

结构复审必须同时检查“已有小节是否空薄”和“必要子主题是否没有建立”。脚本没有发现空小节，不代表文章已完整；相关术语出现在正文、表格或容器中，也不等于已经达到职责卡要求的使用、解释或诊断深度。

| 复审信号 | 必须核对的问题 | 可采用的修订 |
|----------|----------------|--------------|
| 全篇仅有二级标题 | 是否只是一个窄问题，还是把模型、具体机制和操作细节全部平铺 | 保留并说明理由，或按真实从属关系重组 |
| 一个标题同时列出多个概念 | 它们是否共同组成一个必要比较，还是各有独立机制和边界 | 保留对照，或分别展开；不按“与”“和”的字面机械拆分 |
| 核心机制只有一段或一行表格 | 读者能否解释过程、预测行为并判断错误 | 补充缺失的状态、因果、适用条件或最小证据；是否增加标题另行判断 |
| 大段完整代码承担全部说明 | 关闭折叠后是否还能理解关键过程与结果 | 在相关知识处补充关键机制解释，保留完整实现和入口 |
| 子节之间不断互相引用 | 是否拆散了本应连续理解的一条推导或操作 | 合并或调整顺序，减少不必要层级 |
| 文章出现多个宽泛父标题 | 是否只是用“基础、进阶、实践”等词把旧标题整体降级 | 回到具体技术问题命名和分组，删除没有内容职责的父层 |

新建与全文重写在动笔前完成语义大纲判断，写完后将职责卡中的必讲内容逐项对应到正文解释和证据。批量治理对每篇记录“保留结构、重组层级、补足解释”中实际采用的处理及理由，可以组合；记录放在治理报告中，不把审阅说明写入技术正文。

调整标题时检查实际生成的锚点，同步修正全部受影响站内引用。旧标题锚点直接作废，不添加隐藏标签保留旧锚点；页面目录应反映新的真实层级。工程检查只能证明格式与链接有效，不能替代上述语义判断。

## 十、标题命名

章节名称、文章标题和二至四级标题必须**准确概括、表达精简**。先确定技术对象和实际范围，再删除不影响识别的修饰与解释；同一含义能够清楚表达时，选择更短的名称。目录与 sidebar 中的展示名称遵循同一原则。

| 检查项 | 命名要求 |
|--------|----------|
| 技术对象 | 读者能直接识别正在讲解的概念、API、机制或问题，标题与实际内容范围一致 |
| 表达形式 | 优先使用“技术对象 + 必要限定”的短语；问题型标题可以保留简短问句，不把职责卡的完整问题机械照抄成标题 |
| 解释位置 | 背景、原因、步骤细节与完整结论放在节首正文，不把标题写成长句式摘要或逐项罗列全部知识点 |
| 必要限定 | 保留影响含义的对象、场景、版本和差异；标准术语与 API 名称保持准确，不为缩短而截断或生造缩写 |
| 上下文 | 小节可以省略父标题已经明确且不会产生歧义的范围；文章标题仍应能在搜索结果中独立识别主题 |
| 冗余措辞 | 删除无信息量的“关于……的介绍”“相关知识”“全面详解”“从入门到精通”等套话，不用“核心”“其他”等空泛词代替技术主题 |

以下示例只展示命名调整；实际修改前必须核对正文范围，不能仅凭标题猜测内容。

| 用途 | 冗长表达 | 精简表达 |
|------|----------|----------|
| 章节名称 | Java 语言中的面向对象编程相关知识 | 面向对象 |
| 文章标题 | Java 变量的声明、常量的定义以及变量的作用域规则 | Java 变量、常量与作用域 |
| 小节标题 | invokeExact 的返回上下文也是调用点类型 | invokeExact 调用点返回类型 |

不设置统一字数上限，也不要求标题等长。较长标题应检查能否去掉赘词；必要的技术限定可以保留。多个并列主题若共同构成比较或完整机制，可以合并命名；若实际承载独立问题，再按职责调整范围，不为缩短标题增加层级或拆分文章。

标题缩短后必须复核含义、术语与正文职责，按“同时复审层级缺失与内容深度”一节更新受影响锚点引用；文章标题仍需与 Frontmatter 的 `title` 一致。
