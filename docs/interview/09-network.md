# 网络面试题

## 1. 地址栏输入URL回车之后发生了什么？
::: tip 详细解释
1. URL 解析 ：检查和纠错、转换，
    - 检查URL地址是否完整，不完整需要补全，
    - 检查URL是否存在，是否可以访问，是否存在重定向。
    - 转换URL，将其转换为标准格式 `Ascii码`。
2. DNS 查询 ：DNS 服务器解析域名，将域名解析为 IP 地址。

3. 建立 TCP 连接 ：TCP 三次握手建立 TCP 连接。
    - 第一次握手：客户端发送 SYN 报文，服务器接收到 SYN 报文，并发送 SYN+ACK 报文。
    - 第二次握手：服务器发送 ACK 报文，客户端接收到 ACK 报文，并发送 ACK 报文。
    - 第三次握手：客户端发送 ACK 报文，服务器接收到 ACK 报文，连接建立成功。
    - SSL/TLS 握手：如果是 HTTPS 协议，还需要进行 SSL/TLS 握手。
4. 准备请求：准备请求头：Cookie + ... 
5. 发送 HTTP 请求 ： 客户端向服务器发送 HTTP 请求，请求方式为 GET。
6. 服务器处理请求 ：服务器接收到 HTTP 请求，并从数据库或其他存储介质中获取请求资源。
7. 服务器返回响应 ：服务器将请求资源返回给客户端，并发送 HTTP 响应。
8. 客户端接收响应头 ：客户端接收到 HTTP 响应，并显示响应内容。
9. 客户端处理响应头 ：客户端处理 HTTP 响应头，如设置 Cookie 、处理content-type、缓存、状态码、connection：keep-alive保活等。
10. 客户端收响应体 ：客户端如果收到HTML，需要一边接收一边渲染，如果收到其他类型文件，则直接显示。
11. 渲染：
    - 1. 解析HTMl文档（预处理线程，资源加载、资源描述符：async / defer/ prefetch/ preload ）：render 树+ CSSOM 树 生成
    - 2. 样式计算
    - 3. 布局：生成渲染树，并计算布局（回流）
    - 4. layer分层：将渲染树分层，并生成图层树
    - 5. `paint`绘制：将图层树绘制到屏幕上 ，主线程结束工作 
    - 6. 合成：将图层合成到页面上，合成线程开始工作。
    - 7. tiles分块：将合成结果分成小块，页面优先显示一部分。
    - 8. 栅格化
    - 9. draw 绘制: 将渲染结果绘制到屏幕上。
12. 根据情况决定是否断开连接：客户端接收完响应体后，再决定是否断开连接。
13. 关闭 TCP 连接 ：TCP 四次挥手关闭 TCP 连接。
    - 第一次挥手：客户端发送 FIN 报文，服务器接收到 FIN 报文，并发送 ACK 报文。
    - 第二次挥手：服务器发送 FIN 报文，客户端接收到 FIN 报文，并发送 ACK 报文。
    - 第三次挥手：客户端发送 ACK 报文，服务器接收到 ACK 报文，连接关闭。
    - 第四次挥手：服务器发送 ACK 报文，客户端接收到 ACK 报文，连接关闭。
:::


## 2. 什么是跨域
::: tip 详细解释
- 跨域是一种**浏览器的安全策略**：浏览器出于安全考虑，对同源请求放行，对异源请求限制，这种限制规则称为同源策略。
- 同源：两个页面具有相同协议、域名、端口号。
- 同源请求：**页面源**向 **同源目标源** 发送请求获取资源的行为。
- 浏览器如何限制：
    - 对`标签`发出的跨域请求轻微限制。
    - 对`AJAX`发出的跨域请求严格限制。浏览器会正常发送请求，服务器正常响应，浏览器会对跨域请求的响应进行校验。如果服务器响应头中没有`Access-Control-Allow-Origin`字段，浏览器会拦截响应。
- 跨域解决方案：
    - CORS(官方推荐)：跨源资源共享机制，是 W3C 标准，通过`服务器`设置响应头，允许跨域请求。
    - JSONP（老版本）：利用 `<script>` 标签的 `src` 属性，服务器响应数据时会运行一个函数，这个函数与前端的一个函数的名字相同，服务器响应这个函数时，浏览器会执行这个函数，并将数据作为参数传入。（缺陷：只支持 GET 请求）
    - `Proxy`代理服务器: 浏览器向代理服务器进行数据请求，由代理服务器向目标服务器请求数据，然后返回给浏览器。

- CORS 将请求分为两类：
    - **简单请求：**
        1. 请求方法是 GET、HEAD、POST；
        2. 请求头没有特别的限制；
        3. `Content-Type` 仅限于 `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`。
    - **预检请求:** 非简单请求。

    - **通过简单请求**：浏览器会自动带上`Origin`:表示当前页面源。服务器通过`Access-Control-Allow-Origin`响应头来允许页面源 通过跨域请求。
    - **通过预检请求：**浏览器会先发送预检请求，预检请求的请求方法为`OPTIONS`，请求头中包含`Origin`（当前页面源）和`Access-Control-Request-Method`（请求方法）和`Access-Control-Request-Headers`（这次请求改动的哪些请求头），服务器通过返回的`Access-Control-Allow-Origin`、`Access-Control-Allow-Methods`、`Access-Control-Allow-Headers`、`Access-Control-Max-Age`（**预检请求的有效期**）响应头来允许页面源 通过跨域请求，并确定是否可以发送真实请求。
:::


## 3. GET和POST的区别

>[!TIP] 详细解释
>1.  **语义**（主要区别）：GET 通常用于获取或查询资源，而 POST 通常用于创建或修改资源。
>2. **幂等**：GET 请求是幂等的，即多次重复执行不会改变资源的状态，而 POST 请求是不幂等的，即每次执行可能会产生不同的结果或影响资源的状态。
>3. **格式**：GET 请求的参数通常放在 URL 中，形成查询字符串（querystring），而 POST 请求的参数通常放在请求体（body）中，可以有多种编码格式，如 application/x-www-form-urlencoded、multipart/form-data、application/json 等。GET 请求的 URL 长度受到浏览器和服务器的限制，而 POST 请求的 body 大小则没有明确的限制。不过，实际上 GET 请求也可以用 body 传输数据，只是并不推荐这样做，因为这样可能会导致一些兼容性或者语义上的问题。
>4. **缓存**：由于 GET 请求是幂等的，它可以被浏览器或其他中间节点（如代理、网关）缓存起来，以提高性能和效率。而 POST 请求则不适合被缓存，因为它可能有副作用，每次执行可能需要实时的响应。
>5. **安全性**：GET 请求和 POST 请求如果使用 HTTP 协议的话，那都不安全，因为 HTTP 协议本身是明文传输的，必须使用 HTTPS 协议来加密传输数据。另外，GET 请求相比 POST 请求更容易泄露敏感数据，因为 GET 请求的参数通常放在 URL 中。

:::details 粗略介绍
>[!important] 区别
>- **协议层面**
>   - 只有语义的差别
>   - HTTP报文由请求行、请求头、空行和请求体组成。
>-  **应用层面**
>   - 约定俗成的规范：往往会把一些请求（如`GET`）的请求体置空。（不是没有）

>[!tip] GET
>- 将请求的数据附加在 URL 后面，以查询字符串的形式出现，一般用于查询。
>- 数据量有限制，通常不超过 2KB。
>- 适合请求无状态的操作，如页面跳转、检索数据等

>[!tip] POST
>- 用于向服务器发送数据。它将数据存储在请求体中，不会出现在 URL 中。
>- 数据量没有限制，适合请求有状态的操作，如登录、注册等。

:::

## 4. HTTP状态码
>[!tip] 详细解释
> - 1xx：信息提示类，表示接收到请求，需要进一步处理。
>   - 100 Continue：客户端应当继续发送请求。
>   - 101 Switching Protocol：服务器切换协议。
>   - 102 Processing：由 WebDAV扩展的状态码，表示请求尚未完成。
> - 2xx：成功类，表示请求成功收到，理解并处理。
>   - 200 OK：请求成功,响应中包含请求的数据（网页、API 返回 JSON）。
>   - 201 Created：请求成功，且服务器创建了新的资源（POST 新建用户后返回）。
>   - 202 Accepted：服务器已接受请求，但未处理完成（异步任务）。
>   - 204 No Content：请求成功，但响应无内容（DELETE 删除资源后返回）。
>   - 206 Partial Content：服务器返回部分数据（用于分块下载或断点续传）。
> - 3xx：重定向类，表示需要进行附加操作以完成请求。
>   - 301 Moved Permanently：永久重定向，请求的资源已被分配新的
>   - 302 Found：临时重定向，请求的资源已被分配新的.（A/B 测试）
>   - 303 See Other：强制要求重定向后使用 GET 方法（常用于 POST 后跳转）。
>   - 304 Not Modified：客户端发送附带条件的请求，服务器端允许请求访问资源，但未满足条件。
>   - 307 Temporary Redirect：临时重定向，且保持原始 HTTP 方法。
>   - 308 Permanent Redirect：永久重定向，且保持原始 HTTP 方法。
> - 4xx：客户端错误类，表示请求包含语法错误或无法完成请求。
>   - 400 Bad Request：请求语法错误。 
>   - 401 Unauthorized：请求要求身份验证。 
>   - 403 Forbidden：服务器拒绝请求。 
>   - 404 Not Found：服务器无法找到请求的资源。 
>   - 405 Method Not Allowed：请求方法不被允许。 
>   - 408 Request Timeout：请求超时。 
>   - 429 Too Many Requests：请求过多。 
> - 5xx：服务器错误类，表示服务器在处理请求的过程中发生了错误。
>   - 500 Internal Server Error：服务器内部错误。
>   - 502 Bad Gateway：网关错误。
>   - 503 Service Unavailable：服务不可用。
>   - 504 Gateway Timeout：网关超时。
>   - 511 Network Authentication Required：网络认证要求。


## 5. 强缓存和协商缓存

>[!tip] 强缓存
> 1. 强缓存是指浏览器在请求资源时，先查看浏览器缓存中是否有缓存的副本，
> 2. 如果有，则直接使用缓存副本，不再向服务器发送请求。
> - 强缓存的优点：
>   - 缓存命中率高，减少请求数，加快页面响应速度。
>
> - 强缓存的缺点：
>   - 缓存过期时间无法设置，缓存时间一旦过期，则需要重新向服务器请求资源。
>   - 缓存无法更新，当缓存数据被更新时，浏览器并不会请求新的资源，而是继续使用旧的缓存。

>[!tip] 协商缓存
> 1. 浏览器在请求资源时，先向服务器发送请求，服务器根据请求头判断是否命中缓存，
> 2. 如果命中，则返回 304 状态码，浏览器从缓存中获取资源，否则返回 200 状态码，并返回新的资源。
> - 优点：
>   - 缓存有效期可以设置，可以根据情况指定缓存过期时间。
>   - 缓存可以更新，当缓存数据被更新时，浏览器会请求新的资源，并更新缓存。
> 
> - 缺点：
>   - 缓存命中率低，增加了请求数，增加了服务器压力。
>   - 缓存无法命中，如果资源未被缓存，则需要向服务器请求资源。

## 6. Socket 长连接和短连接

>[!tip] 长连接
> 1. 长连接：在一个 TCP 连接上可以发送多个 HTTP 请求，多个请求复用同一个 TCP 连接。
> 2. 优点：
>   - 减少建立 TCP 连接的时间，减少了延迟。
>   - 同一个 TCP 连接可以发送多个请求，减少了网络流量。
> 
> - 缺点：
>   - 服务器资源消耗较多，因为每个 TCP 连接都需要维护。
>   - 服务器需要维护大量的 TCP 连接，消耗系统资源。

>[!tip] 短连接
> 1. 短连接：在一个 TCP 连接上只发送一个 HTTP 请求，服务器处理完请求后，立即断开 TCP 连接。
> 2. 优点：
>   - 减少了建立 TCP 连接的时间，减少了延迟。
>   - 减少了服务器资源消耗，因为每个 TCP 连接只处理一个请求。
> 
> - 缺点：
>   - 同一个 TCP 连接上只能发送一个请求，不能发送多个请求。
>   - 服务器需要维护大量的 TCP 连接，消耗系统资源。

## 7. 轮询、长轮询、SSE、WebSocket
### 7.1、轮询
>[!tip] 轮询
> 1. 指客户端不使用长连接，每隔一段时间就向服务器发送请求，询问是否有新数据。
> 2. 优点：
>   - 实现简单：实现起来比较简单。
>   - 兼容性好： 所有浏览器和服务器都支持基本的 HTTP 请求。
> 
> - 缺点：
>   - 无论服务器是否有新数据，都会立即响应（可能包含新数据，也可能为空）。
>   - 网络带宽： 大量请求（尤其是空响应）浪费带宽。
>   - 高延迟：数据更新只能在轮询间隔之后被客户端感知。间隔短则延迟低但开销大，间隔长则延迟高。
>   - 资源浪费巨大: 服务器端需要不断的向客户端推送数据，会消耗服务器资源。
>   - 服务器负载： 即使没有数据，服务器也要处理大量请求，消耗 CPU、内存和连接资源。
>   - 实时性差：客户端需要等待服务器返回数据，延迟较大。

### 7.2、长轮询
>[!tip] 7.2、长轮询
> 1. 客户端发起一个 HTTP 请求到服务器。服务器不会立即响应，而是保持连接打开直到：
>   - 有新数据时才向客户端发送响应。
>   - 超时时间到达时，服务器关闭连接。
>   - 客户端收到响应后，立即（或稍作延迟）发起下一个新的长轮询请求。
> 2. 优点：
>   - 实时性好，客户端可以及时收到服务器的数据。
> 
> - 缺点：
>   - 实现起来比较复杂。
>   - 服务器端需要不断的向客户端推送数据，会消耗服务器资源。

### 7.3、SSE
>[!tip] SSE
> 1. SSE（Server-Sent Event，服务器推送事件）是一种基于 HTTP 协议的轻量级的消息推送技术。
> 2. 优点：
     >   - 简单，实现起来比较简单。
>   - 实时性好，客户端可以及时收到服务器的数据。
>
> - 缺点：
    >   - 兼容性不好，只有现代浏览器支持。
>   - 无法发送自定义消息。

### 7.4、WebSocket
>[!tip] WebSocket
> 1. WebSocket 是一种通信协议，它实现了浏览器与服务器全双工通信（full-duplex communication）。
> 2. 优点：
>   - 建立在 TCP 协议之上，协议简单，易于实现。
>   - 双向通信，实时性好。
> 
> - 缺点：
>   - 兼容性不好，只有现代浏览器支持。
>   - 服务器端需要支持 WebSocket 协议。
