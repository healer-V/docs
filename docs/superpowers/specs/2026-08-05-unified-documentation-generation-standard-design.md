# 统一文档内容生成规范设计

当前仓库已经对 Frontmatter、标题、代码块、示例和目录编号提出了较完整的格式要求，但格式合规不能保证教程的知识范围、章节顺序、文章粒度和内容深度正确。本设计在现有规则之上增加知识建模与分阶段生成机制，使 AI 能够先识别知识方向，再生成与该方向匹配的系统教程。

## 一、设计目标

统一规范面向具备基本编程常识、但对当前知识方向零基础的读者。教程应从该方向的基础内容开始，逐步覆盖核心能力、运行机制、工程实践和生产边界。

| 目标 | 完成标准 |
|------|----------|
| 系统完整 | 先建立知识项清单和覆盖矩阵，再生成目录，重要知识不得依赖 AI 临时联想 |
| 顺序明确 | 章节按照知识依赖排序，通过目录编号和 sidebar 表达顺序 |
| 方向适配 | 编程语言、框架、数据库和基础设施分别使用对应的知识覆盖模型 |
| 粒度稳定 | 每篇文章只解决一个明确学习问题，避免巨型文章和骨架化小节 |
| 事实可靠 | 关键结论以官方文档、规范或官方仓库为依据，版本边界明确 |
| 示例有效 | 示例能够证明正文结论，无法验证时明确记录环境和阻塞原因 |
| 批量可控 | 先评审蓝图，再校准样板，最后逐章生成，不允许直接盲目批量写作 |

本设计不要求所有知识方向使用相同的章节名称，也不要求所有文章使用相同标题模板。统一的是生成流程、决策依据、输出契约和质量门禁，而不是具体知识内容。

## 二、现状问题与根因

仓库抽样检查显示，当前问题已经超出 Markdown 格式范围。

| 现象 | 根因 | 影响 |
|------|------|------|
| 同一模块的文章长度和深度差异明显 | 缺少单篇职责和拆分依据 | 有的文章接近百科，有的文章只有概念提纲 |
| Java、React 和微服务分别依赖专项设计稿 | 通用规范没有提供知识方向识别与蓝图模型 | 每次重构都需要重新发明目录设计方法 |
| 概述、原理、教程和实践文章结构混用 | 只规定通用格式，没有规定文章类型的内容契约 | 示例形式与文章目标不匹配 |
| 新旧文档仍出现课程式串联话术 | 目录顺序和正文连续性没有明确分工 | 正文出现“前文”“下一篇”“学习路线”等元叙述 |
| 构建成功但不会发现内容漏项或重复 | 工程检查没有覆盖知识完整性和跨篇归属 | 无法证明教程已经形成知识闭环 |

因此，新规范必须先解决“生成什么、为什么这样排序、每篇负责什么”，再处理“具体怎么写”。

## 三、已确认的设计决策

| 决策项 | 采用方案 |
|--------|----------|
| 教程定位 | 系统性完整教程 |
| 连续性表达 | 使用知识依赖、目录编号和 sidebar，不在正文中使用串联话术 |
| 读者基线 | 具备基本编程常识，对当前知识方向零基础 |
| 生成流程 | 模块蓝图评审、样板文章校准、逐章批量生成 |
| 目录模型 | 使用统一生成流程，具体知识覆盖按方向分类 |
| 版本策略 | 每个模块只使用一个主版本基线，版本差异集中处理 |
| 事实来源 | 优先使用官方文档、规范和官方仓库，示例实际验证 |
| 文章粒度 | 每篇只承担一个明确学习问题，不设置机械字数限制 |
| 规范架构 | 使用入口文件、阶段规范、质量门禁和模板组成的分层体系 |

## 四、规范架构

规范采用分层文件组织，避免继续扩张根目录 `AGENTS.md`。

| 层级 | 建议路径 | 职责 |
|------|----------|------|
| 执行入口 | `AGENTS.md` | 保存强制原则、任务分类、指令优先级和规范加载规则 |
| 规范索引 | `.agents/documentation/README.md` | 根据任务阶段指示 AI 读取对应规范 |
| 知识体系规范 | `.agents/documentation/knowledge-system.md` | 定义读者、知识方向、版本、前置知识和范围边界 |
| 目录蓝图规范 | `.agents/documentation/module-blueprint.md` | 定义知识项清单、依赖、章节聚合、职责卡和覆盖矩阵 |
| 单篇内容规范 | `.agents/documentation/article-contracts.md` | 定义文章类型、内容闭环、深度、拆分和合并规则 |
| 生成流程规范 | `.agents/documentation/generation-workflow.md` | 定义任务建档、蓝图、样板、批量生成和验收阶段 |
| 质量门禁 | `.agents/documentation/quality-gates.md` | 定义事实、语义、格式、链接、构建和变更范围检查 |
| 输出模板 | `.agents/documentation/templates/` | 保存模块蓝图、文章职责卡和样板评审模板 |

规范索引必须根据任务类型规定最小加载范围。

| 任务类型 | 必须读取的规范 |
|----------|----------------|
| 新建或全文重构模块 | 知识体系、目录蓝图、生成流程、单篇内容、质量门禁 |
| 新建单篇文章 | 当前模块蓝图、单篇内容、质量门禁 |
| 全文重写单篇文章 | 当前模块蓝图、单篇内容、质量门禁 |
| 局部修改历史文章 | 与修改内容直接相关的单篇规则和质量门禁 |
| 目录规划 | 知识体系、目录蓝图、生成流程中的蓝图阶段规则 |
| 批量质量治理 | 质量门禁、迁移范围和当前模块蓝图 |

根目录 `AGENTS.md` 中现有的有效规则应迁移到职责对应的文件，并在入口中保留不可绕过的硬性要求。迁移不能删除现有 Frontmatter、Markdown、示例、链接、代码注释和工程检查约束。

## 五、知识方向分类

通用规范只定义生成方法，不提供一份适用于所有技术的“基础知识清单”。AI 必须先识别知识方向，再选择对应覆盖模型。

| 知识方向 | 典型模块 | 方向特有的核心内容 |
|----------|----------|--------------------|
| 编程语言 | Java、JavaScript、Python | 标识符、变量、常量、类型、转换、运算符、控制流、函数、对象模型、模块、异常和运行时 |
| 框架与类库 | React、Vue、Spring Boot | 前置语言要求、框架心智模型、核心抽象、组件或 API、数据流、生命周期、扩展能力和工程接入 |
| 数据库与存储 | MySQL、PostgreSQL、Redis | 数据模型、字段类型、查询语言、索引、事务、并发、一致性、性能、安全和恢复 |
| 工程化工具 | Vite、Webpack、Jenkins | 安装配置、构建模型、任务流程、插件扩展、缓存、优化、调试和持续交付 |
| 基础设施与平台 | Linux、Docker、Kubernetes、Nginx | 资源模型、配置、生命周期、网络、存储、安全、可观测性和故障恢复 |
| 协议与 Web API | HTTP、DOM、WebSocket | 消息模型、字段语义、状态变化、API、事件、安全限制、兼容性和调试 |
| 架构与方法 | 微服务、DDD、事件驱动 | 问题背景、参与角色、边界、交互、状态、一致性、治理、取舍和演进 |
| AI 工程 | 模型接入、RAG、Agent、LLMOps | 模型接口、上下文、知识检索、工作流、评测、安全、成本、可观测性和部署 |

### 1. 前置知识与当前知识

每个模块必须区分三类内容：

| 内容类别 | 处理方式 |
|----------|----------|
| 跨方向前置知识 | 明确列出并引用负责讲解的模块，不在当前教程重复完整展开 |
| 当前方向基础知识 | 作为教程起点完整讲解，不能因“基础”而省略 |
| 工程与生态扩展 | 在核心知识之后按依赖和使用场景组织，并明确与核心模块的边界 |

React 教程应把 JavaScript、HTML、CSS 和 DOM 基础列为前置知识，不重新讲解 JavaScript 标识符、变量和通用数据类型；React 元素、JSX、组件、Props、State、事件和 Hooks 属于 React 自身基础，必须完整覆盖。

Java 教程属于编程语言教程，标识符、变量与常量、基本类型与引用类型、类型转换、运算符、控制流、数组和方法都属于当前方向基础，必须进入知识项清单。

### 2. 混合知识方向

一个模块同时涉及多个方向时，必须指定一个主方向和必要的辅助方向。主方向决定教程结构，辅助方向只补充完成目标所必需的内容。

例如 Spring Boot 以“框架与类库”为主方向，可以引用 Java 语言教程，并按需要组合数据库、Web 协议和工程化内容；不能因此在 Spring Boot 模块重新生成 Java 基础语法教程。

## 六、模块蓝图

模块蓝图是正文生成前的强制交付物。未通过蓝图评审时，不得创建或批量重写正文。

### 1. 模块教学契约

模块蓝图首先回答以下问题：

| 字段 | 必须明确的内容 |
|------|----------------|
| 模块定位 | 教程解决的问题、所属知识方向和主要使用场景 |
| 读者基线 | 默认具备的知识和需要从零讲解的当前方向内容 |
| 版本基线 | 主版本、运行环境、依赖版本和版本差异处理位置 |
| 完成能力 | 读者最终能够认识、使用、解释、设计或诊断什么 |
| 前置知识 | 当前模块依赖但不重复完整讲解的内容 |
| 范围排除 | 明确不纳入当前模块的关联主题及其归属 |
| 事实来源 | 官方文档、规范、官方仓库和验证环境 |

### 2. 知识项清单

AI 必须依据知识方向模型和官方资料先生成知识项清单，再组织目录。知识项不能从通用章节模板直接推导。

| 字段 | 说明 |
|------|------|
| 知识点 ID | 在当前模块中唯一，用于表达依赖和归属 |
| 知识点名称 | 使用明确技术名称，不使用“其他能力”等空泛表述 |
| 知识层级 | 当前方向基础、核心能力、机制、工程、质量、生产或演进 |
| 前置知识点 | 学习当前知识点前必须理解的模块内知识 |
| 来源依据 | 对应的官方资料、规范章节或官方仓库 |
| 目标深度 | 认识、使用、解释、设计或诊断 |
| 证据形式 | 代码、命令、输出、日志、指标、状态图、案例或决策表 |
| 内容归属 | 负责完整讲解该知识点的文章 |
| 覆盖状态 | 已覆盖、部分覆盖、未覆盖或不适用 |

知识完整性以知识项清单为基础，并使用跨方向检查问题补充审计。检查问题包括定位与边界、当前方向基础、核心能力、运行机制、组合与设计、工程接入、质量属性、生产实践以及版本演进。某个检查问题不适用时必须说明原因，不能为了形式生成无关章节。

### 3. 依赖与章节聚合

目录按照以下顺序生成：

```text
识别知识方向
→ 确定模块和版本基线
→ 声明前置知识与排除范围
→ 依据官方资料生成知识项清单
→ 建立知识点依赖关系
→ 检查遗漏、重复和循环依赖
→ 聚合为章节和文章
→ 生成逐篇职责卡与覆盖矩阵
```

章节聚合必须遵守以下原则：

- 共享同一心智模型、目标能力和相近前置条件的知识点可以进入同一章；
- 章节顺序由知识依赖决定，不按文件创建时间或固定模板排序；
- 文章数量服从知识边界，不为了编号整齐拆分或合并；
- 概述文章建立整体模型和边界，不承担后续 API 与工程细节；
- 对比、迁移、排障和速查内容通常放在具备必要基础之后；
- 目录有序性通过章节文件夹、文章编号和 sidebar 表达。

### 4. 文章职责卡

每篇文章在生成正文前必须具有职责卡。

| 字段 | 约束 |
|------|------|
| 唯一学习问题 | 一篇文章只回答一个能够明确描述的问题 |
| 前置主题 | 使用知识点 ID 或文章 ID 表达，不写进正文串联话术 |
| 主文章类型 | 只能选择一个主类型 |
| 辅助文章类型 | 最多选择一个，且不能改变文章核心目标 |
| 必须覆盖 | 当前文章负责完整讲解的知识点 |
| 明确不覆盖 | 由其他文章负责或不在当前模块范围内的内容 |
| 目标深度 | 认识、使用、解释、设计或诊断 |
| 证据形式 | 当前文章用于证明结论的示例或资料 |
| 验证结果 | 读者如何判断代码、配置或判断过程正确 |
| 重复归属 | 与其他文章重叠时，负责完整讲解的位置 |

## 七、分阶段生成流程

规范采用“任务建档 + 三阶段生成 + 整体验收”。

| 阶段 | AI 必须完成的工作 | 交付物 | 放行条件 |
|------|--------------------|--------|----------|
| 0. 任务建档 | 审计目录、sidebar、历史文档、版本和工作区状态 | 范围、版本、来源和排除项 | 任务边界明确 |
| 1. 蓝图设计 | 建立知识项、依赖、章节、职责卡和覆盖矩阵 | 完整模块蓝图 | 用户确认后才能写正文 |
| 2. 样板校准 | 选择最能体现模块深度和示例要求的文章完成全文 | 样板文档和评审记录 | 用户确认内容深度与表达方式 |
| 3. 批量生成 | 按依赖逐章生成，每章完成后立即检查 | 正文、sidebar 和必要资源 | 当前章节通过后进入下一章 |
| 4. 整体验收 | 检查覆盖、重复、版本、示例、链接和构建 | 验收结果与未验证项 | 所有硬性门禁通过 |

默认只生成一篇样板。一个模块包含差异显著的文章类型，且现有样板无法证明另一类型的生成标准时，应在蓝图中明确增加第二篇样板及原因，而不是在批量阶段临时改变写法。

出现以下情况时必须暂停当前阶段：

- 新内容与已确认蓝图发生实质偏离；
- 官方资料无法支持关键结论；
- 单篇文章开始承担多个独立学习问题；
- 相邻文章出现大段重复；
- 核心示例无法验证；
- 现有用户改动与计划范围冲突。

## 八、单篇内容契约

文章必须先确定主类型，再选择与目标匹配的内容和证据。

| 主类型 | 必须讲清的内容 | 必须提供的证据 |
|--------|----------------|----------------|
| 基础概念 | 定义、核心对象、关系、边界和常见误解 | 场景、关系图、状态变化、对比或反例 |
| 语法与 API | 形式、参数、返回值、规则、边界和错误用法 | 最小代码、输入输出或实际调用结果 |
| 运行机制 | 参与对象、执行顺序、状态、失败传播和业务约束 | 时序、状态图、日志、指标或可观察代码 |
| 接入教程 | 环境、依赖、配置、实现、执行、结果和错误处理 | 可复现示例及真实预期输出 |
| 设计与实践 | 场景、约束、候选方案、取舍、实施和验证 | 决策矩阵、对照案例或迁移案例 |
| 测试与排障 | 现象、证据、定位、根因、修复、恢复和预防 | 命令、测试、日志、指标或故障注入 |
| 速查与参考 | 参数、命令、返回值、限制、版本和来源 | 最小使用示例与官方资料链接 |

### 1. 内容闭环

文章不强制套用相同标题，但正文必须形成与主类型匹配的论证闭环：

```text
当前问题或概念
→ 核心结论
→ 原因、机制或使用规则
→ 示例或证据
→ 结果解释
→ 边界、错误或判断方法
```

正文禁止固定生成“学习目标”“本章路线”“前文回顾”“下一篇预告”“实践任务”“机械化总结”和与正文重复的文章目录。

### 2. 内容深度

| 深度 | 读者最终能力 |
|------|--------------|
| 认识 | 能说明概念、对象关系和适用边界 |
| 使用 | 能正确调用、配置或操作 |
| 解释 | 能解释执行机制、状态变化和行为差异 |
| 设计 | 能根据场景和约束完成方案选择 |
| 诊断 | 能根据证据定位并处理问题 |

模块可以包含不同深度的文章，但职责卡必须提前声明目标深度。不能通过重复结论或机械增加小节制造内容深度。

### 3. 拆分与合并

出现以下任一情况时，应重新评估是否拆分文章：

- 同时回答两个以上相互独立的学习问题；
- 不同部分需要完全不同的验证环境；
- 同时承担基础语法、底层机制和生产排障等多个主类型；
- 某个部分脱离当前文章后仍能形成完整教程；
- 标题依靠多个并列技术主题才能描述范围。

出现以下情况时，应优先合并或重新组织：

- 某个主题只有简短定义，无法形成独立学习结果；
- 多篇文章重复相同概念、示例和边界；
- 拆分后必须依靠其他文章才能理解当前文章的基本结论。

同一章节可以复用统一业务场景和命名，但每篇文章必须保留理解当前问题所需的最小上下文。示例不得依赖“上一篇的代码”才能执行。

## 九、质量门禁

质量检查分为机器可验证项和需要语义判断的内容项。VitePress 构建成功只能证明工程语法基本有效，不能证明教程内容合格。

### 1. 阶段门禁

| 门禁 | 必须检查的内容 | 失败处理 |
|------|----------------|----------|
| 方向识别 | 分类、前置知识、排除范围和版本基线 | 分类不清时停止目录规划 |
| 蓝图 | 知识覆盖、依赖顺序、章节职责和文章归属 | 存在漏项、循环依赖或冲突时不得写正文 |
| 事实 | 关键结论来源、版本和验证依据 | 无法确认的核心事实不得推测 |
| 样板 | 深度、粒度、示例和语言风格 | 样板未确认不得批量生成 |
| 单篇 | 内容闭环、示例结果、失败边界和来源 | 当前文章不合格时不得进入下一篇 |
| 章节 | 跨篇重复、遗漏、命名和场景一致性 | 当前章节不合格时不得进入下一章 |
| 工程 | Frontmatter、sidebar、链接、资源和构建 | 工程检查失败不得交付 |
| 整体 | 完整性、顺序、版本和生产能力 | 任一硬性门禁失败都不能标记完成 |

### 2. 机器检查

- Frontmatter 合法且 `title` 与唯一一级标题一致；
- 标题层级与编号连续；
- sidebar 指向真实文件；
- 章节文件夹和文章编号连续；
- Markdown 容器、表格和代码块闭合；
- 内部链接和图片路径有效；
- 代码块具有正确语言标识；
- 新增示例函数和多入参函数符合代码注释规范；
- VitePress 完整构建通过。

### 3. 语义检查

- 没有错误套用其他知识方向的基础内容；
- 没有遗漏当前方向官方知识体系中的重要主题；
- 每篇文章只承担一个明确学习问题；
- 不存在只有定义、没有机制、应用或证据的骨架内容；
- 相邻文章没有重复完整讲解相同知识；
- 示例能够证明正文结论；
- 没有混用不同版本的默认行为；
- 没有把前置知识重复写成当前模块正文；
- 没有为了连续感加入无信息量的串联话术。

## 十、异常处理

| 异常 | AI 必须采取的行为 |
|------|--------------------|
| 模块属于混合知识方向 | 指定主方向和必要辅助方向，再组合覆盖模型 |
| 官方资料存在版本差异 | 回到版本基线核对，将差异移入版本说明或迁移内容 |
| 示例无法运行 | 记录环境和阻塞原因，标记未验证，不生成虚假输出 |
| 蓝图之外出现重要知识 | 先更新蓝图并重新确认，不直接塞入现有文章 |
| 文章范围持续膨胀 | 回到职责卡重新拆分，而不是继续增加并列小节 |
| 现有文档与新规范冲突 | 按任务范围增量治理，不擅自重写无关历史文档 |
| 工作区已有用户改动 | 保留改动；发生重叠时基于现状调整，无法兼容才暂停确认 |

## 十一、模板输出要求

模块蓝图模板必须按以下顺序提供内容：

1. 模块教学契约；
2. 知识方向分类与适用模型；
3. 版本基线与官方来源清单；
4. 前置知识和范围排除；
5. 知识项清单；
6. 知识依赖关系；
7. 章节目录与章节职责；
8. 逐篇文章职责卡；
9. 知识覆盖矩阵；
10. 样板文章选择及理由；
11. 示例与工程验证方案。

样板评审记录必须覆盖以下维度：

| 维度 | 评审问题 |
|------|----------|
| 方向匹配 | 是否只讲当前知识方向负责的内容 |
| 内容深度 | 是否达到职责卡声明的能力层级 |
| 文章粒度 | 是否仍然只解决一个学习问题 |
| 事实与版本 | 是否由官方资料支持且符合主版本基线 |
| 示例有效性 | 示例是否可执行并能够证明核心结论 |
| 表达方式 | 是否直接讲知识，避免课程式元叙述 |
| 可复制性 | 后续同类型文章能否复用其质量标准 |

## 十二、实施边界

首次实施只建立分层规范、模板和入口引用，不自动重写整个知识库。现有历史文档继续遵循增量治理原则：新建文档完整采用新规范，全文重写时迁移目标模块，局部修改只保证受影响内容合规。

为验证规范有效性，应选择一个边界清晰且具有代表性的模块执行试点。试点必须完整走过蓝图、样板、逐章生成和整体验收，不能直接使用当前已批量生成的内容反推规范已经有效。

现有 `AGENTS.md` 和工作区包含未提交改动。实施时必须基于当前内容拆分和迁移规则，不得覆盖或撤销其他已有修改。

## 十三、验收标准

- 根目录 `AGENTS.md` 能够根据任务类型引导 AI 读取正确规范；
- 不同知识方向具有独立覆盖模型，不共享错误的基础知识清单；
- 模块正文生成前必须完成知识项清单、依赖关系和文章职责卡；
- 目录顺序能够由知识依赖解释，不依赖课程式正文串联；
- 每篇文章具有唯一学习问题、明确边界、目标深度和验证证据；
- 生成流程具有蓝图确认和样板确认两个不可绕过的人工门禁；
- 批量生成按章节推进，并在每章结束后检查遗漏与重复；
- 事实、版本、示例、Markdown、链接、sidebar 和构建均有明确检查方式；
- 规范实施不强制全量迁移历史文档，也不覆盖用户已有改动。
