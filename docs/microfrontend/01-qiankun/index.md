# Qiankun 微前端框架

微前端（Micro-frontends）将单体前端应用拆分为多个独立子应用，各子应用可独立开发、部署、运行。Qiankun 是目前国内最主流的微前端框架，基于 single-spa 封装，提供了开箱即用的 JS 沙箱、样式隔离等能力。

## 一、微前端概念与解决的问题

### 1. 什么是微前端

微前端借鉴了微服务的理念，将前端应用拆分为多个可以独立开发、独立部署的子应用，由一个主应用（基座）负责统一路由调度和应用加载。

### 2. 解决的核心问题

| 问题 | 说明 |
|------|------|
| 巨石应用难以维护 | 代码库庞大，构建缓慢，团队协作冲突频繁 |
| 技术栈锁定 | 历史遗留 Angular/jQuery 应用难以迁移到 Vue/React |
| 独立部署困难 | 任何改动都需要重新部署整个应用 |
| 团队边界不清 | 多团队共同维护一个前端仓库，职责难以划分 |

## 二、Qiankun 基于 single-spa

Qiankun 是基于 [single-spa](https://single-spa.js.org/) 实现的上层框架，在 single-spa 的基础上增加了：

- **JS 沙箱**：隔离子应用的全局变量，防止相互污染
- **样式隔离**：防止子应用样式溢出到其他应用
- **HTML Entry**：直接使用子应用的 HTML 作为入口，无需改造打包配置
- **预加载**：空闲时预加载子应用资源，减少切换等待时间
- **应用间通信**：提供全局状态管理机制

::: tip Qiankun vs single-spa
直接使用 single-spa 需要手动处理沙箱、样式隔离等问题，配置繁琐。Qiankun 封装了这些通用能力，仅需少量配置即可接入子应用，是生产环境的首选。
:::

## 三、核心特性

### 1. JS 沙箱

JS 沙箱确保子应用的全局变量（`window` 属性、定时器、事件监听）在卸载时被完整清理，不会影响主应用或其他子应用。Qiankun 提供三种沙箱实现：

- **SnapshotSandbox**：基于快照，不支持多实例，兼容性最好
- **LegacySandbox**：基于 Proxy，单实例，性能好于快照
- **ProxySandbox**（默认）：基于 Proxy，支持多实例，能力最强

### 2. 样式隔离

防止子应用的 CSS 泄漏到其他应用：

- **`strictStyleIsolation`**：Shadow DOM 方式，完全隔离
- **`experimentalStyleIsolation`**：给子应用 CSS 添加选择器前缀，兼容性好

### 3. 应用间通信

通过 `initGlobalState` 提供全局状态，主应用与子应用都可以读写和监听状态变化。

### 4. 预加载

通过 `prefetchApps` 或设置 `prefetch: 'all'`，在浏览器空闲时预加载子应用资源。

## 四、框架对比

| 维度 | Qiankun | Module Federation | Iframe |
|------|---------|-------------------|--------|
| 隔离性 | JS 沙箱 + 样式隔离 | 无隔离（共享运行时） | 完全隔离（天然沙箱） |
| 通信 | `initGlobalState` / 自定义事件 | 共享模块直接调用 | `postMessage` |
| 性能 | 良好（HTML Entry，支持预加载） | 最佳（模块级共享，按需加载） | 较差（独立上下文开销大） |
| 样式隔离 | 支持（Shadow DOM / CSS 前缀） | 不支持 | 完全隔离 |
| SEO | 支持 | 支持 | 不支持 |
| 接入成本 | 中等（需改造子应用） | 低（仅需 Webpack 配置） | 极低 |
| 路由控制 | 主应用统一控制 | 各自控制 | 各自独立 |
| 适合场景 | 多团队大型平台 | 组件/依赖共享 | 完全独立的第三方应用 |
| 技术栈限制 | 无（任意框架） | 需要 Webpack 5 | 无 |

::: warning Iframe 的局限
Iframe 虽然隔离性最好，但存在：URL 不同步（刷新丢失路由状态）、弹窗无法全屏覆盖宿主页面、通信繁琐、性能开销大等问题，不推荐作为微前端主要方案。
:::

## 五、适用场景

Qiankun 适合以下场景，不适合的场景也需要提前评估：

**适合场景：**

- 大型平台需要拆分为多个子系统，由不同团队维护
- 需要将历史遗留系统（Angular 1/jQuery）逐步迁移到新技术栈
- 多个独立产品需要在同一个域名/基座下整合
- 需要子应用独立开发、独立部署、独立运行

**不适合场景：**

- 小型单团队项目（引入微前端增加复杂度，得不偿失）
- 子应用间有大量共享状态和频繁交互（考虑 Module Federation）
- 对性能要求极高的场景（每次切换子应用有一定开销）

::: details Qiankun 整体架构示意

```
主应用（基座）
│
├── /                → 主应用自身内容（导航、布局框架）
├── /vue-app/*       → 子应用 1（Vue 3，独立仓库）
├── /react-app/*     → 子应用 2（React，独立仓库）
└── /legacy-app/*    → 子应用 3（历史 jQuery 应用）

每个子应用：
- 独立 Git 仓库
- 独立 CI/CD 流水线
- 独立部署（不同服务器/端口）
- 可独立运行（不依赖主应用也能访问）
```

:::
