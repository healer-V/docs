# Prompt 基础

Prompt（提示词）是你与大语言模型交互的唯一接口。模型不会"猜"你的需求，它完全依赖你给出的文本指令来生成回答。一个好的 Prompt 能让模型精准完成任务，而一个模糊的 Prompt 往往导致冗长、跑题甚至错误的输出。

## 一、什么是 Prompt

Prompt 是发送给大语言模型的输入文本，用于描述你希望模型完成的任务。它可以是一个简单的问题，也可以是一段包含角色设定、上下文信息、输出要求的复杂指令。

::: tip 核心理念
Prompt 本质上是一种"编程语言"——你用自然语言编写指令，模型用自然语言返回结果。Prompt 的质量直接决定了输出的质量。
:::

### 1. Prompt 的基本形式

| 形式 | 说明 | 示例 |
|------|------|------|
| 简单提问 | 直接提出问题 | "什么是 RESTful API？" |
| 指令式 | 明确告诉模型做什么 | "将以下英文翻译为中文：..." |
| 对话式 | 多轮对话逐步深入 | "帮我分析一下这段代码的性能问题" |
| 模板式 | 提供结构化模板 | "按照以下格式输出：标题/摘要/要点" |

### 2. Prompt 与传统搜索的区别

传统搜索引擎基于关键词匹配，而大语言模型基于语义理解。这意味着你在写 Prompt 时需要转变思维：

- **搜索引擎思维**：`Vue3 组合式API 教程`
- **Prompt 思维**：`请用简洁的中文解释 Vue 3 组合式 API 的核心概念，包括 ref、reactive、computed 和 watch 的用法，每个概念给出一个实际的代码示例。`

Prompt 越具体、越有结构，模型的输出就越符合你的预期。

## 二、Prompt 的四大构成要素

一个完整的 Prompt 通常由四个核心要素组成：**角色（Role）**、**任务（Task）**、**上下文（Context）** 和 **格式（Format）**。

### 1. 角色（Role）

角色定义了模型应该以什么身份来回答问题。设定角色可以显著影响模型的输出风格、专业度和视角。

::: details 角色设定示例
```text
你是一位拥有 10 年经验的高级前端工程师，精通 Vue 3、React 18 和 TypeScript。
你擅长用通俗易懂的方式讲解复杂概念，并且总是给出可运行的代码示例。
```
:::

常用的角色设定方向：

| 角色类型 | 适用场景 | 示例 |
|----------|----------|------|
| 技术专家 | 代码审查、架构设计 | "你是一位 Node.js 后端架构师" |
| 教学导师 | 概念讲解、知识梳理 | "你是一位耐心的编程教师" |
| 写作助手 | 文档撰写、内容创作 | "你是一位技术博客作者" |
| 面试官 | 模拟面试、知识评估 | "你是一位资深的前端面试官" |

### 2. 任务（Task）

任务是 Prompt 的核心，明确告诉模型你需要它做什么。任务描述越具体，输出越精准。

::: warning 避免模糊的任务描述
- 模糊："帮我优化一下代码"
- 清晰："请对以下 React 组件进行性能优化，重点关注不必要的重渲染问题，使用 React.memo 和 useMemo 进行优化，并解释每处优化的原因。"
:::

### 3. 上下文（Context）

上下文为模型提供完成任务所需的背景信息，包括：

- **项目背景**：技术栈、框架版本、业务场景
- **约束条件**：性能要求、兼容性要求、代码规范
- **相关代码**：需要分析或修改的代码片段
- **错误信息**：报错日志、异常堆栈

::: details 包含上下文的 Prompt 示例
```text
## 上下文
- 项目使用 Vue 3.4 + TypeScript 5.3 + Pinia 2.1
- 目标浏览器：Chrome 90+、Safari 15+
- 项目采用组合式 API 风格

## 任务
请帮我实现一个用户认证的 Pinia Store，需要包含以下功能：
1. 登录/登出
2. Token 自动刷新
3. 用户信息持久化到 localStorage

## 要求
- 使用 setup store 语法
- 包含完整的 TypeScript 类型定义
- 处理 Token 过期的边界情况
```
:::

### 4. 格式（Format）

格式指定了模型输出的结构和样式。明确的格式要求能避免模型的输出偏离你的需求。

::: details 格式约束示例
```text
请按照以下格式输出：

## 问题分析
（用 2-3 句话概括问题的根本原因）

## 解决方案
（分步骤说明解决方法，每步包含代码示例）

## 注意事项
（列出需要注意的边界情况和潜在风险）
```
:::

## 三、Zero-shot 与 Few-shot

Zero-shot 和 Few-shot 是 Prompt 工程中最基础也最重要的两种模式，区别在于是否在 Prompt 中提供示例。

### 1. Zero-shot（零样本）

Zero-shot 是指不提供任何示例，直接给出任务描述。适合简单、明确的任务。

::: details Zero-shot 示例
```text
将以下文本分类为"正面"、"负面"或"中性"：

文本："这款新发布的 MacBook Pro 性能提升明显，但价格实在太高了。"

分类结果：
```
:::

### 2. Few-shot（少样本）

Few-shot 是指在 Prompt 中提供 2-5 个示例，帮助模型理解期望的输入输出模式。适合需要特定格式或风格的任务。

::: details Few-shot 示例
```text
请根据以下示例，将技术文章标题转换为 URL slug：

示例：
- 输入："Vue 3 组合式 API 入门指南"
  输出：vue3-composition-api-guide
- 输入："TypeScript 高级类型系统详解"
  输出：typescript-advanced-type-system
- 输入："React 18 并发特性深度解析"
  输出：react18-concurrent-features

请转换：
- 输入："Webpack 5 模块联邦实战教程"
  输出：
```
:::

### 3. 如何选择

| 特征 | Zero-shot | Few-shot |
|------|-----------|----------|
| 任务复杂度 | 简单、常见任务 | 复杂、定制化任务 |
| 格式要求 | 低或无特殊要求 | 需要严格遵循特定格式 |
| Token 消耗 | 少 | 较多（每个示例消耗 Token） |
| 适用场景 | 翻译、摘要、问答 | 数据转换、分类、代码生成 |

::: tip 实践建议
优先尝试 Zero-shot，如果输出不符合预期，再添加 1-3 个示例切换到 Few-shot 模式。示例的质量比数量更重要——确保每个示例都准确反映你期望的输出格式。
:::

## 四、System Prompt 与 User Prompt

在 API 调用场景中，Prompt 分为 System Prompt 和 User Prompt 两个层级，它们的作用不同。

### 1. System Prompt（系统提示词）

System Prompt 设定模型的全局行为规则，通常在对话开始时设置一次，对整个会话生效。

::: details System Prompt 示例
```text
你是一个专业的代码审查助手。你的职责是：

1. 审查用户提交的代码，识别潜在的 Bug、性能问题和安全风险
2. 按照严重程度（高/中/低）对问题进行分级
3. 对每个问题给出具体的修复建议和修复后的代码
4. 使用中文回复，代码注释也使用中文
5. 如果代码质量良好，明确肯定并给出进一步优化的建议

你不需要解释基础语法，假设用户具有中级以上的编程能力。
```
:::

### 2. User Prompt（用户提示词）

User Prompt 是每次对话中用户发送的具体请求，通常包含需要处理的具体内容。

::: details User Prompt 示例
```text
请审查以下 Vue 3 组件代码：

```vue
<script setup lang="ts">
import { ref, onMounted } from 'vue'

const userList = ref([])
const loading = ref(false)

const fetchUsers = async () => {
  loading.value = true
  const response = await fetch('/api/users')
  const data = await response.json()
  userList.value = data
  loading.value = false
}

onMounted(() => {
  fetchUsers()
})
</script>
```
:::

### 3. 两者的关系与区别

| 维度 | System Prompt | User Prompt |
|------|---------------|-------------|
| 作用范围 | 全局，影响整个会话 | 单次请求 |
| 设置频率 | 通常一次 | 每次对话都会变化 |
| 内容类型 | 角色设定、行为规则、输出约束 | 具体的任务和数据 |
| 优先级 | 高（模型优先遵循） | 正常 |
| 可见性 | 用户通常不可见 | 用户直接输入 |

## 五、常用 Prompt 模式

### 1. 指令跟随模式

直接下达具体指令，适合明确的执行类任务。

::: details 指令跟随模式示例
```text
请将以下 JavaScript 代码重构为 TypeScript，要求：
1. 为所有变量和函数参数添加类型注解
2. 使用 interface 定义复杂对象类型
3. 使用 enum 替代魔法字符串
4. 保持原有的业务逻辑不变

// 原始代码
function createOrder(product, quantity, discount) {
  const basePrice = product.price * quantity
  const finalPrice = basePrice * (1 - discount)
  return {
    productId: product.id,
    productName: product.name,
    quantity,
    basePrice,
    discount,
    finalPrice,
    status: 'pending',
    createdAt: new Date().toISOString()
  }
}
```
:::

### 2. 模板填充模式

提供一个输出模板，让模型按照模板结构填充内容。

::: details 模板填充模式示例
```text
请按照以下模板为 "useDebounce" 自定义 Hook 编写文档：

## Hook 名称
（Hook 的名称和一句话描述）

## 使用场景
（列出 3-5 个典型使用场景）

## API
| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
（参数表格）

## 基础用法
（代码示例）

## 高级用法
（代码示例）

## 注意事项
（使用时需要注意的问题）
```
:::

### 3. 约束限制模式

通过明确的约束条件限制模型的输出范围，避免冗余或离题的内容。

::: details 约束限制模式示例
```text
请回答以下问题，严格遵守这些约束：
- 回答长度不超过 200 字
- 只使用初学者能理解的词汇
- 不要使用类比或比喻
- 给出一个 5 行以内的代码示例

问题：什么是 JavaScript 的闭包？
```
:::

## 六、最佳实践

### 1. 编写有效 Prompt 的核心原则

::: tip 六大原则

1. **具体而非模糊**：用精确的描述替代笼统的要求
2. **结构化表达**：使用标题、列表、编号组织 Prompt
3. **提供上下文**：给模型足够的背景信息做出判断
4. **明确输出格式**：告诉模型你期望的输出结构
5. **设定边界**：明确模型应该做什么、不应该做什么
6. **迭代优化**：根据输出结果不断调整 Prompt
:::

### 2. 常见错误与改进

| 常见错误 | 问题 | 改进方式 |
|----------|------|----------|
| "帮我写个组件" | 缺少具体需求 | 明确组件的功能、props、事件、样式要求 |
| 一次提太多要求 | 模型容易遗漏细节 | 将复杂任务拆分为多个步骤 |
| 不提供上下文 | 模型只能猜测 | 附带技术栈、版本、项目背景 |
| 接受第一次输出 | 可能不是最优结果 | 通过追问和反馈迭代优化 |
| 使用否定指令 | "不要用 class 组件" | 使用肯定指令 "使用函数组件和 Hooks" |

### 3. Prompt 调试技巧

当模型的输出不符合预期时，你可以尝试以下调试方法：

1. **添加示例**：从 Zero-shot 切换到 Few-shot，给模型具体参照
2. **分步执行**：将复杂任务拆成多个步骤，逐步完成
3. **要求解释**：让模型解释它的理解和推理过程
4. **调整角色**：换一个更匹配任务的角色设定
5. **限制范围**：缩小输出范围，聚焦核心问题

::: warning 注意事项
Prompt 工程不是"一劳永逸"的，不同模型、不同版本对同一 Prompt 的响应可能不同。当你切换模型或模型更新版本后，建议重新测试核心 Prompt 的输出效果。
:::
