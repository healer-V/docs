## 二、问题陈述

### 1. 当前问题

我们的 B2B SaaS 产品已覆盖任务管理、文档协作和项目管理三大核心场景，但用户在日常协作中仍需要离开产品、切换到 Miro 或 FigJam 等第三方白板工具来完成以下工作：

- 产品团队的 sprint 规划、用户故事映射和功能优先级排序；
- 设计团队的设计评审、用户流程图梳理和组件关系讨论；
- 远程团队的头脑风暴、回顾会议和异步讨论。

用户访谈中反复出现的高频反馈：

| 编号 | 反馈摘要 | 影响 |
|------|----------|------|
| U1 | "切换工具太麻烦，希望在一个地方完成所有工作" | 打断工作流，增加认知负担 |
| U2 | "Miro 功能太多，我们只需要基础的便签和连线" | 复杂工具造成学习成本和决策疲劳 |
| U3 | "实时协作很重要，但不需要视频/音频" | 过于重的协作工具反而干扰专注 |
| U4 | "希望能直接链接到我们产品中的其他对象（任务、文档）" | 白板内容与工作流脱节 |
| U5 | "移动端支持不重要，主要在桌面端用" | 可以聚焦桌面端体验优化 |

### 2. 市场定位

| 维度 | Miro | FigJam | Google Jamboard | 我们的白板 |
|------|------|--------|-----------------|------------|
| 复杂度 | 极高，300+ 模板 | 中等，偏设计场景 | 极简，仅有基础绘图 | 轻量，聚焦核心协作 |
| 产品内集成 | 否 | 否 | G Suite 内有限集成 | 深度集成，直接引用产品对象 |
| 定价 | 独立付费 | 独立付费 | 免费但功能少 | 包含在现有订阅中 |
| 目标用户 | 大型团队、咨询 | 设计师、产品 | 教育、轻量脑暴 | 中小产品/设计/远程团队 |

**定位**：比 Miro 简单 80%，比 Google Jamboard 功能丰富 3 倍，且深度集成在我们的产品工作流中。

### 3. 目标与非目标

**目标：**

1. 提供轻量、开箱即用的协作白板，用户无需额外学习即可上手；
2. 支持便签、连线、自由文本和基础图形四种原子元素，覆盖 80% 的日常协作场景；
3. 实时多人协作，延迟控制在 500ms 以内；
4. 深度集成产品内对象（任务、文档、项目），白板元素可以直接关联并导航到对应对象；
5. MVP 在 Q2 发布，完整版在 Q3 发布。

**非目标：**

1. 不提供视频/音频通话能力（用户反馈 U3 明确不需要）；
2. 不提供移动端原生编辑器（MVP 阶段仅桌面端 Web，后续版本可以评估只读预览）；
3. 不提供 AI 生成、模板市场、插件系统等高级功能（属于 V2 评估范围）；
4. 不替代 Figma/Miro 的设计评审能力——不做原型连线、设计标注和设计组件库。

### 3. 明确不在范围内的功能（V2 评估）

| 功能 | 排除原因 |
|------|----------|
| 视频/音频通话 | 用户访谈 U3 明确不需要，且与产品战略定位冲突 |
| 移动端编辑器 | MVP 阶段用户明确主要在桌面端使用（U5） |
| AI 智能生成 | 属于 V2 差异化功能，需要评估模型成本和准确率后决策 |
| 模板市场/社区 | MVP 阶段模板数量有限，社区生态需要用户规模支撑 |
| 第三方工具嵌入（嵌入 Figma、Miro 文件） | 优先级低于原生白板体验，且涉及跨产品授权和渲染兼容性问题 |
| 离线编辑 | 技术复杂度高（CRDT 离线合并），3 个月时间窗口不足以稳定交付 |
| 高级权限（元素级可见性控制） | MVP 阶段白板级读写权限已足够 |

## 五、成功指标

### 1. 指标体系

将指标分为**领先指标**（短期可观测、驱动行为）和**滞后指标**（长期业务结果）。

#### 1.1 领先指标（发布后 2 周内可观测）

| 指标 | 目标 | 测量方式 | 预警阈值 |
|------|------|----------|----------|
| 白板创建率 | 每周至少 30% 的活跃团队创建了至少 1 个白板 | 事件埋点 `whiteboard.created` / 活跃团队数 | < 15% 触发推广 Review |
| 首日留存（白板功能） | 首次使用白板后次日再次使用的用户比例 ≥ 40% | 事件埋点 `whiteboard.entered`，按用户去重 | < 25% 触发体验优化 Review |
| 白板平均协作人数 | 每个白板的平均同时编辑人数 ≥ 2.5 人 | 实时连接数统计 | < 1.5 人说明未形成协作习惯 |
| 元素创建量 | 每个活跃白板平均创建 ≥ 20 个元素（便签/图形/文本） | 事件埋点 `element.created` | < 10 说明白板内容太薄 |

#### 1.2 滞后指标（Q3 末评估）

| 指标 | 目标 | 测量方式 |
|------|------|----------|
| 白板会话平均时长 | > 15 分钟（中位数） | 从 `whiteboard.entered` 到 `whiteboard.left` 的时间差 |
| 功能渗透率 | ≥ 30% 的活跃团队每周至少使用 1 次白板 | 周活跃团队中使用过白板的比例 |
| 从外部工具迁移率 | > 20% 的活跃白板团队此前使用过 Miro/FigJam/Jamboard | 用户调研问卷 + 行为数据分析（是否在白板中粘贴来自 Miro 的截图或链接） |
| 白板功能 NPS | ≥ 40 | 产品内 NPS 弹窗，在白板功能使用满 5 次后触发 |
| 产品内跳转率 | 白板便签关联的任务/文档，点击跳转率 ≥ 15% | 埋点统计 `whiteboard.element.click_link` |

### 2. 指标分层监控

```text
L1 — 北极星指标：功能渗透率 ≥ 30%
  ├── L2 — 活跃度：白板会话平均时长 > 15min、白板创建率 ≥ 30%
  ├── L2 — 协作深度：平均协作人数 ≥ 2.5、元素创建量 ≥ 20
  └── L2 — 满意度：NPS ≥ 40、迁移率 > 20%
       ├── L3 — 首日留存 ≥ 40%
       ├── L3 — 产品内跳转率 ≥ 15%
       └── L3 — 模板使用率（Q3 完整版）
```

| 事件名 | 属性 | 用途 |
|--------|------|------|
| `whiteboard.created` | board_id, project_id, user_id | 跟踪创建率 |
| `whiteboard.entered` | board_id, user_id, entry_source | 跟踪进入来源和活跃 |
| `whiteboard.left` | board_id, user_id, duration_seconds | 计算会话时长 |
| `element.created` | board_id, element_type, user_id | 跟踪元素类型分布 |
| `element.updated` | board_id, element_id, user_id, operation | 跟踪编辑操作类型 |
| `element.deleted` | board_id, element_id, user_id | 跟踪删除行为 |
| `element.linked_object` | board_id, element_id, object_type, object_id | 跟踪产品对象关联率 |
| `whiteboard.exported` | board_id, format, user_id | 跟踪导出行为 |

## 六、技术方案

### 1. 架构概览

```text
┌─────────────────────────────────────────────────┐
│                    前端（Web）                     │
│  Canvas 渲染层 (Fabric.js / Konva)                │
│  ├── 元素管理 (便签/连线/图形/文本/图片/绘制)        │
│  ├── 交互层 (选择/拖拽/缩放/框选/撤销重做)           │
│  └── 协作层 (光标同步/操作冲突/在线状态)             │
├─────────────────────────────────────────────────┤
│                WebSocket 实时通道                   │
│  ├── 操作广播 (CRDT / OT 协议)                     │
│  ├── 在线状态管理                                  │
│  └── 心跳与断线重连                                │
├─────────────────────────────────────────────────┤
│                    后端服务                         │
│  ├── 白板 CRUD API                                │
│  ├── 元素持久化 (操作日志 + 快照)                   │
│  ├── 版本历史服务                                   │
│  ├── 产品对象关联服务                               │
│  └── 权限与协作管理                                │
├─────────────────────────────────────────────────┤
│                    数据存储                         │
│  ├── PostgreSQL (白板元数据、权限)                  │
│  ├── 操作日志 (时序数据库或 Redis Stream)           │
│  └── 对象存储 (图片、导出文件)                      │
└─────────────────────────────────────────────────┘
```

### 2. 关键技术决策

#### 2.1 前端渲染引擎

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| Fabric.js | 成熟稳定、社区大、文档丰富、对象模型清晰 | 不支持 WebGL 加速，超大规模元素有性能瓶颈 | 推荐 MVP |
| Konva.js | 分层架构清晰、事件系统好、可扩展性强 | 社区稍小于 Fabric.js | 备选方案 |
| 自研 Canvas | 完全可控 | 3 个月时间窗口不足以开发稳定引擎 | 不推荐 |
| Excalidraw 内核 | 手绘风格、开箱即用、已有协作实现 | 定制化成本高、与产品集成困难 | 不推荐 |

**决策**：使用 Fabric.js 作为 MVP 渲染引擎，原因：(1) 对象模型与便签、图形、连线等元素天然匹配；(2) 社区生态降低了开发风险；(3) 如果 MVP 后性能成为瓶颈，Q3 可以考虑迁移到 Konva.js 或在 Fabric.js 上增加虚拟化优化。

#### 2.2 实时同步协议

必须与现有实时同步架构兼容。根据约束条件，推荐使用 CRDT（Conflict-free Replicated Data Type）方案：

- 每个操作携带逻辑时钟（Lamport timestamp），在服务端做全序排列；
- 并发操作通过 CRDT merge 函数处理，保证最终一致性；
- 白板操作粒度：创建元素、移动元素、编辑文本、删除元素、改变样式；
- MVP 阶段使用 OT（Operational Transformation）作为备选——如果现有同步架构已经基于 OT，则复用现有基础设施。

#### 2.3 数据模型

```text
Whiteboard {
  id: string (UUID)
  name: string
  project_id: string          // 所属项目
  team_id: string              // 所属团队
  owner_id: string             // 创建者
  elements: Element[]          // 元素列表
  viewport: { x, y, zoom }    // 上次保存的视口状态
  created_at: timestamp
  updated_at: timestamp
  version: number              // 乐观锁版本号
}

Element {
  id: string (UUID)
  type: enum[note, line, text, rect, ellipse, arrow, diamond, freehand, image, timer]
  properties: jsonb            // 类型相关的属性（位置、大小、颜色、文本等）
  linked_object: {             // 关联的产品对象（可选）
    type: enum[task, document, project]
    id: string
    title: string?
  }
  created_by: string
  created_at: timestamp
  updated_at: timestamp
}

Operation {
  id: string (UUID)
  board_id: string
  user_id: string
  type: enum[create, update, delete, move, style_change]
  element_id: string
  payload: jsonb               // 操作的具体数据
  lamport_clock: number
  server_timestamp: timestamp
}
```

## 七、用户流程

### 1. 创建与进入白板

```text
项目/团队空间页面
  → 点击"新建白板"按钮
  → 输入白板名称（可跳过，默认"未命名白板-日期"）
  → 白板创建完成，自动进入编辑模式
  → 白板出现在项目/团队空间的"白板"列表页

已有白板
  → 从白板列表页点击缩略图进入
  → 从关联的任务/文档详情页"关联白板"入口跳转进入
```

### 2. 核心操作流程

```text
进入白板后：
  1. 工具栏固定在画布顶部
     [手型] [选择] [便签] [连线] [文本] [矩形] [椭圆] [画笔] [图片] [撤销] [重做]
  2. 点击工具 → 在画布上操作
  3. 选中元素 → 右侧属性面板显示样式选项（颜色/字号/边框等）
  4. 空格 + 拖拽 → 平移画布
  5. 滚轮 → 缩放画布
  6. 框选 → 批量操作（移动/删除/改色）
```

### 3. 产品对象关联流程

```text
方式一：选中便签 → 属性面板 → 点击"关联对象" → 搜索任务/文档 → 选择确认
方式二：在产品任务/文档详情页 → 点击"添加到白板" → 选择目标白板 → 自动创建关联便签
方式三：在白板中粘贴产品内对象链接 → 自动解析为引用卡片
```

### B. 术语表

| 术语 | 定义 |
|------|------|
| 便签 (Sticky Note) | 可拖拽的矩形卡片，包含文本和颜色标签 |
| 连线 (Connector) | 两个元素之间的可视连接线 |
| 自由文本 (Free Text) | 画布上任意位置的独立文本块 |
| 基础图形 (Basic Shapes) | 矩形框、椭圆、箭头、菱形等几何图形 |
| 自由绘制 (Freehand) | 鼠标或触控笔绘制的自由路径 |
| 画布 (Canvas) | 白板的可编辑无限区域 |
| 元素 (Element) | 白板上的任何可视对象（便签、图形、文本等） |
| 对象 (Object) | 产品内已有的业务实体（任务、文档、项目） |
| 框选 (Marquee Select) | 拖拽空白区域选中多个元素 |
| 操作同步 (Operational Sync) | 多个用户编辑操作的实时同步机制 |
