# 服务拆分方法与边界验证

服务拆分不是把类、表或接口平均分组，而是决定哪些业务规则、数据写入和变化应该一起演进。边界判断错误时，代码虽然进入不同进程，一次业务变化仍会同时修改多个服务，一次请求也会产生大量聊天式调用，最终形成分布式单体。

本文延续[单体、模块化单体与微服务](../01-foundation/02-monolith-modular-monolith-and-microservices.md)中的保险案例，验证“产品能力是否适合作为首个服务”。目标不是直接得到唯一正确答案，而是学会收集证据、形成候选方案、发现反例并记录回退条件。

## 一、边界要保护什么

可靠边界通常同时保护三类事物：

- **业务不变量**：必须在一次原子操作中保持成立的规则应该聚合。例如投保申请状态变为“审核通过”时，审核结论和申请版本必须一致。
- **数据写入责任**：每类业务事实只有一个权威修改者。投保服务可以保存提交时的产品快照，但不能修改产品主数据。
- **变化原因**：经常因同一类业务需求一起变化的规则应该靠近；变化节奏长期不同的能力才可能从拆分中受益。

边界不等于完全没有依赖。产品和投保必然协作，关键在于依赖是否能够通过少量、稳定且有业务含义的契约表达，而不是共享内部对象和数据库结构。

```text
边界质量
  = 边界内部业务内聚
  + 边界外部契约稳定
  + 数据写入责任清晰
  + 独立变化确有收益
  - 跨边界协作成本
```

这个表达式用于组织评审问题，不是机械评分公式。任何“高内聚、低耦合”的结论都应由业务场景和变更证据支持。

## 二、从业务流程收集事实

不要从现有包名和数据库表开始拆分。先选择一条有明确用户结果的业务流程，标记参与者、命令、状态变化、规则和外部依赖。

以提交投保申请为例：

```text
客户选择产品版本
  → 填写投保资料
  → 提交申请
  → 校验产品是否可销售
  → 保存产品与客户快照
  → 申请进入待核保状态
```

这条流程可以提取出以下事实：

| 类型 | 示例 | 对边界的提示 |
|------|------|----------------|
| 命令 | 提交投保申请 | 应由一个明确流程所有者接收 |
| 业务规则 | 产品必须处于可销售状态 | 投保需要产品判断，但不拥有产品规则 |
| 状态变化 | 草稿变为待核保 | 申请状态与提交记录需要本地一致 |
| 业务事实 | 提交时使用产品版本 V3 | 应保存在申请快照中，不能随产品变化改写 |
| 外部依赖 | 身份核验、支付或风控 | 需要明确同步、异步和失败策略 |

“校验产品”出现在投保流程中，不代表产品规则属于投保服务。判断所有权时要问：谁定义规则、谁批准变化、谁维护产品版本，以及其他流程是否也需要同一判断。

## 三、使用六类证据形成候选边界

边界不能只依赖一次领域建模会议。应同时检查以下证据：

| 证据 | 关键问题 | 错误信号 |
|------|----------|----------|
| 业务结果 | 该能力最终产生什么可识别结果 | 只能用 Controller、DAO 等技术层描述 |
| 不变量 | 哪些状态必须在同一事务中成立 | 一个强一致规则被拆到多个服务 |
| 数据所有权 | 谁定义字段语义并拥有唯一写入权 | 多个服务直接更新同一张表 |
| 变化历史 | 哪些代码长期随同一需求一起修改 | 每次需求仍同时修改多个候选服务 |
| 运行压力 | 容量、延迟、安全和合规是否不同 | 没有真实差异，只为增加服务数量 |
| 团队责任 | 谁负责需求、发布、告警和故障 | 服务跨越多个只负责技术层的团队 |

建议实际查看需求记录、提交历史、数据库访问、接口调用和故障记录。工作坊中的领域名称只是候选，历史变化和运行数据用于验证候选是否真实。

::: warning 相关变更不等于同一边界
两个模块经常在同一需求中修改，可能因为它们业务内聚，也可能因为当前接口设计差、共享数据库或发布流程强制绑定。需要进一步判断共同变化的原因。
:::

## 四、产品与投保的候选方案

对于产品和投保能力，可以先比较三种候选：

| 方案 | 结构 | 收益 | 主要代价 |
|------|------|------|----------|
| A：同一投保模块 | 产品规则和申请流程一起维护 | 本地调用和事务简单 | 产品无法独立复用、发布和扩容 |
| B：模块化单体中的两个模块 | 公开 `ProductCatalog`，仍同进程部署 | 边界可验证，网络成本低 | 仍然一起发布和扩容 |
| C：独立产品服务 | 投保通过远程契约查询产品 | 独立发布、扩容和数据责任 | 引入超时、兼容和可用性依赖 |

在业务早期，方案 B 通常是更稳妥的起点。只有出现以下证据时，方案 C 才获得足够收益：

1. 产品能力被投保、报价、续期等多个流程复用；
2. 产品版本和销售规则已经相对稳定；
3. 产品查询容量明显高于投保写入容量；
4. 产品与投保由不同团队负责，发布等待已经可测量；
5. 投保只需要少量产品摘要，不依赖产品内部实体；
6. 产品数据已经有唯一写入者，提取后不需要长期共享写表。

如果产品规则每周仍与投保流程一起大幅调整，提前跨进程会让每次需求同时改 Provider、Consumer、契约和测试，独立部署收益无法成立。

## 五、事务和数据决定拆分下限

必须在同一事务中保护的不变量，是服务粒度的重要下限。例如一次提交申请需要同时满足：

- 申请版本没有被并发修改；
- 当前状态允许提交；
- 提交资料和产品快照完整；
- 状态迁移与提交记录同时成功。

这些数据应该由投保服务在一个本地事务中更新。把“申请状态服务”“申请资料服务”和“申请记录服务”分别拆开，会把一个本地不变量改造成分布式一致性问题，却没有获得独立业务价值。

产品服务与投保服务之间则适合通过版本化摘要协作：

```text
product-service（权威数据）
  产品编码、产品版本、销售状态、投保规则摘要

application-service（业务快照）
  申请编号、提交状态、提交时产品版本、保障摘要
```

投保保存产品快照不是复制产品所有权。快照用于证明“申请提交时依据了什么”，不能被其他系统当作当前最新产品信息。

跨服务查询还要明确时效：投保提交需要产品所有者的实时判断，可以同步查询；投保列表展示产品名称可以使用快照；大规模报表不应逐条调用产品服务。不同查询目的可能需要不同协作方式。

## 六、依赖图用于发现隐藏成本

形成候选边界后，需要把依赖画出来，并标记调用类型：

```text
application-service
  ├─[同步查询]→ product-service
  ├─[同步查询]→ customer-service
  └─[异步事件]→ underwriting-service

underwriting-service
  └─[异步事件]→ policy-service
```

重点检查四类问题：

- **循环依赖**：A 调 B、B 又调 A，通常意味着流程所有者或数据所有权不清；
- **长同步链**：入口依次调用多个服务，尾延迟和失败概率会累积；
- **聊天式调用**：循环中逐条查询远程服务，边界过细或契约粒度错误；
- **核心依赖边缘**：投保主流程不应同步等待通知、推荐和统计等非核心能力。

产品查询位于投保提交的关键路径，所以提取前必须接受一个新事实：产品服务不可用时，投保可能无法完成产品判断。缓存、快照或降级不能自动代替权威业务判断，需要由业务规则明确允许。

## 七、用变化场景反向验证边界

边界评审不应停留在服务名称。选择具体变化，逐项判断主要所有者、需要修改的契约和数据影响：

| 变化场景 | 主要所有者 | 合理协作 | 边界异常信号 |
|----------|------------|----------|--------------|
| 调整产品最低保费 | 产品 | 发布新产品版本；新申请使用新版本 | 必须修改投保数据库字段才能发布 |
| 产品暂停销售 | 产品 | 实时判断新申请；历史申请保留快照 | 投保直接修改产品状态表 |
| 增加投保资料字段 | 投保 | 修改申请契约和校验 | 产品服务被迫理解申请内部状态 |
| 调整核保规则 | 核保 | 消费稳定申请信息并产生结论 | 产品服务参与核保流程编排 |
| 保单失效 | 保单 | 发布保单状态事件 | 回写投保申请内部状态作为唯一事实 |

边界通过验证的标志，不是所有变化都只修改一个服务。跨服务业务必然存在协作；更重要的是变化由正确所有者发起，其他服务通过兼容契约响应，而不是共同修改内部实现和共享表。

## 八、把边界约束写进代码

配套模块化单体使用 Spring Modulith 声明允许依赖。投保模块允许依赖产品模块公开 API：

```java
// examples/microservices-insurance/insurance-monolith/src/main/java/
// com/example/insurance/application/package-info.java
@org.springframework.modulith.ApplicationModule(
        displayName = "投保模块",
        allowedDependencies = "product"
)
package com.example.insurance.application;
```

执行边界测试：

```powershell
.\mvnw.cmd -pl insurance-monolith test
```

正常结构的实际结果是：

```text
Tests run: 2, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

为了验证测试确实能够阻止未授权依赖，本文将 `allowedDependencies` 临时改为空集合并重新执行。测试真实失败信息为：

```text
Module 'application' depends on module 'product'
via ApplicationEligibilityService -> ProductCatalog.
Allowed targets: none.

Tests run: 2, Failures: 0, Errors: 1, Skipped: 0
BUILD FAILURE
```

恢复 `allowedDependencies = "product"` 后测试重新通过。这证明依赖规则已经进入自动化反馈，而不是只存在于架构图。

自动化测试仍不能决定业务边界。它只能证明代码遵守当前声明；声明是否正确，仍要通过前面的业务不变量、变化场景和数据责任评审。

## 九、记录决策和回退条件

边界确定后应编写 ADR，至少包含：

| ADR 内容 | 产品服务案例 |
|----------|--------------|
| 决策问题 | 产品能力是否从模块化单体提取为独立服务 |
| 当前约束 | 查询负载高、边界稳定、产品数据有唯一写入者 |
| 候选方案 | 继续同模块、模块化单体、独立产品服务 |
| 选择 | 先验证模块边界，再提取产品查询和写入能力 |
| 代价 | 新增远程可用性、超时、契约和部署成本 |
| 迁移方式 | 通过 `ProductCatalog` 接缝切换本地与远程实现 |
| 回退条件 | 调用可靠性不达标时切回本地实现，数据写入权保持唯一 |
| 复审条件 | 团队责任变化、调用扇出增加、契约频繁破坏 |

完成本文后，读者应能交付四项可评审结果：业务流程与不变量、候选边界图、数据所有权表、包含回退条件的 ADR。只有这四项能够共同解释“为什么拆”和“拆错了怎么办”，服务边界才具备实施基础。

关于模块验证机制可参考 [Spring Modulith 结构验证](https://docs.spring.io/spring-modulith/reference/verification.html)。下一步的服务发现实验会展示边界跨越进程后新增的实例、缓存和部分失败状态。
