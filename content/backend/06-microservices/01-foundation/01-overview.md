# 微服务架构概述

微服务不是把代码拆成多个进程，而是围绕业务能力建立可独立演进的服务。每个服务拥有明确责任、发布边界和数据边界，通过网络契约协作。拆分带来的独立交付能力必须能够覆盖网络、数据和运维复杂度，否则系统只会从“复杂单体”变成“复杂分布式单体”。

## 一、基本定义

判断一个系统是否真正采用微服务，不能只看进程数量。需要同时检查业务责任、数据写入权、发布流程和故障边界；其中任意一项仍被集中绑定，都可能形成“部署形态分散、实际能力不自治”的分布式单体。

- **服务是业务能力单元**：服务应表达稳定业务能力，例如产品管理、投保申请、保单管理，而不是机械对应 Controller、Service、DAO 等技术层。一个服务需要能够说明它负责什么、不负责什么，以及其他服务如何使用它。
- **独立部署是关键边界**：只有一个服务能够在不同时发布其他服务的前提下完成构建、测试、部署和回滚，独立部署才成立。多个进程如果必须固定版本一起上线，仍然形成发布耦合。
- **网络契约替代进程内调用**：服务间通过 HTTP、消息或其他远程协议协作。远程调用存在延迟、超时和部分失败，不能继续按照本地方法调用的假设设计。

## 二、核心特征

这些特征需要组合成立。独立部署却共享写表，会被数据库变更重新绑定；数据已经分离但没有自动化交付，则会把每次变更变成人工协调。评估时应寻找端到端闭环，而不是逐项勾选技术组件。

- **单一业务责任**：服务边界围绕业务语义和变化原因建立。责任单一不等于代码量小，而是主要由同一类业务规则驱动变化。
- **数据所有权**：服务拥有其业务数据的写入规则。其他服务不能绕过契约直接修改数据库表，否则代码虽然拆开，数据耦合仍然存在。
- **技术与运行自治**：服务可以独立调整容量、发布节奏和内部实现，但自治仍受组织安全、可观测性、协议和运行平台规范约束。
- **自动化支撑**：服务数量增加后，人工维护地址、配置和发布过程无法持续。注册发现、配置管理、监控、测试和部署自动化属于架构必要条件。

## 三、典型运行结构

### 1. 请求链路

下面的结构只表达职责关系，不代表所有业务都必须同步调用：

```text
客户端
  → API 网关
    → 投保服务
      → 产品服务
      → 客户服务
    → 保单服务
```

### 2. 治理组件

| 组件 | 解决的问题 | 本教程主线 |
|------|------------|------------|
| 注册中心 | 服务实例在哪里 | Eureka |
| 配置中心 | 服务使用什么配置 | Apollo |
| 客户端负载均衡 | 多个实例中调用哪一个 | Spring Cloud LoadBalancer |
| 声明式客户端 | 如何以接口方式发起 HTTP 调用 | Spring Cloud OpenFeign |
| 健康检查 | 实例是否能够接收流量 | Spring Boot Actuator |

- **平台能力**：日志、指标、追踪、发布流水线和容器平台为全部服务提供公共能力。它们不能消除业务复杂度，但能够降低重复建设和故障定位成本。

## 四、Spring 技术栈职责

- **Spring Boot**：Spring Boot 用于创建可独立运行的应用，负责自动配置、依赖管理、Web 服务器和生产就绪端点。它本身不等于微服务架构。
- **Spring Cloud**：Spring Cloud 提供面向分布式应用的抽象和组件集成，例如 DiscoveryClient、LoadBalancer 和 OpenFeign。它解决常见技术协作问题，不替代服务边界设计。
- **Eureka 与 Apollo**：Eureka 管理运行中的服务实例，Apollo 管理跨环境配置。一个回答“调用地址”，另一个回答“运行参数”，两者职责不同。

## 五、收益来源

收益必须能够通过发布频率、故障影响范围、资源利用率或跨团队等待时间等指标验证。若拆分前后没有可观察变化，新增的网络与治理成本就缺少合理回报。

- **独立交付**：不同业务能力可以按各自节奏发布，缩小一次变更需要验证和回滚的范围。
- **独立扩缩容**：热点服务可以单独增加实例，不必复制整个应用。收益只有在负载差异真实存在时才成立。
- **故障隔离**：合理的超时、容量和依赖边界能够限制故障传播。仅仅分进程不会自动产生隔离能力。
- **团队自治**：一个团队可以端到端负责服务的需求、开发、发布和运行，减少跨团队交接。

## 六、复杂度成本

微服务的成本与服务数量、同步依赖数量和环境数量共同增长。平台可以摊薄重复建设，却不能消除契约兼容、数据一致性和跨团队协作等业务复杂度。

- **网络失败**：本地调用失败通常立即返回，远程调用可能超时、重复执行或只在部分节点成功。
- **数据一致性**：跨服务事务不能依赖单数据库事务自然完成，需要重新设计状态、幂等和补偿。
- **运行成本**：每个服务都需要配置、日志、监控、告警、容量、发布和安全管理。服务越小，固定运行成本占比越高。
- **认知成本**：开发者必须理解调用链、契约兼容、注册发现和故障模式，问题不再局限于当前代码仓库。

## 七、常见误解

- **一个表对应一个服务**：数据库表是存储结构，不是业务边界。按表拆分容易产生大量细粒度调用和分布式事务。
- **服务越小越好**：服务粒度取决于业务内聚、团队能力和独立变化需求。过小服务会放大网络和治理成本。
- **引入 Spring Cloud 就完成微服务改造**：框架可以提供注册、配置和调用能力，不能自动解决职责混乱、共享数据库和发布耦合。
- **微服务天然高可用**：高可用来自冗余、隔离、容量和演练。更多进程也意味着更多故障点。
