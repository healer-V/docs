# 微服务适用条件与成本

微服务是一种用分布式复杂度换取独立演进能力的架构选择。只有独立发布、扩容、隔离或团队自治的收益高于新增成本时，拆分才合理。评估不能只比较代码结构，还要覆盖开发、运行和组织全生命周期。

## 一、适用条件

- **业务边界相对稳定**：团队能够识别主要业务能力、数据所有权和协作方式，边界不会在每个需求中大幅变化。
- **存在独立变化需求**：不同业务能力具有明显不同的发布频率、团队责任或技术生命周期。
- **存在容量差异**：部分能力需要独立扩容、特殊硬件或不同资源配置，整体扩容成本明显。
- **故障隔离有价值**：非核心能力故障需要与核心交易隔离，并且组织愿意投入超时、降级和容量治理。

## 二、组织条件

- **团队能够端到端负责**：团队需要具备开发、测试、发布和运行服务的能力，而不是只完成代码后交接。
- **协作边界清晰**：服务责任与团队责任大体一致，避免一个服务由多个团队频繁共同修改。
- **有架构治理机制**：服务目录、契约评审、版本策略和技术基线能够阻止服务无序增长。

## 三、工程条件

- **自动化测试**：服务可以通过单元、接口和契约测试快速获得反馈，不依赖大型共享环境完成全部验证。
- **自动化交付**：构建、制品、配置、部署和回滚具有可重复流程，服务数量增加不会线性增加人工操作。
- **可观测性**：日志、指标和追踪能够跨服务关联，团队能发现故障影响和依赖路径。
- **安全基线**：身份、密钥、网络、依赖和审计具备统一要求，新增服务不会形成新的无管理入口。

## 四、开发成本

- **工程重复**：每个服务都需要项目结构、配置、错误处理、测试和客户端契约。平台模板可以降低但不能消除成本。
- **本地调试**：跨服务场景需要 Stub、容器或共享环境。开发者不能总是一次启动完整系统。
- **契约协调**：接口变更需要识别消费者、保持兼容并管理迁移窗口。

## 五、运行成本

- **固定资源**：每个 JVM 都有基础内存、线程、连接池和监控开销。过细拆分可能浪费大量资源。
- **基础设施**：注册中心、配置中心、网关、消息、监控和交付平台都需要高可用、升级和备份。
- **故障数量**：服务、实例和网络连接越多，可能出现的故障组合越多。自动化和演练需要同步增长。

评估成本时不能只统计服务器数量。更容易长期被忽略的是每个服务都要承担的固定工作：

| 固定工作 | 可观察指标 | 失控表现 |
|----------|------------|----------|
| 依赖与运行时升级 | 升级完成率、过期版本数量 | 大量长期无人升级的服务 |
| 发布与回滚 | 发布耗时、失败率、回滚耗时 | 发布仍依赖人工逐个操作 |
| 监控与告警 | 有效告警比例、平均发现时间 | 服务故障只能依赖用户反馈 |
| 容量与资源 | 单服务利用率、空闲资源成本 | 大量低流量 JVM 长期占用固定资源 |
| 值班与维护 | 无主服务数量、告警转派次数 | 故障时无法找到真正负责人 |

拆分方案应同时给出预期收益和新增固定成本。只描述“未来更灵活”而无法定义指标，不足以支持架构迁移。

## 六、组织成本

- **跨团队协调**：关键流程跨越多个服务时，需求排期、接口设计和故障处理都可能涉及多个团队。
- **所有权空缺**：团队调整后，服务可能失去维护者。服务目录和生命周期治理必须持续更新。
- **认知碎片化**：过度自治可能产生大量框架、协议和操作方式，平台标准需要控制无收益差异。

## 七、风险信号

- **只为技术潮流拆分**：没有可验证目标时，拆分完成后无法判断收益，也难以决定停止点。
- **共享数据库不调整**：共享写表会保留最强耦合，却增加网络和部署成本。
- **服务与团队数量不匹配**：少量团队维护大量服务，会让升级、告警和发布成为持续负担。
- **只建设框架不建设运行能力**：Eureka、Apollo 和 Feign 可以让服务连接起来，但不能替代监控、测试、容量和故障演练。

## 八、评估问题

| 维度 | 需要回答的问题 |
|------|----------------|
| 业务 | 边界是否稳定，独立变化是否频繁 |
| 团队 | 是否有明确所有者和端到端能力 |
| 发布 | 当前发布瓶颈是否由部署耦合造成 |
| 容量 | 是否存在显著不同的扩缩容需求 |
| 可靠性 | 是否具备超时、隔离、监控和演练能力 |
| 数据 | 是否能够建立明确数据所有权 |
| 成本 | 新增平台与运行成本由谁承担 |

## 九、决策输出

- **不拆分也是结论**：如果模块化单体已经满足目标，应记录保持现状的理由和复查条件。
- **限定拆分范围**：优先选择一两个边界稳定、收益明确的服务，不把“微服务改造”定义为全系统一次性重写。
- **设置停止条件**：当交付速度、故障率或成本没有达到预期时，应暂停继续拆分并复查假设。
- **设置复查时间**：架构决策需要在团队、业务或平台条件变化后重新评估，而不是永久有效。
