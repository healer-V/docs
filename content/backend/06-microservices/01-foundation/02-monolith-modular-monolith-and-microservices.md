# 单体、模块化单体与微服务

单体、模块化单体和微服务不是按代码量划分的三个等级，也不是系统必须依次获得的“架构认证”。它们是对部署边界、数据边界和协作方式的不同选择。真正的问题不是“哪种架构更先进”，而是哪种边界能够用最低的总成本支持当前业务变化。

本文使用同一条保险链路比较三种形态，并回答一个可以执行的决策问题：产品、投保、核保、保单和通知能力，什么时候应该继续留在同一个应用，什么时候才值得跨越网络边界。

## 一、先确定比较对象

架构比较必须使用相同业务范围，否则“微服务更灵活”或“单体更简单”都只是空泛结论。本文固定以下业务：

```text
查询产品
  → 提交投保申请
  → 核保
  → 创建保单
  → 发送通知
```

读者需要观察的不是目录数量，而是五类证据：

| 维度 | 需要回答的问题 |
|------|----------------|
| 部署 | 修改产品规则是否必须同时发布整个系统 |
| 数据 | 谁能修改产品、申请和保单数据，事务边界在哪里 |
| 故障 | 产品查询变慢时，哪些业务会一起受影响 |
| 交付 | 不同能力能否独立测试、发布和回滚 |
| 组织 | 一个变化需要多少团队协调，运行问题由谁负责 |

同一个系统可以在不同阶段得到不同答案。架构决策需要随业务和组织约束变化，而不是在项目创建时永久确定。

## 二、架构形态由边界决定

判断架构形态时，至少需要同时检查代码、进程、数据库和发布四个边界。

| 形态 | 部署单元 | 代码边界 | 数据写入 | 远程协作 |
|------|----------|----------|----------|----------|
| 单体 | 一个 | 可以清晰，也可以混乱 | 通常同一数据库和事务 | 非必要 |
| 模块化单体 | 一个 | 业务模块边界明确并受约束 | 可以共用实例，但写入责任分区 | 非必要 |
| 微服务 | 多个且可独立发布 | 服务内部自治，服务间只依赖契约 | 每类业务事实有唯一写入方 | HTTP、消息等网络协议 |

“一个仓库”不等于单体，“多个进程”也不等于微服务。多个应用如果必须使用固定版本一起上线、共享写表并依赖彼此内部实现，仍然是分布式单体。相反，模块化单体即使只有一个进程，也可以拥有清晰的业务边界和可验证的依赖方向。

::: tip 判断重点
微服务最关键的能力是独立演进，而不是进程数量。只有独立构建、测试、部署、回滚、数据责任和故障处理共同成立，进程拆分才产生真实收益。
:::

## 三、单体并不是错误起点

单体把全部业务能力编译并部署为一个应用。一次投保请求在同一进程中调用产品、投保和核保代码，多个模块也可能使用同一数据库事务。

```text
客户端
  → insurance-application
      ├─ 产品代码
      ├─ 投保代码
      ├─ 核保代码
      ├─ 保单代码
      └─ 通知代码
          → insurance_db
```

这种结构减少了分布式系统的固定成本：

- 方法调用不会产生网络超时和序列化问题；
- 本地事务可以直接保护跨模块数据不变量；
- 本地调试能够观察完整调用链；
- 构建、部署、配置和监控对象较少；
- 小团队可以在一个代码库中快速调整尚未稳定的业务边界。

单体的风险来自边界失控，而不是“所有代码在一个进程”。当任何模块都能调用其他模块的内部类、跨模块更新表、共享全局状态时，修改会逐渐扩散。最终每次发布都需要回归整个系统，热点能力也只能通过复制全部应用扩容。

因此，单体阶段的首要任务不是尽快拆服务，而是建立业务模块和依赖规则。没有边界的单体直接拆成多个进程，只会把原来的代码耦合转换为网络、数据和发布耦合。

## 四、模块化单体把业务边界变成可验证规则

模块化单体仍然只有一个部署单元，但代码按照业务能力组织。模块只公开稳定 API，内部实现、Repository 和实体不能被其他模块直接访问。

配套案例位于 `examples/microservices-insurance/insurance-monolith/`，核心结构如下：

```text
com.example.insurance
├─ product
│  ├─ ProductCatalog.java          # 公开接口
│  ├─ ProductView.java             # 公开只读视图
│  └─ internal
│     └─ InMemoryProductCatalog.java
└─ application
   ├─ ApplicationEligibilityService.java
   └─ ApplicationEligibilityController.java
```

投保模块只依赖产品模块公开的 `ProductCatalog`，不知道产品目录如何存储：

```java
// examples/microservices-insurance/insurance-monolith/src/main/java/
// com/example/insurance/product/ProductCatalog.java
public interface ProductCatalog {
    /**
     * 查询指定产品的投保摘要。
     *
     * @param productCode 产品编码，不能为空
     * @return 当前产品摘要
     */
    ProductView findByCode(String productCode);
}
```

模块的依赖方向不是靠约定维持，而是通过 Spring Modulith 声明和测试：

```java
// examples/microservices-insurance/insurance-monolith/src/test/java/
// com/example/insurance/ModularityTest.java
class ModularityTest {
    /** 产品模块不得反向依赖投保模块，投保模块只能使用产品公开 API。 */
    @Test
    void verifiesModuleBoundaries() {
        ApplicationModules.of(InsuranceMonolithApplication.class).verify();
    }
}
```

在示例工程目录执行：

```powershell
.\mvnw.cmd -pl insurance-monolith test
```

本文实际验证得到的核心结果为：

```text
Tests run: 2, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

这项测试证明当前代码没有模块循环，且投保模块没有访问产品模块的非公开类型。它不能证明业务边界一定正确；边界是否合理还需要用业务变化、数据所有权和团队责任验证。

## 五、微服务改变的是运行模型

把产品模块提取为 `product-service` 后，投保模块不再进行本地方法调用。调用链变为：

```text
application-service
  → 服务发现与实例选择
    → HTTP 请求
      → product-service
        → HTTP 响应或网络失败
```

这个变化带来独立部署和独立扩容，也引入了单体中不存在的状态：

| 新状态 | 单体中的表现 | 微服务中的表现 |
|--------|--------------|----------------|
| 目标位置 | 对象引用已经确定 | 需要从服务发现或 DNS 获得实例 |
| 调用耗时 | 通常是进程内执行 | 包含连接、排队、传输和序列化 |
| 部分失败 | 进程异常通常整体失败 | Consumer、网络、Provider 可以分别失败 |
| 结果未知 | 本地异常通常能判断事务结果 | Consumer 超时不代表 Provider 未提交 |
| 契约兼容 | 编译器可同时检查调用双方 | 新旧服务版本会在运行期间并存 |
| 数据一致性 | 可以使用单数据库事务 | 跨服务状态需要消息、补偿或对账 |

因此，微服务的成本不是“多写几个 Controller”。它要求团队承担契约、超时、重试、幂等、服务发现、可观测性、部署、容量和故障演练等持续成本。

::: warning 分布式单体
如果提取后的产品服务仍允许投保服务直接更新产品表，或者两个服务每次都必须同时发布，那么系统只增加了网络故障点，没有获得独立演进能力。
:::

## 六、使用约束而不是口号做选择

三种形态不存在脱离约束的固定排名。可以从下面的决策矩阵开始：

| 当前约束 | 单体 | 模块化单体 | 微服务 |
|----------|------|------------|--------|
| 业务边界仍在频繁变化 | 合适 | **优先** | 拆分后迁移成本高 |
| 团队人数少、发布节奏一致 | 合适 | **优先** | 基础设施成本通常不划算 |
| 多团队需要独立发布 | 发布协调增加 | 边界清晰但仍一起部署 | **具备直接收益** |
| 产品查询负载远高于投保写入 | 只能整体扩容 | 只能整体扩容 | **可以独立扩容** |
| 一个模块需要不同安全或合规边界 | 隔离能力有限 | 代码边界可控 | **运行隔离更明确** |
| 缺少自动化测试和可观测性 | 尚可维护 | 可以先补基础 | 拆分风险很高 |
| 大量跨模块强一致规则 | 本地事务直接 | **通常更合适** | 会引入分布式事务成本 |

决策时应比较“拆分收益”与“分布式固定成本”：

```text
净收益
  = 独立交付收益
  + 独立扩容收益
  + 故障隔离收益
  + 团队自治收益
  - 网络与一致性成本
  - 平台与运维成本
  - 契约和协作成本
```

这个表达式不是财务公式，而是评审提醒。每个收益项都应该对应实际指标，例如跨团队等待时间、发布频率、热点容量或故障影响范围；不能只写“提升可维护性”。

## 七、保险案例的合理演进顺序

假设保险系统最初由一个团队开发，产品规则、投保和保单边界仍在变化。合理起点是模块化单体：

1. 按产品、投保、核保、保单和通知组织代码；
2. 禁止模块访问其他模块的内部实现和数据访问层；
3. 为核心业务流程建立自动化测试；
4. 记录各模块的变更频率、调用关系和容量数据；
5. 当独立发布或扩容收益被证据确认后，再提取服务。

下面的变化信号可以支持首先提取产品服务：

| 观察到的事实 | 为什么支持提取产品服务 |
|--------------|--------------------------|
| 产品查询量显著高于投保写入量 | 产品能力具备独立扩容收益 |
| 产品版本和销售规则边界稳定 | 远程契约不需要频繁破坏性调整 |
| 产品发布经常被投保回归阻塞 | 独立发布能够减少等待和回归范围 |
| 投保只需产品公开摘要和版本 | 依赖可以通过少量稳定契约表达 |
| 产品数据已有唯一写入责任 | 提取后不需要长期共享写表 |

若这些事实不存在，仅仅因为“微服务项目更标准”而拆分，没有足够决策依据。

## 八、常见错误判断

| 错误判断 | 问题 | 更可靠的判断方式 |
|----------|------|------------------|
| 代码超过某个行数就拆服务 | 代码量不能表达业务内聚 | 查看变化原因、不变量和发布收益 |
| 一个数据库表对应一个服务 | 表是存储结构，不是业务能力 | 按业务结果和数据写入责任聚合 |
| 使用 Spring Cloud 就是微服务 | 框架只提供技术能力 | 检查部署、数据、故障和团队边界 |
| 微服务天然提高可用性 | 更多进程也意味着更多故障点 | 用冗余、超时、隔离和演练证明 |
| 模块化单体只是过渡方案 | 它可以长期满足大量系统 | 只有出现明确拆分收益才演进 |
| 所有服务放在一个仓库就不独立 | 仓库策略不直接决定部署边界 | 检查构建、发布和版本是否可独立 |

## 九、完成判断

学完本文后，应该能够针对一个具体系统回答：

- 当前最需要隔离的是代码变化、数据写入、发布、容量还是故障；
- 模块边界能否先在单进程中建立并自动验证；
- 服务提取后会新增哪些网络和一致性状态；
- 独立部署能够改善哪个已经被测量的问题；
- 哪些条件出现时应该暂停拆分或重新合并。

对于本文保险案例，当前结论是：先建立模块化单体，再以产品服务作为有条件的首个提取候选。下一步需要学习如何从业务流程、不变量、数据和变化证据验证这个边界，而不是直接创建新的 Spring Boot 项目。

相关机制与版本资料可参考 [Spring Modulith](https://docs.spring.io/spring-modulith/reference/) 和 [Spring Cloud](https://spring.io/projects/spring-cloud/)。
