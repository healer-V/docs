# 超时、重试与幂等

超时限制资源等待，重试尝试恢复瞬时故障，幂等防止重复执行造成额外业务结果。三者必须共同设计：没有超时会耗尽资源，没有幂等的重试可能扩大事故，没有预算的多层重试会形成重试风暴。

## 一、端到端预算

- **从入口目标开始**：如果投保接口要求 3 秒内返回，所有本地计算、产品查询、客户查询和错误处理必须共享这 3 秒预算。
- **预留上游处理时间**：不能把每个下游读取超时都设置为 3 秒。上游还需要序列化、业务处理和返回时间。
- **预算逐层递减**：下游调用获得剩余预算的一部分，重试也只能使用剩余时间。
- **记录预算耗尽**：区分下游自身超时和上游预算已经不足，便于识别调用链设计问题。

以入口目标 3 秒、产品与客户两个查询并行执行为例，预算不是把 3 秒复制给每个依赖，而是显式分配：

| 消耗项 | 示例预算 | 说明 |
|--------|----------|------|
| 网关与网络预留 | 300 ms | 覆盖入口转发和响应返回 |
| 本地校验与序列化 | 300 ms | 包含参数校验、对象转换和决策组装 |
| 远程查询窗口 | 1800 ms | 产品与客户并行共享截止时间，而不是各自串行占用 1800 ms |
| 安全余量 | 600 ms | 覆盖调度抖动、连接池等待和失败处理 |

预算值必须来自真实延迟分布和服务目标，表中数值只用于说明分配方法。若两个查询改为串行，最坏耗时会相加，此时应重新审查是否能并行、缓存或提前准备数据，而不是单纯提高入口超时。

## 二、超时类型

- **连接超时**：限制建立网络连接所需时间，常见原因包括地址不可达、端口无监听和网络策略。
- **读取超时**：连接建立后等待响应数据的时间。Provider 过载、慢查询或下游等待都会触发。
- **连接池获取超时**：客户端连接池耗尽时，等待可用连接也需要上限，否则请求在发送前就长期排队。
- **总调用超时**：部分 HTTP Client 的连接和读取超时不等于总请求预算，业务层仍需控制完整调用时长。

## 三、Feign 配置

### 1. 按客户端设置

::: details 查看 application-service 的按客户端超时配置
```yaml

# application-service/src/main/resources/application.yml
spring:
  cloud:
    openfeign:
      client:
        config:
          product-service:
            connectTimeout: 1000
            readTimeout: 2000
          customer-service:
            connectTimeout: 1000
            readTimeout: 1500
```
:::

数值单位为毫秒。示例值用于展示结构，真实值来自服务目标、延迟分布和故障演练。

- **不使用统一超时**：查询、小文件和长任务具有不同成本，应按依赖和方法分类，而不是全局设置一个很大的值。
- **Apollo 动态调整**：超时可以通过配置管理，但并非所有底层 Client 都会在属性更新后自动重建。必须验证生效方式和连接池影响。

## 四、何时重试

- **瞬时连接失败**：目标实例刚下线且还有其他健康实例时，查询请求可以在预算内切换一次。
- **明确可重试状态**：Provider 可以通过稳定错误语义表达临时过载或稍后重试，并提供合理退避提示。
- **读取超时谨慎处理**：服务端可能已经执行请求。查询通常可重试，写入必须先满足幂等或状态查询条件。
- **永久错误不重试**：参数错误、权限拒绝、产品不存在和反序列化错误不会通过重试恢复。

## 五、重试层次

- **可能存在的层次**：网关、业务代码、OpenFeign、LoadBalancer、HTTP Client 和消息系统都可能重试。
- **次数乘法**：上游重试 2 次、下游再重试 2 次，最坏可能产生 4 次甚至更多实际调用。
- **选择唯一责任层**：明确哪个层次根据业务幂等和时间预算决策，其他层默认关闭自动重试。
- **OpenFeign 默认边界**：Spring Cloud OpenFeign 默认创建 `Retryer.NEVER_RETRY`，与原生 Feign 默认行为不同。启用 Retryer 必须显式评审。

## 六、退避与抖动

- **立即重试风险**：下游过载时，大量客户端立即重试会进一步增加负载。
- **指数退避**：每次失败后增加等待时间，给依赖恢复窗口。
- **随机抖动**：为等待时间增加随机量，避免大量实例在同一时刻再次请求。
- **最大次数和时间**：退避不能突破上游预算，也不能让队列无限增长。

## 七、幂等设计

- **幂等定义**：同一业务请求执行多次，对最终业务状态产生与执行一次相同的效果。
- **幂等键**：调用方为创建类请求生成稳定请求 ID，Provider 保存请求 ID 与处理结果。
- **原子去重**：检查幂等键和写入业务结果必须位于同一事务或具备等价原子约束。
- **返回既有结果**：重复请求命中已完成记录时返回原结果，而不是简单报告“重复错误”。

Provider 可以用幂等记录表达请求处理状态，并把状态变更与业务写入放在同一原子边界内：

| 幂等记录状态 | 首次请求行为 | 重复请求行为 |
|--------------|--------------|--------------|
| 不存在 | 原子创建 `PROCESSING` 记录并开始处理 | 只有一个请求能够创建成功 |
| `PROCESSING` | 继续当前处理 | 返回处理中或要求稍后查询，不并发执行第二次 |
| `SUCCEEDED` | 返回业务结果并保存摘要 | 返回同一业务标识和结果 |
| `FAILED_RETRYABLE` | 按业务规则允许重新处理 | 由明确状态迁移触发，不由网络层盲目重试 |
| `FAILED_FINAL` | 返回最终失败 | 重复请求返回相同失败语义 |

幂等键需要绑定调用方和业务操作，防止不同用户或不同类型请求误用同一键。去重记录也要设置符合业务审计要求的保留周期，不能在原请求仍可能重试时提前删除。

## 八、结果未知

- **超时场景**：Consumer 发送创建请求后超时，无法判断 Provider 是否已经提交。
- **状态查询**：使用请求 ID 查询处理状态，比直接重新创建更安全。
- **补偿不是重试**：业务已经产生副作用时，需要执行明确补偿流程，不能把相反操作当作网络重试。
- **用户表达**：对结果未知状态返回“处理中”或可查询标识，不虚假显示失败后诱导用户重复提交。

## 九、重试指标

- **原始请求与尝试次数**：分别统计业务请求数量和实际远程尝试次数，才能发现重试放大。
- **按原因分类**：连接失败、超时、5xx 和限流分别统计，避免所有异常合并。
- **恢复收益**：记录多少重试最终成功、增加了多少延迟和下游负载。
- **幂等冲突**：监控重复请求、处理中冲突和结果不一致，发现客户端或去重实现问题。

## 十、检查清单

### 1. 超时

- 是否设置连接、读取和池获取超时；
- 下游总预算是否小于上游目标；
- 超时值是否经过负载与故障测试。

### 2. 重试

- 是否只有一个明确重试层；
- 是否只重试可恢复错误；
- 是否使用退避、抖动和最大次数。

### 3. 幂等

- 写操作是否具有稳定幂等键；
- 去重与业务写入是否原子；
- 超时后是否能够查询结果。
