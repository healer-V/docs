# 微服务通信模型

服务通信方式决定运行时依赖、故障传播和数据一致性。同步调用适合立即获得结果，异步消息适合解耦时间和削峰，但没有一种方式适合全部场景。选择前应先明确业务需要什么结果、多久需要以及失败如何恢复。

## 一、通信维度

- **时间耦合**：同步调用要求调用方和被调用方在同一时间可用；异步消息允许双方在不同时间处理。
- **空间耦合**：调用方是否需要知道具体服务身份、地址或主题。服务发现降低地址耦合，不能消除契约耦合。
- **契约耦合**：双方需要共同理解请求、响应、事件和错误语义。JSON 并不会自动让契约松耦合。
- **数据时效**：有些场景需要实时结果，有些场景允许秒级或分钟级最终一致。时效目标决定可选方案。

## 二、同步请求响应

### 1. 基本流程

```text
Consumer → 发送请求 → Provider
Consumer ← 返回响应 ← Provider
```

### 2. 适用场景

- 后续业务必须立即使用结果；
- 操作耗时可预测；
- Provider 可用性满足上游目标；
- 失败能够在当前请求中明确处理。

- **主要成本**：下游延迟和故障会进入上游请求路径，串行依赖越多，尾延迟和失败概率越高。

## 三、异步命令

- **基本语义**：调用方提交需要执行的动作，不等待最终业务结果。接收方稍后处理并记录状态。
- **适用场景**：耗时任务、削峰和允许后台完成的流程，例如生成文档或发送通知。
- **必须补充的能力**：命令 ID、幂等、状态查询、失败重试和死信处理不能因为“异步”而省略。

## 四、领域事件

- **表达已发生事实**：事件使用过去式语义，例如“投保申请已受理”，发布方不指定哪个服务必须执行什么动作。
- **多消费者**：多个服务可以独立订阅，但事件 Schema 和业务语义仍需要版本治理。
- **最终一致**：消费者处理存在延迟和失败，业务必须定义中间状态、收敛时间和补偿方式。

## 五、RPC 的含义

- **调用语义**：RPC 让调用方以调用接口或方法的方式发起远程请求。它描述编程模型，不限定底层一定是二进制协议。
- **HTTP RPC**：Feign 使用 Java 接口生成 HTTP 客户端代理，常用 JSON 传输。公司 Catfish RPC 基于 Feign 改造，也属于声明式 HTTP RPC 方向。
- **二进制 RPC**：gRPC 通常使用 HTTP/2 与 Protocol Buffers，具有强 Schema 和流式能力，但与 Feign 的调用链和治理方式不同。
- **远程调用不是本地调用**：即使代码看起来像接口方法，仍必须处理序列化、网络、超时、部分失败和版本兼容。

## 六、数据交换

- **在线 API**：适合小规模、低延迟查询和命令，不应返回无界集合或大型文件。
- **批量文件**：大批量历史数据可以通过对象存储和清单交换，避免长时间占用在线 API。
- **数据同步**：变更数据捕获和事件投影用于构建本地读模型，需要监控延迟、重复和顺序。
- **共享数据库不是通信协议**：服务直接读写对方表会绕过业务契约，形成最强数据耦合。

## 七、组合方式

- **查询同步、后续异步**：提交投保前同步查询产品和客户资格，受理后的通知与分析可以异步处理。
- **命令同步确认、结果异步完成**：接口立即返回任务 ID，客户端稍后查询或接收结果事件。
- **读模型预计算**：对频繁聚合查询，使用事件构建本地投影，避免每次请求同步调用大量服务。

一个完整业务流程通常同时使用多种通信方式。以提交投保申请为例：

| 步骤 | 通信方式 | 选择理由 | 失败处理 |
|------|----------|----------|----------|
| 查询产品是否在售 | 同步查询 | 当前请求必须立即决定是否继续 | 超时后返回依赖不可用，不假装产品不可售 |
| 查询客户准入资格 | 同步查询或本地投影 | 取决于资格结果的实时性要求 | 明确数据时间，禁止静默使用无限期旧数据 |
| 受理投保申请 | 同步命令 | 需要立即返回申请标识和受理结果 | 使用幂等键避免超时重提产生重复申请 |
| 发送通知 | 异步命令 | 不应阻塞核心受理结果 | 重试、死信和人工补偿 |
| 生成分析数据 | 领域事件 | 多个消费者独立使用已发生事实 | 监控积压、重复和投影延迟 |

选择通信方式的起点是业务时效和失败语义，而不是团队已经部署了哪种中间件。同一流程中强制统一为全部同步或全部异步，通常都会制造不必要耦合。

## 八、选择问题

| 问题 | 倾向同步 | 倾向异步 |
|------|----------|----------|
| 是否立即需要结果 | 是 | 否 |
| 是否允许稍后完成 | 否 | 是 |
| 下游是否必须同时在线 | 是 | 否 |
| 是否需要天然削峰 | 弱 | 强 |
| 失败是否在当前请求处理 | 是 | 否，需要状态与补偿 |

## 九、常见误区

- **异步一定更可靠**：消息系统能够保存请求，但重复、乱序、积压和毒消息会引入新的失败模式。
- **RPC 一定比 REST 快**：RPC 是调用风格，性能取决于协议、序列化、连接、负载和实现。Feign RPC 通常仍是 HTTP 调用。
- **统一协议即可消除耦合**：真正的耦合来自业务语义、调用时序和数据所有权，不只来自编码格式。
- **所有内部调用都同步**：过长同步链路会放大尾延迟和故障传播，应逐项判断是否需要立即结果。
