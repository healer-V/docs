# 服务版本与兼容性治理

微服务独立发布意味着系统长期处于多版本共存状态。版本治理的核心不是给 URL 加 `/v2`，而是让 Provider、Consumer、数据和配置在迁移窗口内保持可协作，并能够确认旧版本何时可以安全删除。

## 一、版本维度

- **应用版本**：表示某次服务构建制品，用于发布、回滚和问题定位。
- **接口版本**：表示请求、响应、错误和行为契约。接口可以在不改变 URL 的情况下保持兼容演进。
- **实例版本**：Eureka 中同时运行的实例可能来自不同应用版本，发布系统需要识别其流量与健康。
- **配置版本**：Apollo Release 决定实例使用的运行配置。应用版本相同但配置不同，行为也可能不同。
- **数据版本**：数据库结构、事件 Schema 和业务记录也具有版本，必须与应用滚动升级兼容。

## 二、兼容方向

- **新 Provider 兼容旧 Consumer**：滚动发布 Provider 时，旧消费者仍在运行，新实现不能立即删除旧字段和旧行为。
- **新 Consumer 兼容旧 Provider**：消费者先发布时，可能调用尚未升级的 Provider，不能假设新字段和新接口已经全量可用。
- **双向兼容窗口**：发布顺序不确定或回滚要求高时，需要一段新旧双向兼容期。

## 三、兼容变更

- **增加可选字段**：通常比删除或重命名字段安全，但消费者需要忽略未知字段，Provider 需要处理字段缺失。
- **扩展枚举**：新增枚举值可能让旧消费者反序列化或 Switch 失败，不应把枚举扩展自动视为兼容。
- **放宽输入**：接受更多输入通常兼容，但业务规则改变仍需确认错误语义和安全边界。
- **保持错误契约**：错误码、HTTP 状态和可重试语义是契约的一部分，不能只关注成功 DTO。

## 四、破坏性变更

- **删除字段或接口**：必须先证明没有消费者使用，并经过弃用和迁移窗口。
- **改变字段含义**：名称不变但单位、时区或业务语义变化属于高风险破坏性变更。
- **改变默认行为**：同一请求返回不同结果可能破坏消费者，即使 JSON 结构完全不变。

## 五、展开与收缩

- **展开阶段**：Provider 同时支持旧契约和新契约，数据结构先增加兼容能力。
- **迁移阶段**：逐个升级 Consumer，监控旧契约调用量，并处理未迁移调用方。
- **收缩阶段**：确认旧调用量归零并超过回滚窗口后，删除旧接口、字段和兼容代码。
- **不跳过观察**：代码搜索不能发现所有外部消费者，需要网关、服务端日志或契约登记提供运行证据。

## 六、Eureka 元数据

### 1. 记录实例版本

```yaml

# product-service/src/main/resources/application.yml
eureka:
  instance:
    metadata-map:
      api-version: v1
      release: stable
```

- **元数据不是协议协商本身**：消费者还需要明确选择规则、无匹配实例行为和回退策略。
- **避免随意分组**：版本标签长期并存会分裂容量和监控。完成迁移后应清理旧分组。

## 七、Consumer 清单

- **记录依赖关系**：服务目录应记录接口消费者、负责人、版本和使用场景。
- **运行证据**：通过接口指标、日志和追踪确认实际调用，避免只依赖人工登记。
- **外部消费者**：无法统一升级的外部客户端需要更长兼容周期、明确弃用公告和版本策略。

## 八、滚动升级

- **先验证混合版本**：测试环境需要同时运行新旧 Provider 和 Consumer，验证四种组合。
- **观察实例维度**：错误率和延迟按服务版本区分，避免全局平均值掩盖新版本问题。
- **保持回滚能力**：新版本写入的数据必须允许旧版本继续读取，至少覆盖预期回滚窗口。

混合版本测试至少覆盖以下四种组合，失败时能够判断问题位于 Provider 兼容性还是 Consumer 假设：

| Consumer | Provider | 验证重点 |
|----------|----------|----------|
| 旧版本 | 旧版本 | 建立升级前业务基线 |
| 旧版本 | 新版本 | 新 Provider 是否仍满足旧请求、字段和错误契约 |
| 新版本 | 旧版本 | 新 Consumer 是否处理字段缺失和旧错误行为 |
| 新版本 | 新版本 | 新能力是否正确，且没有破坏共同路径 |

如果数据库或事件 Schema 同时变化，还要把旧应用读取新数据、新应用读取旧数据纳入矩阵。只测试最终全新组合无法证明滚动发布和回滚安全。

## 九、URL 版本策略

- **何时使用新版本**：无法通过兼容扩展表达的重大语义变化，可以建立明确的新接口版本。
- **不为每次变更增加版本**：频繁创建版本会让 Provider 和消费者长期维护大量重复代码。
- **明确下线条件**：每个旧版本需要负责人、消费者清单、截止时间和下线验证。

## 十、治理清单

### 1. 设计

- 成功和失败契约是否兼容；
- 新旧版本能否双向协作；
- 数据和配置是否支持回滚。

### 2. 发布

- 是否按版本观察指标；
- 是否记录 Consumer 迁移状态；
- 是否定义停止与回滚条件。

### 3. 清理

- 旧调用量是否归零；
- 兼容层和灰度元数据是否删除；
- 文档和契约是否只保留有效版本。
