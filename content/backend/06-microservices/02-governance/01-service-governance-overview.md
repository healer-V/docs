# 服务治理概述

服务治理用于管理大量动态服务实例的身份、位置、配置、健康和流量。它不是一个单独产品，而是一组贯穿实例生命周期的能力。Eureka、Apollo、Actuator 和 LoadBalancer 分别解决其中一部分问题，需要组合成闭环。

## 一、治理问题来源

- **实例地址动态变化**：扩缩容、发布和故障恢复会不断改变实例 IP 与端口，调用方不能维护静态地址清单。
- **配置跨环境变化**：同一制品在开发、测试和生产使用不同参数。配置还需要审计、灰度和回滚。
- **实例状态持续变化**：进程存在不代表能够接收业务流量。启动、就绪、停机和依赖异常需要不同状态表达。
- **多版本同时存在**：滚动发布期间，新旧实例和消费者会同时运行，路由与接口必须保持兼容。

## 二、控制面与数据面

- **控制面**：控制面管理期望状态和元数据，例如注册表、配置、路由规则和发布策略。Eureka Server 与 Apollo 属于控制面组件。
- **数据面**：数据面处理真实业务请求，例如投保服务调用产品服务。OpenFeign、HTTP 客户端和服务实例位于数据路径。
- **故障关系**：控制面短暂不可用时，数据面应尽量依靠缓存继续处理已有流量，但新增实例、实例剔除和配置发布可能受影响。

## 三、服务身份

- **服务名**：`spring.application.name` 表示逻辑服务身份，例如 `product-service`。调用方应依赖服务名，不依赖具体实例地址。
- **实例标识**：同一服务的多个进程需要唯一实例标识，通常由服务名、主机、端口或平台实例 ID 组成。
- **元数据**：版本、区域和灰度标签可以附加到实例，但元数据键需要组织规范，不能由每个服务任意解释。

## 四、实例生命周期

- **启动**：应用完成必要初始化后注册到 Eureka。尚未准备好处理流量时不应过早暴露可用状态。
- **续约**：实例周期性发送心跳维持租约。注册中心根据租约判断实例是否仍然存在。
- **服务**：调用方从本地注册表缓存选择实例，并在请求时应用负载均衡和超时策略。
- **下线**：计划停机应先停止接收新流量，再等待在途请求完成并注销。异常退出则依赖租约到期和故障检测。

## 五、核心治理能力

| 能力 | 核心问题 | 主线组件 |
|------|----------|----------|
| 注册发现 | 服务实例在哪里 | Eureka |
| 健康管理 | 实例能否接收流量 | Actuator、Eureka |
| 配置管理 | 服务使用什么参数 | Apollo |
| 负载均衡 | 本次请求选择哪个实例 | Spring Cloud LoadBalancer |
| 版本治理 | 新旧契约如何共存 | 接口兼容、实例元数据 |
| 灰度发布 | 新版本先接收哪些流量 | 元数据、路由和配置策略 |

## 六、治理闭环

- **状态采集**：服务注册身份、上报健康、暴露指标，并从配置中心读取运行参数。
- **决策**：注册中心、发布系统和负载均衡根据实例状态、版本和策略确定可用目标。
- **执行**：客户端选择实例并发送请求，配置监听器应用受控变更，发布系统调整流量。
- **反馈**：错误率、延迟和业务指标反馈决策效果，异常时停止灰度或回滚。

治理闭环必须落到一次可追踪的状态变化中。以产品服务滚动发布为例，各组件应提供相互对得上的证据：

| 阶段 | 控制面变化 | 数据面行为 | 验证证据 |
|------|------------|------------|----------|
| 新实例启动 | Eureka 出现新实例，Apollo 提供目标配置 | 新实例尚未就绪，不接收正式流量 | 启动日志、健康状态、注册时间 |
| 实例就绪 | 发布平台允许接流，注册信息进入消费者缓存 | LoadBalancer 开始选择新实例 | 实例维度请求量和版本标签 |
| 灰度观察 | 路由或配置规则逐步扩大范围 | 新旧实例共同处理请求 | 业务成功率、错误率和尾延迟对比 |
| 旧实例下线 | 停止接流、注销并结束租约 | Consumer 不再选择旧实例 | 旧实例调用量归零、在途请求完成 |

如果只能看到“部署成功”，却无法证明消费者何时发现实例、何时开始接流以及旧实例何时退出，就还没有形成治理闭环。

## 七、治理不解决什么

- **不解决错误边界**：注册中心能够连接两个服务，不能让不合理的服务拆分变得正确。
- **不保证数据一致**：配置和路由组件不提供跨服务业务事务。状态一致性需要单独设计。
- **不自动提供高可用**：组件本身也需要容量、高可用、监控和备份。引入治理平台会增加新的运行依赖。
- **不替代调用可靠性**：即使注册表只返回健康实例，网络和服务仍可能在请求期间失败，调用方仍需超时和错误处理。

## 八、治理设计原则

- **先定义失败行为**：明确 Eureka、Apollo 或下游服务不可用时，应用是继续、拒绝启动还是降级。
- **默认配置可运行**：本地开发和测试应有确定性配置，不依赖生产控制面才能执行基础测试。
- **变更可观察可回退**：配置、版本和流量变更都需要审计、指标和明确回滚步骤。
- **元数据标准化**：服务名、环境、区域、版本和灰度标签使用统一命名与取值。

## 九、本章路径

- **实例治理**：先学习 Eureka 架构、注册发现、健康检查和客户端负载均衡。
- **配置治理**：再学习 Apollo 的模型、Spring Boot 接入和动态变更边界。
- **发布治理**：最后处理版本兼容、灰度路由和故障演练，形成完整治理检查表。
