# Apollo 架构与配置模型

Apollo 用于集中管理应用配置，支持环境隔离、配置发布、审计、灰度和客户端实时更新。配置中心解决的是运行参数治理，不应保存业务主数据，也不能把任意代码行为都转化为动态开关。

## 一、核心组件

- **Portal**：Portal 提供配置编辑、发布、权限、审计和回滚界面。它属于管理入口，不在业务请求数据路径上。
- **Admin Service**：Admin Service 处理配置修改和发布等管理操作，连接配置数据库。
- **Config Service**：Config Service 向客户端提供已发布配置和变更通知。业务应用运行时主要与它交互。
- **Client**：Apollo Client 获取配置、保存本地缓存、监听变更并向 Spring Environment 注入属性。

## 二、配置维度

- **AppId**：AppId 标识应用。一个服务应使用稳定且唯一的 AppId，不能随实例变化。
- **Environment**：环境用于隔离开发、测试和生产配置。生产应用不能回退读取测试环境。
- **Cluster**：集群允许同一应用在不同机房、区域或部署组使用差异配置。默认集群之外的命名需要组织规范。
- **Namespace**：Namespace 按用途组织配置，例如 `application`、`insurance.rules` 和公共基础配置。Namespace 过多会增加优先级和权限复杂度。

## 三、配置类型

- **应用私有配置**：只由当前 AppId 使用，例如产品查询超时和本地缓存容量。
- **公共配置**：多个应用共享的基础属性可以进入公共 Namespace，但服务必须评估公共配置变更的影响范围。
- **关联配置**：应用通过关联使用公共 Namespace。关联不等于复制，公共配置发布可能影响全部关联应用。
- **文件型配置**：YAML、JSON 等文件型 Namespace 适合结构化内容，但整文件变更、差异审查和局部更新需要额外谨慎。

## 四、配置发布流程

- **编辑**：配置修改先形成未发布草稿，不应立即影响运行实例。
- **审核**：高风险配置需要审批或双人复核，确认范围、边界和回滚值。
- **发布**：发布生成新的 Release，Config Service 向客户端提供已发布值。
- **观察**：发布后观察客户端同步、业务指标和错误日志，不能只看 Portal 显示成功。
- **回滚**：回滚恢复历史配置值，但应用状态和已经触发的业务操作不会自动恢复。

## 五、客户端更新机制

- **首次获取**：应用启动时根据 AppId、环境、集群和 Namespace 获取配置。
- **变更通知**：客户端通过通知机制感知 Release 变化，再获取最新配置内容。
- **本地缓存**：客户端把配置保存到本地。当 Config Service 短暂不可用时，可以使用最近成功配置继续启动或运行，具体行为需按客户端版本和缓存状态验证。
- **实例收敛**：配置发布不是跨全部实例的瞬时事务。短时间内新旧值可能共存，业务设计必须允许过渡。

一次配置修改需要区分“编辑内容”和“线上生效版本”，两者之间存在明确发布边界：

| 状态 | 是否影响运行实例 | 主要控制点 |
|------|------------------|------------|
| 编辑但未发布 | 否 | 权限、格式校验、变更原因 |
| 创建 Release | 开始影响目标范围 | 发布人、环境、集群、Namespace、灰度规则 |
| 客户端接收新值 | 仅影响已收敛实例 | 监听耗时、值校验、实例维度配置版本 |
| 回滚 Release | 恢复到选定历史版本 | 回滚范围、业务数据影响、实例收敛状态 |

配置回滚只能改变后续运行参数，不能撤销已经发送的消息、写入的数据或调用的外部系统。动态配置涉及不可逆业务动作时，必须另行设计补偿和停止条件。

## 六、配置优先级

- **来源不止 Apollo**：Spring 应用还可能读取命令行、系统属性、环境变量和本地配置文件。
- **优先级必须可解释**：团队需要明确哪些属性允许由 Apollo 覆盖，以及紧急环境变量是否拥有更高优先级。
- **避免同名多处维护**：同一属性同时存在于多个 Namespace 和本地文件会增加排查难度，应确定唯一常规来源。

## 七、动态配置边界

- **适合动态变更**：功能开关、受控阈值和非结构性超时可以在验证后动态更新。
- **不适合动态变更**：线程模型、数据库结构、Bean 拓扑和需要重新初始化的大型资源不应假设修改属性后自动安全生效。
- **监听器需要幂等**：配置监听可能重复触发，处理逻辑应快速、幂等且不阻塞 Apollo 通知线程。

## 八、高可用与故障

- **Config Service 多实例**：客户端应能够发现多个 Config Service 实例，避免单节点故障阻止配置获取。
- **Portal 故障**：Portal 不可用会影响管理操作，但已发布配置和业务请求不应因此中断。
- **数据库故障**：管理和发布可能受阻，客户端通常继续使用已发布配置与缓存。需要分别监控控制面和客户端状态。
- **缓存缺失**：新实例首次启动且无法连接 Config Service 时可能没有可用配置，必须定义拒绝启动还是使用安全默认值。

## 九、安全与审计

- **权限最小化**：按应用、Namespace 和环境控制编辑与发布权限，生产权限不应与开发环境完全相同。
- **敏感配置**：密码和密钥需要结合密钥管理、加密和访问控制。配置中心不是自动安全的明文仓库。
- **发布审计**：记录操作人、时间、变更内容、原因和发布范围，关键变更关联工单或发布记录。
- **客户端日志脱敏**：应用不能在启动和变更日志中输出敏感配置值。

## 十、模型检查

| 项目 | 检查内容 |
|------|----------|
| AppId | 是否稳定、唯一并有负责人 |
| 环境 | 是否严格隔离且地址正确 |
| Namespace | 职责和优先级是否明确 |
| 发布 | 是否有审核、观察和回滚 |
| 客户端 | 是否有缓存、同步和失败监控 |
| 安全 | 是否最小权限、脱敏和审计 |
