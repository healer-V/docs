# 工具契约

工具契约是应用与工具实现之间共同遵守的约定：允许传入什么、返回什么、会改变什么，以及失败后如何判断执行结果。模型看到的函数名称、描述和 JSON Schema 只是契约的一部分；权限、超时、幂等和结果核对还需要由应用执行。

虚构客服任务 `CASE-1042` 涉及订单 `ORD-2048`。查询订单状态、读取工单备注和创建退款提议具有不同的风险，不能只用同一个“调用成功”标记解释所有结果。退款提议仅产生待审批记录，不执行退款或付款。

## 一、契约的两个视图

### 1. 模型可见的工具描述

模型需要知道工具的用途、适用条件和输入格式，才能提出合适动作。JSON Schema 是描述 JSON 数据结构的规则，例如字段类型、必填字段、枚举和额外字段限制。

`get_order_status` 的模型描述可以采用以下函数工具定义。它是提供给 Responses API 的配置对象，没有包含网络请求或执行器，因此不能单独运行。

::: details 查看订单查询函数工具定义

```json
{
  "type": "function",
  "name": "get_order_status",
  "description": "查询已提供订单号的状态，只读，不修改订单或发送通知。",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "pattern": "^ORD-[0-9]{4}$"
      }
    },
    "required": ["order_id"],
    "additionalProperties": false
  },
  "strict": true
}
```

:::

`strict` 用于约束支持该模式的模型输出结构。即使生成的参数符合 Schema，订单也可能不存在、属于其他租户，或者当前用户没有读取权限。应用必须再次验证这些业务条件。

### 2. 应用持有的执行策略

应用维护名称到实现的明确映射，并在映射中配置授权、超时和结果规则。下表是应用自己的执行元数据，不应把这些字段直接添加到 API 的函数工具对象中。

| 元数据 | 订单查询的约定 | 作用 |
|--------|----------------|------|
| 工具名称 | `get_order_status` | 精确匹配注册实现 |
| 契约版本 | `1` | 标识当前输入、输出和行为约定 |
| 副作用 | 只读 | 不改变订单状态，不发送通知 |
| 授权范围 | 当前身份可读取的订单集合 | 限制对象访问 |
| 超时预算 | 演示执行器中为 0.2 秒 | 限制协作式本地调用等待时间 |
| 公开错误 | 参数错误、无权限、未找到、超时 | 为运行器提供稳定决策依据 |
| 结果规则 | 订单号、状态、来源与观察时间有效 | 防止错对象或不完整结果进入证据 |

真实超时预算应根据服务延迟和任务总时限确定。表中的 0.2 秒只用于本地演示，不是订单服务的通用配置建议。

::: warning 描述不产生执行权限
工具描述中写“只读”或“仅管理员使用”，不会自动约束函数实现。执行器必须绑定可信身份、检查对象范围，并保证实现没有隐藏的写操作。
:::

## 二、输入与副作用

### 1. 三种工具的边界

工具应保持职责足够小，让运行器可以判断调用是否完成了明确动作。读取状态与提交业务动作分开，有助于针对副作用设置不同恢复策略。

| 工具 | 模型提供的业务参数 | 成功结果 | 副作用与授权 |
|------|--------------------|----------|--------------|
| `get_order_status` | `order_id` | 状态、观察时间、来源 | 只读；检查订单读取范围 |
| `read_case_note` | `case_id` | 工单备注、观察时间、来源 | 只读；检查工单读取范围，备注仍是不可信内容 |
| `propose_refund` | `case_id`、`order_id`、`amount_cents` | 提议 ID、金额、待审批状态 | 创建提议；检查工单与订单关系、金额约束，保留业务幂等记录 |

`amount_cents` 是以分为单位的整数。例如 `1200` 表示 `12.00` 元，不能把浮点数 `12.00` 当作同一个输入。创建提议与实际退款属于两个不同动作，返回 `pending_approval` 不代表款项已退回。

### 2. 参数与可信上下文

模型可以提出订单号和提议金额。租户、当前身份、授权范围及业务操作键由应用提供；即使用户在消息里声称自己是管理员，也不能直接进入可信上下文。

模型参数应做以下检查，且次序先于执行：

1. 限制参数大小并解析 JSON 对象；
2. 检查允许字段、必填字段和实际类型；
3. 检查标识格式及数值范围；
4. 将业务对象与当前身份的可见范围绑定；
5. 对写操作复核业务关系与动作条件。

::: tip Python 整数校验要区分布尔值
Python 中 `bool` 是 `int` 的子类。金额字段若要求严格整数，应使用 `type(value) is int` 或明确排除布尔值，否则 `true` 可能被当作 1 分。类型校验之后仍需检查金额范围。
:::

允许额外字段的接口容易出现含义不明的参数。例如 `approved=true` 既不应被静默采用，也不应覆盖应用审批记录。契约不支持的字段应被拒绝，避免工具升级前后改变含义。

## 三、输出与错误

### 1. 成功结果

工具结果需要包含可验证的业务事实。可以使用统一外层结构表达成功与执行元数据，同时为每个工具定义独立的 `data` 结构。

以下是订单查询的成功结果示意，标识和时间均为演示数据：

::: details 查看订单查询成功结果

```json
{
  "ok": true,
  "data": {
    "order_id": "ORD-2048",
    "status": "in_transit",
    "updated_at": "2026-09-29T02:00:00+00:00",
    "source": "orders-memory"
  },
  "error": null,
  "meta": {
    "tool": "get_order_status",
    "contract_version": 1,
    "execution_id": "call_1"
  }
}
```

:::

`execution_id` 关联本次工具调用，`source` 表示应用读取的来源。一个 JSON 字段声称自己来自订单库，并不能证明真实性；运行器还应确认响应确实来自注册实现，并在需要时回查可信业务存储。

### 2. 错误结果与执行状态

错误应同时说明稳定原因和执行状态。`retryable` 表示错误是否具有临时性，运行器仍需结合副作用、剩余预算和执行记录决定是否重试。

| `outcome` | 含义 | 常见场景 |
|-----------|------|----------|
| `not_started` | 执行前已拒绝 | 未知工具、参数错误、无权限 |
| `unknown` | 已进入执行，当前无法确认最终结果 | 超时、通信中断、返回格式损坏 |
| `confirmed` | 当前尝试的业务结果已经明确 | 只读查询确认订单不存在，或业务服务明确拒绝动作 |

以下是超时错误示意。它没有声称后端一定未执行：

::: details 查看超时错误结果

```json
{
  "ok": false,
  "data": null,
  "error": {
    "code": "tool_timeout",
    "retryable": true,
    "outcome": "unknown"
  },
  "meta": {
    "tool": "get_order_status",
    "contract_version": 1,
    "execution_id": "call_2"
  }
}
```

:::

业务错误还可能包含已经执行的部分结果。例如批量操作部分成功时，应另行定义逐项状态，不能用一个 `confirmed` 替代详细结果。本章示例只处理单对象工具。

### 3. 敏感信息

公开结果只保留模型完成任务所需字段。底层异常中的连接字符串、请求头、内部地址和客户原文不应直接成为工具错误文本。

运行轨迹可以记录工具名、契约版本、调用 ID、耗时及稳定原因码。需要内部排查时，用关联标识查受控日志，并分别设置访问权限和保留时间。工具输出中的文本也应继续按数据处理，不能借备注中的指令修改运行器权限。

## 四、超时、幂等与版本

### 1. 时间限制与取消

超时是等待边界，取消是停止工作的请求。协作式协程可以在等待点响应取消；阻塞函数、外部服务或已经提交的动作，不一定随本地任务取消而停止。

对于有副作用的工具，运行器应保留业务操作键和当前执行状态。响应丢失后优先查询既有操作，只有明确满足重放条件时才再次提交。简单地把所有超时转换成“未执行”会造成重复动作。

### 2. 调用 ID 与业务操作键

`call_id` 用于把模型调用项与本次结果对应起来。业务操作键用于识别同一个逻辑动作的重复提交，两者的生命周期不同。

| 标识 | 一次重试中的变化 | 主要用途 |
|------|------------------|----------|
| 模型 `call_id` | 可能变化 | 工具协议关联 |
| 运行 ID | 恢复策略下可能变化 | 追踪一次 Agent 运行 |
| 业务操作键 | 同一个逻辑动作应保持稳定 | 防止重复副作用并查询执行结果 |

同一操作键必须绑定规范化参数和契约版本。同一个键却换了金额，应返回冲突，而不是复用旧结果或再创建新提议。

### 3. 契约升级

契约版本至少关联输入规则、输出结构、副作用及错误语义。把“创建待审批提议”改成“立即退款”属于行为变更，即使输入字段没有变化，也不能作为兼容升级发布。

旧任务恢复时，应检查它使用的工具与契约版本是否仍可执行。无法保持兼容时，暂停任务并迁移或重新确认业务动作。单工具版本在这里明确；整套 Agent 配置与发布恢复需要结合状态存储制定策略。

## 五、契约检查

以 `propose_refund` 为例，只有下列问题都有明确答案，才具备可实施契约：

| 判断项 | 当前约定 | 缺失时的风险 |
|--------|----------|--------------|
| 动作是什么 | 创建待审批提议 | 模型与实现对完成含义不一致 |
| 参数单位是什么 | 正整数分；演示货币为 CNY | 金额被错误解释 |
| 谁能访问对象 | 应用绑定租户、工单与订单 | 跨对象越权 |
| 重复如何识别 | 业务操作键与参数摘要 | 重复创建记录 |
| 响应丢失如何判断 | 查询可信执行记录 | 把未知结果误当失败重做 |
| 成功如何核对 | 比较持久记录的对象、金额、状态与时间 | 接受错对象、伪造或陈旧结果 |
| 版本如何变化 | 保留契约版本并拒绝不兼容重放 | 旧任务触发新行为 |

工具契约先定义可观察的行为，执行器再将这些约定落实为校验和状态。函数能够被调用，只证明入口连通；完整契约还需要约束业务含义和失败后的处理。
