# Agent 与工作流

Agent 是一种由应用持续控制的执行方式：模型根据目标和已有观察选择动作，应用检查并执行允许的动作，再把结果交给模型判断是否继续。这里的“动作”通常是查询、读取或提交提议等工具调用；模型输出动作建议，真正的执行权仍在应用中。

确定性工作流由代码预先规定步骤和转移规则。工作流可以调用模型进行分类、提取或生成，但模型不会因此自动获得选择任意执行路径的权力。**区分两者的关键是下一步由谁决定，以及这种选择受到哪些限制。**

## 一、三种执行方式

### 1. 单次模型调用

单次调用把已经准备好的输入交给模型，取得一次结果后结束。例如，应用已经读取工单 `CASE-1042` 的全部文字，只需要提取其中的订单号和问题类型。输入足够、输出可校验时，不需要维护工具循环。

模型给出的订单号仍需核对格式及来源。单次调用减少了运行状态和调用次数，但不会自动解决事实错误、输出格式或敏感数据问题。

下面的局部过程表示一次提取任务，不是可执行程序：

```text
应用读取已授权的工单文字
→ 模型提取订单号和问题类型
→ 应用校验字段及来源
→ 返回结构化结果或提取失败
```

### 2. 确定性工作流

如果业务规则已经规定“读取工单、查询订单、核对配送承诺、生成摘要”，应用可以固定执行这条流程。查询失败就按规则返回资料不足，订单号缺失就请求补充，模型只负责其中明确的提取或表达任务。

确定性不等于每一步都没有分支，也不等于模型结果完全可重复。代码仍可以依据条件分支、重试或并行；确定的是分支规则和允许的路径，而不是生成文本逐字相同。

| 条件 | 代码规定的动作 | 可检查的结果 |
|------|----------------|--------------|
| 工单包含唯一有效订单号 | 查询对应订单 | 工单与查询对象一致 |
| 工单没有订单号 | 请求用户补充 | 不猜测订单 |
| 查询成功 | 使用状态和更新时间生成摘要 | 摘要受查询证据约束 |
| 查询失败 | 返回查询失败并保留原因码 | 不把失败改写成订单状态 |

流程适合步骤稳定、规则明确、结果容易分解验收的任务。它的主要成本是需要预先设计分支；遗漏的业务情况必须通过规则修订解决。

### 3. Agent

假设工单只说“物流已经两天没有变化，备注中又写了更换收件时间”。应用允许模型选择先查订单还是先读备注，再依据观察决定是否需要补充另一项证据。执行路径会随任务内容和工具结果改变，这才体现 Agent 的动态选择能力。

应用仍应限定可查询的订单、可使用的工具、最大步数和结束条件。模型能够建议“退款”不表示拥有退款权限；只读调查 Agent 应返回调查结果或待确认提议。

::: warning 工具调用本身不能证明存在 Agent
模型返回一次函数调用、应用执行后直接返回结果，只能证明完成了工具调用协议。如果应用预先固定所有步骤，也仍是工作流。Agent 的特征是模型依据反馈参与下一步选择，而应用对整个循环保持控制。
:::

## 二、客服工单的选择依据

### 1. 先检查任务是否需要动态路径

任务描述宽泛并不意味着一定需要 Agent。先列出任务所需事实、已知步骤和可能失败，再判断这些变化能否由有限规则表达。

| 任务 | 必要信息 | 推荐执行方式 | 选择原因 |
|------|----------|--------------|----------|
| 从工单中提取 `ORD-2048` | 当前工单文字 | 单次调用或普通解析 | 不需要额外观察及动作 |
| 每天生成已发货订单摘要 | 固定查询和规则 | 确定性工作流 | 数据来源、处理顺序和提交条件明确 |
| 调查不完整的配送投诉 | 工单、订单及相关备注 | 有界 Agent | 查询顺序和补充证据取决于已获取的结果 |

这些建议依赖上述条件。如果配送调查始终只有两个固定查询，直接并行读取再核对更容易检查；如果事实来源很多且并非每次都需要访问，动态选择才有降低无关查询的价值。

### 2. 同时比较控制成本

Agent 的收益来自能够根据观察改变路径，代价也来自这部分自由度。模型可能重复调用、选择无关工具、过早结束或在失败后继续猜测。更多步骤还会增加时延、费用和诊断难度。

| 维度 | 单次调用 | 确定性工作流 | Agent |
|------|----------|--------------|-------|
| 路径选择 | 无后续执行路径 | 代码及显式规则 | 模型建议，应用约束 |
| 状态管理 | 输入与结果 | 当前节点和分支 | 观察、动作、证据、预算及终态 |
| 失败定位 | 请求或结果校验 | 具体节点 | 需要还原选择与反馈关系 |
| 调用成本 | 通常一次模型请求 | 可预估各节点上限 | 必须设置总体上限 |
| 更适合的约束 | 输入已经充分 | 路径稳定 | 允许受控探索，成功条件可验证 |

“工具很多”只是候选动作多，不是必须使用 Agent 的理由。工具越多，越需要权限分组、清楚的契约和评测样本，否则模型的选择空间会增加失败机会。

::: tip 先写成功条件，再决定控制方式
对订单调查，可以要求取得当前订单的成功查询证据，结果保留订单号、状态和来源。若无法说明完成应依据什么事实，增加工具或多轮调用只会把验收问题延后。
:::

## 三、模型选择与应用责任

### 1. 模型提出动作

模型可以在已提供的工具定义中选择名称及参数，也可以依据错误反馈尝试补充条件。它不能替代应用校验身份、授权范围和业务前置条件。

对于 `CASE-1042`，用户任务说明涉及 `ORD-2048`。即使模型输出了另一个格式合法的订单号，应用仍需核对其是否属于该工单、是否对当前身份可见。Schema 只能约束参数结构，不能证明授权成立。

### 2. 应用执行和验收

应用至少负责四条边界：

1. 调用前：工具白名单、参数及身份授权成立。
2. 执行时：时间、资源和副作用处于允许范围。
3. 反馈时：传回真实成功结果或明确错误，不伪造观察。
4. 结束时：核对结果与证据，并返回明确终止原因。

例如，查询返回 `order_not_found` 后，模型又给出“订单正在运输”。应用应判定缺少证据，不能因为文本流畅就把任务标记为完成。

这些责任同样适用于使用框架的 Agent。框架可以组织消息、路由和状态，但业务授权与成功条件需要应用提供。

## 四、采用与回退

### 1. 在受控范围内引入 Agent

把固定流程改成 Agent 前，应保留一个可比较的工作流基线。先允许模型选择只读动作，在固定测试工单上比较证据准确率、完成率、调用次数和总耗时；指标定义应包含查询失败和信息不足的样本。

采用顺序应围绕实际风险展开：先验证事实调查，再引入待确认提议，最后才考虑有业务副作用的执行。每次增加能力，都要重新确认可执行对象、权限和验收条件，而不是仅修改工具描述。

### 2. 回退到固定路径

如果任务的动态分支没有带来收益，或者 Agent 在预算内无法取得足够证据，可以返回可诊断的未完成结果，再由固定流程或人工处理。回退不能悄悄扩大权限，也不能用旧的模型猜测填补缺失事实。

| 观察到的问题 | 应对方式 | 回退时保留的信息 |
|--------------|----------|------------------|
| 两种路径取得同样证据，Agent 调用更多 | 固定查询顺序或并行读取 | 对比数据和原有验收规则 |
| 经常重复调用或预算耗尽 | 收窄选择范围，使用固定关键步骤 | 已取得的事实、剩余问题及终止原因 |
| 涉及高风险写操作 | 固定审批和提交流程 | 具体动作、对象、参数及确认状态 |

动态选择适合解决证据获取路径的不确定性，业务规则和授权不应随模型判断改变。
