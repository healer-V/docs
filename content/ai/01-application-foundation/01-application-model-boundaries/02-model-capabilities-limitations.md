# 模型能力与限制

客服把一张工单交给模型整理，得到五个字段：客户升级到的版本 4.2.0、首次打开报表要等 8 秒、本月订单总额 1280 元、问题在 4.2.1 中已修复、客户情绪“部分满意”。五个字段写得同样整齐，可信程度却完全不同：有的在工单原文里能找到，有的需要重新计算，有的原文根本没有提到。

模型擅长理解和书写文字，但它写出的每一项内容是否可信，要由应用逐项检查。一个任务能不能交给模型，关键不在于模型能不能回答，而在于应用能不能检查它的回答。

## 一、模型擅长什么

### 1. 处理说法多变的文字

“首次打开报表要等 8 秒左右”和“报表第一次加载大约 8 秒”说的是同一件事。同一个意思有无数种说法，普通代码很难写全所有规则，模型却能读懂它们。应用里常见的模型用法有四种：

| 用法 | 做什么 | 例子 |
|------|--------|------|
| 写 | 按要求写出新内容 | 回复草稿、商品描述 |
| 提取 | 从原文中找出指定信息 | 版本号、订单号、日期 |
| 概括 | 把长文字压缩成要点 | 工单概括、会议纪要 |
| 分类 | 给出类别或倾向 | 问题类型、客户情绪 |

开头的五个字段就涵盖了其中三种：版本号和等待时间是提取，“已修复”是概括，客户情绪是分类。

### 2. 越容易检查的任务越适合交给模型

四种用法的检查难度不同。提取最容易检查，答案应该原样出现在原文中；概括要逐项核对里面的事实；分类给出的是一种判断，原文往往无法证明它对不对，只能限定可选的类别，再由人或规则决定是否采用。

所以判断任务时，先问应用用什么来检查结果。说不出检查办法的任务，就不适合让模型的结果直接生效，应该加入人工确认，或者改用普通代码实现。

## 二、模型保证不了什么

### 1. 事实

模型的知识来自训练时读过的文字，训练有截止时间，截止之后的事情它不知道。更常见的情况是，应用需要的事实本来就不在模型读过的文字里：某个版本是否修复了某个问题、订单现在是什么状态，这些信息存放在公司自己的系统中，模型只能看到应用发给它的内容。

开头的“问题在 4.2.1 中已修复”就属于这种情况。工单原文没有提到 4.2.1，这句话要么是模型编出来的，要么需要应用去发布记录里查证。模型写出它时语气和其他字段一样确定，单看文字无法分辨。

### 2. 精确计算

模型写数字和写文字的方式一样，是“写出看起来合适的内容”，而不是执行算术。它可能算对简单的加法，但金额、数量这类必须精确的结果，要由程序计算。开头的订单总额，正确做法是从原文取出三笔金额，用代码相加，再和模型给出的值比较。

### 3. 每次结果一致

同一段输入调用两次，模型的措辞、顺序甚至结论都可能不同。OpenAI 的 [Text generation 指南](https://developers.openai.com/api/docs/guides/text) 说明，模型生成的内容是非确定性的，同一系列模型的不同版本也可能给出不同结果。今天测试通过，不代表明天每次都通过。

需要每次完全相同的结果，例如类别只能是固定的四种之一，就要由代码检查或映射。这些限制和 [AI 应用组成](./01-application-components.md) 中“模型写出的内容不一定对”是同一件事的三个方面。

## 三、动手核对模型给出的字段

### 1. 准备目录

下面用一个小程序重现“拿到模型结果之后逐项核对”这一步，看看五个字段分别该怎么处理。

::: info 实验环境与边界
程序只用 Python 3.12 标准库，不需要 API Key，也不联网。五个字段由本文构造，用来模拟模型的整理结果，不是真实模型的输出，也不代表真实模型的出错频率。
:::

在自己新建的空目录中操作，`python3.12` 需要指向已安装的 Python 3.12：

```bash
mkdir model-limits
cd model-limits
python3.12 --version
```

Windows 可以用 `py -3.12 claim_check.py` 运行，该命令未经实测。

### 2. 程序做了什么

在当前目录新建 UTF-8 编码的 `claim_check.py`。`SOURCE` 是工单原文，`CANDIDATE` 是模拟的模型结果。`check_field()` 对每个字段选择一种核对方式：

- 订单总额：从原文取出三笔金额，用代码重新相加；
- 客户情绪：属于判断，直接标记为需要人工复核；
- 其余字段：检查原文里有没有出现相同的值。

::: details 查看 claim_check.py 完整代码

```python [claim_check.py]
import re

SOURCE = (
    "工单 T-2048：客户于 2026-11-03 升级到 4.2.0。升级后批量导出恢复正常，"
    "但首次打开报表仍需等待约 8 秒。客户本月三笔订单金额分别为 420 元、385 元、485 元。"
)

# 本文构造的候选结果，模拟模型从原文抽取和归纳出的字段，不是某个真实模型的输出。
CANDIDATE = {
    "版本": "4.2.0",
    "等待秒数": 8,
    "订单总额": 1280,
    "修复版本": "4.2.1",
    "客户情绪": "部分满意",
}

# 只能由人判断、原文无法直接证明的字段。
JUDGEMENT_FIELDS = {"客户情绪"}


def numbers_in(text: str) -> list[str]:
    """返回文本中出现的全部数字和点分版本号，如 8、420、4.2.0。"""
    return re.findall(r"\d+(?:\.\d+)*", text)


def check_field(name: str, value) -> tuple[str, str]:
    """按字段类型核对一个候选值，返回（结论，依据）。

    Args:
        name: 候选字段名。
        value: 候选字段值。
    """
    if name == "订单总额":
        expected = sum(int(amount) for amount in re.findall(r"(\d+) 元", SOURCE))
        verdict = "一致" if value == expected else "不一致"
        return verdict, f"程序按原文重新计算为 {expected}"
    if name in JUDGEMENT_FIELDS:
        return "需人工复核", "属于判断，原文不能直接证明"
    if str(value) in numbers_in(SOURCE):
        return "一致", "原文出现相同的值"
    return "原文无依据", "需要查询原文以外的可信来源"


def main() -> None:
    """逐个核对候选字段并打印结论，不返回值。"""
    for name, value in CANDIDATE.items():
        verdict, basis = check_field(name, value)
        print(f"{name}={value!r}: {verdict}（{basis}）")


if __name__ == "__main__":
    main()
```

:::

### 3. 运行与观察

```bash
python3.12 claim_check.py
```

2026-11-26 在 macOS、Python 3.12.16 上运行，退出码为 0，实际输出如下：

```text
版本='4.2.0': 一致（原文出现相同的值）
等待秒数=8: 一致（原文出现相同的值）
订单总额=1280: 不一致（程序按原文重新计算为 1290）
修复版本='4.2.1': 原文无依据（需要查询原文以外的可信来源）
客户情绪='部分满意': 需人工复核（属于判断，原文不能直接证明）
```

前两个字段在原文中能找到相同的值，可以直接接受。订单总额看起来和其他数字一样整齐，但原文的 420、385、485 相加是 1290，模型给的 1280 少了 10，只有重新计算才能发现。

修复版本 4.2.1 在原文中找不到。程序不能断定它是错的，只能断定原文证明不了它，所以结论是去发布记录这类可信来源查证。客户情绪是一种判断，原文没有“满意”或“不满意”的字样，任何程序都无法用原文证明它，只能交给人决定是否采用。

五行输出对应三种处理方式：

| 字段类型 | 处理方式 |
|----------|----------|
| 原文里有的（版本、秒数）、能重算的（总额） | 程序直接核对 |
| 原文里没有的事实（修复版本） | 查其他可信来源，查不到就标记为未知 |
| 判断类结果（客户情绪） | 限定可选值，交给人确认 |

## 四、判断一个任务能不能交给模型

### 1. 三个问题

拿到一个任务时，依次回答三个问题：

1. **结果允许多种说法吗？** 允许，才需要模型；只有一个正确答案的，用普通代码实现。
2. **应用能检查结果吗？** 能用原文、系统数据或规则检查，结果才可以在检查后自动使用；不能检查的，只能给人参考。
3. **结果出错时，能在生效前改正吗？** 能，就可以先给出草稿让人修改；不能，就不能让模型的结果直接触发操作。

### 2. 摘要与扣款的对比

客户反馈摘要和“根据客户描述决定是否扣款”都从一段文字开始，三个问题的答案却不同：

| 问题 | 客户反馈摘要 | 根据客户描述决定是否扣款 |
|------|--------------|--------------------------|
| 允许多种说法 | 是，措辞可以不同 | 否，扣不扣、扣多少只有一个正确答案 |
| 能检查 | 能，摘要可与原文对照 | 部分能，金额和账户状态要查账务系统 |
| 出错能在生效前改正 | 能，客服确认后才发送 | 否，扣款执行后就造成损失 |
| 分工 | 模型写摘要，程序核对数字，客服确认 | 模型最多整理出客户诉求，扣款由业务规则和有权限的人决定 |

两个任务可能用的是同一个模型，差别在于应用能不能检查结果、出错后能不能挽回。

## 五、两个常见误解

### 1. 试一次成功就说明可靠

用一张工单测试，模型给出的字段全部正确，只说明这一次调用正确。同一张工单再调用一次可能出错，换一张写法不同的工单也可能出错。判断模型在某个任务上是否可靠，要用一组有代表性的样本统计答对的比例，做法见 [任务与模型选择](./03-task-model-selection.md)。

### 2. 格式正确就说明内容正确

模型接口可以把输出限制成固定的格式，例如要求订单总额必须是整数。OpenAI 的 [Structured Outputs 指南](https://developers.openai.com/api/docs/guides/structured-outputs) 说明，这个功能约束的是输出格式，应用仍需检查格式表达不了的业务规则。本文实验中，五个字段的格式都没有问题，其中仍有一个算错、一个没有依据、一个需要人判断。

::: warning 格式检查不能代替内容核对
格式检查回答“程序能不能读取这个结果”，内容核对回答“这个结果说的是不是真的”。两项都要做，前者通过推不出后者通过。
:::

本文实验验证的是核对程序的行为：给定一张工单和五个构造的字段，程序能把它们分成可直接核对、需查其他来源和需人工判断三类。它没有调用真实模型，不说明任何模型的出错频率；数字核对用的是“原文里出现相同数字”的简化判断，真实应用需要按字段含义精确定位。重复调用时结果怎样变化，在 [非确定性与事实校验](../02-generation-mechanics/03-nondeterminism-factuality.md) 中观察。
