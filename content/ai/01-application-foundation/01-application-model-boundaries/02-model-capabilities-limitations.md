# 模型能力与限制

生成式模型适合处理自然语言中存在多种合理表达的任务，但不能单独保证事实、权限、实时数据、精确计算和业务状态。判断模型是否适用，关键不在于“能不能回答”，而在于应用能否验证结果并承担失败成本。

::: tip 能力不等于产品保证
模型能够生成某类结果，只说明它可以作为候选方案的一部分。只有应用补齐数据、校验和业务控制后，系统才能对外承诺质量。
:::

## 一、适用任务

生成式模型的优势是从复杂输入中形成具有语义的输出。任务允许一定表达差异、结果可以校验或人工修订时，模型通常更有价值。

### 1. 文本生成

文本生成根据主题、约束和上下文产生新的自然语言内容，例如回复草稿、说明文字或产品描述。

适合交给模型的生成任务通常具有以下特征：

- 存在多种可接受表达；
- 质量可以通过样例、规则或人工检查；
- 输出错误不会直接造成不可逆业务后果；
- 应用能够限制输入和输出范围。

模型生成的是候选内容。正式发布、通知客户或写入关键记录之前，仍需要应用侧审核规则。

### 2. 归纳总结

归纳任务把较长输入压缩为主题、摘要或要点。客户反馈摘要、会议记录整理和工单概括都属于这一类。

归纳任务并不天然安全。模型可能遗漏限定条件、改变数字含义或把推测写成事实，因此应用应保留原文关联，并对版本号、金额、日期等关键字段单独核对。

### 3. 内容转换

转换任务改变表达形式但不应改变核心含义，例如：

- 调整语气和受众；
- 从自由文本提取候选字段；
- 翻译自然语言；
- 把非结构化内容转换为规定格式。

转换质量需要明确的输出契约。能够生成 JSON 样式文本，不代表结果一定满足 Schema 或业务语义；格式与字段约束仍应由程序验证。

### 4. 辅助推理

模型可以根据输入材料进行分类、比较、解释和方案分析，适合提供候选判断或辅助决策。

辅助推理与最终决策必须分开。模型可以分析客户反馈属于性能问题还是功能问题，但退款、封禁、授信或医疗处置等高风险动作不能只由模型结果驱动。

## 二、能力限制

限制不是“模型完全做不到”，而是应用不能把对应结果当作稳定保证。一个模型偶尔回答正确，不足以证明任务边界成立。

### 1. 事实限制

模型可能生成流畅但没有来源支撑的陈述。它的已有知识也可能早于当前业务数据，无法替代实时数据库或权威资料。

| 场景 | 不能只依赖模型的原因 | 应用补充 |
|------|----------------------|----------|
| 产品当前版本 | 发布状态会变化 | 查询发布系统或配置中心 |
| 客户合同条款 | 需要对应具体合同 | 读取获准的合同数据 |
| 故障最新进展 | 状态持续变化 | 查询事件平台 |
| 法规要求 | 地区和时间范围严格 | 使用权威来源并由专业人员复核 |

事实性和语言流畅度是两个维度。输出读起来合理，不能作为事实正确的证据。

### 2. 计算限制

模型可以解释计算方法，也可能完成简单计算，但不能替代需要精确性和可审计性的计算引擎。

金额、税费、配额和统计指标应由确定性代码计算。模型可以帮助识别需要哪些字段或解释结果，但最终数值应来自经过测试的程序。

### 3. 权限限制

模型不会自动继承应用的用户身份、数据权限和审批状态。把“只能查看自己客户的数据”写进 Prompt，不能代替真正的访问控制。

权限必须在数据读取和工具执行之前由应用检查。模型最多只能看到应用选择发送给它的上下文，因此控制数据边界是应用责任。

### 4. 实时性限制

模型的训练知识具有时间边界，也不会自动知道应用数据库刚刚发生的变化。需要当前状态时，应用必须连接实时数据源或工具。

::: warning 不要用模型记忆替代实时查询
“模型可能知道”与“系统已经查到”是不同证据。订单状态、库存、余额和故障进展必须来自当前可信数据源。
:::

### 5. 一致性限制

生成过程允许多个合理结果，相同输入可能得到措辞、顺序或细节不同的输出。降低随机性或固定 Prompt 可以减少变化，但不能把概率生成变成绝对相同的业务规则。

需要完全一致的字段，应使用枚举、Schema、程序映射或数据库约束。模型更适合生成这些确定性结构之外的语义内容。

## 三、任务分类

判断任务是否适合模型，可以按“模型独立完成、模型加外部数据、确定性系统完成”三类划分。

### 1. 模型候选任务

结果允许表达差异，错误可以低成本发现和修订时，可以让模型直接生成候选内容。

| 任务 | 使用方式 | 必要控制 |
|------|----------|----------|
| 客户反馈摘要 | 模型生成一句摘要 | 核对关键事实并保留原文 |
| 回复草稿 | 模型生成候选回复 | 人工确认后发送 |
| 主题分类 | 模型给出候选标签 | 校验标签集合和置信边界 |
| 文案改写 | 模型调整语气 | 检查禁用词与事实不变 |

这里的“直接”是指不需要额外业务数据，不代表可以绕过输出校验。

### 2. 数据增强任务

任务依赖当前事实、企业知识或用户信息时，模型需要由应用提供外部数据。

例如回答“4.2.0 是否已经修复批量导出问题”，应用应先从发布说明或工单系统取得证据，再让模型组织回答。没有证据时，模型应返回信息不足，而不是根据已有知识猜测。

这种模式的核心不是让模型记住更多内容，而是让应用控制来源、权限和更新时间。

### 3. 确定性任务

需要精确结果、强一致性或不可逆动作时，应由确定性系统完成。

| 任务 | 正确负责方 |
|------|------------|
| 计算退款金额 | 经过测试的业务代码 |
| 判断账号权限 | 身份与权限服务 |
| 更新订单状态 | 事务性业务服务 |
| 扣减账户余额 | 账务系统 |
| 验证字段长度 | 输入校验代码 |

模型可以解释这些结果或生成操作建议，但不能成为唯一执行依据。

## 四、判断方法

任务评估必须同时考虑输出差异、错误代价、事实来源和验证能力。

### 1. 可接受变化

先确定哪些变化不影响业务。

客户反馈摘要可以接受“首次打开报表较慢”和“首次加载约需 8 秒”两种表达，但不能把 `8 秒` 改成 `8 分钟`，也不能省略“批量导出已恢复”这一事实。

将可接受变化写清楚，才能区分自然语言差异和真正的质量错误。

### 2. 错误代价

错误代价决定需要多强的控制。

| 错误后果 | 典型处理 |
|----------|----------|
| 用户可以立即修订 | 展示模型草稿并允许编辑 |
| 会造成错误信息传播 | 引用来源并在发送前审核 |
| 会改变业务状态 | 使用确定性规则和审批 |
| 会造成资金、合规或安全风险 | 不允许模型独立决定 |

错误代价越高，越不能用“模型通常正确”作为上线依据。

### 3. 验证能力

应用必须知道如何判断结果是否可用。验证可以来自：

- 结构与字段规则；
- 原始输入或权威数据源；
- 代表性测试集；
- 人工审核；
- 下游业务约束。

无法定义验证方法的任务，不适合直接自动化。此时应缩小范围、增加人工环节或改用确定性实现。

## 五、场景对比

相似的自然语言输入，可能因为业务责任不同而得到完全不同的实现选择。

### 1. 客户反馈摘要

摘要任务允许多种表达，结果可以与原文对照，错误也能在展示前拦截。合理设计是：

1. 应用读取获准的反馈文本。
2. 模型生成候选摘要。
3. 应用检查非空、长度和关键事实。
4. 客服人员确认后采用。

模型负责归纳语言，应用保留事实来源和最终决定权。

### 2. 账户扣款决策

“根据客户描述判断是否扣款”不适合由模型独立完成。扣款涉及金额、权限、账户状态、交易规则和审计，任何错误都可能造成直接损失。

正确分工是模型最多提取用户意图或生成客服说明；是否扣款、扣多少、由谁批准，应由业务规则和交易系统决定。

### 3. 错误反例

下面的判断方式都不成立：

- 输出语言流畅，因此事实正确；
- 单次测试成功，因此结果稳定；
- Prompt 写了“必须准确”，因此不需要校验；
- 模型能力更强，因此可以跳过权限；
- 模型能解释公式，因此可以替代账务计算。

这些反例把模型能力误当成系统保证，忽略了应用仍需承担的产品责任。

## 六、应用责任

模型选型不能消除应用责任。模型越强，应用越需要明确哪些结果由模型生成、哪些条件由程序保证。

输入、输出和动作属于三个连续的控制边界。应用在每个边界都需要提供模型本身无法保证的确定性约束。

| 边界 | 应用责任 | 不能交给模型保证的事项 |
|------|----------|------------------------|
| 输入 | 控制来源、权限、长度和敏感字段 | 未经授权的数据不能因为模型需要上下文就被发送 |
| 输出 | 定义格式、事实核对和失败处理 | 无法验证的结果只能作为参考，不能伪装成确定结论 |
| 动作 | 控制对外发送、数据修改和业务执行 | 高风险动作需要审批、幂等、审计和回滚 |

模型可以为每个边界提供候选内容，但应用始终保留放行权。能力越强不代表权限越大，也不减少应用对失败结果的责任。
