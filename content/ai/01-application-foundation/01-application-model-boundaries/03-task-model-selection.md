# 任务与模型选择

模型选择不是从名称或榜单中挑“最强模型”，而是寻找满足当前任务质量门槛，同时符合时延、成本、能力和可用性约束的模型。

本文继续使用客户反馈摘要场景。`gpt-6-luna` 作为本模块的初始基线，是因为 OpenAI 将它定位为面向聚焦、高吞吐任务的高效模型；这个定位只能支持候选初选，不能替代业务样本验证。

::: tip 先定义任务，再比较模型
没有输入边界、输出契约和质量门槛时，任何“模型更好”的结论都无法复现，也无法指导上线后的回退。
:::

## 一、任务定义

业务描述需要转换为可测量的任务契约。任务契约回答输入是什么、输出给谁、什么结果算成功，以及失败会造成什么影响。

### 1. 输入边界

客户反馈摘要的输入不是“任意文本”，而是来自已授权工单的一段反馈正文。

| 约束 | 示例定义 | 设计原因 |
|------|----------|----------|
| 来源 | 已授权的客户反馈字段 | 防止混入未获准数据 |
| 语言 | 以中文为主，可包含产品名和版本号 | 决定样本组成 |
| 长度 | 应用设定最大字符数 | 控制延迟、上下文与异常输入 |
| 内容 | 可能包含数字、时间和否定表达 | 需要重点验证事实保留 |
| 数据类型 | 纯文本 | 当前任务不需要音频或图像 |

输入边界决定模型必须处理的真实难点。只用短句测试，不能证明模型能够处理带版本号、转折和多个问题的生产反馈。

### 2. 输出契约

输出契约规定消费者真正需要什么，而不是描述模型“尽量生成得好”。

本场景的输出要求为：

- 使用一句中文摘要；
- 保留版本、功能状态和时间等关键事实；
- 不补充输入中没有的原因或结论；
- 允许措辞变化，但不能改变事实关系；
- 输出为空或无法确认时进入失败处理。

如果下游需要稳定字段，应使用结构化输出和 Schema；本文只为基础模块定义自然语言摘要契约。

### 3. 质量门槛

质量门槛必须能够在样本上判断。客户反馈摘要至少检查四个维度：

| 维度 | 合格条件 | 失败示例 |
|------|----------|----------|
| 事实保留 | 关键实体、数字和状态与原文一致 | 把 `8 秒` 改成 `8 分钟` |
| 信息覆盖 | 保留影响处理的主要事实 | 省略“批量导出已恢复” |
| 无事实扩展 | 不增加原文没有的原因或承诺 | 声称“数据库性能导致” |
| 可读性 | 一句摘要，语义完整 | 只有零散关键词 |

这些门槛比“读起来不错”更可复现，也便于比较不同模型。

## 二、约束收集

质量只是选型的一部分。应用还需要考虑模态、上下文、延迟、成本和所需能力。

### 1. 能力约束

先排除不满足硬条件的模型。

| 约束 | 需要核对的问题 |
|------|----------------|
| 模态 | 是否支持当前输入和输出类型 |
| 上下文 | 输入、指令、工具和预留输出能否放入窗口 |
| 输出上限 | 是否能容纳目标结果和必要推理 |
| API 能力 | 是否支持流式、结构化输出或工具调用 |
| 数据处理 | 是否满足项目的数据驻留和保留要求 |
| 项目可用性 | 当前 API 项目是否有权调用 |

客户反馈摘要只需要文本输入和文本输出，因此无需为图像、音频或复杂工具能力支付额外复杂度。

### 2. 运行约束

运行约束来自产品体验和容量目标。

| 约束 | 摘要场景中的问题 |
|------|------------------|
| 时延 | 客服是在等待单条结果，还是后台批量处理 |
| 吞吐 | 高峰期每分钟需要处理多少条反馈 |
| 成本 | 每条成功摘要可以接受多少 Token 和费用 |
| 限流 | 项目层级的请求与 Token 限制是多少 |
| 稳定性 | 超时或模型不可用时是否允许转人工 |

这些值应由业务量和体验目标给出，不能从模型宣传材料反推。

### 3. 风险约束

错误代价决定是否需要更强模型、更多校验或人工审核。

客户反馈摘要用于客服参考，允许人工修订，风险低于自动发信或自动退款。即使如此，应用仍需阻止事实被改变，并保留原文入口。

高风险任务不能只通过升级模型解决。权限、审批、事实来源和业务规则必须独立存在。

## 三、候选模型

候选集合应小而有理由。先依据官方能力和任务约束筛选，再用代表性样本验证。

### 1. 候选依据

OpenAI 当前对 GPT-6 系列的定位可以形成初选假设：

| 模型 | 官方定位摘要 | 在本任务中的候选角色 |
|------|--------------|----------------------|
| `gpt-6-luna` | 聚焦、高吞吐任务的高效模型 | 默认基线 |
| `gpt-6-sol` | 面向要求较高的推理任务 | 复杂反馈的质量候选 |
| `gpt-6-astra` | 最高能力层级 | 只有基线质量不足且收益可证明时再评估 |

这张表只描述候选角色，不代表 `astra` 一定更适合，也不代表 `luna` 已经达到业务质量门槛。模型能力、价格和项目可用性会变化，选型时必须重新核对官方模型页。

### 2. 硬条件筛选

对客户反馈摘要，硬条件包括：

1. 支持文本输入和文本输出。
2. 支持 Responses API。
3. 当前项目可以调用。
4. 上下文和输出上限覆盖目标样本。
5. 数据处理方式满足应用要求。

任何硬条件不满足，模型就不进入效果对比。不能用更高质量分数抵消权限或合规问题。

### 3. 初始基线

本模块选择 `gpt-6-luna` 作为教学基线，理由是任务短、目标聚焦，并且需要低复杂度的可重复调用。

::: warning 教学基线不是生产选型结论
样板中的一次成功响应只能证明 API 链路可用。生产选型还需要代表性数据、质量评测、延迟分布和实际成本。
:::

## 四、对照实验

模型比较必须使用相同输入、相同任务约束和相同记录方式。一次演示结果不能代表稳定质量。

### 1. 样本设计

样本应覆盖正常输入和容易失败的边界。

| 样本类型 | 重点观察 | 建议数量 |
|----------|----------|---------:|
| 单一问题 | 基础摘要能力 | 5 |
| 多个问题 | 信息覆盖 | 5 |
| 数字与版本 | 事实保留 | 5 |
| 否定与转折 | 关系理解 | 5 |
| 噪声和口语 | 归纳能力 | 5 |
| 信息不足 | 是否拒绝补充事实 | 5 |

30 条可以作为小规模初筛，不足以代替生产评测。样本必须来自经过脱敏的真实分布，而不是只挑模型容易回答的句子。

### 2. 控制变量

每轮比较只改变模型，其他条件保持一致：

- 使用相同 `instructions` 和 `input`；
- 使用同一 SDK 与 API；
- 使用相同输出长度约束；
- 在相近时间窗口执行；
- 记录实际模型、状态、用量和延迟；
- 对非确定性任务进行重复运行。

同时修改 Prompt、模型和参数后，即使结果变化，也无法知道是哪项因素造成。

### 3. 结果记录

对每次请求记录原始证据，再汇总为模型级指标。

| 字段 | 用途 |
|------|------|
| `sample_id` | 关联固定测试样本 |
| `model` | 记录服务端实际模型 |
| `response_id` | 定位具体请求 |
| `status` | 区分完成与失败 |
| `input_tokens` / `output_tokens` | 观察用量 |
| `latency_ms` | 观察端到端延迟 |
| `fact_pass` | 关键事实是否保持 |
| `coverage_pass` | 主要信息是否覆盖 |
| `unsupported_claim` | 是否增加无来源事实 |

评审人员还应保留失败原因，而不是只记录一个总分。总分相同的两个模型，可能在不同风险维度上失败。

## 五、决策矩阵

决策矩阵把实验结果与业务约束连接起来。权重应由任务风险决定，不应固定套用。

### 1. 比较维度

客户反馈摘要可以使用以下维度：

| 维度 | 建议优先级 | 判断依据 |
|------|------------|----------|
| 事实保留 | 阻断项 | 数字、版本、状态不得改变 |
| 无事实扩展 | 阻断项 | 不得补充无来源原因或承诺 |
| 信息覆盖 | 高 | 主要问题与恢复状态不能遗漏 |
| 可读性 | 中 | 摘要简洁、语义完整 |
| P95 延迟 | 中 | 符合客服交互目标 |
| 单次成功成本 | 中 | 结合重试与失败率计算 |

阻断项不应与其他分数简单相加。事实错误率超过门槛时，即使延迟和成本更低，也不能直接选用。

### 2. 选择规则

一个可执行的选择规则可以写成：

1. 先淘汰不满足硬能力和项目可用性的模型。
2. 再淘汰未达到事实与无扩展门槛的模型。
3. 在剩余模型中比较信息覆盖、延迟和单次成功成本。
4. 选择满足门槛的最小模型，而不是默认选择最大模型。
5. 保存模型版本、Prompt 版本、样本版本和决策日期。

这个顺序保证质量底线先于优化指标。

### 3. 本模块结论

`gpt-6-luna` 作为本模块示例的初始基线，已经通过最小 API 调用验证，但没有完成 30 条样本对照实验。

因此可以得出的结论是“它适合用于教学示例和继续建立评测基线”，不能写成“它是客户反馈摘要的最佳生产模型”。

## 六、回退条件

选型记录必须包含何时重新评估，以及异常时切换到什么路径。

### 1. 重新评估

以下变化会使原结论失效：

- 输入长度、语言或业务领域发生明显变化；
- 输出从人工参考变为自动执行依据；
- 模型版本、Prompt 或关键参数发生变化；
- 质量、延迟或成本持续越过门槛；
- 项目权限、数据处理或 API 能力发生变化。

发生变化时，应重新运行代表性样本，而不是沿用历史印象。

### 2. 运行回退

回退可以是另一个模型，也可以是停止自动化。

| 失败条件 | 合理回退 |
|----------|----------|
| 模型暂时不可用 | 转人工或进入待处理队列 |
| 结果未通过事实校验 | 展示原文并要求人工修订 |
| 延迟超过交互目标 | 改为异步处理或使用已验证候选 |
| 成本超过预算 | 缩小输入、降低调用频率或重新选型 |

没有经过同样测试的备用模型，不能称为可靠回退。

### 3. 常见误区

- 只看模型名称和参数规模；
- 只运行一条“效果很好”的样本；
- 同时改变模型、Prompt 和参数；
- 只比较单次价格，不计算失败和重试；
- 没有阻断质量门槛；
- 没有记录模型与样本版本。

这些做法产生的是印象，不是可复现的工程决策。
