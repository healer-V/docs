# AI 应用组成

不少电商商品页的评价区上方有一句“买家评价摘要”，例如“买家认可物流速度，但反映尺码偏小”。这句话不是运营人员写的，而是程序把评价交给大语言模型，由模型读完后写出来的。像这样让模型写出一部分结果的软件，就是 AI 应用。

在这个功能里，只有“写出这句话”一步交给了模型。挑选哪些评价、写出来的话能不能显示，仍然由开发者写的普通代码决定。看懂这一点，就看懂了 AI 应用的基本结构。

## 一、一句摘要是怎样产生的

### 1. 五个步骤

用户打开商品页到看见摘要，背后依次发生五件事：

1. **收到请求**：商品页请求这个商品的评价摘要。
2. **准备输入**：程序从评价表里挑出审核通过的评价，只取评价正文，前面加一句“用一句话概括下列买家评价”，拼成一段文字。
3. **调用模型**：把这段文字发给模型，模型返回一句摘要。
4. **检查结果**：程序检查这句摘要，例如是否太长、有没有评价里根本没出现过的数字。
5. **显示或退回**：检查通过就显示摘要；不通过就不显示摘要，直接展示评价列表。

### 2. 模型只负责第 3 步

五步中只有第 3 步由模型完成，其余四步都是开发者写的普通代码。其中第 2 步和第 4 步最关键：第 2 步决定模型能看到什么，第 4 步决定模型写的内容能不能被用户看到。

模型写得好，第 4 步通过的次数就多；模型写得不好，第 4 步把它拦下，页面退回显示评价列表，功能仍然可用。AI 应用是否可靠，很大程度取决于这两步怎么写。

## 二、模型是什么

### 1. 大语言模型会“接着往下写”

大语言模型（Large Language Model，LLM）是用海量文本训练出来的程序。它的规则不是人逐条写的，而是从大量文字中学出来的。它学会的能力可以概括为一句话：**给它一段文字，它接着往下写出最合适的内容。**

这一个能力可以完成很多任务。给它“用一句话概括下列评价：……”，最合适的后文就是一句摘要；给它“把这段话翻译成英文：……”，后文就是译文。所以同一个模型既能写摘要，也能分类、改写和回答问题。模型怎样一步步写出文字，在 [生成过程与参数](../02-generation-mechanics/02-generation-process-parameters.md) 中讲解。

### 2. 开发者调用的是模型服务

训练大语言模型需要大量数据和机器，这不是应用开发者的工作。开发者使用的是别人训练好、部署在服务器上的模型：程序通过网络接口（API）把一段文字发过去，模型服务返回生成的文字。本文后面说的“模型”，都指这样一个服务。

对写应用的人来说，模型服务有两个必须记住的特点：

- **它只看得到你发过去的文字。** 评价表、订单、用户信息，没有放进请求，模型就完全不知道；反过来，放进请求的手机号也会被一起发出去。
- **它写出的内容不一定对。** 模型写的是“看起来合适”的文字，可能出现原文里没有的信息；同样的输入调用两次，结果也可能不同。OpenAI 的 [Text generation 指南](https://developers.openai.com/api/docs/guides/text) 明确说明，模型生成的内容是非确定性的。

这两个特点，正是第一节第 2 步和第 4 步存在的原因：发什么由程序挑选，写回来的内容由程序检查。

## 三、四个组成部分

把评价摘要拆开，一个 AI 应用由四部分组成：

| 组成部分 | 在评价摘要中是什么 | 做什么 |
|----------|--------------------|--------|
| 页面 | 商品页 | 发起请求，显示最终结果 |
| 应用代码 | 后端的摘要程序 | 挑选数据、拼接输入、调用模型、检查结果 |
| 业务数据 | 评价表 | 提供评价正文、审核状态等事实 |
| 模型服务 | 通过 API 调用的大语言模型 | 根据收到的文字写出摘要 |

数据流动的顺序如下，模型的前后都是应用代码：

```text
评价表 → 应用代码（挑选、拼接）→ 模型服务（写摘要）→ 应用代码（检查）→ 商品页
```

::: tip 数据进出模型，都要经过应用代码
模型不会自己去读评价表，也不会自己把结果写到页面上。发给模型什么、模型写的内容能不能用，都由应用代码决定，这也是开发 AI 应用时主要写代码的地方。
:::

## 四、运行一个评价摘要程序

### 1. 准备目录

下面用一个约 50 行的 Python 程序重现上面的五步，亲眼看看应用代码在模型前后做了什么。

::: info 实验环境与边界
程序只用 Python 3.12 标准库，用两段固定文字代替模型的回复，不需要 API Key，也不联网。真实调用模型的做法见 [Responses API 调用](../03-minimal-application/02-responses-api-call.md)。
:::

在自己新建的空目录中操作，`python3.12` 需要指向已安装的 Python 3.12：

```bash
mkdir review-summary
cd review-summary
python3.12 --version
```

Windows 可以用 `py -3.12 review_summary.py` 运行，该命令未经实测。

### 2. 程序做了什么

在当前目录新建 UTF-8 编码的 `review_summary.py`。程序里的每一部分对应一个组成部分：

- `REVIEWS` 是业务数据：四条评价，每条有正文、手机号和审核状态。第四条还没通过审核，正文里写着手机号。
- `build_input()` 是第 2 步“准备输入”：只挑审核通过的评价，只取正文。
- `fake_model()` 代替第 3 步的模型：回复 A 是合格的摘要，回复 B 写了一个评价里没有的“98%”。
- `check_summary()` 是第 4 步“检查结果”：检查长度，并要求摘要里的数字都能在输入中找到。

::: details 查看 review_summary.py 完整代码

```python [review_summary.py]
import re

# 业务数据：评价表中的记录。手机号和审核状态只供应用使用。
REVIEWS = [
    {"text": "物流很快，第二天就到了。", "phone": "13800000001", "status": "visible"},
    {"text": "尺码偏小，建议买大一码。", "phone": "13800000002", "status": "visible"},
    {"text": "包装有破损，客服处理很及时。", "phone": "13800000003", "status": "visible"},
    {"text": "垃圾商家，联系我 13800000004 退钱！", "phone": "13800000004", "status": "pending"},
]

INSTRUCTION = "用一句话概括下列买家评价，不超过 40 个字，不要添加评价中没有的信息。"

# 代替模型服务的两段固定回复：A 符合要求，B 写入了评价中不存在的数字。
FAKE_REPLIES = {
    "A": "买家认可物流速度和客服处理，但反映尺码偏小、包装有破损。",
    "B": "98% 的买家给出好评，物流快，尺码偏小。",
}


def build_input(reviews: list[dict]) -> str:
    """应用代码：只选已审核通过的评价，只取正文，拼成发给模型的输入文本。"""
    lines = [f"- {r['text']}" for r in reviews if r["status"] == "visible"]
    return INSTRUCTION + "\n" + "\n".join(lines)


def fake_model(input_text: str, case: str) -> str:
    """代替模型服务：接收输入文本，返回一段生成文本；这里按 case 返回固定回复。"""
    return FAKE_REPLIES[case]


def check_summary(summary: str, input_text: str) -> str | None:
    """应用代码：用确定的规则检查摘要，通过返回 None，不通过返回原因。"""
    if not summary or len(summary) > 40:
        return f"长度为 {len(summary)}，不在 1～40 字之间"
    for number in re.findall(r"\d+", summary):
        if number not in input_text:
            return f"摘要中的“{number}”在评价原文中不存在"
    return None


def main() -> None:
    """依次执行组装输入、调用模型和检查结果三步，并打印每一步的结果。"""
    input_text = build_input(REVIEWS)
    print("【发给模型的输入】")
    print(input_text)
    print("输入中包含手机号：", any(r["phone"] in input_text for r in REVIEWS))
    for case in FAKE_REPLIES:
        summary = fake_model(input_text, case)
        problem = check_summary(summary, input_text)
        decision = "展示在商品页" if problem is None else f"不展示，改为显示评价列表（{problem}）"
        print(f"【模型回复 {case}】{summary}")
        print(f"【应用处理 {case}】{decision}")


if __name__ == "__main__":
    main()
```

:::

### 3. 运行与观察

```bash
python3.12 review_summary.py
```

2026-11-26 在 macOS、Python 3.12.16 上运行，退出码为 0，实际输出如下：

```text
【发给模型的输入】
用一句话概括下列买家评价，不超过 40 个字，不要添加评价中没有的信息。
- 物流很快，第二天就到了。
- 尺码偏小，建议买大一码。
- 包装有破损，客服处理很及时。
输入中包含手机号： False
【模型回复 A】买家认可物流速度和客服处理，但反映尺码偏小、包装有破损。
【应用处理 A】展示在商品页
【模型回复 B】98% 的买家给出好评，物流快，尺码偏小。
【应用处理 B】不展示，改为显示评价列表（摘要中的“98”在评价原文中不存在）
```

先看“【发给模型的输入】”下面的四行，这就是模型能看到的全部内容。评价表里有四条评价，这里只有三条：未审核的第四条在第 2 步被挑掉了，它正文里的手机号也没有发出去，`输入中包含手机号： False` 确认了这一点。

再看两段回复。A 通过检查，显示在商品页。B 读起来同样通顺，但输入里没有任何数字，“98%”是模型编出来的；检查发现了它，页面不显示这句摘要，改为显示评价列表。

::: warning 检查规则只能拦住它能判断的错误
`check_summary()` 能发现编造的数字，却发现不了“买家普遍觉得质量很好”这种不含数字的错误概括。规则检查只是第一道防线，其余质量问题需要用一批样本去评测。
:::

## 五、两个常见误解

### 1. 模型知道我系统里的数据

模型只知道请求里的文字。实验中模型从没接触过评价表，它看到的只是程序拼好的几行字。反过来，如果第 2 步把整张评价表连同手机号都放进请求，这些数据也会全部发给模型服务；拿到结果后再决定不显示，已经发出去的数据也收不回来。所以哪些数据能发给模型，要在准备输入时决定。

### 2. 模型写出来的就能直接用

回复 B 说明，通顺的文字里也可能有编造的内容。只是显示在页面上时，错误会被用户看到；如果模型的输出直接用来改订单、发邮件，错误就会变成真实的损失。模型输出要先经过应用代码检查，再交给页面或其他系统使用。

## 六、哪些交给模型，哪些留给代码

设计一个 AI 功能时，可以对每项要求问一句：**它能不能写成一条确定的规则？** 能写成规则的，由代码保证；需要理解语言的，交给模型，再由代码检查。以评价摘要为例：

| 要求 | 能否写成规则 | 由谁负责 |
|------|--------------|----------|
| 只用审核通过的评价，不发送手机号 | 能 | 代码，在准备输入时过滤 |
| 把几条评价概括成一句话 | 不能，需要理解语言 | 模型 |
| 摘要不超过 40 个字、不出现编造的数字 | 能 | 代码，在拿到结果后检查 |
| 摘要不合格时页面显示什么 | 能 | 代码，按业务决定 |

即使在给模型的那句指令里写了“不超过 40 个字”，代码里也要再检查一次，因为模型只是大多数时候做得到，不是每次都做得到。

本文实验验证的是应用代码的行为：给定四条评价和两段固定回复，程序能挑选数据、拦下编造数字的摘要并退回显示评价列表。它没有调用真实模型，不说明任何模型写摘要的质量；模型在哪些事情上可以依赖、在哪些事情上不行，见 [模型能力与限制](./02-model-capabilities-limitations.md)。
