# AI 应用组成

AI 应用不是“一个模型加一个输入框”。模型只负责根据输入生成候选结果；输入是否合法、数据能否访问、结果是否可信以及是否执行后续业务动作，都由应用系统负责。

本文使用“客户反馈摘要”作为统一场景：用户提交一段反馈，模型生成摘要，应用校验结果后再交给客服人员查看。

::: tip 核心边界
模型提供概率性的生成能力，应用提供确定性的权限、数据、校验和流程控制。任何需要稳定保证的业务条件，都不能只写进模型指令。
:::

## 一、应用边界

AI 应用同时包含传统软件系统和模型服务。两者通过明确的输入输出契约协作，但不共享同一种责任。

### 1. 模型服务

模型服务接收文本、图像或其他受支持的输入，根据模型能力生成输出。它擅长处理自然语言中难以穷举规则的模式，例如归纳一段反馈、改写语气或提取可能的主题。

模型服务不知道应用当前用户是否有权限读取某条客户记录，也不能自行确认业务数据库中的最新事实。即使输出语言流畅，结果仍然是一次生成，不是数据库查询或业务事务。

| 模型可以提供 | 模型不能独立保证 |
|--------------|------------------|
| 生成候选摘要 | 摘要中的每个事实都正确 |
| 识别文本主题 | 用户具有数据访问权限 |
| 转换表达方式 | 操作满足业务审批规则 |
| 根据上下文推理 | 数据一定是最新状态 |

### 2. 应用系统

应用系统负责把模型能力放入可控制的业务流程。它决定谁可以发起请求、允许使用哪些数据、调用哪个模型、如何处理失败，以及结果可以流向哪里。

传统代码仍然承担确定性职责。长度限制、字段格式、权限判断、金额计算和状态转换都应由程序或业务服务实现，而不是期望模型每次遵守自然语言要求。

::: warning 模型输出不是业务事实
把模型输出保存到业务记录之前，应用必须知道需要验证哪些字段、使用什么证据验证，以及验证失败后如何处理。
:::

## 二、参与对象

一个最小 AI 应用至少包含用户入口、应用代码、模型服务、业务数据和输出消费者。缺少任何对象，都可能让调用可以运行但无法形成可用的业务闭环。

### 1. 用户入口

用户入口负责接收请求和原始输入，可以是命令行、Web 表单、移动端页面或另一个服务的 API。入口必须在数据进入模型之前完成基础校验。

| 入口职责 | 客户反馈摘要示例 |
|----------|------------------|
| 确认调用身份 | 当前客服账号已经登录 |
| 接收输入 | 获取待摘要的反馈正文 |
| 检查格式 | 拒绝空文本或超长输入 |
| 展示状态 | 区分处理中、完成和失败 |

入口不应该直接持有长期 API Key，也不应该绕过应用后端直接决定高风险业务动作。

### 2. 应用代码

应用代码是调用链的控制中心。它把业务输入转换为模型请求，再把模型响应转换为应用能够判断的结果。

应用代码通常承担以下工作：

- 校验输入、身份和权限；
- 从可信数据源读取必要上下文；
- 选择模型并组织请求；
- 处理超时、限流和 API 错误；
- 校验输出格式、事实和业务规则；
- 记录必要的响应 ID、用量和错误证据。

这些职责不会因为引入模型而消失。模型调用只是应用代码中的一个外部依赖。

### 3. 模型服务

模型服务通过 API 暴露生成能力。应用发送模型标识、指令和输入，服务返回状态、内容和用量等结构化信息。

模型服务的可用性、模型版本和能力范围会影响结果，但应用仍需把它当作外部系统处理：调用可能失败，响应可能未完成，输出也可能不满足业务约束。

### 4. 业务数据

业务数据为模型提供完成任务所需的上下文，例如客户反馈、产品版本、工单状态或知识库片段。数据来源必须明确，不能把模型自身的已有知识当作当前业务事实。

| 数据问题 | 应用必须回答 |
|----------|--------------|
| 来源 | 数据来自用户输入、数据库还是检索系统 |
| 时效 | 数据在什么时间点有效 |
| 权限 | 当前调用者是否可以读取 |
| 范围 | 哪些字段允许发送给模型 |
| 追踪 | 输出如何关联回原始数据 |

### 5. 输出消费者

输出消费者是真正使用模型结果的人或系统。它可以是客服人员、页面组件、搜索索引或后续服务。

不同消费者需要不同的质量门槛。供客服参考的摘要可以允许人工修订；自动触发退款的结果则必须通过确定性规则和审批流程，不能只依赖模型判断。

## 三、调用链

调用链说明数据如何移动，以及每个阶段由谁负责。只有把输入、生成和输出分开，才能定位错误和安排校验。

### 1. 输入阶段

输入阶段从用户请求开始，到模型请求发出前结束。此阶段全部由应用控制。

```text
用户提交反馈
  → 入口检查身份与格式
  → 应用读取允许使用的业务数据
  → 应用组织模型指令与输入
```

如果反馈为空、用户无权限或数据包含不应外发的字段，应用应在此处停止，不应先调用模型再处理。

### 2. 生成阶段

生成阶段由模型服务执行。应用发送请求，模型根据输入逐步生成候选输出，再返回结构化响应。

```text
应用发送请求
  → 模型服务验证请求
  → 模型生成候选摘要
  → API 返回状态、内容与用量
```

应用能够控制请求内容和部分参数，但不能把生成过程变成绝对确定的业务规则。

### 3. 输出阶段

输出阶段从应用收到响应开始。应用先判断接口状态和文本结构，再执行事实、格式和业务规则校验。

```text
应用接收 Response
  → 检查状态与错误
  → 检查文本与格式
  → 核对事实和业务规则
  → 交给获准的消费者
```

只有最后一步完成，模型结果才真正进入业务流程。API 返回成功不代表整个应用任务已经成功。

## 四、责任分界

责任分界的目标不是限制模型，而是把概率性能力放在应用可以观察和控制的位置。

### 1. 模型责任

模型负责在输入和能力范围内生成候选结果。对于客户反馈摘要，它应尽量保留原始事实、压缩冗余表达，并遵循应用给出的输出要求。

模型责任是一种能力目标，不是服务对业务正确性的保证。应用需要通过样本和评测确认模型在目标场景中的实际表现。

### 2. 应用责任

应用负责所有需要稳定保证的条件。

| 责任 | 负责方 | 原因 |
|------|--------|------|
| 用户身份与数据权限 | 应用 | 模型不掌握授权上下文 |
| 输入长度和字段格式 | 应用 | 可以用确定性代码检查 |
| 候选摘要生成 | 模型 | 自然语言归纳难以穷举规则 |
| 事实来源核对 | 应用 | 需要关联可信原始数据 |
| 保存、发送或执行动作 | 应用 | 涉及业务副作用和审计 |
| 失败恢复和回滚 | 应用 | 必须控制业务状态 |

把这些责任写入调用契约，可以避免团队把“模型通常能做到”误写成“系统能够保证”。

### 3. 确定性与概率性

确定性逻辑在相同条件下应给出可预测结果，例如字符串是否为空、金额是否超过限额、用户是否拥有权限。概率性生成则可能在措辞、顺序或细节上出现变化。

| 问题 | 合适的实现 |
|------|------------|
| 反馈是否为空 | 应用代码 |
| 用户是否能查看反馈 | 权限服务 |
| 如何压缩为自然语言摘要 | 模型 |
| 摘要是否超过 80 个字 | 应用代码 |
| 是否允许自动退款 | 业务规则与审批 |

::: danger 不要让模型替代权限和交易规则
模型可以解释规则或生成建议，但不能成为权限判断、金额计算和不可逆业务动作的唯一决策者。
:::

## 五、摘要场景

客户反馈摘要能够清楚展示模型和应用的协作边界：模型负责语言归纳，应用负责数据、约束和结果去向。

### 1. 正常链路

输入反馈为：“升级到 4.2.0 后，批量导出恢复正常，但首次打开报表仍需等待约 8 秒。”

一个完整处理过程包括：

1. 应用确认当前用户可以读取这条反馈。
2. 应用拒绝空输入，并限制允许发送的长度。
3. 模型生成一句候选摘要。
4. 应用确认响应完成且文本非空。
5. 应用核对版本号、功能和等待时间均来自原文。
6. 客服人员查看摘要并决定是否采用。

每一步都有明确负责方，因此失败时能够判断应该修复输入校验、模型请求、输出校验还是业务流程。

### 2. 缺失控制

下面的实现看似更短，但缺少关键应用责任：

```text
读取客户反馈
  → 发送给模型
  → 把返回文字直接写入工单
```

它没有验证调用者权限、响应状态、空输出、事实一致性和保存权限。模型即使大多数时候生成正确，也不能消除这些系统缺口。

### 3. 验收问题

检查一个 AI 应用是否形成闭环时，可以逐项回答：

- 输入由谁提供，进入模型前经过哪些检查；
- 模型需要哪些业务数据，数据来自哪里；
- 模型输出的哪些部分允许变化；
- 哪些字段必须由应用确定性验证；
- 输出由谁消费，是否会产生业务副作用；
- 失败后如何停止、恢复或转人工处理。

任何问题没有明确负责方，都表示应用边界仍不完整。

## 六、适用边界

本文只建立 AI 应用的参与对象、调用链和责任分界，不展开具体 API 参数、Prompt 技巧、RAG 检索或 Agent 工具执行。

后续设计必须保持两个原则：模型输出始终经过应用边界，业务副作用始终由具有权限和审计能力的应用代码控制。
