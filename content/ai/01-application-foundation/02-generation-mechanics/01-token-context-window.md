# Token 与上下文窗口

模型不是按字符或单词直接处理文本，而是先把输入转换为 Token。一次请求能否执行、可以生成多长的结果，以及消耗多少用量，都需要以 Token 为单位判断。

本文继续使用客户反馈摘要场景。示例输入包含中文、数字、版本号和标点，适合观察“可见字符数”与“模型实际计数”之间的差异。

::: tip 容量判断的基本关系
请求占用不只有用户输入。系统指令、业务输入、工具定义、历史消息、模型输出和部分模型的推理 Token，都可能进入同一份上下文预算。
:::

## 一、Token 单位

### 1. 基本含义

Token 是模型处理文本时使用的离散单位。一个 Token 可能对应一个完整单词、单词片段、汉字、标点或其他文本片段，具体划分由模型使用的分词方式决定。

因此，下面三种数量不能相互替代：

| 数量 | 统计对象 | 适合解决的问题 |
|------|----------|----------------|
| 字符数 | 字符和标点 | 应用输入框限制、数据库字段限制 |
| 单词数 | 按语言规则划分的词 | 人类阅读量和编辑规范 |
| Token 数 | 模型分词后的单位 | 上下文容量、输出预算和 API 用量 |

应用可以用字符数做第一层输入保护，但不能用“一个汉字等于一个 Token”估算模型容量。中文、英文、数字和符号混合后，固定换算比例更不可靠。

### 2. 分词差异

相同语义的两段文字，Token 数可能不同；相同字符数的两段文字，Token 数也可能不同。模型、编码方式和文本结构都会影响结果。

例如，客户反馈中的 `4.2.0`、`8 秒` 和中文句子会被共同分词。应用只看字符长度，无法知道模型最终使用多少输入 Token。

::: warning 不维护手工换算公式
“一个 Token 约等于几个字符”只能用于非常粗略的容量预估，不能作为请求放行、成本结算或超限诊断的依据。需要精确值时，应使用当前模型对应的计数能力或读取实际响应用量。
:::

### 3. 工程作用

Token 计数主要服务三个工程判断：

1. 请求发送前，判断输入是否可能超出模型上下文窗口。
2. 请求发送时，为输出和推理保留足够预算。
3. 请求完成后，核对实际用量并发现输入膨胀或输出异常。

它不直接表示内容质量。两个请求消耗相同 Token，也可能在事实准确性和业务价值上完全不同。

## 二、上下文组成

### 1. 输入内容

输入 Token 不等于用户文本的 Token。一次请求可能同时包含以下内容：

| 输入来源 | 客户反馈摘要中的示例 |
|----------|----------------------|
| 任务指令 | “压缩为一句中文摘要，不补充事实” |
| 用户输入 | 当前客户反馈正文 |
| 历史消息 | 多轮对话中的前文，本文未使用 |
| 工具定义 | 工具名称、参数 Schema，本文未使用 |
| 结构约束 | 结构化输出 Schema，本文未使用 |

只统计客户反馈正文会低估请求规模。随着历史消息、工具和 Schema 增加，这种低估会变得明显。

### 2. 输出内容

模型输出同样占用上下文。应用必须在发送请求前预留输出空间，不能让输入独占整个窗口。

摘要场景的输出很短，但“短”仍应转化为明确上限。本文实验设置 `max_output_tokens=120`，作用是限制一次生成可以使用的最大输出预算，而不是要求模型必须生成 120 个 Token。

### 3. 推理内容

部分推理模型会在生成最终文本前使用推理 Token。官方文档将这些 Token 计入生成预算，因此可见文本长度可能小于应用为输出设置的上限。

如果任务启用了推理能力，容量规划应同时考虑：

- 可见回答需要的长度；
- 模型完成任务需要的推理空间；
- 达到上限后响应未完成的处理路径。

本文的计数实验不依赖长推理，但应用仍需依据实际模型和请求配置读取 `usage`，不能只测量屏幕上看见的摘要。

## 三、容量限制

### 1. 上下文窗口

上下文窗口是模型一次请求能够处理的 Token 总容量。对支持推理 Token 的模型，可以用下面的关系理解容量边界：

```text
输入 Token + 输出 Token + 推理 Token ≤ 上下文窗口
```

这是容量关系，不是计费公式。实际字段、限制和计费方式应以当前模型与 API 文档为准。

### 2. 输出上限

模型通常还会单独限制最大输出 Token。一次请求需要同时满足上下文窗口和输出上限，不能因为总窗口足够就忽略单次输出限制。

截至本文验证日期，`gpt-6-luna` 模型页列出的上下文窗口为 `1,050,000` Token，最大输出为 `128,000` Token。模型限制会随产品更新而变化，应用配置和文档都应记录核对日期，不能永久复制这一数值。

### 3. 应用预算

应用不应把模型公布的最大值直接当作日常请求目标。更稳妥的预算包含四部分：

| 预算 | 说明 |
|------|------|
| 固定输入 | 指令、工具和结构约束 |
| 业务输入 | 当前文本、附件和历史消息 |
| 输出预留 | 目标结果需要的最大空间 |
| 安全余量 | 模板变化、分词差异和重试策略留下的空间 |

客户反馈摘要可以先设置字符级业务上限，再通过 Token 计数做模型级检查。两层限制解决的问题不同，不应只保留其中一层。

## 四、用量观测

### 1. 请求前计数

Responses API 提供输入 Token 计数能力。下面的程序使用与摘要请求相同的模型、指令和输入，在真正生成文本前取得计数。

::: details 查看输入 Token 计数程序

```python
# count_tokens.py
from __future__ import annotations

import os

from openai import OpenAI


def main() -> None:
    """计算固定摘要请求的输入 Token，并输出计数结果。"""
    client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])
    model = os.getenv("OPENAI_MODEL", "gpt-6-luna")
    result = client.responses.input_tokens.count(
        model=model,
        instructions="将客户反馈压缩为一句中文摘要，不补充输入中没有的事实。",
        input="客户反馈：升级到 4.2.0 后，批量导出恢复正常，但首次打开报表仍需等待约 8 秒。",
    )
    print(result.input_tokens)


if __name__ == "__main__":
    main()
```

:::

在 Python 3.12.14、OpenAI Python SDK 3.19.2 和 `gpt-6-luna` 下，本文实测输出为：

```text
50
```

该结果只对应代码中完整的请求形状。增加工具、历史消息、结构约束或其他参数后，必须重新计数。

### 2. 响应后用量

真实生成请求返回的 `usage` 是本次执行的最终用量证据。样板请求的一次实际响应记录为：

```json
{
  "input_tokens": 60,
  "output_tokens": 34,
  "total_tokens": 94
}
```

计数接口得到的 `50` 与实际响应中的 `60` 不应被强行解释为固定差值。两条记录来自不同的请求配置：生成实验额外设置了推理与输出参数。工程上应保存完整请求配置，并分别把请求前计数用于容量预检、把响应 `usage` 用于本次执行核对。

### 3. 指标设计

生产环境至少应按模型、功能和请求结果聚合以下指标：

| 指标 | 主要用途 |
|------|----------|
| 输入 Token 分布 | 发现输入模板或历史消息持续膨胀 |
| 输出 Token 分布 | 发现模型生成过长或被过早截断 |
| 总 Token / 成功请求 | 观察完成一次业务任务的真实用量 |
| 未完成响应占比 | 发现预算不足或输入接近容量边界 |
| Token / 输入字符 | 发现语言或数据结构变化 |

平均值容易掩盖长尾请求。容量和时延分析应同时观察 P95、P99 与最大值。

## 五、超限处理

### 1. 请求前拦截

应用在发送请求前应执行以下顺序：

1. 校验业务字符上限和输入类型。
2. 组合最终指令、业务输入、历史消息和工具定义。
3. 使用当前模型计算输入 Token。
4. 加上输出预留和安全余量。
5. 超过应用预算时停止请求或进入压缩流程。

只有对“最终请求形状”计数，结果才可用于放行判断。先对原文计数、随后再追加大段指令和工具定义，会使预检失去意义。

### 2. 输入缩减

输入超过预算时，应根据业务信息优先级缩减，而不是从字符串末尾机械截断。

| 方法 | 适用条件 | 风险 |
|------|----------|------|
| 删除无关历史 | 多轮消息含重复上下文 | 可能丢失当前指代关系 |
| 分段处理 | 长文可按自然边界拆分 | 需要合并中间结果 |
| 检索相关片段 | 存在可查询的知识来源 | 检索遗漏会造成信息缺口 |
| 先结构化过滤 | 输入包含大量无关字段 | 过滤规则需要维护 |

客户反馈摘要通常应在业务入口限制单条反馈长度；长工单则需要分段和汇总策略，不能沿用单句示例。

### 3. 输出未完成

当生成达到 `max_output_tokens`，Responses API 可能返回 `incomplete`，并在 `incomplete_details.reason` 中指出 `max_output_tokens`。应用不能把已有片段当作完整结果继续处理。

合理处理顺序是：

1. 保存响应 ID、状态和 `incomplete_details`。
2. 判断任务是否确实需要更长输出。
3. 在模型限制和应用预算内调整输出上限。
4. 重新执行并再次验证完整状态。

如果输入已经接近上下文窗口，只增加输出上限并不能解决问题，还可能使请求没有足够总容量。

## 六、容量诊断

### 1. 请求被拒绝

请求在生成前因容量被拒绝时，先核对完整输入，而不是只检查用户最后输入的一句话。

诊断清单包括：

- 模型名称和当前上下文限制；
- `instructions`、历史消息、工具和 Schema；
- 请求前计数结果；
- 为输出和推理保留的空间；
- 最近是否新增了检索片段或隐藏模板。

### 2. 响应被截断

响应状态不是 `completed` 时，检查 `incomplete_details` 和实际输出用量。若原因为输出上限，先判断预期结果是否过长，再决定提高上限或缩小任务。

::: warning 不按句号判断完成
被截断的文本也可能刚好以句号结尾；完整文本也可能按业务格式不使用句号。应用应读取响应状态和结束原因，而不是用标点猜测。
:::

### 3. 用量持续上升

用量上升不一定来自用户输入。按下面顺序分解可以快速定位：

1. 比较业务输入字符数和 Token 数是否同步增长。
2. 比较固定指令、工具定义和 Schema 的版本变化。
3. 检查历史消息是否缺少裁剪策略。
4. 区分输入、输出与推理 Token 的增量。
5. 使用固定样本复现变化，并记录模型和参数版本。

只有确定增长来自哪一部分，才能选择缩短输入、调整输出、减少工具定义或更换模型。
