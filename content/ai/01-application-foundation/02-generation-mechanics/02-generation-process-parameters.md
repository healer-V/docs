# 生成过程与参数

调用模型时，除了要发送的文字，请求里还可以带几个参数，例如回答最多写多长、思考多少、措辞多随意。这些参数之所以有用，是因为模型生成回答的方式很特别：它不是从某处取出一段现成的答案，而是一个 Token 一个 Token 地往下写，每一步都从多个候选中选一个。

## 一、模型怎样写出回答

### 1. 一次写一个 Token

模型写回答的过程是一个循环：

1. 读入当前的全部内容，包括请求里的文字和已经写出的部分；
2. 给每个可能的下一个 Token 算出一个概率，例如读完“这家店物流很”之后，“快”的概率最高，“慢”次之；
3. 按概率选出一个 Token，接到已写内容的后面；
4. 回到第 1 步，直到回答结束。

每一步的选择都会影响后面的内容。第一句选了“速度很快”还是“发货及时”，接下来的句子就会沿着不同的方向写下去。所以同一个问题问两次，两段回答的措辞常常不同，即使意思一样。Token 是什么，见 [Token 与上下文窗口](./01-token-context-window.md)。

### 2. 什么时候停下来

循环在以下情况之一发生时结束：模型认为回答已经写完；写出的 Token 达到了请求设置的上限；请求被程序中途取消。

第二种情况下回答会写到一半就停住。所以应用不能只看“有没有返回文字”，而要读取响应的状态：OpenAI Responses API 的响应中，`status` 为 `completed` 表示正常写完，为 `incomplete` 表示没有写完，原因写在 `incomplete_details.reason` 中。读取状态的实际代码见 [Responses API 调用](../03-minimal-application/02-responses-api-call.md)。

## 二、三类生成参数

### 1. 参数一览

以 OpenAI Responses API 为例，影响生成的参数主要有三类。下表的说明依据 2026-11-26 核对的 [Responses API 参考](https://developers.openai.com/api/reference/resources/responses/methods/create)：

| 参数 | 控制什么 | 取值 |
|------|----------|------|
| `max_output_tokens` | 回答最多能用多少 Token | 整数，最小 16 |
| `reasoning.effort` | 推理模型回答前思考多少 | `none`、`low`、`medium`、`high` 等，默认 `medium` |
| `temperature`、`top_p` | 每一步怎样从候选中选 Token | `temperature` 为 0～2，默认 1；`top_p` 默认 1 |

一个同时设置三类参数的请求大致如下。这段代码只展示参数写在哪里，本文没有运行它，真实调用的完整步骤见最小应用一章：

```python
response = client.responses.create(
    model="模型名称",
    input="用一句话概括这条评价：物流很快，但尺码偏小。",
    max_output_tokens=200,
    reasoning={"effort": "low"},
)
```

### 2. 输出上限：最多写多少

`max_output_tokens` 是回答能使用的 Token 上限，不是要求写满的长度。设成 200，模型写完 30 个 Token 就可以正常结束。

这个上限同时包括可见的回答和推理模型的思考过程。思考用掉的 Token 也算数，所以上限设得太小时，推理模型可能还没写出一个字就用完了，响应状态变成 `incomplete`。另外，“只写一句话”“不超过 40 个字”这类要求说的是内容，应该写进指令并由程序检查，不能靠调小 Token 上限来实现：上限只会让回答在中途被截断。

### 3. 推理强度：思考多少

推理模型在写出回答之前，会先在内部“思考”：拆解问题、比较几种做法。`reasoning.effort` 控制这个思考的多少。参考文档说明，降低推理强度可以让响应更快、用在思考上的 Token 更少，而且不是每个推理模型都支持全部取值。

强度越高，通常越适合步骤多、容易出错的问题，但也更慢、更贵。概括一条评价这样的简单任务，用较低强度往往就够了。具体选多少，要用一组样本实际比较质量、耗时和费用，方法见 [任务与模型选择](../01-application-model-boundaries/03-task-model-selection.md)。

### 4. 温度：怎样从候选中选

`temperature` 改变每一步选 Token 的方式。参考文档的说明是：较高的值（如 0.8）让输出更随机，较低的值（如 0.2）让输出更集中、更确定。`top_p` 是另一种控制方式，只在概率排在前面的一部分候选中选择。文档建议一般只调其中一个，不要两个同时改。

温度不改变模型对候选的判断，只改变选择时是否偏向高分候选。下一节用一个小程序直观地看看这一点。

## 三、用一个小程序观察温度

### 1. 程序做了什么

程序虚构了一个场景：模型读完“这家店物流很”之后，给“快”“慢”“一般”“稳”四个候选分别打了分。程序在 0.2、1.0、1.8 三个温度下，把分数换算成每个候选被选中的概率，再按概率抽选 20 次，统计每个候选被选中几次。

::: info 实验环境与边界
程序只用 Python 3.12 标准库，不需要 API Key，也不联网。候选和分数是虚构的，换算方法是温度作用的常见示意，不是任何模型服务的内部实现；程序固定了随机种子，所以每次运行结果相同。
:::

在自己新建的空目录中操作，`python3.12` 需要指向已安装的 Python 3.12：

```bash
mkdir sampling-demo
cd sampling-demo
python3.12 --version
```

在当前目录新建 UTF-8 编码的 `sampling.py`。`probabilities()` 把分数除以温度后换算成概率，`main()` 对每个温度打印概率并抽选 20 次。

::: details 查看 sampling.py 完整代码

```python [sampling.py]
import math
import random
from collections import Counter

# 虚构的打分：假设模型读完“这家店物流很”之后，给几个候选 Token 的分数，分数越高越合适。
SCORES = {"快": 3.0, "慢": 1.5, "一般": 1.0, "稳": 0.5}


def probabilities(temperature: float) -> dict[str, float]:
    """把分数换算成每个候选被选中的概率；温度越低，高分候选的概率越集中。"""
    weights = {token: math.exp(score / temperature) for token, score in SCORES.items()}
    total = sum(weights.values())
    return {token: weight / total for token, weight in weights.items()}


def main() -> None:
    """对三个温度分别打印候选概率，并按概率抽选 20 次，统计每个候选被选中的次数。"""
    for temperature in (0.2, 1.0, 1.8):
        probs = probabilities(temperature)
        rng = random.Random(42)  # 固定随机种子，让每次运行的抽选结果相同
        picks = rng.choices(list(probs), weights=list(probs.values()), k=20)
        shown = "  ".join(f"{token} {p:.0%}" for token, p in probs.items())
        counts = dict(Counter(picks).most_common())
        print(f"温度 {temperature}：{shown}")
        print(f"  抽选 20 次：{counts}")


if __name__ == "__main__":
    main()
```

:::

### 2. 运行与观察

```bash
python3.12 sampling.py
```

2026-11-26 在 macOS、Python 3.12.16 上运行，退出码为 0，实际输出如下：

```text
温度 0.2：快 100%  慢 0%  一般 0%  稳 0%
  抽选 20 次：{'快': 20}
温度 1.0：快 69%  慢 15%  一般 9%  稳 6%
  抽选 20 次：{'快': 17, '慢': 2, '一般': 1}
温度 1.8：快 50%  慢 22%  一般 16%  稳 12%
  抽选 20 次：{'快': 11, '慢': 6, '一般': 2, '稳': 1}
```

温度 0.2 时，“快”的概率接近 100%（显示时四舍五入），20 次全选了“快”，结果几乎固定。温度 1.0 时，“快”仍然最常被选中，但“慢”和“一般”也各出现了几次。温度 1.8 时，概率被拉平，“快”只占一半左右，四个候选都出现过。

这说明了温度的作用：温度越低，选择越集中在最高分的候选上；温度越高，低分候选被选中的机会越大。但无论哪个温度，模型给各候选的打分都没有变，温度没有让模型“更懂”这家店的物流。

## 四、常见误解

### 1. 温度调到最低，结果就准确、就固定

温度低只是让选择集中在模型认为最合适的候选上。如果模型对这个问题的判断本身是错的，低温度只会更稳定地输出错误答案。另外，参考文档的措辞是“更集中、更确定”，并没有承诺每次完全相同；需要固定结果的部分，仍要由程序检查，方法见 [非确定性与事实校验](./03-nondeterminism-factuality.md)。

### 2. 参数在所有模型和接口上都一样

参数是否可用、取值范围多大，取决于具体的模型和接口。不是每个推理模型都支持所有推理强度；不同接口的参数名也不同，例如从其他接口照搬 `max_tokens` 到 Responses API 是错误的写法。在 openai Python SDK 3.59.0 中实测，这样写会在请求发出前报 `TypeError`，提示不认识 `max_tokens`。换模型或升级 SDK 后，要对照当时的文档重新检查参数。

### 3. 调参数能解决所有问题

回答缺少事实、格式不对、把分类弄错，原因往往在于输入的信息不够或者任务说得不清，而不是参数。调参数之前，先确认指令和输入是否完整；调的时候一次只改一个参数，并用同一组样本比较结果，否则说不清是哪个改动起了作用。

本文实验验证的是温度的示意计算：在虚构的分数下，温度越低，选择越集中。它没有调用模型，不说明任何模型在某个温度下的实际输出；参数说明依据官方参考文档，`max_tokens` 报错一项在本地 SDK 中实测，没有发送真实请求。
