# 生成过程与参数

文本生成不是从资料库中取出一段固定答案。模型根据当前上下文计算后续 Token 的概率，再按照请求配置选择 Token，循环生成直到满足停止条件。

理解这个过程后，参数不再是一组可以随意试调的旋钮：输出上限控制资源边界，推理参数影响解决问题的计算方式，采样参数影响候选 Token 的选择方式。

::: tip 参数必须服务于任务契约
先定义输出长度、事实边界和质量门槛，再选择参数。没有业务判据时，仅凭“读起来更自然”调参无法形成可复现结论。
:::

## 一、生成流程

### 1. 上下文构建

API 先把模型、指令、用户输入、历史消息、工具定义和结构约束组合成当前请求的上下文。上下文中的每一部分都会影响后续生成。

客户反馈摘要的最小上下文包括：

| 内容 | 本文示例 |
|------|----------|
| 任务指令 | 压缩为一句中文摘要，不补充事实 |
| 业务输入 | 客户反馈原文 |
| 输出边界 | 最大输出 Token |
| 推理配置 | `reasoning.effort` |
| 采样配置 | `temperature` |

参数不在文本中出现，但它们仍属于请求配置。保存实验记录时，不能只保存 Prompt。

### 2. Token 预测

模型在每一步为可能的后续 Token 计算分布。已经选择的 Token 会加入当前上下文，再影响下一步预测。

```text
请求上下文 → 候选 Token 分布 → 选择一个 Token
                         ↑              ↓
                         └── 更新上下文 ─┘
```

生成是一连串依赖前文的选择。早期一个措辞变化可能改变后续候选，即使最终两条摘要表达相同事实，字面文本也可能不同。

### 3. 停止条件

生成会在某个停止条件满足时结束，常见条件包括模型完成回答、达到输出上限或请求被中止。

应用不能只检查是否已有文本。Responses API 返回的 `status` 和未完成原因才是判断生成是否正常结束的主要证据。

## 二、输出参数

### 1. 输出上限

Responses API 使用 `max_output_tokens` 限制一次请求可生成的 Token。该上限包含可见输出，以及适用模型产生的推理 Token。

```python
response = client.responses.create(
    model=model,
    input="将这条客户反馈压缩为一句中文摘要。",
    max_output_tokens=120,
)
```

这个参数是资源上限，不是目标长度。模型可以在达到 120 个 Token 之前正常结束。

### 2. 结果完整性

输出上限过低时，响应可能处于 `incomplete` 状态。应用应读取状态和 `incomplete_details.reason`，不能把已有片段直接当作完整结果。

| 观察结果 | 判断 | 处理方向 |
|----------|------|----------|
| `completed` 且文本非空 | 生成过程完成 | 继续业务校验 |
| `incomplete`，原因为输出上限 | 预算不足 | 调整任务或上限后重试 |
| 状态异常但已有文本 | 结果仍不完整 | 保存证据并停止正常流程 |

### 3. 长度约束

“一句摘要”是语义要求，`max_output_tokens` 是资源限制，两者不能互相替代。

模型可能在较高上限下仍输出一句，也可能在较低上限下生成不完整的一句。需要严格字数、字段数或格式时，应使用应用校验或结构化输出，而不是只调整 Token 上限。

## 三、推理参数

### 1. 推理强度

支持推理配置的模型可以通过 `reasoning.effort` 调整解决任务时使用的推理强度。更高强度通常为复杂任务提供更多推理空间，同时可能增加延迟和 Token 消耗。

客户反馈摘要是短而聚焦的任务，本文实验显式设置 `reasoning={"effort": "none"}`，目的是把观察重点放在采样参数，不代表所有摘要任务都应固定关闭推理。

### 2. 任务匹配

推理强度应根据任务难度和错误代价评估：

| 任务 | 初始策略 | 验证重点 |
|------|----------|----------|
| 短文本改写 | 从较低强度开始 | 事实保持、延迟、成本 |
| 多约束分类 | 比较多个强度 | 边界样本准确率 |
| 复杂分析 | 为推理预留空间 | 结论证据与失败模式 |
| 高风险决策 | 不依赖模型单独决定 | 规则、数据源与人工审批 |

提高推理强度不能替代事实来源、权限控制和确定性业务规则。

### 3. 用量核对

推理 Token 可能不会全部显示在最终文本中。调高推理强度后，应同时比较：

- 任务质量是否跨过业务门槛；
- 输入、输出和推理相关用量；
- P50、P95 延迟；
- 未完成响应和错误率。

如果质量没有可测量改善，单纯增加推理成本没有工程收益。

## 四、采样参数

### 1. 温度

`temperature` 影响从候选 Token 分布中选择结果的方式。较低值通常让选择更集中，较高值通常增加变化空间，但它不是“准确率”或“创造力”的线性刻度。

本文使用同一模型、指令、输入和输出上限，只改变温度：

```python
response = client.responses.create(
    model="gpt-6-luna",
    reasoning={"effort": "none"},
    temperature=0.2,
    instructions=INSTRUCTIONS,
    input=f"客户反馈：{FEEDBACK_TEXT}",
    max_output_tokens=120,
)
```

### 2. 核采样

`top_p` 通过累计概率范围限制候选集合，是另一种采样控制方式。OpenAI 文档建议通常调整 `temperature` 或 `top_p` 其中一个，不要同时修改两者。

同时改变多个采样参数会破坏实验归因。即使输出变好，也无法判断是哪个参数产生作用。

### 3. 模型差异

参数是否支持、取值如何生效，取决于模型、API 端点和请求模式。应用应按照当前模型文档核对，并在升级模型或 SDK 后重新执行兼容测试。

::: warning 不从一次成功推断永久兼容
本文环境中的 `gpt-6-luna` 接受 `reasoning.effort="none"` 与 `temperature` 组合，只能证明当前模型、端点和 SDK 基线下该请求成功，不能替代其他模型的参数文档。
:::

## 五、对照实验

### 1. 实验条件

本文在 Python 3.12.14、OpenAI Python SDK 3.19.2 和 `gpt-6-luna` 下进行对照。固定输入为：

```text
升级到 4.2.0 后，批量导出恢复正常，但首次打开报表仍需等待约 8 秒。
```

两次请求都使用 `reasoning.effort="none"` 和 `max_output_tokens=120`，只改变 `temperature`。

### 2. 实际结果

| 温度 | 状态 | 输出 Token | 实际摘要 |
|-----:|------|-----------:|----------|
| `0.2` | `completed` | `33` | 升级至 4.2.0 后批量导出已恢复正常，但首次打开报表仍需等待约 8 秒。 |
| `1.2` | `completed` | `33` | 升级到 4.2.0 后批量导出已恢复正常，但首次打开报表仍需等待约 8 秒。 |

这组结果只出现“至”和“到”的措辞差异，关键事实一致。它证明温度变化没有保证文本一定明显变化，也不能据此断言某个温度更准确。

### 3. 结论边界

一对结果不能形成参数选型结论。有效实验还需要：

1. 使用覆盖正常与边界情况的固定样本集。
2. 每个配置重复运行，记录非确定性分布。
3. 按事实、覆盖、格式、延迟和成本评分。
4. 只改变一个参数，保存模型与 SDK 版本。
5. 达到业务门槛后再比较成本和时延。

参数的作用应由聚合结果证明，而不是用单条输出的主观观感判断。

## 六、参数诊断

### 1. 参数名称错误

不同 API 端点可能使用不同参数名称。Responses API 的输出上限参数是 `max_output_tokens`；把其他接口中的 `max_tokens` 原样迁移，会在本文 SDK 基线中触发客户端错误。

实际错误为：

```text
TypeError
Responses.create() got an unexpected keyword argument 'max_tokens'
```

该错误发生在请求发送前，因此没有 HTTP 状态或响应 ID。处理方式是核对当前 SDK 方法签名和 Responses API 文档，而不是重试网络请求。

### 2. 参数不受支持

如果参数通过 SDK 校验但被 API 拒绝，应保留以下证据：

| 证据 | 作用 |
|------|------|
| 模型与端点 | 确认兼容范围 |
| SDK 版本 | 排除本地接口差异 |
| HTTP 状态和错误体 | 判断服务端拒绝原因 |
| 请求 ID | 支持问题定位 |
| 最小复现参数 | 排除其他配置干扰 |

不要通过不断删除随机参数“试到成功”。先把请求缩减为最小配置，再逐项恢复需要的能力。

### 3. 输出不符合预期

请求成功但结果不符合预期时，按下面顺序排查：

1. 核对输入和输出契约是否明确。
2. 检查状态是否完成、输出是否被截断。
3. 使用固定样本重现，并只改变一个参数。
4. 比较质量、Token 和延迟，而不是只看文本差异。
5. 如果事实仍不可靠，增加验证或调整应用流程。

降低温度不能保证完全相同的输出，也不能保证事实正确。需要确定性的部分必须由程序规则、结构校验或可信数据源承担。
