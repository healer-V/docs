# 非确定性与事实校验

把同一条客户反馈交给模型概括三次，可能得到三句不同的摘要。一句只是把“升级到”换成了“升级至”；一句把“约 8 秒”写成了“约 8 分钟”；还有一句多出了“由于数据库较慢”，而原文根本没提原因。三句话读起来都很通顺，却只有第一句可以直接使用。

模型每次的回答可能不同，这叫非确定性。应用要做的不是让回答每次一字不差，而是在每次拿到回答后，检查其中的事实有没有被改动或编造。

## 一、同样的输入，不同的回答

### 1. 为什么每次不一样

模型一个 Token 一个 Token 地写回答，每一步按概率从候选中选一个，早一步选得不同，后面就会写得不同，原理见 [生成过程与参数](./02-generation-process-parameters.md)。调低温度能让选择更集中，但不能保证每次完全相同。OpenAI 的 [Text generation 指南](https://developers.openai.com/api/docs/guides/text) 说明，模型生成的内容是非确定性的，同一系列模型的不同版本也可能给出不同结果，并建议正式上线的应用固定使用具体的模型版本。

所以“测试时连续三次一样”不能推出“以后每次都一样”。必须每次都相同的值，例如订单号、金额、状态，应该由程序从数据库读取或计算，而不是让模型写。

### 2. 两种变化

回答之间的变化可以分成两种：

| 变化 | 例子 | 能否接受 |
|------|------|----------|
| 说法变了 | “升级到”变成“升级至”，语序调整 | 可以，意思没变 |
| 意思变了 | “约 8 秒”变成“约 8 分钟”；多出原文没有的原因 | 不可以，事实被改动或编造 |

因此，检查回答时不能要求它和某个标准答案逐字相同，那会把可以接受的改写也判成错误；而要检查其中的事实是否和原文一致。

## 二、怎样检查回答

### 1. 先列出必须保留的事实

检查之前，先从原文中列出摘要必须保留的事实。以开头的反馈为例，原文是“升级到 4.2.0 后，批量导出恢复正常，但首次打开报表仍需等待约 8 秒”，必须保留的事实有四项：

- 版本号 `4.2.0`；
- 批量导出已经恢复；
- 问题出在报表上；
- 等待时间约 `8 秒`。

摘要的措辞可以变，但这四项一项都不能少、不能改。另外，原文没有说明慢的原因，摘要里出现原因就是添加了原文没有的内容。

### 2. 三层检查

拿到回答后，可以从三个层次检查，每一层回答一个不同的问题：

| 检查 | 回答什么问题 | 摘要场景中的例子 |
|------|--------------|------------------|
| 格式 | 结果能不能被程序读取、是否完整 | 状态为已完成，文字不为空，长度不超限 |
| 事实 | 说的是不是真的 | 四项事实都在，没有原文以外的数字和原因 |
| 业务 | 能不能用在这个地方 | 只给客服参考可以；自动发给客户需要人确认 |

三层要依次通过。格式正确不代表事实正确，事实正确也不代表可以直接拿去执行操作。

原文以外的事实又是另一种情况：用户问“订单现在到哪了”，答案不在用户发来的文字里，模型也不会知道，应用必须先从订单系统查出来，再交给模型组织语言，并在结果中注明数据来源。

## 三、动手检查三次回答

### 1. 程序做了什么

下面的程序用开头的三句摘要模拟同一请求的三次回答，按第二节的事实清单逐句检查。`check()` 依次检查三件事：四项必需事实是否都出现；有没有原文以外的数字；有没有“由于”“导致”这类表示原因的词。

::: info 实验环境与边界
程序只用 Python 3.12 标准库，不需要 API Key，也不联网。三句回答由本文构造，用来模拟重复调用时可能出现的变化，不是真实模型的输出，也不代表真实模型出现这些错误的频率。
:::

在自己新建的空目录中操作，`python3.12` 需要指向已安装的 Python 3.12：

```bash
mkdir fact-check
cd fact-check
python3.12 --version
```

在当前目录新建 UTF-8 编码的 `fact_check.py`：

::: details 查看 fact_check.py 完整代码

```python [fact_check.py]
import re

SOURCE = "升级到 4.2.0 后，批量导出恢复正常，但首次打开报表仍需等待约 8 秒。"

# 摘要必须保留的事实：每一项都要在摘要中出现。
REQUIRED_FACTS = ["4.2.0", "批量导出", "报表", "8 秒"]

# 原文没有给出原因，摘要中出现这些词时，说明可能添加了原文没有的解释。
CAUSE_WORDS = ["因为", "由于", "导致"]

# 模拟同一请求的三次回答：措辞不同；数字被改；添加了原因。
REPLIES = [
    "升级至 4.2.0 后批量导出已恢复，但首次打开报表仍要等约 8 秒。",
    "升级到 4.2.0 后批量导出已恢复，但首次打开报表仍要等约 8 分钟。",
    "升级到 4.2.0 后批量导出已恢复，但由于数据库较慢，首次打开报表仍要等约 8 秒。",
]


def check(summary: str) -> str:
    """按事实清单检查一次摘要，返回处理结论。"""
    missing = [fact for fact in REQUIRED_FACTS if fact not in summary]
    if missing:
        return f"拦截：缺少或改变了事实 {missing}"
    extra_numbers = [n for n in re.findall(r"\d+(?:\.\d+)*", summary) if n not in SOURCE]
    if extra_numbers:
        return f"拦截：出现原文没有的数字 {extra_numbers}"
    causes = [word for word in CAUSE_WORDS if word in summary]
    if causes:
        return f"转人工：出现原因词 {causes}，原文没有给出原因"
    return "通过：可以显示"


def main() -> None:
    """逐个检查三次回答，打印回答内容和处理结论。"""
    for number, reply in enumerate(REPLIES, start=1):
        print(f"第 {number} 次：{reply}")
        print(f"  {check(reply)}")


if __name__ == "__main__":
    main()
```

:::

### 2. 运行与观察

```bash
python3.12 fact_check.py
```

2026-11-26 在 macOS、Python 3.12.16 上运行，退出码为 0，实际输出如下：

```text
第 1 次：升级至 4.2.0 后批量导出已恢复，但首次打开报表仍要等约 8 秒。
  通过：可以显示
第 2 次：升级到 4.2.0 后批量导出已恢复，但首次打开报表仍要等约 8 分钟。
  拦截：缺少或改变了事实 ['8 秒']
第 3 次：升级到 4.2.0 后批量导出已恢复，但由于数据库较慢，首次打开报表仍要等约 8 秒。
  转人工：出现原因词 ['由于']，原文没有给出原因
```

第 1 次只是措辞不同，四项事实都在，可以显示。第 2 次把“8 秒”改成了“8 分钟”，事实清单中的“8 秒”找不到，被拦截。第 3 次事实都对，却多出了“由于数据库较慢”，程序无法判断这个原因是不是真的，于是转给人确认。

第 3 次也说明了规则检查的局限：程序只认识列出来的几个原因词，换成“数据库慢，所以……”就发现不了。规则检查能挡住数字、版本号这类明确的错误，更细的语义问题需要人工审核，或者用一批样本统计评测。

## 四、检查不通过时怎么办

检查不通过时，应用要有事先设计好的处理方式，而不是把结果照样显示出来：

| 情况 | 处理方式 |
|------|----------|
| 格式不对或没写完 | 在次数限制内重新请求一次，仍失败就转人工 |
| 事实被改动或编造 | 不显示摘要，改为显示原文 |
| 需要的事实查不到 | 明确告诉用户“暂时无法确认”，不让模型猜 |
| 结果要用于退款、改权限等操作 | 无论检查是否通过，都要由规则和有权限的人决定 |

每次拦截都应记录原文、回答、模型版本和触发的规则，之后用这些记录改进指令和检查规则。

## 五、常见误解

### 1. 多问几次，选出现最多的那个

重新请求可以修复偶然的格式问题，但不能用来确认事实。模型几次都写出同一个错误数字，并不说明这个数字是对的。事实对不对，只能和原文或可信的数据核对。

### 2. 让模型自己说明是否确定

在回答里要求模型附上“我确定”或给自己打分，得到的仍然是模型写出来的文字，和回答本身一样需要检查。判断事实的依据应该来自原文、数据库或人，而不是模型的自我评价。

### 3. 测过几次没问题，上线就没问题

几次测试只覆盖了几种输入、几次生成。真实输入的写法更多，模型版本也可能更新。上线前要用一组覆盖各种情况的样本测试，上线后还要持续抽查，并在更换模型版本时重新测试，样本的准备方法见 [任务与模型选择](../01-application-model-boundaries/03-task-model-selection.md)。

本文实验验证的是事实检查程序的行为：给定一段原文和三句构造的回答，程序能放行措辞变化、拦截改动的数字，并把无法判断的原因转给人。它没有调用模型，不说明任何模型出错的频率；原因词检查是简化示例，真实应用需要更完整的规则或人工审核。
