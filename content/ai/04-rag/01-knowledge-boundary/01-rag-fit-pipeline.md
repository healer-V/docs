# RAG 适用条件与链路

检索增强生成（Retrieval-Augmented Generation，RAG）是在回答问题时检索外部资料，并把选中的资料提供给模型生成回答的方式。模型负责理解和表达，检索系统负责找候选，应用负责授权、证据选择和结果验收。

例如，客服需要回答“标准配送通常需要多久”。模型的训练知识不能代表当前店铺政策；应用可以检索现行配送资料，再让模型依据具体条款答复。**RAG 的价值来自可更新、可定位的外部证据，成立条件是资料本身可信、可用并足以支撑问题。**

## 一、外部知识与模型输入

### 1. 什么问题需要外部资料

模型参数是训练形成的内部表示，不能作为当前企业资料的版本记录。店铺政策、产品说明和内部流程会变化，也有访问范围；回答这些问题时，需要在请求中提供当前允许使用的资料。

资料已经很少且全部适用时，可以直接放入模型上下文。资料量大、问题只涉及其中一部分，或者资料有不同权限和版本时，检索可以减少无关输入，并留下候选与来源记录。

| 任务条件 | 外部信息要求 | 对 RAG 的影响 |
|----------|--------------|--------------|
| 政策会更新 | 使用现行版本及适用条件 | 索引需要及时更新并排除失效版本 |
| 资料量大 | 只选与问题相关的部分 | 需要评测召回和证据预算 |
| 不同身份可见范围不同 | 每次请求只使用获授权资料 | 权限参与检索及证据选择 |
| 回答需要出处 | 定位到原文和版本 | 保留文档、片段及来源映射 |

这些条件不能单独保证效果。资料缺少关键条款、解析丢失否定条件、检索未召回相关段落或生成歪曲原文，都会造成错误回答。

### 2. 检索结果为何需要再验收

检索算法回答的是“哪些候选更相关”，并不直接回答“哪份资料是正确事实”。一篇已撤回政策仍可以非常相关；同名店铺的资料也可以有很高相似度，但不属于当前租户。

应用应分别检查可见性、有效版本、相关性和证据支持。只有进入当前模型输入的片段，才能成为该次回答的引用候选；模型自行写出的文档名不构成来源证明。

::: warning 召回不等于事实正确
检索得分不能解释为答案正确概率。分数还受到检索模型、分词、索引和候选集合影响，不应直接用一个通用阈值承诺回答质量。
:::

## 二、入库链路与问答链路

### 1. 入库链路

入库链路把允许处理的原始资料转换为可检索对象。它可以定时运行或由资料变化触发，不要求每次提问都重新解析全部文档。

```text
登记来源与处理许可
→ 读取原始资料
→ 解析、清洗并保留结构
→ 切分为带元数据的片段
→ 建立关键词或向量索引
→ 验证并启用当前知识版本
```

解析提取正文和结构，清洗处理导航噪声等无关内容，切分把长文划为可检索单元。片段需要保留标题、条件和来源位置，否则一段单独看起来合理的文字会失去适用语境。

向量索引使用嵌入模型把文本映射为数值向量，以相似度查找候选；关键词索引依据词项匹配。两者都属于候选获取机制，RAG 不要求每个应用安装向量数据库。

### 2. 问答链路

问答链路接收具体问题和已认证身份，在允许访问的资料中寻找证据，再形成可校验回答。

```text
接收问题与身份上下文
→ 确定可见资料及有效版本
→ 检索候选，必要时重排
→ 去重并按预算组织证据
→ 使用问题和证据调用模型
→ 检查回答、引用和业务条件
→ 返回答案或明确的资料不足
```

这条链路至少会出现三种不同情况：没有可见候选；候选存在但不能回答；证据充分但生成结果不受支持。诊断时需要保留各阶段结果，不能把它们统一解释为“模型不够好”。

::: tip 两条链路共享资料标识与版本
入库确定文档及片段身份，问答使用这些身份定位证据。重建索引后，如果片段 ID 和来源映射不一致，旧引用就无法可靠复核；应把版本一致性作为更新条件。
:::

### 3. 核心对象

| 对象 | 例子 | 与其他对象的关系 |
|------|------|------------------|
| 来源 | 店铺配送政策发布流程 | 决定资料由谁提供、何时有效及允许怎样处理 |
| 文档 | `shipping-policy` | 同一逻辑资料可以有多个版本 |
| 片段 | `shipping-v1-01` | 文档中的一部分，需保留位置及必要语境 |
| 索引 | 关键词索引或向量索引 | 用于寻找片段，不替代原文及业务记录 |
| 候选 | 某次问题检索到的片段 | 未必全部进入生成输入 |
| 证据 | 当前请求实际使用的可见片段 | 由排序、去重、预算和版本规则确定 |
| 回答 | 配送时效及其引用 | 必须能映射到证据，并核对事实支持 |

索引是派生数据。它应能根据获准保存的原文和处理规则重建；如果只保留向量而丢失原文、权限和来源，应用难以解释回答或处理撤回。

## 三、与其他方式比较

### 1. 直接调用与长上下文

直接调用可以用于信息已经齐全的提取、分类和改写。长上下文方式把较多完整资料放入请求，减少独立检索环节，但仍要筛选授权资料、控制输入长度并验证输出。

资料完全放得下不代表模型一定正确使用所有信息。对较长输入，应测试不同资料位置、问题类型和无关内容的影响；不能把扩大上下文窗口当作证据验收的替代品。

### 2. RAG 与训练

RAG 在请求时引入外部资料，资料更新主要影响入库、索引和证据选择。训练或微调改变模型参数及行为，需要训练数据与独立评测；它不自动提供最新资料的引用和请求级授权。

| 方式 | 更合适的条件 | 应用仍需负责 | 典型边界 |
|------|--------------|--------------|----------|
| 直接调用 | 输入已经充分，任务范围稳定 | 输入校验和结果验收 | 模型不能补造当前业务事实 |
| 长上下文 | 资料量有限，任务需要整体比较 | 权限、长度、内容组织及事实核对 | 长输入中相关信息不一定得到正确使用 |
| RAG | 大量可更新资料，问题只涉及部分内容 | 入库质量、权限、检索、引用及维护 | 未召回证据不能靠生成补齐 |
| 训练或微调 | 需要调整稳定行为、表达或特定任务能力 | 数据治理、训练验证和发布 | 不代替即时知识读取和来源核对 |
| 业务 API 查询 | 要求当前订单等精确实时记录 | 身份授权、字段和更新时间核对 | 索引同步副本不能直接等同当前事务事实 |

这些方式可以组合。例如，用固定 API 取得订单状态，再检索配送规则解释其业务含义。组合后仍要区分订单事实与一般政策，保留各自来源。

## 四、售后场景判断

### 1. 政策更新

假设虚构店铺的政策版本 1 为“发出后 3 至 5 个工作日”，版本 2 为“特定活动期间发出后 5 至 7 个工作日”。问题涉及活动订单时，应用需要检索有效版本和适用条件。

如果版本 2 尚未进入有效索引，模型仍可能依据版本 1 给出过时答案。应检查来源发布时间、采集状态、索引版本及证据 ID；重新训练模型或修改措辞都不能替代这条更新链路。

版本 2 也不能无条件覆盖版本 1：不同时间或订单范围可能适用不同规则。是否启用、共存或撤回，应由资料契约决定。

### 2. 订单实时状态

“标准配送需要多久”是知识问题，“`ORD-2048` 此刻是否已签收”是业务记录查询。配送政策不能支撑某个订单已经签收的结论。

如果将订单快照放入索引，必须说明同步时间、数据延迟和适用范围。要求实时判断时，应读取权威业务接口并核对订单及返回时间；RAG 可以提供规则解释，不能把陈旧索引结果包装成实时查询。

### 3. 固定工单分类

工单分类只要求把已经提供的文字分为“配送咨询”“地址修改”等固定类别时，单次模型调用或确定性规则即可形成闭环。为这类任务额外检索无关知识，会增加输入、时延和失败点。

如果分类依据不断更新且有复杂例外的业务规则，则可以检索当前规则后分类。采用检索的理由是规则证据需要更新与追踪，不能仅因为任务使用了模型就增加 RAG。

## 五、诊断与适用边界

| 观察到的现象 | 优先检查的证据 | 处理方向 |
|--------------|----------------|----------|
| 回答使用旧政策 | 来源、采集与有效索引版本 | 修复更新或有效性判断 |
| 相关资料存在但未进入候选 | 查询、过滤条件、片段与检索排名 | 区分授权限制和召回损失 |
| 候选正确但模型未看到 | 实际证据 ID 和预算选择 | 调整证据组织，保留必要条件 |
| 引用存在但结论错误 | 引用原文与具体答案 | 检查事实支持及生成约束 |
| 用户看到其他租户信息 | 候选、模型输入及权限上下文 | 停止使用违规结果，修复前置授权 |

RAG 适合依赖外部知识的回答，并要求维护从来源到引用的链路。选择时先确认需要什么事实、由谁提供、多久更新、谁能使用，再决定资料输入和检索方案。缺少可信资料或成功条件时，增加检索组件不会自动解决问题。
