# 工程化面试题

前端工程化关注同一份源码能否在不同开发者和环境中稳定构建、验证与发布。讨论工具性能时，应先说清是在比较开发启动、代码修改后的反馈，还是生产构建。

## 一、为什么 Vite 开发启动通常比传统 Webpack 配置快？

**核心原因是开发阶段处理源码的时机不同。** Vite 将应用源码按浏览器请求转换为原生 ES Modules（ESM）；传统 Webpack 开发配置通常先从入口构建依赖图并产出可供浏览器使用的模块结果。因此，大项目首次打开少量页面时，Vite 不必预先处理所有尚未访问的应用模块。

### 1. 开发启动与热更新如何减少工作量

1. **启动：** Vite 启动开发服务器后，按浏览器实际访问转换源码；第三方依赖会进行必要的预构建与缓存。Webpack 也有持久化缓存和增量编译，不能说它每次保存一个文件都会从零重打包全部模块。
2. **热更新：** Vite 基于 ESM 模块边界通知浏览器更新受影响的模块；Webpack 的热模块替换（HMR）也能局部更新，但需要先完成对应构建过程。更新范围还取决于模块依赖、插件与框架组件边界。
3. **代价：** 按需转换把部分工作移到浏览器请求时；首次访问新的深层页面可能仍要等待转换。大量细碎模块、昂贵插件和依赖优化失效，也可能使 Vite 变慢。

::: tip 面试回答先限定比较阶段
可回答为“传统打包式开发配置通常在服务就绪前处理较大依赖范围，Vite 借助原生 ESM 按需提供应用源码，因此启动与局部更新往往更快”。不要把“开发快”直接推成“任何项目的生产构建都更快”。
:::

### 2. 为什么生产构建仍需比较

生产环境还需考虑代码拆分、压缩、兼容目标、资源缓存和请求数量，Vite 也会生成优化后的构建产物。Webpack 可以通过缓存、合理缩小编译范围和插件配置改善开发体验；两者表现不能脱离项目规模、依赖和目标浏览器比较。

| 比较场景 | 观察指标 | 可能的影响因素 |
|----------|----------|----------------|
| 冷启动 | 从运行命令到页面可交互的时间 | 依赖预构建、插件、入口大小 |
| 热更新 | 保存文件到浏览器显示新结果的时间 | 模块边界、依赖链、是否整页刷新 |
| 生产构建 | 构建耗时、产物体积和加载表现 | 压缩、拆包、缓存、兼容目标 |

验证时使用同一项目、同一硬件、相同页面和构建条件，分别记录冷启动与缓存后的结果。只比较终端打印“server ready”的时间，会漏掉首次页面请求的处理成本。

参考：[Vite：为什么选择 Vite](https://vite.dev/guide/why.html)、[Vite：依赖预构建](https://vite.dev/guide/dep-pre-bundling.html)、[Webpack：构建性能](https://webpack.js.org/guides/build-performance/)。

## 二、前端工程化解决什么问题，如何衡量价值？

**工程化是把依赖、构建、测试和发布约定固化为可重复执行的流程。** 它要减少“只在某个人电脑上能运行”、手工发布遗漏步骤以及多人协作时的质量漂移，而不是单纯增加工具数量。

### 1. 哪些环节需要形成闭环

1. **输入可复现：** 固定运行环境、依赖版本与包管理规则，使新成员和 CI 能得到一致的安装与构建结果。
2. **变更可验证：** 对代码进行格式、静态检查、必要的自动化测试和构建；失败时阻止有问题的产物进入发布流程。
3. **产物可追踪：** 记录源码版本、构建配置和部署产物的对应关系，出现故障时能够定位与回退。
4. **运行可观察：** 关注页面错误、性能和关键业务操作的结果，把线上反馈用于下一轮修复。

以订单页面为例，开发者提交修改后，CI 安装锁定依赖、运行检查并构建；发布系统部署经过验证的产物。若上线后错误率上升，团队可根据构建版本定位变更并回退，而不是依靠记忆还原手工操作。

### 2. 如何判断工程化是否真的有效

| 目标 | 可观察的证据 |
|------|--------------|
| 交付更稳定 | 构建可复现，发布失败与回退次数下降 |
| 反馈更及时 | 提交后检查耗时可接受，问题在上线前被发现 |
| 运行更可靠 | 错误率、关键操作成功率与页面性能有持续监测 |
| 协作成本更低 | 新成员能按文档完成环境准备，配置差异可定位 |

::: warning 自动化流程不能代替业务判断
测试通过只说明已覆盖的行为符合预期；权限、支付和数据迁移等高风险变更仍需明确验收与回退条件。新增检查也有维护和等待成本，应选择能降低真实失败风险的门禁。
:::

参考：[Webpack：构建性能](https://webpack.js.org/guides/build-performance/)、[Vite：生产构建](https://vite.dev/guide/build)。

## 三、Webpack 的 loader、plugin 和 HMR 分别解决什么问题？

**loader 转换模块内容，plugin 参与构建过程，HMR 在开发时替换已更新的模块。** 三者处于不同层次：不能把“能处理 CSS”当成 plugin 的定义，也不能把 HMR 等同于完整刷新页面。

1. **loader：** 模块进入依赖图后，按规则把源码转换成后续构建能处理的内容，例如转换 TypeScript 语法或处理 CSS。loader 的顺序与匹配范围会影响转换结果和速度。
2. **plugin：** 使用编译器提供的钩子参与更广的构建阶段，例如生成 HTML、抽取资源或输出分析报告。plugin 可以访问构建上下文，不局限于单个文件的内容转换。
3. **HMR：** 变更模块后，开发服务器发送更新，运行时沿依赖边界应用新模块；框架集成可能保留部分组件状态。更新无法被接受时通常退化为整页刷新。

面试中可用“修改一个样式文件”串起流程：loader 处理样式模块，plugin 可能抽取生产环境 CSS；开发时 HMR 将变化送到页面。**是否保留状态取决于更新边界和框架集成**，不是 HMR 天然保证。

参考：[Webpack：loader](https://webpack.js.org/concepts/loaders/)、[Webpack：plugin](https://webpack.js.org/concepts/plugins/)、[Webpack：HMR](https://webpack.js.org/concepts/hot-module-replacement/)。

## 四、Babel、TypeScript 编译器和 polyfill 各解决哪类兼容问题？

**语法转换、类型检查和运行时 API 补齐是三件事。** 能把可选链转换为旧语法，不意味着旧浏览器就有 `Promise`、`URL` 等运行时能力。

| 工具或步骤 | 主要职责 | 不会自动保证 |
|------------|----------|--------------|
| Babel / SWC 等转换器 | 按目标环境转换受支持的语法 | 所有运行时 API 都存在 |
| TypeScript 类型检查 | 检查源码中的类型约束 | 运行时参数一定符合类型 |
| TypeScript 输出 | 擦除类型并按配置转换语法 | 自动注入所有 polyfill |
| polyfill | 补齐目标环境缺少的内建 API | 转换不受支持的源码语法 |

因此，要先确定目标浏览器和运行环境，再检查构建目标、类型检查是否独立运行，以及缺失的 API 是否需要 polyfill。若构建链只做快速转译，CI 仍应单独运行 `tsc --noEmit` 等类型检查；不能以“产物构建成功”证明类型正确。

参考：[Babel：preset-env 与 polyfill](https://babeljs.io/docs/babel-preset-env#usebuiltins)、[TypeScript：tsc CLI](https://www.typescriptlang.org/docs/handbook/compiler-options.html)。

## 五、Tree Shaking、代码拆分与按需加载有什么区别？

**Tree Shaking 移除可静态判断为未使用的代码；代码拆分把产物分成多个块；按需加载决定何时请求某个块。** 三者可以共同降低首屏脚本成本，但分别回答“保留什么、如何分包、何时加载”。

1. ES Modules 的静态导入导出便于构建器分析引用；动态属性访问和无法证明无副作用的模块初始化会限制删除。`sideEffects` 标记是开发者对副作用的承诺，误标可能删掉必要代码。
2. 动态 `import()` 常形成异步边界，使订单详情的代码在进入相应页面时再下载。拆包过细会增加请求、解析和依赖调度成本。
3. 验证要比较**实际产物、首屏传输量与交互时间**。源码中“按需 import”不等于网络上必然少下载，还要检查公共块和预加载策略。

::: warning 不能用开发模式的模块请求数推断生产性能
开发服务器与生产构建的输出形式不同；应在生产构建和目标网络条件下测量。
:::

参考：[Webpack：Tree Shaking](https://webpack.js.org/guides/tree-shaking/)、[Webpack：代码拆分](https://webpack.js.org/guides/code-splitting/)。

## 六、锁文件与语义化版本为什么影响构建可复现性？

**`package.json` 描述允许的依赖范围，锁文件记录解析后的具体依赖图。** `^`、`~` 只是版本选择约束，不会独自固定所有间接依赖。

1. 提交锁文件，并让本地与 CI 使用同一包管理器及受控运行时版本；CI 使用对应的严格安装命令，例如 npm 的 `npm ci`，在锁文件与清单不一致时直接失败。
2. 更新依赖时审查锁文件差异，尤其是间接依赖、平台可选包和构建工具；不能只看顶层版本号。
3. 构建可复现还受 Node.js 版本、环境变量、系统依赖及远程构建输入影响。锁文件是必要条件之一，不是唯一条件。

面试追问“明明没改代码，为何 CI 失败”时，应检查安装命令、锁文件是否提交、运行时版本和缓存，而不是直接删除锁文件重新安装。

参考：[npm：package-lock.json](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json)、[npm：npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci)。

## 七、Source Map 应如何在生产环境使用？

**Source Map 把压缩产物的位置映射回源代码，便于定位线上异常。** 它不修复错误，也不代替发布版本号和可观测日志。

1. 为每次发布保留产物与对应映射文件，并在错误平台记录构建版本；否则同一压缩位置可能被错误地映射到另一版源码。
2. 根据暴露策略决定是否向浏览器公开映射文件。含源码的映射文件可能泄露实现细节，应限制访问或只上传到受控错误平台。
3. 验证时主动触发测试错误，检查上报堆栈能否映射到正确文件和行列；同时确认敏感信息没有进入日志或构建产物。

::: tip 先关联版本再定位代码
线上异常至少需要版本、页面、操作上下文和堆栈。只有一张“脚本错误”的截图，即使有 Source Map 也难以复现。
:::

参考：[MDN：Source Map](https://developer.mozilla.org/en-US/docs/Glossary/Source_map)、[Webpack：Devtool](https://webpack.js.org/configuration/devtool/)。

## 八、前端 CI/CD 应设置哪些门禁，发布失败如何回退？

**CI 验证变更，CD 将确定的构建产物发布到目标环境；回退要能恢复一份已验证的产物。** 重新从旧提交构建可能得到不同依赖或配置，不如按版本保留不可变产物可靠。

1. CI 固定依赖与运行时，依次完成静态检查、类型检查、关键测试和生产构建；测试范围随风险调整。
2. 发布记录源码版本、构建产物、配置版本与发布时间；先在小范围观察页面错误和关键操作成功率，再逐步扩大流量。
3. 指标恶化时停止扩大并恢复上一版产物，同时确认 HTML、静态资源与 API 的版本兼容。带内容哈希的旧资源需要在缓存有效期内仍可获取。

数据库迁移、服务端协议变化或客户端持久化数据格式变化会限制单独回退前端，因此发布前要确认跨版本兼容。**“构建通过”只证明构建阶段成功，不证明真实用户路径可用。**

参考：[Webpack：生产构建](https://webpack.js.org/guides/production/)、[web.dev：Core Web Vitals](https://web.dev/articles/vitals)。
