# 网络面试题

网络题不能只背固定流程。地址栏导航、页面中的 fetch、缓存命中与实时连接走的是不同路径；回答时先确定请求类型、协议版本、是否已有缓存或连接，再说明相应步骤。

## 一、地址栏输入 URL 后，浏览器如何完成一次导航？

**导航是解析地址、取得响应、构建页面并加载后续资源的过程。** DNS、建连和服务器取回完整 HTML 不一定每次都发生，缓存、Service Worker、重定向与连接复用都可能改变路径。

### 1. 请求发出前要判断什么

1. **确定目标：** 浏览器解析 URL 的协议、主机、端口和路径；地址栏输入也可能触发搜索、历史记录或浏览器内部页面，不能假定文本必然直接变为一个 HTTP 请求。
2. **查找可用资源：** 导航请求可能使用浏览器缓存或由已注册且控制该页面的 Service Worker 处理。需要访问网络时，才根据主机解析地址并选择可用连接。
3. **建立或复用连接：** 新 HTTPS 连接涉及传输层与 TLS 协商；HTTP/1.1、HTTP/2 常基于 TCP，HTTP/3 使用 QUIC。已有连接可以复用，不应说“每个资源都要重新做 TCP 三次握手”。

### 2. 响应返回后如何形成页面

1. **处理响应：** 浏览器可能跟随重定向，按缓存和内容类型处理最终响应；服务器也可能返回错误页、下载内容或非 HTML 资源。
2. **解析与加载：** HTML 解析形成 DOM，遇到样式、脚本和图片等再发起资源请求；CSS 形成样式信息，脚本的加载属性会影响执行与解析时机。
3. **布局与显示：** 浏览器根据 DOM、样式和视口计算布局、绘制并合成。JavaScript 修改 DOM 或样式后，相关阶段还可能再次进行。

::: tip 面试中按条件讲流程
先给“解析地址 → 获取响应 → 解析资源 → 布局绘制”的主线，再说 DNS、TLS、缓存、重定向与连接复用何时出现。把所有可选步骤背成一次导航的必经动作，会在缓存命中或 HTTP/3 场景下答错。
:::

参考：[MDN：HTTP 概述](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)、[MDN：页面加载性能](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/How_browsers_work)。

## 二、什么是同源策略，CORS 为什么需要服务端参与？

**同源由协议、主机和端口共同决定。** 浏览器允许发出许多跨源请求，但会限制页面脚本读取某些跨源响应；CORS（跨源资源共享）是服务器声明哪些来源可读取响应的机制。

### 1. 请求与响应读取要分开判断

1. **同源判断：** 页面 `https://shop.example` 请求 `https://api.example`，主机不同，属于跨源。路径不同但协议、主机和端口相同，则仍同源。
2. **普通跨源请求：** 浏览器可能把请求发出去，服务器也可能正常响应；若响应不满足 CORS 要求，页面脚本仍不能读取结果。不能把控制台报错理解为“请求一定没到服务器”。
3. **预检：** 使用某些方法、请求头或内容类型时，浏览器先发 OPTIONS 预检，询问服务器是否允许实际请求；预检通过后才继续。不是所有跨源请求都要预检。

### 2. 如何排查与配置

检查请求的 `Origin`、是否出现 OPTIONS、响应的 `Access-Control-Allow-Origin`、允许的方法与请求头，以及是否携带凭据。带 Cookie 等凭据的跨源请求还需客户端显式选择相应凭据模式，服务器返回允许凭据的响应；此时允许来源不能写成 `*`。

| 方案 | 适用边界 |
|------|----------|
| 服务端配置 CORS | 浏览器直接访问受控的跨源 API |
| 同源反向代理 | 浏览器请求自身来源，由代理转发到后端 |
| JSONP | 利用脚本加载的历史方案，只适合特定 GET 式读取，无法替代通用 HTTP API |

::: warning CORS 不是服务端鉴权
允许某个 Origin 读取响应，不代表该请求有权访问订单。服务端仍需校验身份、权限和输入；代理也不能自动消除后端的权限责任。
:::

参考：[MDN：CORS 指南](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)。

## 三、GET 与 POST 的本质区别是什么？

**主要区别是 HTTP 方法语义，而非参数只能放在哪里。** GET 请求获取资源的当前表示，按设计应为安全且幂等；POST 请目标资源按自身语义处理提交的内容，通常可能产生状态变化。

| 维度 | GET | POST |
|------|-----|------|
| 典型用途 | 查询订单详情或列表 | 创建订单、提交支付 |
| 安全与幂等 | 方法语义为安全、幂等 | 默认不保证幂等 |
| 请求内容 | 通常通过 URL 等方式表达查询；GET 请求体没有通用定义的语义 | 通常在请求体携带提交内容 |
| 缓存 | 符合缓存头规则时可复用响应 | 标准允许在明确条件下缓存，实际支持较少 |
| 重试 | 相同请求可按语义重试 | 写操作须评估重复执行风险 |

1. **URL 与请求体不是安全边界：** URL 更容易进入历史记录、日志和分享链路；POST 请求体也不因“不在地址栏”而自动保密。敏感数据依赖 HTTPS、权限控制及日志治理。
2. **大小限制不是固定数字：** URL、请求头和请求体都可能受到浏览器、代理或服务器的实现与配置限制，没有统一的“GET 最多 2 KB、POST 无限大”规则。
3. **业务幂等需单独保证：** 提交支付即使用 POST，也可以通过幂等键和服务端状态约束避免重复扣款；仅换成 GET 不会使有副作用的实现安全。

::: tip 回答重试时先问是否可能重复写入
连接中断后，客户端可能不知道服务端是否已经完成 POST。对创建和支付操作，应由服务端提供幂等保证或查询确认机制，不能只根据客户端超时决定再次提交。
:::

参考：[RFC 9110：HTTP 方法语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-9)、[RFC 9110：幂等方法](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)。

## 四、常见 HTTP 状态码如何按处理动作回答？

**状态码先给出处理结果类别，再由具体码说明下一步。** 不能只背“2xx 成功、4xx 客户端错误、5xx 服务端错误”，还要说明客户端是否应重试、跳转或修正输入。

| 状态码 | 含义 | 客户端常见处理 |
|--------|------|----------------|
| 200 / 201 / 204 | 成功 / 已创建 / 成功但无响应体 | 按响应契约解析；204 不按有 JSON 内容处理 |
| 301 / 302 / 307 / 308 | 重定向 | 按 Location 导航；307/308 保留原方法语义 |
| 304 | 条件请求所用表示未变化 | 配合已有缓存复用响应体 |
| 400 / 422 | 请求格式或语义无效 | 修正输入并提示用户 |
| 401 / 403 | 缺少有效身份 / 已识别但禁止访问 | 处理登录或权限提示，不无限重试 |
| 404 / 409 | 资源不存在 / 与当前状态冲突 | 核对资源标识或状态版本 |
| 429 | 请求过多 | 按服务端策略与 Retry-After 退避 |
| 500 / 502 / 503 | 服务端错误 / 网关上游问题 / 暂不可用 | 记录证据，按幂等性谨慎重试 |

### 1. 为什么 304 不能当普通成功响应处理

304 是条件 GET 或 HEAD 的缓存协商结果，表示客户端已有的响应表示仍可用。它不携带新的响应体；没有可用缓存时，单独拿到 304 也无法还原资源内容。

例如客户端已保存带 `ETag` 的订单列表，过期后用 `If-None-Match` 重新请求。服务器返回 304 时，客户端继续使用已保存的列表内容，并按缓存规则更新相关元数据；返回 200 时则用新的响应内容替换旧表示。排查“304 后仍为空白”要确认旧响应体是否实际存在。

### 2. 如何分析同一个状态码

1. **定位请求：** 记录方法、URL、请求发起位置和是否已经产生写入，避免脱离操作场景解读状态码。
2. **读取响应：** 结合 `Location`、`Retry-After`、认证挑战等相关响应头和业务错误体，确定是跳转、修正输入、重新认证还是等待。
3. **确认重试条件：** 401 并不自动要求清空所有本地状态，可能涉及刷新身份；429 要看服务端限流范围与等待时间。创建或支付等写操作还要先确认幂等策略，不能让所有客户端立即重试。

参考：[RFC 9110：状态码](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)。

## 五、强缓存与协商缓存分别减少什么工作？

**新鲜缓存可直接满足请求，协商缓存需与服务器确认旧表示还能否复用。** 二者围绕响应是否可用与是否新鲜，不是两套互不相干的存储系统。

### 1. 新鲜期内如何使用

服务器用 `Cache-Control: max-age=600` 等规则声明新鲜期。客户端在条件满足时可复用本地表示，通常不需要为同一资源再向源服务器取回完整响应。共享缓存还要考虑 `public`、`private`、`Vary` 等约束。

例如带内容哈希的静态脚本可在响应允许的有效期内直接复用，浏览器 Network 面板不会出现一次完整的源站响应体下载。判断是否真的命中新鲜缓存，还要核对请求与响应的缓存指令、资源 URL 是否变化，以及是否有强制重新验证的条件；不能仅凭“第二次更快”下结论。

### 2. 过期后如何协商

1. 若保存了 `ETag`，可发送 `If-None-Match`；若只保存了修改时间，可发送 `If-Modified-Since`。服务器判断表示未变时返回 304，客户端继续使用已有内容。
2. `Cache-Control: no-cache` 表示使用前需要重新验证，不等于完全禁止存储；`no-store` 才要求缓存不存储该响应。接口涉及个人数据时还需结合身份与共享缓存策略。
3. 验证时在开发者工具查看是否真正发生网络请求、请求与响应头，以及最终使用的内容。工具显示“来自缓存”与“304 协商后复用”不是同一种路径。

::: warning 304 不包含新的资源实体
若客户端没有保存旧响应体，304 本身不能展示页面资源。排查“页面空白但返回 304”时，要同时检查缓存是否被错误清理或中间代理是否返回了不一致的验证结果。
:::

参考：[RFC 9111：HTTP 缓存](https://www.rfc-editor.org/rfc/rfc9111.html)、[RFC 9110：304](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5)。

## 六、连接复用与 WebSocket 的“长连接”是一回事吗？

**不是。连接复用描述传输连接如何承载多个 HTTP 请求；WebSocket 是建立持久双向消息通道的协议。** 同一个 TCP 连接保持一段时间，并不意味着服务器已能按 WebSocket 语义主动推送消息。

1. **HTTP/1.1 持久连接：** 多个请求可复用连接，但请求与响应仍遵循 HTTP 语义。
2. **HTTP/2：** 可在一条连接上复用多个并发流；不能简化为“一次只处理一个请求”。HTTP/3 基于 QUIC，讨论时不应称其为 TCP 长连接。
3. **WebSocket：** 经过握手建立双向消息通道，适合持续互动；还需处理认证、心跳、断线重连和服务端资源。

::: tip 先说明是哪一层的“长”
面试题说“长连接”时先确认是 TCP 持久连接、HTTP 请求复用，还是 WebSocket 应用通道。比较前先对齐层级，才能解释保活、并发和推送能力。
:::

参考：[MDN：HTTP 概述](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)、[MDN：WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)。

## 七、轮询、长轮询、SSE 与 WebSocket 如何选择？

**核心差别是更新由谁发起、连接如何保持，以及通信方向。** 先看业务是否只要服务端推送，还是双方频繁交换消息，再看部署环境与故障恢复成本。

| 方案 | 通信方式 | 适合场景 | 主要代价 |
|------|----------|----------|----------|
| 定时轮询 | 客户端定期发 HTTP 请求 | 低频状态查询，实时性要求不高 | 空请求与响应延迟 |
| 长轮询 | 客户端发请求，服务端等到更新或超时再响应，客户端续发 | 需要推送体验但缺少流式通道 | 请求重建与超时管理 |
| SSE | 服务端通过 HTTP 流单向推送，浏览器常用 EventSource 接收 | 通知、进度、日志流 | 客户端上行仍需单独请求 |
| WebSocket | 双向消息通道 | 协作编辑、实时互动 | 连接管理、认证与消息协议 |

1. **可靠性：** 无论哪种方案，都应明确消息编号、断线恢复、重复消息和最终状态查询。SSE 可使用事件 ID 帮助续接，但服务端也要支持相应恢复逻辑。
2. **部署条件：** 代理超时、连接数和缓冲策略会影响长轮询与 SSE；WebSocket 要确认代理与负载均衡能处理升级或相应协议通道。
3. **选择例子：** 订单状态每几十秒检查一次可用轮询；持续输出构建日志可评估 SSE；需要双方即时协作时可评估 WebSocket。协议名称不能替代实际延迟、并发与故障恢复验证。

::: warning 实时通道不能代替最终状态查询
客户端断线期间可能错过更新。重连后要以服务端当前状态或可重放的事件序列校正界面，不能假定连接恢复就自动补齐所有业务消息。
:::

参考：[MDN：Server-Sent Events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)、[MDN：WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)。

## 八、HTTPS 的 TLS 握手和证书验证分别保证什么？

**TLS 在验证对端身份后协商连接密钥，并对传输数据提供加密与完整性保护。** HTTPS 不代表服务器业务逻辑可信，也不能阻止已登录用户自己发送越权请求。

1. 浏览器连接目标站点时，服务端提供证书链；浏览器校验证书的域名、有效期、签发链和信任状态。校验失败时不能简单忽略警告继续输入凭据。
2. 握手协商协议参数并建立共享密钥；后续 HTTP 数据在 TLS 连接中传输。TLS 1.3 的握手轮次受会话恢复等条件影响，不能背成所有 HTTPS 必经相同次数的往返。
3. 若页面仍通过 HTTP 加载脚本，或后端缺乏授权校验，HTTPS 无法替这些环节兜底。

排查证书报错时先检查访问域名、证书链及系统时间；排查接口 403 则应看授权逻辑。

参考：[MDN：TLS](https://developer.mozilla.org/en-US/docs/Web/Security/Transport_Layer_Security)、[RFC 8446：TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446)。

## 九、HTTP/1.1、HTTP/2 和 HTTP/3 对页面加载分别改变了什么？

**三者改变连接上的请求承载与传输方式，不能仅用“版本越高就一定越快”回答。** 页面收益仍取决于网络、服务器、资源安排和浏览器支持。

| 协议 | 关键变化 | 需要避免的误解 |
|------|----------|----------------|
| HTTP/1.1 | 持久连接可复用；浏览器常通过多个连接并行请求 | 不等于每个请求都重新建连 |
| HTTP/2 | 在一条连接上多路复用流，并压缩头部 | 基于 TCP，丢包仍可能影响该连接上的流 |
| HTTP/3 | 基于 QUIC，独立流减少传输层队头阻塞 | 不保证绕过应用自身依赖或拥塞 |

服务端可通过协商选择协议。面试问“HTTP/2 是否还需要域名分片”时，先解释旧方案旨在绕过连接并发限制，再说明在 HTTP/2 下额外域名可能增加 DNS、TLS 与连接成本；是否迁移要看实际部署。

参考：[MDN：HTTP 演进](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Evolution_of_HTTP)、[RFC 9114：HTTP/3](https://www.rfc-editor.org/rfc/rfc9114)。

## 十、DNS 解析与 CDN 缓存分别会如何影响请求？

**DNS 把主机名解析为可连接的地址；CDN 在靠近用户的节点提供可缓存资源。** DNS 命中只减少解析等待，不说明资源已缓存；CDN 命中也不能消除浏览器解析和执行脚本的时间。

1. 浏览器、系统与递归解析器可能有缓存，解析路径并非每次都从根服务器开始。DNS 记录有 TTL，但实际刷新时机还受各层缓存策略影响。
2. CDN 节点根据缓存键、响应头和自身配置决定是否复用内容。带个人信息的订单响应不能因为“走 CDN”就设为公共缓存。
3. 出现“有人看到旧页面”时，分别检查 DNS 解析结果、CDN 命中与回源、浏览器缓存、Service Worker 和 HTML 所引用的资源版本。

::: warning 静态资源和 HTML 采用不同缓存策略
带内容哈希的静态文件适合长期缓存；引用它们的 HTML 需要可及时更新。回滚期间应保留旧版本引用的资源。
:::

参考：[MDN：DNS](https://developer.mozilla.org/en-US/docs/Glossary/DNS)、[MDN：HTTP 缓存](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)。

## 十一、Cookie 的 SameSite、Secure、HttpOnly 能阻止哪些风险？

**三个属性作用不同：`Secure` 限制发送通道，`HttpOnly` 限制页面脚本读取，`SameSite` 控制跨站请求中的发送条件。** 它们都不能替代服务端会话校验与授权。

| 属性 | 解决的问题 | 边界 |
|------|------------|------|
| `Secure` | 仅经安全通道发送 Cookie | 无法阻止同源脚本发起带 Cookie 的请求 |
| `HttpOnly` | 防止 JavaScript 直接读取 Cookie 值 | XSS 仍可代用户执行操作 |
| `SameSite=Lax/Strict/None` | 限制跨站场景携带 Cookie | 与同源策略、CORS 不是同一个判断维度 |

跨站嵌入等确需 `SameSite=None` 的场景还需 `Secure`。敏感写操作仍应按威胁模型使用 CSRF Token、`Origin` 检查等服务端防护；`SameSite` 只是防线之一。诊断登录态丢失时，检查 Cookie 的域、路径、过期、SameSite、Secure 以及请求的 credentials 模式。

参考：[MDN：Cookie 指南](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)、[OWASP：CSRF 防护](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。

## 十二、PUT、PATCH、DELETE 的语义与幂等性如何区分？

**幂等指同一请求执行一次和执行多次，对服务端目标状态的预期效果相同；不等于每次响应状态码相同。** HTTP 方法语义是设计约定，业务实现仍可能违反它。

| 方法 | 典型语义 | 幂等性 |
|------|----------|--------|
| PUT | 用请求表示创建或替换目标资源 | 按方法语义应幂等 |
| PATCH | 对目标资源执行部分修改 | 取决于补丁语义与实现 |
| DELETE | 删除目标资源 | 按方法语义应幂等 |

例如“把订单备注设为已确认”可以重复执行而保持同一目标状态；“每次调用把金额增加 10”不具备这种性质。网络超时后，即使使用幂等方法，也要区分**目标状态**与外部副作用（通知、扣费）；支付等操作依赖服务端幂等键与唯一约束。

参考：[RFC 9110：方法语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-9)、[RFC 5789：PATCH](https://www.rfc-editor.org/rfc/rfc5789)。
