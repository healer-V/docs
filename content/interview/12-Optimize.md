# 项目常考面试题

项目面试题要说明“遇到什么问题、根据什么证据选择方案、实施后如何验证”，而不只是报出工具清单。下面用订单系统作为贯穿场景：用户访问订单页、登录、查看有权限的数据并完成注册或操作。

## 一、前端性能优化应先从哪里入手？

**先定位慢在网络、脚本、渲染还是交互响应，再针对证据处理。** 未测量就把压缩、CDN、懒加载和 `memo` 全部列上，无法说明哪个措施会改善当前用户体验。

### 1. 用哪些指标确定问题

| 用户感受 | 观察指标与证据 | 可能的瓶颈 |
|----------|----------------|------------|
| 首屏主要内容出现慢 | LCP、网络瀑布、主资源与关键图片时间 | 服务端响应、资源阻塞、图片或字体 |
| 点击后反馈慢 | INP、Performance 长任务、组件分析 | 主线程脚本、昂贵计算、布局 |
| 页面跳动 | CLS、布局偏移记录 | 图片或广告无尺寸、字体替换 |
| 订单列表滚动卡顿 | 帧时间、DOM 节点数、内存 | 大量节点、重复计算、绘制 |

先记录真实用户或稳定复现步骤，再用浏览器 Performance、Network 和框架分析工具找到耗时阶段。开发环境的额外检查可能改变结果，关键优化应在相同数据与生产构建下复测。

### 2. 根据瓶颈选择措施

1. **资源加载慢：** 减少首屏不需要的脚本和样式，压缩并正确缓存资源，按路由拆分非首屏代码。对关键图片给出合适尺寸和优先级，不要把首屏主要图片也延迟到滚动后才加载。
2. **交互计算慢：** 缩小状态更新范围，避免重复计算；长计算可分批或转移到 Worker。只有测出重复渲染确实昂贵，才评估缓存或组件跳过更新。
3. **DOM 与绘制慢：** 长列表评估分页或虚拟化，减少不必要的布局读写；动画优先选择能避免频繁布局的属性，但也要检查图层与显存成本。
4. **发布与缓存问题：** 为带内容哈希的静态产物设置合适缓存，确认 HTML 与旧产物兼容和回退路径。CDN 改善传输距离，不能自动解决主线程阻塞。

::: tip 优化结论必须有前后证据
回答“把订单列表改为虚拟化”时，应交代原始节点数量、复现操作、目标指标、改动后的耗时与副作用。不能只说“用了虚拟列表，性能提升很多”。
:::

### 3. 哪些做法可能适得其反

过度拆包会增加后续导航请求；大量 `will-change` 会增加内存压力；无依据地加缓存会使状态依赖复杂；骨架屏只能改善等待感受，不会缩短数据真实到达时间。优化需要同时复测可访问性、功能正确性和内存占用。

例如把订单详情拆成许多极小分块后，首屏脚本可能减少，但每次进入详情页都要等待更多资源发现和请求。应在相同网络、缓存状态与订单数据下比较首屏和后续导航，而不是只看打包产物体积。对 `will-change` 也应观察图层数量与内存变化，确认收益后才长期保留。

参考：[web.dev：Web Vitals 工具](https://web.dev/articles/vitals-tools)、[web.dev：渲染性能](https://web.dev/articles/rendering-performance)。

## 二、登录鉴权如何设计，前端承担哪些职责？

**认证回答“你是谁”，授权回答“你能访问什么”。** 前端负责收集凭据、发起登录、维护登录体验和处理过期状态；服务端负责验证身份、签发或管理会话，并在每个受保护请求上执行授权。

### 1. 先选择会话方式

| 方式 | 核心机制 | 主要考虑 |
|------|----------|----------|
| 服务端会话 + Cookie | 浏览器携带会话标识，服务端查会话 | 会话存储、Cookie 属性与 CSRF 防护 |
| BFF（前端专用后端） | 浏览器使用受保护 Cookie，BFF 代管上游令牌 | 多一层服务，令牌不必暴露给页面脚本 |
| 浏览器直接使用访问令牌 | 页面向 API 携带令牌 | 令牌暴露与更新、XSS 风险更难管理 |

OAuth 2.0 是授权框架，OpenID Connect 才在其上提供标准化身份信息；单点登录（SSO）是跨多个应用共享登录体验的架构目标。它们不是与 Cookie、JWT 并列且只能四选一的“登录方式”。JWT 也只是令牌格式之一，是否可撤销取决于服务端设计。

### 2. 一次登录的完整路径

1. 用户通过 HTTPS 提交凭据；服务端验证账号、密码或其他认证因子，并处理失败次数与风险。
2. 服务端建立会话并设置 `HttpOnly`、`Secure` 和适当 `SameSite` 的 Cookie，或按已选择的架构交付受限令牌。前端根据响应进入已登录界面。
3. 后续订单请求由服务端检查会话有效性与订单归属。前端遇到 401 时按协议重新认证或恢复会话；遇到 403 时显示权限不足。
4. 登出时服务端使会话或刷新凭据失效，前端清理本地界面状态。仅删除前端变量不能保证已签发凭据失效。

::: danger 不要把长期认证凭据放进 Web Storage
`localStorage` 和 `sessionStorage` 可被同源页面脚本读取，XSS 会扩大令牌泄露风险。使用受保护 Cookie 或 BFF 时，仍要根据请求方式处理 CSRF、Cookie 作用域与会话固定等风险。
:::

参考：[OWASP：会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)、[OWASP：认证](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)。

## 三、访问令牌与刷新令牌为何要分开？

**短期访问凭据减少泄露后的有效时间，刷新凭据用于在用户会话仍有效时换取新访问凭据。** “双 Token”不自动安全；刷新令牌更敏感，必须有存储、重放检测、撤销和过期策略。

### 1. 正常刷新与并发请求如何处理

1. API 返回表示访问凭据过期的认证失败，客户端先确认这是可刷新状态，而不是密码变更、权限不足或会话已撤销。
2. 同一时刻多个请求过期时，只发起一次刷新；等待中的请求共享结果。刷新成功后按新凭据重试原请求，最多按协议重试一次，避免无限循环。
3. 刷新失败时清理客户端登录状态并引导重新认证。创建订单或支付等写请求不能因为“没收到响应”就盲目重试，仍要考虑服务端幂等性。

### 2. 服务端为什么要轮换刷新凭据

对公开客户端，如果签发刷新令牌，OAuth 安全最佳实践要求采用发送方约束或刷新令牌轮换来检测重放。轮换会签发新凭据并使旧凭据失效；旧凭据再次出现时，应按服务端策略撤销相关凭据并要求重新授权。

| 风险 | 必须有的处理 |
|------|--------------|
| 刷新凭据泄露 | 受保护存储、作用范围限制、重放检测 |
| 用户登出或改密 | 服务端撤销会话或刷新凭据 |
| 多个请求同时过期 | 单次刷新与请求排队，避免互相覆盖 |
| 设备长时间闲置 | 闲置过期与重新认证 |

::: warning 刷新成功不等于原请求一定安全重试
客户端取消、断网或超时无法证明服务端没有处理写操作。对有副作用的接口，应先定义幂等键与结果查询方式，再决定自动重试范围。
:::

参考：[RFC 9700：OAuth 2.0 安全最佳实践](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14)、[OWASP：会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

## 四、页面、按钮和数据权限应该如何配合？

**前端权限控制改善导航与操作体验，服务端授权才决定数据与动作是否允许。** 隐藏按钮、删除路由或修改菜单都不能阻止用户直接构造 HTTP 请求。

### 1. 三种权限处在不同层次

| 层次 | 前端职责 | 服务端职责 |
|------|----------|------------|
| 页面与菜单 | 按当前身份展示可访问入口，处理直接打开无权页面 | 对页面依赖的 API 继续校验 |
| 按钮与操作 | 隐藏或禁用不可执行命令，并说明原因 | 在每个写接口核对动作权限 |
| 数据与资源 | 仅展示服务端返回的可见数据 | 校验租户、订单归属、字段与行级范围 |

### 2. 如何设计授权链路

1. 服务端定义角色或属性与资源、动作的关系，按实际业务采用 RBAC（基于角色的访问控制）或更细的属性条件。
2. 登录后前端获取用于界面展示的权限信息，决定菜单与按钮状态；用户权限变化时及时刷新，不把过期权限当作服务端许可。
3. 每个受保护 API 根据可信身份与目标资源重新授权。查询订单详情时，即使两个用户都有“查看订单”按钮，也必须检查该订单是否属于可访问范围。
4. 测试既要检查无权用户看不到入口，也要直接发送绕过前端的请求，确认服务端返回 403 或按隐私策略隐藏资源存在性。

::: danger 前端路由守卫不是安全边界
路由配置和按钮条件都能被绕过。真正的越权防护必须在服务端，对每次资源读取和修改都使用可信身份与资源范围判断。
:::

参考：[OWASP：授权](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

## 五、手机号注册如何防止冒用与滥用？

**手机号注册至少要证明申请者当前能接收该号码的验证码，再由服务端创建账户。** 前端表单只能改善输入体验，不能单独证明手机号归属、阻止机器请求或安全保存密码。

### 1. 注册流程如何闭合

1. 前端收集手机号及必要的账户信息，通过 HTTPS 请求服务端发送一次性验证码。服务端规范化号码并限制发送频率、总量和目标号码的请求次数。
2. 服务端生成有有效期、使用次数限制的随机验证码，关联号码和注册会话；不得把验证码明文长期保存在可读日志中。
3. 用户提交验证码后，服务端验证匹配、过期、重放与尝试次数，再创建账户。账户创建应防重复并考虑并发注册。
4. 注册成功后由服务端建立会话或要求再次登录；前端处理倒计时、错误提示和防重复提交，但不把倒计时当作服务端限流。

### 2. 密码与验证码各有什么安全边界

- 浏览器与服务端之间必须使用 HTTPS；浏览器自行“加密一次密码”不能替代传输保护。
- 若注册需要密码，服务端使用适当的自适应密码哈希算法保存校验信息，不保存明文或可逆密文。
- 图形挑战或行为验证可提高批量攻击成本，但不能替代验证码次数限制、账户枚举防护与服务端风控。
- 注册接口的“号码已存在”提示要结合产品体验与枚举风险设计，错误日志应保留追踪信息但避免泄露凭据。

::: warning 验证码发送成功不等于完成身份验证
只有服务端在创建账户时核对有效验证码，并将其一次性消费，才能证明当前注册流程通过了号码验证。客户端提交一个“已验证”布尔值没有可信性。
:::

参考：[OWASP：认证](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)、[OWASP：密码存储](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)、[OWASP：忘记密码流程中的验证码控制](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)。

## 六、项目中如何区分并防护 XSS 与 CSRF？

**XSS 让攻击者脚本在可信页面执行；CSRF 借用浏览器自动携带的登录凭据发起非预期请求。** 二者攻击入口不同，但 XSS 可绕过不少基于页面可信性的 CSRF 防护，因此输入输出处理是基础。

| 风险 | 常见入口 | 优先处理 |
|------|----------|----------|
| XSS | 用户内容被当作 HTML 或脚本执行 | 默认文本转义、避免不可信 HTML、必要时严格净化并配置 CSP |
| CSRF | 跨站页面诱导浏览器发送带 Cookie 的写请求 | 服务端校验 CSRF Token 或 Origin、设置合适 SameSite、避免 GET 修改状态 |

订单备注展示时，使用框架的文本渲染而不是把用户输入直接交给 `innerHTML`。若确需富文本，明确允许的标签和属性并使用经过维护的净化方案。对取消订单等写操作，服务端应核对会话、权限和 CSRF 防护；前端隐藏按钮不能构成安全边界。

::: warning `HttpOnly` 不能让 XSS 变得无害
它能阻止脚本直接读取 Cookie，但恶意脚本仍可在当前页面发起用户有权执行的请求。要同时防止脚本注入和越权操作。
:::

参考：[OWASP：XSS 防护](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)、[OWASP：CSRF 防护](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。

## 七、订单列表渲染卡顿时，如何判断该分页还是虚拟化？

**先确认瓶颈是数据传输、主线程计算还是大量 DOM 节点。** 分页减少一次获取和展示的数据；虚拟化保持长列表的连续浏览体验，但只渲染视口附近的条目。

1. 用相同数据和设备复现滚动、筛选与选择操作，记录 DOM 节点数、长任务和内存；接口慢则先看服务端分页或查询。
2. 用户按页处理订单时，服务端分页通常更简单；需要连续滚动浏览大量订单时，可评估虚拟化。
3. 虚拟化要处理动态行高、焦点、键盘导航、搜索定位、选中状态和读屏体验；它不减少已下载数据，不能代替服务端分页。

改造后比较首屏、滚动帧时间、内存与任务完成率。**只展示“DOM 从一万降到几十”不足以证明业务体验改善**，还需验证定位和选择不会丢失。

参考：[web.dev：虚拟化长列表](https://web.dev/articles/virtualize-long-lists-react-window)、[web.dev：渲染性能](https://web.dev/articles/rendering-performance)。

## 八、搜索建议和订单提交为什么需要不同的请求去重策略？

**搜索是“只显示最新结果”的读取；提交订单是“不能重复生效”的写入。** 前者可取消旧请求并校验响应序号，后者必须由服务端提供幂等保证。

1. 搜索输入变化时用 `AbortController` 取消上一次 `fetch`，并在响应到达时确认查询词仍是当前值；取消不保证服务器没有处理请求。
2. 订单提交时按钮可临时禁用以改善交互，但刷新、重试、双设备或网络超时仍会产生重复请求风险。
3. 写操作使用服务端支持的幂等键和唯一业务约束；超时后先查询订单状态或用同一个键重试，不能盲目生成新键再次提交。

面试回答应说明失败场景：如果请求已在服务器完成但响应丢失，客户端无法靠“按钮只点一次”判断是否成功。

参考：[MDN：AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController)、[RFC 9110：幂等](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)。

## 九、线上白屏或报错时，如何建立可定位的监控链路？

**先把用户看到的故障和发布版本、页面、操作及可复现证据关联。** 单纯统计 `window.onerror` 次数会遗漏请求失败、资源加载失败和业务上的空状态。

1. 为每次构建生成可追踪版本，收集脚本异常、资源错误、接口失败、关键操作成功率和 Web Vitals，避免上报密码、令牌与用户私密内容。
2. 把错误分组并结合 Source Map 还原堆栈，记录发生的路由、浏览器版本与时间；对异常突增设置告警阈值。
3. 先判断是否由最近发布引起，必要时回退；随后用相同环境与请求条件复现并修复。监控 SDK 自身应限制流量和失败重试，不能加重白屏。

::: tip 以业务结果验证恢复
错误量下降只是一个信号；还要确认用户能打开订单页、加载数据并完成关键操作。
:::

参考：[MDN：Window error 事件](https://developer.mozilla.org/en-US/docs/Web/API/Window/error_event)、[web.dev：Web Vitals](https://web.dev/articles/vitals)。

## 十、前端静态资源发布为何会出现旧 HTML 引用失效文件？

**HTML 与带哈希的静态资源可能在不同缓存层、不同时间完成更新。** 如果先删除旧资源，再让缓存中的旧 HTML 继续被访问，浏览器就会请求已经不存在的文件。

1. 构建产物使用内容哈希命名；HTML 保持可更新，旧版本静态文件在可能的缓存和回退窗口内继续可用。
2. 部署顺序先上传新静态资源，再切换 HTML 或入口；回退时恢复对应版本的入口，并确认 API 兼容。
3. 发生白屏时检查失败请求的 URL、HTTP 状态、HTML 内容、CDN 缓存和 Service Worker 版本，定位到底是哪一层指向旧文件。

仅清浏览器缓存可帮助定位，不是完整修复。**发布协议要允许新旧页面在短期内并存。**

参考：[MDN：HTTP 缓存](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)、[web.dev：缓存最佳实践](https://web.dev/articles/love-your-cache)。
