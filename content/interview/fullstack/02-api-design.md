# 接口设计面试题

接口是前后端之间的契约，一旦被客户端使用，修改成本就远高于修改内部实现。接口设计题的回答重点是：语义是否符合 HTTP 规范，失败时客户端能否做出正确处理，以及接口如何在不破坏旧客户端的前提下演进。

## 一、REST 与 HTTP 语义

### 1. RESTful 接口应如何设计？

**RESTful 接口用 URL 表示资源，用 HTTP 方法表示对资源的操作，用状态码表示结果。** 资源使用名词复数，层级关系通过路径表达。

| 操作 | 方法与路径 | 成功状态码 |
|------|------------|------------|
| 查询订单列表 | `GET /orders?status=paid` | 200 |
| 查询单个订单 | `GET /orders/1001` | 200 |
| 创建订单 | `POST /orders` | 201，`Location` 头指向新资源 |
| 整体替换 | `PUT /orders/1001` | 200 或 204 |
| 部分修改 | `PATCH /orders/1001` | 200 或 204 |
| 删除订单 | `DELETE /orders/1001` | 204 |
| 查询订单的商品 | `GET /orders/1001/items` | 200 |

“取消订单”这类无法自然映射为增删改的业务动作，可以建模为子资源 `POST /orders/1001/cancellation`，或采用约定的动作路径 `POST /orders/1001:cancel`。关键是在整个 API 中保持一致，而不是追求形式上的“纯 REST”。

参考：[RFC 9110：HTTP 语义](https://www.rfc-editor.org/rfc/rfc9110)、[Google API 设计指南：自定义方法](https://cloud.google.com/apis/design/custom_methods)。

### 2. 哪些 HTTP 方法是安全和幂等的，PUT 与 PATCH 有什么区别？

**安全方法不改变服务器状态，幂等方法执行一次和多次的效果相同。** GET、HEAD、OPTIONS 既安全又幂等；PUT 和 DELETE 不安全但幂等；POST 和 PATCH 既不安全也不保证幂等。

| 方法 | 安全 | 幂等 | 说明 |
|------|------|------|------|
| GET | 是 | 是 | 不应产生业务副作用 |
| PUT | 否 | 是 | 用请求体完整替换资源，重复执行结果相同 |
| DELETE | 否 | 是 | 第二次删除可返回 404，但资源状态相同 |
| POST | 否 | 否 | 重复提交可能创建多个订单 |
| PATCH | 否 | 不保证 | 取决于补丁格式，如“数量加一”不幂等 |

幂等的意义在于重试：网关或客户端在超时后可以安全地重试 GET、PUT、DELETE，而 POST 重试需要幂等键保护。用 GET 执行删除等操作是严重错误，浏览器预加载、爬虫和缓存都可能自动发出 GET 请求。

参考：[RFC 9110：安全方法与幂等方法](https://www.rfc-editor.org/rfc/rfc9110#name-common-method-properties)、[RFC 5789：PATCH](https://www.rfc-editor.org/rfc/rfc5789)。

### 3. 状态码应如何选择，错误响应应包含什么？

**状态码让客户端和中间件（网关、监控、重试逻辑）无需解析响应体就能判断结果类别；响应体提供机器可读的错误码和便于排查的信息。**

| 状态码 | 含义 | 典型场景 |
|--------|------|----------|
| 400 | 请求格式或参数错误 | JSON 解析失败、字段缺失 |
| 401 | 未认证 | 缺少或过期的令牌 |
| 403 | 已认证但无权限 | 普通用户访问管理接口 |
| 404 | 资源不存在 | 订单 ID 不存在 |
| 409 | 与当前状态冲突 | 重复创建、版本号冲突 |
| 422 | 格式正确但业务校验失败 | 库存不足 |
| 429 | 请求过多 | 触发限流 |
| 500 / 502 / 503 | 服务端错误 / 上游错误 / 暂不可用 | 客户端可按策略重试 |

“所有响应都返回 200，用响应体中的 `code` 字段区分成功失败”会让网关监控把错误统计为成功，也让通用重试逻辑失效。RFC 9457 定义了标准错误格式 `application/problem+json`，包含 `type`、`title`、`status`、`detail` 和 `instance` 字段，可在此基础上扩展业务错误码和请求追踪 ID。

::: warning 错误信息不要泄露内部细节
响应中不要返回数据库异常、SQL 语句或堆栈；这些信息记录在服务端日志中，通过追踪 ID 关联。登录失败时统一提示“用户名或密码错误”，避免攻击者枚举存在的账号。
:::

参考：[RFC 9457：Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457)。

## 二、分页与演进

### 1. 偏移分页和游标分页如何选择？

**偏移分页用 `page` 和 `size` 计算 `OFFSET`，支持跳页但深分页性能差；游标分页用上一页最后一条记录的排序键作为游标，性能稳定但只能顺序翻页。**

| 维度 | 偏移分页 `?page=50&size=20` | 游标分页 `?after=eyJpZCI6MTAwMX0&limit=20` |
|------|-----------------------------|---------------------------------------------|
| 跳到任意页 | 支持 | 不支持 |
| 深分页性能 | 越往后越慢 | 稳定，走索引定位 |
| 数据变化时 | 新增或删除会导致重复或遗漏 | 不受前面数据变化影响 |
| 适用场景 | 后台管理表格 | 信息流、无限滚动、开放 API |

游标通常是排序字段值的编码，例如把 `{"createdAt": "...", "id": 1001}` 做 Base64 编码；排序字段不唯一时必须加上 ID 作为第二排序键，否则相同时间的记录可能被跳过。游标对客户端应是不透明的字符串，服务端可以修改内部格式而不破坏客户端。

参考：[GitHub GraphQL API：分页](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api)。

### 2. 接口如何做版本管理和兼容演进？

**优先通过向后兼容的方式演进接口，只有不可避免的破坏性变更才发布新版本。** 版本可以放在路径（`/v2/orders`）、请求头或媒体类型中，路径方式最直观，便于网关路由。

| 变更 | 是否兼容 | 说明 |
|------|----------|------|
| 新增可选请求字段 | 兼容 | 旧客户端不传，服务端使用默认值 |
| 响应中新增字段 | 兼容 | 前提是客户端忽略未知字段 |
| 删除或重命名字段 | 破坏 | 旧客户端读取失败 |
| 修改字段类型或含义 | 破坏 | 如金额从“元”改为“分” |
| 新增必填请求字段 | 破坏 | 旧客户端请求被拒绝 |
| 枚举新增取值 | 可能破坏 | 客户端使用穷举判断时会出错 |

废弃旧版本时，先在响应头中声明弃用与下线时间，统计旧版本的调用方和调用量，通知迁移后再下线。RFC 8594 定义了 `Sunset` 响应头，用于告知资源停止服务的时间。

参考：[RFC 8594：Sunset HTTP Header](https://www.rfc-editor.org/rfc/rfc8594)。

## 三、接口风格选择

### 1. REST、GraphQL 和 gRPC 如何选择？

**REST 适合面向资源的通用 HTTP 接口，GraphQL 适合客户端需要灵活组合数据的场景，gRPC 适合服务之间高性能、强类型的内部调用。**

| 维度 | REST | GraphQL | gRPC |
|------|------|---------|------|
| 数据获取 | 服务端决定返回结构 | 客户端声明需要的字段 | 由 Protobuf 定义 |
| 传输 | HTTP，通常 JSON | HTTP，通常单一 POST 端点 | HTTP/2，Protobuf 二进制 |
| HTTP 缓存 | 天然支持 GET 缓存 | 需要持久化查询等额外方案 | 不适用 |
| 浏览器直连 | 支持 | 支持 | 需要 gRPC-Web 代理 |
| 典型场景 | 开放 API、通用后端 | 多端聚合、复杂前端页面 | 微服务内部通信、流式调用 |

GraphQL 解决的是“过度获取”和“获取不足”：移动端只需要订单号和金额，REST 接口却返回全部字段；详情页需要订单、用户和商品，REST 需要三次请求。代价是服务端复杂度上升：需要防范深层嵌套查询耗尽资源（限制查询深度和复杂度），错误时通常仍返回 200，监控方式与 REST 不同。

参考：[GraphQL：查询](https://graphql.org/learn/queries/)、[gRPC：核心概念](https://grpc.io/docs/what-is-grpc/core-concepts/)。

### 2. 什么是 N+1 查询问题，如何解决？

**N+1 查询指先用 1 次查询取出 N 条主记录，再为每条记录各发 1 次查询取关联数据，总共 N+1 次。** 在 ORM 的懒加载和 GraphQL 的字段解析器中都很常见。

查询 20 个订单后逐个查询下单用户，就会产生 1 次订单查询和 20 次用户查询。解决方法是把逐条查询合并为批量查询：ORM 中使用预加载或 JOIN（如 Prisma 的 `include`、JPA 的 `JOIN FETCH`）；GraphQL 中使用 DataLoader，把同一事件循环周期内的多个 `load(userId)` 合并为一次 `WHERE id IN (...)`。

发现 N+1 的方法是开启 SQL 日志，观察一次接口调用产生的查询数量；若查询数随返回条数线性增长，就存在这个问题。

参考：[GraphQL：DataLoader](https://github.com/graphql/dataloader)。

### 3. 什么是 BFF，什么时候需要它？

**BFF（Backend For Frontend）是为特定前端（Web、App、小程序）单独提供的后端层，负责聚合下游服务、裁剪字段和适配前端需要的数据格式。**

一个商品详情页需要调用商品、库存、价格、评论四个微服务。若由前端直接调用，移动网络下多次往返耗时长，前端还要感知微服务拆分方式。BFF 在服务端并行调用这些服务后返回一个组合结果，也是放置登录态转换（Cookie 转为内部令牌）的合适位置。

BFF 的代价是多了一层需要维护和部署的服务。若多个端的需求差异不大，一个通用 API 网关加聚合接口可能就够了；BFF 中不应放置核心业务规则，否则同一规则会在多个 BFF 中重复实现并逐渐不一致。

参考：[Sam Newman：Backends For Frontends](https://samnewman.io/patterns/architectural/bff/)。
