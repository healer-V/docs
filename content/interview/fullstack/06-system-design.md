# 全栈系统设计面试题

系统设计题没有唯一答案，面试官考查的是分析过程：先澄清需求和规模，再给出能工作的最小设计，然后针对瓶颈和失败场景逐步改进。每个设计决策都应说明它解决了什么问题、付出了什么代价。

## 一、设计方法

### 1. 系统设计题应该按什么步骤回答？

**按“澄清需求 → 估算规模 → 设计接口与数据模型 → 画出整体架构 → 深入瓶颈与失败处理”的顺序推进。** 一开始就讨论分库分表或消息队列，往往是在为不存在的规模做设计。

1. **澄清需求：** 区分功能需求（短链接要支持自定义别名吗、要统计点击吗）和非功能需求（读写比例、延迟要求、可用性目标、数据保留多久）。
2. **估算规模：** 用日活和人均操作次数估算 QPS 与存储量。例如每天新增 1000 万条记录，平均写入约 1000 万 ÷ 86400 ≈ 116 QPS，按峰值为均值 3～5 倍估算约 350～580 QPS。
3. **接口与数据模型：** 写出核心接口的请求与响应，以及主要表结构和索引，这一步能暴露很多需求中的模糊之处。
4. **整体架构：** 从客户端、网关、服务、缓存、数据库画出请求的完整路径，先保证正确性。
5. **深入改进：** 根据估算找出瓶颈，讨论缓存、分片、异步化；再讨论组件故障、网络超时和重复请求时如何处理。

参考：[Google SRE：服务水平目标](https://sre.google/sre-book/service-level-objectives/)。

## 二、经典场景

### 1. 如何设计一个短链接服务？

**核心是为长链接生成唯一的短码，访问短链接时查到长链接并重定向。** 这是读多写少的系统，读写比可能达到 100:1，设计重点在短码生成和重定向性能。

| 设计点 | 方案 | 说明 |
|--------|------|------|
| 短码生成 | 分布式 ID 转 Base62 | 62 个字符的 7 位编码约有 3.5 万亿种组合，不会冲突 |
| 另一种生成方式 | 对长链接哈希后截取 | 需要处理截取后的冲突，相同长链接天然得到相同短码 |
| 存储 | `short_code` 主键，`long_url`、`created_at`、`expire_at` | 按短码点查，可以用 KV 存储 |
| 重定向 | 301 永久或 302 临时 | 301 会被浏览器缓存，后续访问不再经过服务，无法统计点击 |
| 读取加速 | 热门短码放 Redis | 布隆过滤器拦截不存在的短码，防止穿透 |
| 点击统计 | 重定向时异步发送事件 | 不阻塞跳转，由消费者批量写入分析库 |

自增 ID 直接转 Base62 会让短码连续可猜，别人可以遍历所有短链接；需要时可以对 ID 做可逆的混淆后再编码。还要防止服务被用于传播恶意链接，创建时校验目标地址并对异常创建频率限流。

参考：[MDN：301 Moved Permanently](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/301)、[MDN：302 Found](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/302)。

### 2. 如何设计秒杀系统？

**秒杀的特点是瞬时流量远超库存数量，设计目标是不超卖、不崩溃，并让绝大多数无效请求在到达数据库之前被拦截。**

1. **前端与网关拦截：** 活动开始前按钮置灰，点击后短时间禁用；静态页面放 CDN；网关按用户和 IP 限流，过滤重复提交和机器请求。
2. **Redis 预扣库存：** 活动前把库存加载到 Redis，用 Lua 脚本原子地完成“检查是否已购买、检查库存、扣减库存、记录用户”，库存为 0 后直接返回售罄。
3. **异步下单：** 预扣成功的请求发送消息，订单服务按数据库能承受的速度消费并创建订单，前端轮询或接收推送获取结果。
4. **数据库兜底：** 扣减时使用 `UPDATE stock SET count = count - 1 WHERE item_id = ? AND count > 0`，并以“用户 + 商品”唯一索引防止一人多单。
5. **超时释放：** 订单在限定时间内未支付则取消，并把库存归还 Redis 和数据库。

Redis 和数据库的库存可能暂时不一致，例如消息消费失败。数据库的条件更新是最终的正确性保证，Redis 只负责挡住流量；需要定期对账，并让消费失败的消息重试或进入死信队列人工处理。

参考：[Redis 文档：Lua 脚本](https://redis.io/docs/latest/develop/programmability/eval-intro/)。

### 3. 如何实现大文件上传和断点续传？

**把文件切分为固定大小的分片分别上传，服务端记录已收到的分片，全部到达后合并；中断后只需上传缺失的分片。**

1. **计算文件标识：** 前端用 `File.slice()` 切片，在 Web Worker 中增量计算整个文件的哈希（如 SHA-256），避免阻塞页面。
2. **秒传与续传检查：** 上传前用文件哈希询问服务端，若文件已存在则直接完成；否则返回已上传的分片序号列表。
3. **并发上传分片：** 每片携带文件哈希和序号，控制并发数（如 3～6 个），失败的分片单独重试。
4. **合并与校验：** 所有分片到达后服务端按序号合并，重新计算哈希与客户端提供的值比对。

使用对象存储时，可以直接利用 S3 的分片上传（Multipart Upload）或兼容接口：服务端为每个分片生成带签名的临时上传地址，浏览器直传到对象存储，不经过应用服务器带宽。未完成的分片上传会持续占用存储，需要配置生命周期规则自动清理。

参考：[MDN：Blob.slice](https://developer.mozilla.org/en-US/docs/Web/API/Blob/slice)、[AWS S3：分片上传](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)。

### 4. 实时消息推送应选择轮询、SSE 还是 WebSocket？

**轮询实现简单但延迟和开销大；SSE 基于普通 HTTP 提供服务端到客户端的单向流；WebSocket 提供全双工通道，适合双向频繁通信。**

| 方案 | 方向 | 特点 | 适用场景 |
|------|------|------|----------|
| 短轮询 | 客户端拉取 | 间隔内的消息有延迟，大量空请求 | 低频状态查询 |
| 长轮询 | 客户端拉取 | 服务端有消息才返回，实现比轮询复杂 | 兼容性要求高的环境 |
| SSE | 服务端推送 | 基于 HTTP，浏览器自动重连，只能传文本 | 通知、进度、AI 流式输出 |
| WebSocket | 双向 | 独立协议，需要自行处理心跳和重连 | 聊天、协同编辑、游戏 |

多实例部署时，用户的连接只落在其中一台服务器上，向某个用户推送消息时需要找到他所在的实例：可以用 Redis Pub/Sub 或消息队列广播，由持有连接的实例推送。连接断开期间的消息需要持久化，客户端重连时携带最后收到的消息 ID 补拉，SSE 的 `Last-Event-ID` 请求头正是为此设计的。

参考：[MDN：Server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)、[MDN：WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)。

### 5. 关注流（Feed）应如何设计推拉模式？

**推模式在发布时把内容写入每个粉丝的收件箱，读取快但写入放大；拉模式在读取时汇总所有关注对象的最新内容，写入简单但读取慢。** 实际系统通常采用推拉结合。

| 模式 | 发布时 | 读取时 | 问题 |
|------|--------|--------|------|
| 推（写扩散） | 写入所有粉丝的 Feed 列表 | 直接读取自己的列表 | 千万粉丝的账号发布一次要写千万次 |
| 拉（读扩散） | 只写自己的发件箱 | 合并所有关注者的发件箱并排序 | 关注数多时读取慢 |
| 推拉结合 | 普通用户推给粉丝；大 V 只写发件箱 | 读自己的列表，再合并关注的大 V 内容 | 实现复杂度较高 |

Feed 列表可以存在 Redis 的 Sorted Set 中，以发布时间为分数，只保留最近若干条；更早的内容按需从数据库加载。对只保存内容 ID 的列表，读取时再批量查询内容详情，内容被删除时只需过滤，不必修改每个粉丝的列表。分页使用游标而不是偏移，避免新内容插入导致重复。

参考：[Redis 文档：Sorted Set](https://redis.io/docs/latest/develop/data-types/sorted-sets/)。

### 6. 如何设计一个后台权限系统？

**常用 RBAC（基于角色的访问控制）：用户关联角色，角色关联权限，权限对应可执行的操作或可访问的资源。** 需要按数据范围控制时，再增加数据权限。

最小的数据模型包括用户、角色、权限三张表，以及用户角色、角色权限两张关联表。权限标识采用 `order:read`、`order:refund` 这样的“资源:操作”格式，后端接口用它做校验，前端用同一份权限列表控制菜单和按钮显示。

| 层面 | 职责 |
|------|------|
| 后端接口 | 每次请求校验权限，这是唯一可信的控制 |
| 前端菜单与按钮 | 根据权限隐藏不可用功能，改善体验 |
| 数据权限 | 查询时附加范围条件，如只能看本部门的订单 |

数据权限是容易遗漏的部分：两个运营人员都有“查看订单”权限，但分属不同区域时，只能看到各自区域的数据，这需要在查询层统一追加条件，而不能依赖每个接口自行处理。权限变更后要让缓存的权限及时失效，否则被撤销的权限在缓存过期前仍然有效。需要按属性（时间、地点、资源所有者）动态判断时，可以考虑 ABAC。

参考：[NIST：基于角色的访问控制](https://csrc.nist.gov/projects/role-based-access-control)、[OWASP：授权备忘单](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。
