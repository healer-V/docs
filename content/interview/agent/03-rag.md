# RAG面试题

“RAG 的流程与理解”是字节、腾讯 AI 应用岗面经中排名前十的高频题，追问通常沿着整条链路展开：文档怎么切、Embedding 怎么选、向量检索原理是什么、BM25 和向量怎么融合、召回了但答案不对怎么排查。回答时要把每个环节的选择和失败方式讲清楚，并能结合自己的项目给出具体参数。

## 一、整体链路

### 1. RAG 的完整流程是什么，离线和在线链路如何拆分？

**RAG 分为离线入库和在线问答两条链路：离线链路把文档处理成可检索的索引，在线链路根据问题检索相关片段并交给模型生成回答。** 两条链路独立部署，离线链路的更新不影响在线服务。

| 链路 | 步骤 |
|------|------|
| 离线入库 | 文档采集 → 解析与清洗 → 切分 → 补充元数据 → Embedding → 写入向量索引和关键词索引 |
| 在线问答 | 问题改写 → 混合检索 → 重排序 → 权限过滤 → 组装提示词 → 生成回答并标注引用 |

RAG 解决的是模型知识的三个限制：训练数据有截止时间、不包含企业私有资料、回答无法追溯出处。修改知识只需更新索引，不需要重新训练模型。面试官常追问“RAG 和微调怎么选”：需要补充经常变化的知识、需要引用出处时用 RAG；需要改变输出风格和任务模式时考虑微调，两者可以组合。

参考：[Lewis et al.：Retrieval-Augmented Generation](https://arxiv.org/abs/2005.11401)。

### 2. 文档解析有哪些难点？

**RAG 的效果上限由入库数据的质量决定，解析阶段的错误会一路传到回答中。** PDF、扫描件、表格和图片是主要难点。

PDF 只记录字符在页面上的位置，并不保存段落和阅读顺序，双栏排版容易被解析成左右交错的乱序文本；页眉、页脚和页码会混入正文；表格被拆成零散的单元格后丢失行列关系；扫描件需要 OCR，图片和图表中的信息需要多模态模型提取描述。

处理时应使用版面分析工具识别标题、段落和表格，把表格转换为 Markdown 或 HTML 保留结构，删除页眉页脚等重复内容，并保留标题层级作为后续切分和元数据的依据。解析完成后要抽样人工检查，而不是直接入库。

参考：[Unstructured：文档分区](https://docs.unstructured.io/open-source/core-functionality/partitioning)。

## 二、切分与向量化

### 1. 文档如何切分，Markdown 没有标题时怎么切？

**切分要在“片段语义完整”和“检索精确”之间取舍：片段太大会混入无关内容、浪费上下文；太小则缺少理解所需的背景。**

| 切分方式 | 做法 | 适用内容 |
|----------|------|----------|
| 按结构切分 | 按标题、段落、列表等自然边界切分 | 有清晰结构的文档、手册 |
| 递归切分 | 先按大分隔符（段落）切，超长的再按小分隔符（句子）切 | 通用默认选择 |
| 固定长度 + 重叠 | 按 Token 数切分，相邻片段重叠 10%～20% | 结构不明显的纯文本 |
| 语义切分 | 计算相邻句子的向量相似度，在相似度骤降处切分 | 话题转换频繁的长文 |

Markdown 没有标题时，退回到按空行分隔的段落做递归切分；段落过短时合并到相邻段落，过长时按句子拆分，并保留重叠。无论哪种方式，都应在片段开头补充所属文档名和章节路径，例如“退货政策 > 生鲜商品：签收后 24 小时内……”，否则片段单独被检索出来时缺少上下文。

片段大小常见起点是 300～800 个 Token，最终应在评测集上比较不同参数的召回率来确定，而不是凭经验固定。

参考：[LangChain：文本切分器](https://python.langchain.com/docs/concepts/text_splitters/)、[Anthropic：Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)。

### 2. Embedding 模型如何选择？

**Embedding 模型把文本转换为向量，语义相近的文本向量距离也相近。选型时看检索效果、语言支持、向量维度、最大输入长度、部署方式和成本。**

1. **效果：** 参考 MTEB 排行榜（中文看 C-MTEB 等中文子集）中检索任务的得分，但最终以自己业务数据上的召回率为准。
2. **语言和领域：** 中文业务优先选择在中文语料上训练充分的模型；专业领域（医疗、法律）效果不足时，可以用领域数据微调。
3. **维度与长度：** 维度越高存储和检索成本越高；最大输入长度要大于切分后的片段长度，否则会被截断。
4. **部署：** 数据不能出内网时选择可本地部署的开源模型。

同一个索引的入库和查询必须使用同一个模型和维度，更换模型需要全量重新向量化。部分模型要求查询和文档分别加不同的前缀指令，忘记添加会显著降低效果。

参考：[MTEB 排行榜](https://huggingface.co/spaces/mteb/leaderboard)。

## 三、检索

### 1. 向量检索的原理是什么，HNSW 是怎么工作的？

**向量检索找出与查询向量距离最近的 k 个向量，常用余弦相似度或内积衡量距离。数据量大时精确计算全部距离太慢，因此使用近似最近邻（ANN）索引，用少量召回损失换取数量级的速度提升。**

HNSW 把向量组织成多层图：上层节点少、连接跨度大，下层节点多、连接精细。查询时从最上层入口开始，贪心地移动到离查询更近的邻居，到达局部最近点后下降一层继续，最后在底层做精细搜索。

| 参数 | 调大的效果 |
|------|------------|
| `M`（每个节点的连接数） | 召回提高，内存和构建时间增加 |
| `ef_construction` | 索引质量提高，构建变慢 |
| `ef_search` | 查询召回提高，查询变慢 |

另一类常见索引是 IVF：先把向量聚类，查询时只在最近的若干个聚类中搜索，内存占用比 HNSW 小。面试官常追问“向量检索和元数据过滤怎么结合”：先过滤再检索可能让候选太少，先检索再过滤可能让结果不足 k 个，需要了解所用数据库的过滤实现，例如在 HNSW 遍历过程中带条件过滤。

参考：[Malkov & Yashunin：HNSW](https://arxiv.org/abs/1603.09320)、[pgvector：索引](https://github.com/pgvector/pgvector#indexing)。

### 2. BM25 的原理是什么，相比 TF-IDF 改进了什么？

**BM25 是基于词频的关键词检索打分函数：查询中每个词对文档的得分由该词的逆文档频率（IDF）和经过饱和与长度归一化处理的词频共同决定，文档总分是各个查询词得分之和。**

单个词的得分形式为 `IDF × tf × (k1 + 1) / (tf + k1 × (1 − b + b × 文档长度 / 平均文档长度))`，常用默认值 `k1 = 1.2`、`b = 0.75`。

| 改进点 | TF-IDF 的问题 | BM25 的处理 |
|--------|---------------|-------------|
| 词频饱和 | 词频翻倍得分就翻倍，堆砌关键词可以刷分 | 词频增加时得分趋于上限，`k1` 控制饱和速度 |
| 长度归一化 | 长文档天然包含更多词，得分偏高 | 按文档长度相对平均长度调整，`b` 控制归一化强度 |

BM25 在产品型号、错误码、人名等需要精确匹配的查询上表现好，但无法理解同义表达；向量检索正好相反，所以生产系统通常把两者结合使用。

参考：[Robertson & Zaragoza：The Probabilistic Relevance Framework: BM25 and Beyond](https://www.staff.city.ac.uk/~sbrp622/papers/foundations_bm25_review.pdf)、[Elasticsearch：相似度模块](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)。

### 3. BM25 和向量检索怎么融合，RRF 的 k 值怎么设？

**两路检索的分数尺度不同（BM25 分数无上限，余弦相似度在 -1 到 1 之间），不能直接相加。常用倒数排名融合（RRF）只使用排名：文档的融合得分为它在各路结果中排名的倒数之和，`score = Σ 1 / (k + rank)`。**

k 是平滑常数，原论文和 Elasticsearch 的默认值都是 60。k 越大，排名靠前与靠后的文档得分差距越小，融合结果更依赖“在多路结果中都出现”；k 越小，各路中排第一的文档影响越大。通常保持默认值，再用评测集微调。

另一种方式是把两路分数各自归一化到 0～1 后加权求和，可以调整两路的权重，但对分数分布的变化更敏感。融合之后一般再接重排序模型。

参考：[Cormack et al.：Reciprocal Rank Fusion](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf)、[Elasticsearch：RRF](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)。

### 4. 重排序模型起什么作用，查询改写有哪些方法？

**重排序模型（交叉编码器）把问题和每个候选片段一起输入模型计算相关性，比向量的余弦相似度更准确，但速度慢得多。** 常见做法是混合检索召回几十个候选，再用重排序选出最相关的 3～5 个放入上下文。

查询改写解决用户问题表述不适合检索的情况：

| 方法 | 解决的问题 |
|------|------------|
| 结合历史改写 | 多轮对话中“那它多少钱”这样的指代 |
| 多查询扩展 | 一种表述召回不全 |
| 问题分解 | 一个问题涉及多个文档 |
| HyDE（假设答案） | 问题与文档的表述差异大 |

每次改写都增加一次模型调用的延迟和成本，并可能改变原意，所以要在评测集上验证召回率是否真的提升。

参考：[Gao et al.：HyDE](https://arxiv.org/abs/2212.10496)。

## 四、问题排查与工程

### 1. RAG 召回率高但答案不准，怎么排查？

**召回率高只说明正确的片段在候选中，答案不准可能出在排序、上下文组装或生成环节，需要逐层定位。**

1. **看最终上下文：** 正确片段是否真的进入了提示词？可能在重排序或截断时被挤掉了。
2. **看排序位置：** 正确片段排在第几？放入了太多片段时，排在中间的内容容易被模型忽略。
3. **看噪声与冲突：** 是否同时放入了相似但不相关的片段，或者新旧两个版本的政策相互矛盾。
4. **看提示词：** 是否要求模型只依据资料回答？是否允许资料不足时拒答？
5. **看片段本身：** 片段是否缺少上下文，例如一个只有“签收后 24 小时内”的片段，不知道指的是哪类商品。

修复方式对应问题所在：减少放入的片段数量并提高重排序质量、按版本和时间过滤旧资料、优化提示词、在片段中补充标题路径。

参考：[Ragas：评测指标](https://docs.ragas.io/en/stable/concepts/metrics/)。

### 2. 知识库中没有相关内容，模型却答对了，这正常吗？

**这说明模型用到了自身训练数据中的知识（参数知识），而不是检索到的资料。是否接受取决于业务要求。**

开放问答场景可以接受，但应该让用户知道这条回答没有资料依据；企业客服、医疗、法律等要求有据可查的场景不应接受，因为模型这次答对了，下次可能自信地答错，而且回答无法追溯。处理方法是在检索结果为空或相关度低于阈值时，直接返回“未找到相关资料”，或者要求模型明确区分“根据资料”和“根据常识”的内容。

这个问题也提醒评测时要同时统计“有答案时答对”和“无答案时正确拒答”两个指标。

参考：[OpenAI：文件检索](https://developers.openai.com/api/docs/guides/tools-file-search)。

### 3. 知识库如何不停服更新并保证一致性？

**日常变更采用增量更新：为每个文档记录唯一 ID 和内容哈希，检测到修改时先删除该文档的全部旧片段再写入新片段；全量重建时采用新旧索引切换。**

增量更新要注意原子性：删除旧片段和写入新片段之间，检索可能查不到该文档或者查到新旧混合的内容，可以先写入带新版本号的片段，再切换文档的当前版本，最后删除旧片段。

更换 Embedding 模型或切分策略时，新旧向量不能混用，需要全量重建：在后台构建新索引，用评测集验证指标后，通过别名一次性把查询切换到新索引，保留旧索引一段时间以便回退。

参考：[Elasticsearch：索引别名](https://www.elastic.co/docs/manage-data/data-store/aliases)。

### 4. 企业知识库 RAG 如何处理权限？

**检索时必须按当前用户的权限过滤，用户无权查看的片段不能进入上下文，否则模型会在回答中泄露这些内容。** 依靠提示词要求模型“不要透露机密信息”是不可靠的。

做法是入库时为每个片段写入部门、密级或允许访问的用户组等元数据，查询时把用户权限转换为过滤条件，与检索一起执行。文档权限变更时要同步更新索引中的元数据；缓存回答时，缓存键也必须包含权限范围。

参考：[OWASP：LLM02 敏感信息泄露](https://genai.owasp.org/llmrisk/llm022025-sensitive-information-disclosure/)。

### 5. 如何评估 RAG 系统？

**分别评估检索和生成：检索看是否找到了回答所需的资料，生成看回答是否忠实于资料、是否回答了问题。** 只看最终回答，无法知道问题出在哪个环节。

| 环节 | 指标 |
|------|------|
| 检索 | Recall@k（前 k 个结果中包含正确资料的比例）、MRR（第一个正确结果排名倒数的平均值） |
| 生成 | 忠实度（回答中的陈述能否在资料中找到依据）、答案相关性 |
| 端到端 | 正确率、无答案时的正确拒答率、延迟与成本 |

评测集为每个问题标注正确答案和来源片段，覆盖常见问题、多文档问题和知识库中没有答案的问题。忠实度常用大模型作为评审打分，需要用人工标注抽样校准评审的一致率。

参考：[Ragas：评测指标](https://docs.ragas.io/en/stable/concepts/metrics/)。

### 6. GraphRAG 解决什么问题？

**普通 RAG 按片段检索，擅长回答答案集中在少数片段中的问题；GraphRAG 先从文档中抽取实体和关系构建知识图谱，再对图做社区划分和摘要，适合回答需要汇总全局信息或多跳关系的问题。**

例如“这批合同中涉及哪些供应商，它们之间有什么关联”，答案分散在大量文档中，普通 RAG 只能召回其中几段。GraphRAG 的代价是构建成本高（需要用大模型抽取实体关系），更新复杂，并且在简单事实问答上不一定比普通 RAG 更好，应按问题类型选择。

参考：[Microsoft Research：GraphRAG](https://arxiv.org/abs/2404.16130)。
