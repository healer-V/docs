# 大模型原理与调用面试题

AI 应用岗不会要求推导训练细节，但面经中“Transformer 基本结构”“Token 是怎么生成的”“KV Cache 优化什么”“预训练、SFT、RLHF 的区别”出现频率很高，阿里的 AI 应用岗面经里模型原理类题目约占四分之一。回答这类题的标准是：能讲清机制，并说出它对应用开发有什么影响，例如影响延迟、成本还是输出质量。

::: info 题目来源与版本
本篇题目按公开面经中的高频问法整理，答案只讲到应用开发需要的深度。模型参数、价格等数值变化快，题目中的数字只用于说明量级。
:::

## 一、模型结构

### 1. Transformer 的基本结构是什么，为什么现在的大模型大多是 Decoder-only？

**Transformer 由多层相同的块堆叠而成，每个块包含自注意力层和前馈网络层，配合残差连接和层归一化；当前主流大模型（GPT、Llama、Qwen、DeepSeek）采用只保留解码器的 Decoder-only 结构，按从左到右的顺序逐个预测下一个 Token。**

原始 Transformer 是编码器-解码器结构，用于机器翻译：编码器双向读取原文，解码器逐词生成译文。BERT 只用编码器，擅长理解类任务；GPT 系列只用解码器，并使用因果掩码，让每个位置只能看到它之前的 Token。

| 组件 | 作用 |
|------|------|
| Token Embedding | 把 Token ID 映射为向量 |
| 位置编码 | 注入位置信息，主流模型多用旋转位置编码 RoPE |
| 自注意力 | 让每个 Token 根据上下文中的其他 Token 更新自己的表示 |
| 前馈网络 FFN | 对每个位置独立做非线性变换，模型的大部分参数在这里 |
| 输出层 | 把最后一层向量映射为词表上每个 Token 的概率 |

Decoder-only 成为主流的原因是：“预测下一个 Token”这个训练目标可以直接使用海量无标注文本，生成任务与训练方式一致，并且结构简单、便于扩大规模。面试官常追问“Encoder-only 能不能做生成”，可以回答它没有自回归生成的训练目标，更适合分类、抽取和 Embedding。

参考：[Vaswani et al.：Attention Is All You Need](https://arxiv.org/abs/1706.03762)。

### 2. 自注意力是怎么计算的，为什么要除以根号 d？

**自注意力把每个 Token 的向量分别投影为查询 Q、键 K 和值 V，用 Q 与所有 K 的点积衡量相关程度，经 softmax 得到权重后对 V 加权求和：`Attention(Q, K, V) = softmax(QKᵀ / √d_k) V`。**

除以 `√d_k` 是因为向量维度越高，点积的数值方差越大，softmax 的输入过大时输出会趋近于只有一个位置为 1，其余接近 0，梯度变得非常小，训练不稳定。缩放后点积回到合适的数值范围。

多头注意力把 Q、K、V 切成多个头分别计算再拼接，不同的头可以关注不同类型的关系，例如语法依赖或指代。注意力的计算量与序列长度的平方成正比，这是长上下文成本高的根本原因之一，也催生了 FlashAttention 等优化。

参考：[Vaswani et al.：Attention Is All You Need](https://arxiv.org/abs/1706.03762)、[Dao et al.：FlashAttention](https://arxiv.org/abs/2205.14135)。

### 3. MoE 是什么，有什么优势和代价？

**MoE（混合专家）把前馈网络替换为多个“专家”子网络，并增加一个路由器，每个 Token 只被分配给得分最高的少数几个专家计算。** 模型总参数量很大，但每个 Token 实际激活的参数只占一小部分。

以 DeepSeek-V3 为例，总参数约 6710 亿，每个 Token 激活约 370 亿。这让模型可以用接近中等规模模型的计算量，获得更大模型的知识容量。

代价有三点：全部专家参数都要加载到显存，部署所需的显存并不比同等总参数的稠密模型少；路由不均衡时部分专家过载，训练中需要负载均衡策略；多卡部署时专家分布在不同设备上，Token 分发带来通信开销。所以 MoE 降低的是计算量，不是显存占用。

参考：[DeepSeek-V3 技术报告](https://arxiv.org/abs/2412.19437)、[Shazeer et al.：Sparsely-Gated Mixture-of-Experts](https://arxiv.org/abs/1701.06538)。

## 二、推理过程

### 1. 从输入 Prompt 到输出文本，模型推理经历了哪些步骤？

**推理分为预填充（Prefill）和解码（Decode）两个阶段：预填充并行处理全部输入 Token 并生成第一个输出 Token；解码阶段每次只生成一个 Token，把它追加到序列后继续预测，直到遇到结束标记或达到长度上限。**

1. 分词器把文本切分为 Token ID。
2. 预填充：所有输入 Token 一次性通过模型，计算并缓存每层的 K、V，输出第一个 Token 的概率分布。
3. 采样：按 temperature、top_p 等参数从概率分布中选出一个 Token。
4. 解码：新 Token 进入模型，复用已缓存的 K、V，只计算新位置，循环直到结束。
5. 分词器把 Token ID 还原为文本，流式接口会逐段返回。

两个阶段对应两个延迟指标：首 Token 时间（TTFT）主要取决于预填充，输入越长越慢；每个输出 Token 的时间（TPOT）取决于解码，输出越长总耗时越长。“输出 Token 比输入 Token 贵”也与此有关：解码逐个进行，难以并行。

参考：[Hugging Face：LLM 推理优化](https://huggingface.co/docs/transformers/llm_optims)。

### 2. KV Cache 是什么，有哪些优化方式？

**KV Cache 缓存已经计算过的每层 K、V 向量，生成新 Token 时只计算新位置的 Q、K、V，并与缓存拼接后做注意力，避免每一步都重新计算整个序列。** 它用显存换计算，是解码阶段提速的关键。

KV Cache 的大小与层数、注意力头数、头维度、序列长度和并发请求数成正比，长上下文和高并发时常常比模型权重还占显存，成为限制吞吐的瓶颈。

| 优化方式 | 做法 |
|----------|------|
| MQA / GQA | 多个查询头共享一组或几组 K、V 头，减少需要缓存的 K、V |
| MLA | DeepSeek 使用的多头潜在注意力，把 K、V 压缩到低维潜在向量再缓存 |
| PagedAttention | vLLM 按页管理 KV Cache，减少显存碎片，支持更多并发 |
| 量化 | 把 KV Cache 从 FP16 压缩到 INT8 或更低精度 |
| 前缀缓存 | 多个请求共享相同前缀（如系统提示）的 KV Cache |

应用开发者能直接利用的是最后一项：API 的提示缓存本质上就是服务端复用相同前缀的计算结果，所以把固定的系统提示和工具定义放在请求开头能降低成本和首 Token 时间。

参考：[Kwon et al.：PagedAttention / vLLM](https://arxiv.org/abs/2309.06180)、[Ainslie et al.：GQA](https://arxiv.org/abs/2305.13245)。

### 3. temperature、top_p、top_k 和重复惩罚分别起什么作用？

**这些参数控制如何从下一个 Token 的概率分布中采样：temperature 调整分布的尖锐程度，top_k 只保留概率最高的 k 个候选，top_p 只保留累计概率达到 p 的最小候选集合，重复惩罚降低已出现 Token 的概率。**

| 参数 | 调低 | 调高 |
|------|------|------|
| temperature | 输出稳定、保守，适合抽取和分类 | 输出多样，适合创意写作 |
| top_p / top_k | 候选少，结果确定 | 候选多，结果多样 |
| frequency / presence penalty | 允许重复 | 抑制重复用词和话题 |

temperature 为 0 时近似贪心解码，但由于浮点计算顺序和服务端批处理，同样的输入也不能保证逐字相同。推理模型通常固定内部采样策略，不支持修改这些参数。面试官常追问“做 JSON 抽取时 temperature 设多少”，答案是设低并配合结构化输出，而不是只靠调参保证格式。

参考：[Holtzman et al.：The Curious Case of Neural Text Degeneration](https://arxiv.org/abs/1904.09751)。

## 三、训练与对齐

### 1. 预训练、SFT 和 RLHF 分别做什么？

**预训练让模型从海量文本中学习语言和知识，得到会续写的基座模型；SFT（监督微调）用“指令-回答”数据教会模型按指令回答；RLHF（基于人类反馈的强化学习）让模型的回答更符合人类偏好，例如更有帮助、更安全。**

| 阶段 | 数据 | 目标 | 产出 |
|------|------|------|------|
| 预训练 | 万亿级 Token 的无标注文本 | 预测下一个 Token | 基座模型，只会续写 |
| SFT | 数万到数百万条高质量指令数据 | 模仿示范回答 | 能遵循指令的对话模型 |
| 偏好对齐 | 同一问题的多个回答及好坏排序 | 提高被偏好回答的概率 | 更符合人类期望的模型 |

基座模型被问“中国的首都是哪里”，可能续写出另一道类似的问题，而不是回答；SFT 后才会给出回答。应用开发者常做的是在开源模型上做 SFT（多用 LoRA 等参数高效方法），而预训练和大规模 RLHF 通常由模型厂商完成。

参考：[Ouyang et al.：InstructGPT](https://arxiv.org/abs/2203.02155)。

### 2. PPO、DPO 和 GRPO 有什么区别？

**三者都用于偏好对齐或强化学习阶段：PPO 需要先训练奖励模型，再用强化学习优化策略；DPO 直接用偏好数据对优化，不需要奖励模型和强化学习采样；GRPO 去掉了 PPO 中的价值模型，用同一问题多个回答的组内相对得分作为优势估计。**

| 方法 | 需要的模型 | 特点 |
|------|------------|------|
| PPO | 策略模型、参考模型、奖励模型、价值模型 | 经典 RLHF 方法，效果好但训练复杂、显存占用大 |
| DPO | 策略模型、参考模型 | 把偏好优化转化为分类式损失，训练稳定简单 |
| GRPO | 策略模型、参考模型、奖励函数 | 每题采样一组回答，按组内平均分归一化计算优势；DeepSeek 用于数学与推理训练 |

三种方法都会约束新模型不要偏离参考模型太远，常用 KL 散度作为惩罚项。KL 散度衡量两个概率分布的差异，没有这个约束时，模型可能为了刷高奖励而生成奇怪的输出（奖励被“钻空子”），丧失原有的语言能力。

参考：[Schulman et al.：PPO](https://arxiv.org/abs/1707.06347)、[Rafailov et al.：DPO](https://arxiv.org/abs/2305.18290)、[Shao et al.：DeepSeekMath（GRPO）](https://arxiv.org/abs/2402.03300)。

### 3. LoRA 的原理是什么，什么时候需要微调？

**LoRA 冻结原模型权重，只在部分权重矩阵旁增加两个低秩矩阵 A 和 B，训练时只更新它们，推理时把 `B × A` 加回原权重。** 可训练参数通常不到原模型的 1%，显存需求和训练成本大幅下降。

是否需要微调，要先排除用提示词和 RAG 就能解决的问题：

| 需求 | 优先方案 |
|------|----------|
| 模型不知道企业内部知识或最新信息 | RAG |
| 输出格式不稳定 | 结构化输出、少样本示例 |
| 需要固定的风格、领域术语、复杂任务模式 | 微调 |
| 通用大模型太贵、太慢，任务单一 | 用大模型生成数据，微调小模型 |

面试官常追问“微调能不能让模型记住知识库”：微调可以注入部分知识，但更新成本高、无法追溯来源，还可能让模型对没学过的内容更自信地编造，知识类需求应优先使用 RAG。

参考：[Hu et al.：LoRA](https://arxiv.org/abs/2106.09685)。

## 四、调用与问题处理

### 1. 大模型为什么会产生幻觉，应用中如何降低？

**模型按概率生成看起来合理的文本，并没有事实核验机制；训练数据中缺少相关知识、问题超出能力范围，或者训练和评测方式鼓励“猜一个答案”而不是承认不知道，都会导致幻觉。**

应用层的处理按“提供依据、约束输出、验证结果”三步进行：用 RAG 或工具查询提供事实来源，并要求依据资料回答、资料不足时拒答；用结构化输出约束格式，要求标注引用；对金额、订单状态等关键事实，用代码对照数据库或工具结果校验，不一致时不展示或交给人工。

面试官常追问“怎么区分内容过时和模型幻觉”：内容过时是知识库或训练数据本身已经过期，回答与当时的资料一致；幻觉是回答在任何资料中都找不到依据。排查时先看检索到的资料，如果资料就是旧的，修复数据源；如果资料正确但回答错了，修复生成环节。

参考：[OpenAI：Why language models hallucinate](https://openai.com/index/why-language-models-hallucinate/)。

### 2. 模型出现“复读机”现象怎么解决？

**复读指模型反复输出相同的句子或段落，常见于小模型、贪心或低温度解码、长文本生成，以及提示中本身包含大量重复内容的情况。** 一旦某段文本出现，它在上下文中的存在会提高再次生成它的概率，形成自我强化。

处理方法包括：适当提高 temperature 或使用 top_p 采样；设置 frequency penalty、presence penalty 或开源推理框架的 repetition penalty；减少提示中的重复示例；设置最大输出长度，并在服务端检测连续重复的 n-gram，发现后截断或重试。对于开源模型，复读严重通常说明 SFT 数据质量或解码配置有问题。

参考：[Holtzman et al.：The Curious Case of Neural Text Degeneration](https://arxiv.org/abs/1904.09751)。

### 3. 需要生成的内容超过最大输出长度怎么办？

**先判断输出是否被截断：API 返回的结束原因为长度上限（如 Chat Completions 的 `finish_reason: "length"`，Responses API 的 `status: "incomplete"`）时，说明输出未完成。** 处理方式有续写和拆分两种。

续写是把已生成的内容放入上下文，要求模型从断点继续，并在拼接时处理衔接处的重复。更可靠的方式是拆分任务：先让模型生成大纲，再按章节分别生成，每次调用的输出都在上限内，失败时只需重试一个章节，进度也可以持久化以支持断点续传。结构化输出被截断后得到的是不完整的 JSON，不能直接解析，应检测结束原因后重试或拆分。

参考：[OpenAI：Responses API 对象](https://platform.openai.com/docs/api-reference/responses/object)。

### 4. 大量并发请求打满大模型 API 的限流怎么办？

**模型 API 按每分钟请求数（RPM）和每分钟 Token 数（TPM）限流，超限返回 HTTP 429。处理思路是客户端主动控流、对 429 退避重试、削减 Token 消耗，并准备备用容量。**

1. **客户端控流：** 用令牌桶或信号量按 RPM 和 TPM 双维度限制并发，请求超出时排队而不是直接打到 API。
2. **退避重试：** 收到 429 后按响应头中的重试时间或指数退避加随机抖动重试，设置最大重试次数。
3. **优先级队列：** 用户实时请求优先，批量离线任务降级到低峰期或批处理接口。
4. **减少消耗：** 压缩上下文、缓存相同问题的结果、简单请求路由到小模型。
5. **扩充容量：** 申请提高额度，或配置多个账号、多个供应商作为备用，切换前用评测集确认效果。

面试官常追问“重试会不会让限流更严重”：所有客户端同时按固定间隔重试会形成重试风暴，所以必须加随机抖动，并让排队请求有超时上限，超时后向用户返回明确的提示。

参考：[OpenAI：速率限制](https://developers.openai.com/api/docs/guides/rate-limits)。
