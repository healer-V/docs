# 记忆与多Agent面试题

“Agent 记忆系统的设计”在字节、腾讯、阿里的 AI 应用岗面经中都位列高频题；多 Agent 部分的追问越来越具体，例如“主 Agent 怎么知道子 Agent 已经完成”“多个 Agent 写同一个文件怎么避免冲突”“多 Agent 真的比单 Agent 好吗”。这组题考查的是能否把记忆和协作设计成可控的工程模块，而不只是说出“短期记忆、长期记忆”这几个词。

## 一、记忆

### 1. 大模型本身有记忆吗，Agent 的记忆是怎么来的？

**模型 API 本身是无状态的：每次请求都是独立计算，模型不会记住上一次请求的内容。** 训练数据中的知识固化在参数中，可以看作“参数记忆”，但它无法在使用过程中更新。

Agent 的“记忆”完全由应用实现：把需要的历史信息保存在外部存储中，每次调用前选出相关部分放入上下文。所谓多轮对话的连续性，就是应用把之前的消息重新发送给模型。部分 API 提供服务端会话状态（如通过上一个响应 ID 关联），本质上也是服务端替应用保存并拼接了历史。

参考：[OpenAI：对话状态](https://developers.openai.com/api/docs/guides/conversation-state)。

### 2. 短期记忆和长期记忆如何实现，存储怎么选？

**短期记忆服务于当前任务或会话，包括对话历史、工具结果和任务状态；长期记忆跨会话保存，包括用户偏好、关键事实和过去的经验，需要时检索后放入上下文。**

| 层级 | 内容 | 生命周期 | 常用存储 |
|------|------|----------|----------|
| 工作记忆 | 当前上下文中的消息和工具结果 | 单次调用 | 内存 |
| 短期记忆 | 本次会话的历史、滚动摘要、任务状态 | 会话结束或过期 | Redis、数据库会话表 |
| 长期事实记忆 | 用户偏好、身份信息、业务事实 | 长期，可更新删除 | 关系数据库（结构化字段） |
| 长期语义记忆 | 过去的对话片段、经验总结 | 长期 | 向量数据库 |

存储选型按访问方式决定：需要按用户 ID 精确读取、频繁更新的结构化事实（如“偏好顺丰配送”）放关系数据库或键值存储；需要按语义相似度查找的非结构化内容放向量数据库；会话级的高频读写放 Redis 并设置过期时间。面试官追问“为什么不全部放向量库”：结构化事实用向量检索既不精确也难以更新，例如用户修改了收货地址，向量库中旧地址的片段仍可能被召回。

参考：[LangGraph：记忆](https://docs.langchain.com/oss/python/langgraph/memory)、[Packer et al.：MemGPT](https://arxiv.org/abs/2310.08560)。

### 3. 哪些信息需要写入长期记忆，如何召回？

**写入采用“触发式”而不是每轮都写：用户明确表达偏好或纠正、任务完成形成可复用的结论、出现后续可能用到的关键实体时，才抽取并写入。** 全部写入会让记忆库充满噪声，召回质量下降。

写入前做去重和冲突检测：与已有记忆相似的内容合并，矛盾的内容按冲突规则处理。每条记忆记录来源、时间和置信度，便于后续判断和删除。

召回通常组合多种信号：向量相似度找语义相关的记忆，关键词匹配找精确实体，时间衰减让近期记忆权重更高，重要度打分让关键事实优先；最后按 Token 预算截取。召回结果放入上下文时要标明“这是历史记忆，可能已过期”，让模型与当前信息区分开。

参考：[Packer et al.：MemGPT](https://arxiv.org/abs/2310.08560)、[LangGraph：记忆](https://docs.langchain.com/oss/python/langgraph/memory)。

### 4. 长期记忆、短期记忆和当前上下文冲突时怎么办，如何避免召回污染？

**冲突处理的关键是预先定义优先级，而不是让模型自由判断：一般按“用户当前明确的说法 > 当前任务上下文 > 近期记忆 > 早期记忆”的顺序，并以权威数据源（如数据库中的订单信息）为准。**

用户上个月说“发到公司”，今天说“这次发到家里”，应以当前说法为准；如果用户说的是“以后都发到家里”，还要更新长期记忆。对于事实类信息，记忆只是参考，最终以业务系统查询结果为准。

召回污染是指不相关或不适用的记忆被召回，干扰当前任务，例如把用户 A 的偏好召回给用户 B，或把另一个项目的约定用在当前项目。避免方法是按用户、项目、任务类型等维度划分命名空间并作为召回的硬过滤条件，设置相关度阈值，宁可少召回也不召回低相关内容。

参考：[LangGraph：记忆](https://docs.langchain.com/oss/python/langgraph/memory)。

### 5. 长期记忆和 RAG 有什么区别，如何评估记忆的效果？

**两者在技术上都可以用“存储 + 检索”实现，区别在于数据的来源和性质：RAG 检索的是外部知识库中相对稳定、所有用户共享的资料；记忆存储的是 Agent 在与特定用户交互中产生的个性化、持续变化的信息。**

| 维度 | RAG | 长期记忆 |
|------|-----|----------|
| 数据来源 | 文档、知识库，由人维护 | 交互过程中由 Agent 自动产生 |
| 作用范围 | 通常所有用户共享 | 按用户或项目隔离 |
| 变化方式 | 文档更新时批量变化 | 每次交互都可能新增、修改或删除 |
| 主要难点 | 切分和检索质量 | 写入判断、冲突处理和遗忘 |

评估记忆效果可以做对照实验：在评测集上分别开启和关闭记忆，比较任务成功率、需要用户重复提供信息的次数；单独统计记忆召回的准确率（召回的记忆是否相关）和记忆错误导致的失败次数。

参考：[LongMemEval：长期记忆评测基准](https://arxiv.org/abs/2410.10813)。

## 二、多 Agent

### 1. 多 Agent 有哪些协作模式，相比单 Agent 有什么优势？

**常见模式有编排者-执行者、交接（handoff）、并行处理后汇总和流水线；多 Agent 的优势是每个 Agent 职责单一、上下文更小、可以并行，代价是 Token 消耗成倍增加，协调和调试更复杂。**

| 模式 | 过程 | 适用场景 |
|------|------|----------|
| 编排者-执行者 | 主 Agent 拆分任务，委派给子 Agent，汇总结果 | 调研、报告生成 |
| 交接 | 当前 Agent 把对话控制权交给更合适的 Agent | 客服在售前、售后、投诉之间转接 |
| 并行 + 汇总 | 多个 Agent 同时处理不同部分 | 多来源信息收集、多角度评审 |
| 流水线 | 按固定顺序依次处理 | 写作 → 审校 → 格式化 |

Anthropic 公开的多 Agent 调研系统数据可以作为参考：多 Agent 架构在其内部调研评测上比单 Agent 提升了 90.2%，但 Token 消耗约为普通对话的 15 倍，而单 Agent 约为 4 倍。所以多 Agent 适合价值高、可以并行拆分的任务；单 Agent 加合适的工具能解决的问题，不应为了架构而拆分。

参考：[Anthropic：How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)、[OpenAI Agents SDK：交接](https://openai.github.io/openai-agents-python/handoffs/)。

### 2. 子 Agent 之间如何通信，主 Agent 怎么知道子 Agent 已经完成？

**通信方式主要有两种：通过共享状态（黑板）读写，或者通过消息传递；主 Agent 通过子 Agent 的返回结果或任务状态判断完成情况。**

同步委派时，主 Agent 把调用子 Agent 当作一次工具调用，子 Agent 执行完毕返回结果，主 Agent 自然知道已完成。异步执行时，每个子任务在任务表中有明确的状态（待执行、执行中、完成、失败），子 Agent 完成后更新状态并写入结果，主 Agent 轮询或订阅状态变化；必须为每个子任务设置超时，超时后视为失败处理。

委派时应传递结构化的任务说明：目标、约束、可用工具、期望的输出格式和完成标准，而不是把主 Agent 的全部对话历史塞给子 Agent。子 Agent 的返回也应该是结构化的结论和依据，便于主 Agent 汇总和校验。

参考：[Anthropic：How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)、[A2A 协议规范](https://a2a-protocol.org/latest/specification/)。

### 3. 子 Agent 串行还是并行执行，失败了怎么办？

**子任务之间没有依赖时并行执行以缩短总耗时，有依赖时串行执行；失败处理要区分必要子任务和可选子任务。**

并行执行时，必要子任务失败应取消其他子任务并让整体失败或重试；可选子任务失败时记录原因，汇总时标明“该部分信息缺失”，而不是让整个任务失败。重试要限制次数，并且只对临时性错误（超时、限流）重试。

还要防止错误传播：任务拆分阶段的错误会被所有子 Agent 继承并放大。可以在拆分后增加一次校验，检查子任务是否覆盖了原始目标、是否有重叠；汇总时检查子 Agent 结果之间是否矛盾。

参考：[Python：asyncio TaskGroup](https://docs.python.org/3/library/asyncio-task.html#task-groups)。

### 4. 多个 Agent 的结论不一致时怎么处理？

**先区分不一致的原因：是依据的资料不同、资料版本不同，还是推理过程有误。处理策略按任务性质选择。**

有客观标准的问题（数据、事实）以权威数据源或可执行的验证结果为准；可以通过投票处理的问题（分类、判断）可以让多个 Agent 独立作答后多数表决；需要综合判断的问题，交给汇总 Agent 对比各方依据后给出结论，并在结果中保留分歧说明；高风险决策出现分歧时交给人工。不要简单地采用最后一个返回的结果或最“自信”的结果。

参考：[Du et al.：Improving Factuality through Multiagent Debate](https://arxiv.org/abs/2305.14325)。

### 5. 多个 Agent 如何隔离，写同一个文件怎么避免冲突？

**隔离包括三个层面：上下文隔离（每个 Agent 有独立的对话历史）、权限隔离（每个 Agent 只拥有完成职责所需的工具和数据权限）、存储隔离（每个 Agent 有独立的工作目录或命名空间）。**

多个 Agent 写同一资源时的冲突处理方式：

| 方式 | 做法 |
|------|------|
| 职责划分 | 按文件或模块分配，每个文件只由一个 Agent 修改 |
| 锁 | 修改前获取文件或资源锁，用完释放，并设置锁超时 |
| 乐观并发 | 写入时比较版本号或内容哈希，不一致则重新读取后合并 |
| 独立工作区 | 每个 Agent 在独立的 Git 分支或工作树中修改，最后合并并解决冲突 |
| 单一写入者 | 子 Agent 只提交修改建议，由一个汇总 Agent 统一写入 |

编码类多 Agent 系统常用独立工作区方案，冲突在合并阶段由程序检测，再交给 Agent 或人工处理。

参考：[Git：git-worktree](https://git-scm.com/docs/git-worktree)。

### 6. 如何证明多 Agent 确实比单 Agent 好？

**用同一个评测集对比单 Agent 和多 Agent 方案，比较任务成功率、结果质量、总耗时和 Token 成本，只有在质量提升足以抵消成本增加时才采用多 Agent。**

对比时要控制变量：使用相同的模型、相同的工具和相同的总 Token 预算。Anthropic 的分析发现，在其浏览检索评测中，Token 使用量本身就能解释约 80% 的效果差异，这意味着多 Agent 的提升有相当一部分来自“花了更多 Token”。如果给单 Agent 同样的预算（例如更多的步数和更大的上下文）也能达到相近效果，多 Agent 的价值就要打折扣。

参考：[Anthropic：How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)。
