# 分布式与微服务面试题

分布式题的前提是网络不可靠：请求可能超时但实际已执行，消息可能重复投递，节点可能在任意步骤宕机。评价一个方案时，要说明它在这些失败下保证什么、放弃什么，而不是只描述正常流程。

## 一、理论与事务

### 1. CAP 和 BASE 如何理解？

**CAP 指出在发生网络分区（P）时，系统只能在一致性（C）与可用性（A）之间二选一。** 分区在分布式系统中无法避免，所以实际选择是 CP 或 AP，而不是“放弃 P 选 CA”。

| 选择 | 分区时的行为 | 例子 |
|------|--------------|------|
| CP | 拒绝或阻塞部分请求，保证读到最新数据 | ZooKeeper、etcd 的多数派写入 |
| AP | 继续响应，但可能返回旧数据 | Eureka 注册中心、异步复制的缓存 |

这里的一致性指线性一致性：任何读都能看到最近一次完成的写。BASE（基本可用、软状态、最终一致）是 AP 系统的工程实践：允许数据在一段时间内不一致，但保证最终收敛。下单后库存扣减、积分发放通过消息异步完成，就是用最终一致换取下单接口的可用性和性能。

参考：[Martin Kleppmann：A Critique of the CAP Theorem](https://arxiv.org/abs/1509.05393)。

### 2. 2PC、TCC、Saga 和本地消息表有什么区别？

**它们在一致性强度、业务侵入和性能之间取舍：2PC 由协调者保证原子提交，TCC 和 Saga 由业务代码实现补偿，本地消息表借助数据库事务保证消息必达。**

| 方案 | 过程 | 一致性 | 代价 |
|------|------|--------|------|
| 2PC / XA | 准备阶段各参与者锁定资源并投票，提交阶段统一提交或回滚 | 强一致 | 资源长时间锁定，协调者故障时参与者阻塞 |
| TCC | Try 预留资源，Confirm 确认，Cancel 释放预留 | 最终一致 | 每个服务实现三个接口，处理空回滚和悬挂 |
| Saga | 按顺序执行本地事务，失败时逆序执行补偿事务 | 最终一致 | 无隔离，中间状态对外可见 |
| 本地消息表 / Outbox | 业务数据和消息在同一本地事务写入，后台投递消息 | 最终一致 | 需要轮询或 CDC 投递，消费者必须幂等 |

TCC 的两个常见异常需要专门处理：**空回滚**是 Try 因超时未执行，却先收到 Cancel，Cancel 应识别并直接返回成功；**悬挂**是 Cancel 执行后迟到的 Try 才到达，Try 应检查已取消记录并拒绝执行。两者都需要一张记录全局事务状态的表。

::: tip 能不用分布式事务就不用
很多场景可以通过调整边界避免分布式事务：把需要强一致的数据放在同一服务的同一个库中，跨服务的部分用 Outbox 加幂等消费实现最终一致。Seata 等框架降低了实现成本，但不能消除协调开销和补偿逻辑。
:::

参考：[microservices.io：Saga 模式](https://microservices.io/patterns/data/saga.html)、[microservices.io：Transactional Outbox](https://microservices.io/patterns/data/transactional-outbox.html)。

## 二、消息队列

### 1. 消息队列的作用和引入后的问题是什么？

**消息队列用于异步处理、服务解耦和削峰填谷。** 下单后发送“订单已创建”消息，库存、积分、通知服务各自订阅，下单接口不再同步等待这些调用。

引入消息队列后，系统需要额外处理：消息丢失、重复消费、消费顺序、消息积压，以及因为异步带来的数据短暂不一致。可用性也依赖消息队列本身，它宕机会影响所有生产者。所以“加一个 MQ”需要连同这些失败处理一起设计。

参考：[Apache Kafka：设计文档](https://kafka.apache.org/documentation/#design)。

### 2. 如何保证消息不丢失？

**消息可能在生产、存储和消费三个环节丢失，需要分别确认。**

1. **生产端：** 使用同步发送或带回调的异步发送，失败时重试；Kafka 设置 `acks=all`，等待所有同步副本写入后才确认，并开启 `enable.idempotence=true` 避免重试产生重复。
2. **存储端：** Kafka 设置副本数不少于 3、`min.insync.replicas=2`，同时设置 `unclean.leader.election.enable=false`，禁止未同步的副本成为 leader；RocketMQ 可使用同步刷盘和同步复制。
3. **消费端：** 业务处理成功后再提交 offset 或返回消费成功；若先自动提交 offset 再处理，处理过程中宕机这条消息就丢失了。

更严格的端到端保证可以结合本地消息表：发送前先在本地事务中落库，未确认的消息由定时任务补发。

参考：[Apache Kafka：生产者配置](https://kafka.apache.org/documentation/#producerconfigs)。

### 3. 重复消费如何处理？

**消息队列通常只能保证“至少一次”投递，重复消费无法从队列侧完全避免，消费者必须实现幂等。** 消费成功但提交 offset 前宕机、消费者组重平衡、生产者重试，都会让同一消息被处理多次。

| 幂等方式 | 做法 | 适用场景 |
|----------|------|----------|
| 唯一约束 | 以消息 ID 或业务单号建唯一索引，重复插入失败 | 创建类操作 |
| 状态机条件更新 | `UPDATE orders SET status='PAID' WHERE id=? AND status='UNPAID'` | 状态流转 |
| 去重表 | 处理前在同一事务中写入已处理的消息 ID | 通用场景 |
| 乐观锁 | 更新时校验版本号 | 并发修改同一记录 |

只用 Redis `SETNX` 记录消息 ID 去重时，要注意写 Redis 与业务数据库不在同一事务中：先记录后处理失败，消息会被误判为已处理。最稳妥的是把去重记录和业务修改放在同一个数据库事务中。

参考：[microservices.io：Idempotent Consumer](https://microservices.io/patterns/communication-style/idempotent-consumer.html)。

### 4. 如何保证消息顺序，消息积压怎么处理？

**Kafka 只保证单个分区内的消息有序，需要有序的消息应使用相同的消息键发往同一分区，并由一个消费者线程按顺序处理。** 同一订单的“创建、支付、发货”以订单 ID 作为消息键，不同订单之间可以并行。

生产者开启重试时，若允许多个未确认请求并发发送，可能出现后发的消息先写入；Kafka 开启幂等生产者后，在 `max.in.flight.requests.per.connection` 不超过 5 时仍能保证分区内顺序。

消息积压时先判断原因：消费者是否报错卡住、处理逻辑是否变慢、上游流量是否突增。

1. 先修复消费者故障或性能问题，例如慢 SQL、下游接口超时。
2. 增加消费者实例，但 Kafka 中同一消费者组的有效消费者数不会超过分区数，分区不足时需要先扩分区。
3. 积压特别严重时，可以写一个临时消费者把消息快速转发到分区更多的临时主题，再用更多消费者处理。
4. 处理完后回顾监控告警，消费延迟（lag）应在积压初期就触发告警。

参考：[Apache Kafka：消息投递语义](https://kafka.apache.org/documentation/#semantics)。

### 5. Kafka 为什么吞吐量高？

**Kafka 的高吞吐来自顺序写磁盘、依赖操作系统页缓存、零拷贝发送、批量与压缩，以及分区带来的并行度。**

| 设计 | 作用 |
|------|------|
| 追加写日志 | 磁盘顺序写速度远高于随机写 |
| 页缓存 | 读写先经过操作系统缓存，刚写入的数据通常直接从内存读取 |
| 零拷贝 | 用 `sendfile` 把数据从页缓存直接发送到网卡，减少用户态复制 |
| 批量与压缩 | 生产者按 `batch.size` 和 `linger.ms` 攒批，减少请求次数和网络字节 |
| 分区 | 不同分区分布在不同 broker，生产和消费都可以水平扩展 |

吞吐与延迟存在取舍：`linger.ms` 越大，批次越大、吞吐越高，但单条消息的延迟增加。启用 TLS 时数据需要在用户态加密，`sendfile` 零拷贝的优势会减弱。

参考：[Apache Kafka：效率设计](https://kafka.apache.org/documentation/#maximizingefficiency)。

## 三、服务治理

### 1. 如何设计接口幂等？

**幂等指同一请求执行一次和多次的效果相同。** 用户重复点击支付、网关超时重试、客户端网络抖动重发，都要求写接口幂等。

常用做法是幂等键（Idempotency Key）：客户端为每个业务操作生成唯一 ID 放在请求头中；服务端以该 ID 建唯一记录，第一次请求执行业务并保存结果，后续相同 ID 的请求直接返回保存的结果。若第二个请求到达时第一个仍在执行，应返回“处理中”而不是再次执行。

| 环节 | 要求 |
|------|------|
| 键的生成 | 由客户端在发起操作前生成，重试时复用同一个键 |
| 唯一性保证 | 数据库唯一索引或原子的 `SET NX`，不能“先查再插” |
| 参数校验 | 相同键但请求参数不同，应拒绝而不是返回旧结果 |
| 过期策略 | 幂等记录保留时间覆盖客户端最长重试窗口 |

参考：[Stripe API：Idempotent requests](https://docs.stripe.com/api/idempotent_requests)。

### 2. 常见限流算法有哪些？

**限流保护服务不被超出承载能力的流量压垮，常见算法有固定窗口、滑动窗口、漏桶和令牌桶。**

| 算法 | 原理 | 特点 |
|------|------|------|
| 固定窗口 | 每个时间窗口计数，超过阈值拒绝 | 实现简单，窗口边界可能通过两倍流量 |
| 滑动窗口 | 把窗口细分为多个小格，统计最近一段时间 | 平滑边界问题，内存开销稍大 |
| 漏桶 | 请求进入队列，以固定速率流出 | 输出速率恒定，不能应对突发 |
| 令牌桶 | 以固定速率生成令牌，请求取到令牌才放行 | 允许桶容量范围内的突发流量 |

固定窗口的边界问题：阈值为每秒 100，0.9 秒到 1.0 秒来 100 个请求，1.0 秒到 1.1 秒又来 100 个，在 0.2 秒内通过了 200 个。单机限流可用 Guava `RateLimiter`（令牌桶）；集群限流需要用 Redis Lua 脚本或网关统一计数，被限流的请求应返回 HTTP 429 并附带 `Retry-After`。

参考：[Resilience4j：RateLimiter](https://resilience4j.readme.io/docs/ratelimiter)。

### 3. 熔断和降级有什么区别？

**熔断是调用方检测到下游持续失败后，暂时停止调用并快速失败；降级是在资源不足或依赖失败时，返回简化结果以保证核心功能。** 熔断通常触发降级逻辑。

熔断器有三种状态：关闭时正常调用并统计失败率；失败率超过阈值后打开，所有调用直接失败；经过等待时间后进入半开，放行少量请求试探，成功则关闭，失败则再次打开。它的价值是防止下游故障时调用方线程被大量超时请求占满，进而导致故障沿调用链扩散（雪崩）。

商品详情页调用推荐服务失败时，降级为展示热门商品列表；评论服务不可用时隐藏评论区。降级方案需要提前设计并通过演练验证，不能在故障时临时编写。

参考：[Resilience4j：CircuitBreaker](https://resilience4j.readme.io/docs/circuitbreaker)、[Martin Fowler：CircuitBreaker](https://martinfowler.com/bliki/CircuitBreaker.html)。

### 4. 分布式 ID 有哪些方案？

**分布式 ID 需要全局唯一，通常还希望趋势递增以利于数据库索引。**

| 方案 | 优点 | 缺点 |
|------|------|------|
| UUID | 本地生成，无依赖 | 无序，作为 InnoDB 主键引发页分裂；36 字符较长 |
| 数据库自增 + 步长 | 简单，有序 | 依赖数据库，扩容需要调整步长 |
| 号段模式 | 每次从数据库取一段 ID 在内存分配 | 服务重启会浪费未用完的号段 |
| 雪花算法 | 本地生成，趋势递增，性能高 | 依赖机器时钟，需要分配机器 ID |

雪花算法的 64 位由 1 位符号位、41 位毫秒时间戳、10 位机器 ID 和 12 位序列号组成，单机每毫秒最多生成 4096 个 ID。时钟回拨时可能生成重复 ID，实现需要检测：回拨幅度小时等待时钟追上，幅度大时拒绝生成并告警。Java 中 64 位 ID 传给前端 JavaScript 会超出 `Number` 的安全整数范围（2^53 − 1），接口应以字符串返回。

参考：[Twitter：Snowflake 归档仓库](https://github.com/twitter-archive/snowflake)。

### 5. 服务注册与发现如何工作？

**服务实例启动时向注册中心登记地址并定期发送心跳，调用方从注册中心获取可用实例列表，并在本地缓存和负载均衡。** 实例停止心跳超过阈值后被剔除。

注册中心的选型与 CAP 相关：Nacos 默认的临时实例使用 AP 模式，分区时仍可返回可能过期的实例列表；ZooKeeper 和 etcd 是 CP，少数派节点在分区时不可写。服务发现场景通常更看重可用性，因为返回一个稍旧的列表，调用方还可以通过重试和熔断跳过失效实例；而注册中心完全不可用会让所有新调用失败。

优雅下线需要先从注册中心注销、等待调用方的本地缓存刷新，再停止处理请求；直接停止进程，调用方在缓存过期前仍会把请求发到已停止的实例。

参考：[Nacos：架构与概念](https://nacos.io/en/docs/latest/what-is-nacos/)。
