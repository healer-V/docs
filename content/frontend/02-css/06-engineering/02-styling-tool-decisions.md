# CSS 样式处理工具选型

**样式处理工具**帮助作者生成、转换或组织浏览器最终使用的样式。选择时先指出实际问题，再检查工具的输入、输出、运行位置和维护成本。

浏览器仍按 CSS 的匹配、层叠、布局与绘制规则处理结果。工具能改变写法和生产过程，不能让这些规则失效。

## 一、工具分别处理什么

| 方案 | 输入与输出 | 主要发生阶段 |
|------|------------|--------------|
| 原生 CSS | CSS 直接作为样式表 | 浏览器解析与运行 |
| Sass 等预处理器 | 扩展语法编译为 CSS | 构建时 |
| PostCSS | 按插件转换 CSS 或相应语法 | 构建时为主 |
| CSS Modules | 样式与局部类名映射 | 构建时 |
| 工具类体系 | 模板中的工具类生成或使用规则 | 常见为构建时生成 CSS |
| CSS-in-JS | JavaScript 中描述样式 | 可能在构建时提取，也可能运行时注入 |

预处理器可提供函数、混入、编译期变量等；PostCSS 本身是转换平台，具体能力由插件提供。不能仅因为项目安装了 PostCSS，就认定已自动处理前缀、嵌套或所有兼容问题。依据见 [Sass 文档](https://sass-lang.com/documentation/) 与 [PostCSS](https://postcss.org/)。

::: info CSS-in-JS 不是统一的运行时模型
不同方案对提取、服务端呈现、动态样式和注入顺序的处理不同。评估时检查具体库及版本，不能把整个类别都描述为“必然有运行时成本”或“完全没有运行时”。
:::

## 二、按需求选择

| 实际需求 | 先检查的基础方案 | 引入工具的理由 |
|----------|------------------|----------------|
| 颜色和间距复用 | 自定义属性 | 确实需要额外生成逻辑或统一令牌产物 |
| 运行中切换主题 | 变量与类切换 | 状态必须和特定组件系统集成 |
| 类名不冲突 | 明确命名或作用域 | 需要构建强制局部类名映射 |
| 复用编译期逻辑 | 原生重复是否仍可维护 | 混入、计算或代码生成显著减少复杂度 |
| 支持指定浏览器集合 | 检查目标能力并给回退 | 转换或前缀插件能覆盖已确认的差异 |
| 团队统一组合样式 | 组件样式与变量约定 | 工具类体系有明确尺度、约束和协作收益 |

例如页面只需要两个主题，可以用根类切换变量。若组件库需要为多套目标生成静态产物，再评估构建工具。两种需求不能仅因都出现“主题”就使用同一实现。

## 三、编译期值与运行时值

构建阶段可以把一个配置值直接写进生成的 CSS。以下片段只展示可能的 CSS 产物，不是某个工具的接入教程：

```css
.panel { padding: 12px; }
```

浏览器拿到的是固定值；修改构建配置后通常需要重新生成产物。使用原生变量则保留运行中的取值关系：

```css
:root { --space: 12px; }
.panel { padding: var(--space); }
.dense { --space: 8px; }
```

这段局部 CSS 假设面板位于可切换 `.dense` 的区域内。类改变后浏览器重新计算变量，不需要重新编译整个样式包。

::: tip 按值何时改变选择机制
固定生成数据适合编译期处理；用户偏好或组件状态需要运行时变化时，保留浏览器可计算的输入。两者可以组合，不必让所有值走同一条路径。
:::

## 四、兼容与调试责任

### 1. 转换不保证完全等价

新语法有些能转换成旧写法，有些涉及运行时语义而不能完整降级。例如静态替换变量，无法完整复制自定义属性的动态层叠与继承。

前缀处理通常基于目标浏览器配置和兼容数据，也不会自动实现缺失的 Grid、容器查询或所有新 API。验收仍需在目标环境中检查行为。

### 2. 工具类与动态样式

工具类适合通过受约束的尺度组合外观，但模板可读性、类冲突和扫描生成范围也要管理。构建工具不能识别的动态类名，可能导致对应 CSS 没有生成，具体边界见 [Tailwind 工具类](https://tailwindcss.com/docs/styling-with-utility-classes)。

运行时注入方案还需检查样式顺序、服务端与客户端一致性、缓存及首次呈现；构建提取方案则检查构建兼容和静态分析限制。

## 五、引入与回退的验证

对一个小范围组件进行对照，而不是一次替换全部样式：

1. 明确要改善的问题和可观察结果，如类名隔离或目标浏览器行为。
2. 记录当前 HTML、CSS 产物、样式体积和状态表现。
3. 在固定工具版本与配置下转换，检查最终选择器、值和加载顺序。
4. 比较主题、长文本、焦点、响应式和服务端首次呈现等相关场景。
5. 保留能回到原实现的范围，确认删除工具后需要恢复哪些源文件或产物。

::: warning 不要用工具数量衡量工程完善度
没有实际需求的工具会增加配置、升级和调试成本。选型结论应说明它解决了哪个问题、引入什么限制、怎样验证和回退。
:::

这里比较机制和决策边界，不固定某个工具版本或提供安装命令；具体接入应依据项目版本使用对应官方配置，不能把概念片段当成完整工程。
