# 浏览器解析与语法检查

浏览器显示的是解析 HTML 后得到的文档，而不是把源码逐字照搬到页面上。作者写错结构时，浏览器仍会按解析规则继续处理；因此“能看到文字”和“源码符合 HTML 要求”是两项不同判断。

排查这类问题，需要同时保留源码、查看浏览器实际形成的结构，再用检查器核对作者应遵守的规则。只在页面上观察外观，无法可靠判断标签是否放在正确位置。

下面先说明源码怎样形成 DOM，再区分合法省略与错误恢复，最后用三个独立文件完成取证、修复和复检。

::: info 本篇的范围
本篇讲浏览器解析结果与作者语法检查的基本方法。元素之间允许怎样嵌套，见[HTML 元素嵌套与内容模型](./05-nesting-content-models.md)；编码如何影响字节解码，见[HTML 字符编码与语言声明](./08-encoding-language.md)。本篇使用 Nu HTML Checker 作为一致性检查工具，不把它当作资源加载、业务逻辑或无障碍的完整验收。
:::

## 一、源码与文档树

### 1. 从文本到 DOM

HTML 文件保存的是字节。浏览器先依据编码把字节解释为字符，再解析标签、属性和文字，构造**文档对象模型**（DOM，Document Object Model）。DOM 用树组织文档中的对象，元素、普通文字和注释都有对应位置。

下面是可以放入 `body` 的局部内容：

```html
<p>阅读<span>说明</span>。</p>
```

其中 `p` 和 `span` 是元素节点；“阅读”“说明”和句号分别参与文本节点的内容。只画这部分结构，可以得到：

```text
p
├── 文本：阅读
├── span
│   └── 文本：说明
└── 文本：。
```

树形关系表达父子和先后位置，不是屏幕坐标。浏览器可以给元素应用样式，但文字排在左侧或右侧，不会改变这里的父子关系。DOM 的对象职责见 [MDN：文档对象模型](https://developer.mozilla.org/en-US/docs/Web/API/Document_Object_Model)，字符解码与解析过程见 [HTML 解析模型](https://html.spec.whatwg.org/multipage/parsing.html#overview-of-the-parsing-model)。

### 2. 文本节点与元素节点

DOM 不是只由标签组成。元素之间的文字会形成文本节点；注释会形成注释节点；属性和元素内容也不是同一种东西。理解这一点，才能解释为什么 `textContent` 的读数和页面显示不完全相同。

| 源码成分 | DOM 中的对象 | 是否直接绘制为文字 |
|----------|--------------|--------------------|
| `<p>...</p>` | 元素节点 | 元素本身不绘制，内容按规则呈现 |
| 标签之间的文字 | 文本节点 | 是，按 CSS 和布局呈现 |
| `<!-- ... -->` | 注释节点 | 否 |
| `class="note"` | 元素上的属性 | 否，不是正文文本 |

### 3. 源码视图与 Elements 的对象不同

编辑器或“查看网页源代码”显示文档的文本形式。开发者工具的 **Elements** 面板显示当前 DOM，包含浏览器补出的结构，也会反映脚本对节点的修改。两者不必逐字一致。

在 Elements 中临时删除或改写节点，只影响当前页面状态，不会自动保存回本地 HTML 文件。重新加载时，浏览器仍会读取文件中的源码；因此修复应回到编辑器保存，再从原入口重新打开或刷新。Chrome 对这两类观察的区别与操作见 [查看和修改 DOM](https://developer.chrome.com/docs/devtools/dom/)。

## 二、合法省略与错误恢复

### 1. 省略标签不一定构成错误

HTML 在明确条件下允许省略部分标签。省略的是源码中的标记，不代表最终文档树里没有相应元素。下面是一份完整的短文档，可以在空目录 `html-parsing` 中保存为 `omitted.html`：

```html [omitted.html]
<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>标签省略对照</title>
<h1>标签省略对照</h1>
<p>第一段
<p>第二段
</html>
```

这份源码没有显式写出 `head` 和 `body` 的开始、结束标签，也省略了两个 `p` 的结束标签。对当前排列而言，它们符合允许省略的条件；浏览器构造的 DOM 仍包含 `head`、`body` 和两个独立段落。

“省略是否合法”取决于元素及其前后内容，不是任意删除结束标签。初次编写文档时保留清楚的完整结构更容易检查；省略规则用于解释已有源码与 DOM 的差异，不能代替逐个核对。[HTML 可省略标签规则](https://html.spec.whatwg.org/multipage/syntax.html#optional-tags)规定了具体条件。

### 2. 恢复错误不等于认可写法

浏览器也会处理不符合作者规则的输入。例如，在已有段落中遇到 `div` 时，HTML 解析会结束当前段落，而不会把 `div` 保留为作者设想的段内子元素；后面的结束标签又要按当时状态处理。

这种行为使后面的内容仍有机会呈现，但不能证明原本的嵌套合法。应如何安排父子元素，由[元素嵌套与内容模型](./05-nesting-content-models.md)中的作者规则判断；这里关注的是浏览器实际生成了什么，以及怎样找到导致差异的源码。

还要区分结构错误与属性错误。缺少某个必需属性时，浏览器常常仍能创建元素；DOM 中存在这个节点，并不等于元素已经具有完整含义。是否需要属性、属性值是否有效，仍须检查具体定义。

### 3. 修补不等于合法

| 现象 | 源码意图 | 浏览器实际处理 | 判断 |
|------|----------|----------------|------|
| 段落中出现 `div` | 把 `div` 作为段落子元素 | 结束当前段落，`div` 成为后续同级内容 | 作者嵌套不合法 |
| 省略 `head`、`body` 标签 | 不写显式容器 | 自动补出对应元素 | 满足省略条件时合法 |
| 缺少 `img` 的 `alt` | 只提供图片地址 | 仍创建并加载图片 | 元素存在，但声明不完整 |
| 写错结束标签顺序 | 按预想层级闭合 | 按解析状态调整节点关系 | 需对照 DOM 判断 |

::: warning 浏览器能修补，不等于错误可以保留
解析器的容错目标之一是让文档仍可处理，不是替作者证明结构正确。页面能显示、元素能操作，都不能替代源码检查和 DOM 对照。
:::

## 三、保留源码并核对两类证据

### 1. 创建错误文档

在 `html-parsing` 空目录中创建下面的 `invalid.html`。它故意包含段落嵌套错误和图片缺少替代文本两个问题，先保留原文件，不在 Elements 中直接改掉现场：

::: details 查看 invalid.html 完整内容

```html [invalid.html]
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <title>结构检查对照</title>
</head>
<body>
  <h1>结构检查对照</h1>
  <p id="text">前面的文字
    <div>中间的文字</div>
    后面的文字
  </p>
  <img src="dot.svg">
</body>
</html>
```

:::

同目录创建 `dot.svg`，给图片一个确定存在的本地资源。图形本身只是装饰，不承载正文信息；这样可以把资源是否存在和 HTML 是否正确分开观察：

```xml [dot.svg]
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 16 16" width="16" height="16">
  <circle cx="8" cy="8" r="6" fill="black"/>
</svg>
```

双击 `invalid.html`。正文和圆点都能出现，不代表两个作者错误已经消失。这个示例没有外部样式和脚本，也不依赖其他文章的文件。

### 2. 查看源码和实际节点

在 Chrome 中右键页面选择“查看网页源代码”，或直接在编辑器中观察 `invalid.html`，可以看到 `div` 写在 `p` 的开始、结束标签之间。

再按 `F12`，macOS 按 `Option+Command+I`，打开开发者工具。切换到 Elements 后，按 `Ctrl+F`，macOS 按 `Command+F`，搜索 `id="text"`，定位原段落。展开它并观察相邻节点：

1. 原段落只有前面的文字，`div` 不在它里面，而出现在后方的同级位置。
2. “后面的文字”也不再属于原段落，源码末尾的 `</p>` 还会对应恢复出的空段落。
3. `img` 节点已经存在，图片也能请求成功，但源码和节点上都没有 `alt` 属性。

前两项说明实际树与预想嵌套不同；第三项说明即使结构没有明显变化，仍存在作者规则问题。不要只凭看到一个 `p` 或一张图片，就结束检查。

| 证据 | 能说明什么 | 不能说明什么 |
|------|------------|--------------|
| 页面显示文字 | 解析结果仍可呈现 | 源码嵌套合法 |
| 源码中的 `<div>` | 作者写下的标记位置 | 浏览器实际把它放在哪里 |
| Elements 中的父子关系 | 当前 DOM 的结果 | 原文件已经保存成这个结果 |
| 检查器报告 | 作者语法或一致性要求的问题 | 资源一定可用、业务一定正确 |

### 3. 使用 Nu 检查源文件

打开 [Nu HTML Checker](https://validator.w3.org/nu/)，在 **Check by** 下拉框中选择 **file upload**，上传当前保存的 `invalid.html` 并执行 **Check**。如果使用 **text input**，应粘贴完整文件，而不是只粘贴出错的一行或复制 Elements 中恢复后的 HTML。

本地文件地址不能作为公共 URL 交给在线服务读取，因此不能把 `file:///.../invalid.html` 填入远程地址检查框。上传或粘贴输入的是要检查的源码；其中仍应保留 DOCTYPE、语言、编码和标题等必要上下文。

检查器会把报告关联到源码位置。对这份文档，重点是两类报告：

| 报告含义 | 如何定位与解释 |
|----------|----------------|
| `p` 结束标签出现时没有对应的开放段落 | 不能只看被标记的结束标签；还要向前检查使原段落提前结束的 `div` |
| `img` 缺少 `alt` | 节点存在、图片加载成功都没有补上替代文本声明，需要依据图片用途修改源码 |

报告中的 **error** 表示检查器发现了不符合相应要求的问题；**warning** 提醒需要进一步判断的条件。警告也要根据上下文核对，但不能为了消除警告而删除有意义内容；报告数量更不能当作文档质量评分。不同版本的检查器可能合并或拆分同一处问题的报告，应结合源码位置理解，而不是背诵报告条数。Nu 是一致性检查工具，其能力与使用方式见[项目说明](https://validator.github.io/validator/)。

::: warning 检查源码，不用浏览器恢复后的结果替换原文件
将 Elements 中的结构复制出来再检查，会改变被检查的输入。解析阶段已经调整过的关系可能让原错误不再出现，却没有解释作者为什么写错。应先保存原源码，用同一输入关联浏览器现象和检查报告，再修改并复测。
:::

## 四、修复后从原入口复测

### 1. 根据含义修改源码

中间文字只是同一段的一部分，可以使用段内元素 `span`；这个选择来自内容关系，不是为了避开某条报错文案。圆点不提供额外信息，应明确使用空 `alt`，而不是让替代文本处于缺失状态。

创建 `repaired.html`，把修复作为独立文件保留，便于与错误版本逐项对照：

::: details 查看 repaired.html 完整内容

```html [repaired.html]
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <title>结构检查对照</title>
</head>
<body>
  <h1>结构检查对照</h1>
  <p id="text">前面的文字<span>中间的文字</span>后面的文字</p>
  <img src="dot.svg" alt="">
</body>
</html>
```

:::

`alt=""` 与没有 `alt` 是不同声明。如果图片本身包含需要传达的信息，空替代文本就不合适，应提供等价内容；不能把本例修复机械用于所有图片。替代文本的完整选择属于图片元素的使用规则。

### 2. 对照浏览器与检查器结果

保存并打开 `repaired.html`，再次定位 `id="text"`：中间的 `span` 应位于同一 `p` 内，前后文字也属于这个段落。再把修复后的完整文件上传 Nu，确认原先两类错误已消除。

以上独立文件于 2026-11-14 在 macOS 的 Chrome 157.0.8103.79 中核对，并取得 Nu 在线服务的真实报告：

| 文件 | 浏览器观察 | Nu 结果 |
|------|------------|---------|
| `omitted.html` | DOM 中补出 head、body，两个段落保持独立 | 无错误、无警告 |
| `invalid.html` | div 在原段落外；图片能显示，但没有 alt | 两项错误，分别涉及 p 结束标签和 img 缺少 alt |
| `repaired.html` | span 位于原段落内，图片具有空 alt | 无错误、无警告 |

若报告与预期不同，先检查上传的文件是否为刚保存的版本，再按报告位置核对上下文；不要用旧文件的通过结果替代当前输入。在线服务不可达时，只能记录当前未完成语法检查，不能把“浏览器能显示”当作 Nu 已通过。

::: tip 保留三个版本再比较
`omitted.html`、`invalid.html`、`repaired.html` 分别代表合法省略、错误输入和修复结果。保留它们可以减少“改过之后记不清原现象”的干扰，也便于在报告中逐项对照。
:::

### 3. 验证记录

以上结果来自 2026-11-14 的本地浏览器观察和 Nu 在线检查。浏览器版本为 Chrome 157.0.8103.79；Nu 的具体报告条目可能随服务版本调整，但错误类别与源码位置应能对应。未重新验证其他浏览器，也没有把本次检查扩展为资源、脚本或无障碍的完整验收。

## 五、检查通过证明了什么

### 1. 语法与资源分离

检查器主要核对标记及相关一致性要求，不会替代页面的全部使用检查。一个指向不存在文件的合法 `href` 可以通过结构检查，却在浏览器中请求失败；一份语法有效的表单，也不证明接收端已经处理数据。

| 检查对象 | 可以证明 | 不能证明 |
|----------|----------|----------|
| HTML 语法检查 | 当前源码符合相应标记规则 | 图片、样式和脚本都能加载 |
| Network 请求 | 资源地址和响应状态 | 元素嵌套与语义正确 |
| 页面显示 | 当前环境下的呈现结果 | 源码没有错误 |
| 键盘操作 | 当前路径可以操作 | 所有用户和辅助技术都可用 |

### 2. 语法与可访问性、业务分离

同样，合法 HTML 只是可访问页面的基础，无法单凭一份语法报告证明完整的键盘操作、内容等价性或辅助技术体验。结构修复后仍应验证当前文章或页面承诺的结果：这里能够证明原先的嵌套和替代文本声明问题已经消除，而不是网站的所有功能都已完成。

::: info 交付前的三项证据
一次可复现的修复至少留下三类证据：修改前的源码与现象、修改后的源码与现象、以及对应的检查结果。只记录“已修复”或只贴一张正常页面截图，都无法证明问题是在哪个输入上被消除的。
:::
