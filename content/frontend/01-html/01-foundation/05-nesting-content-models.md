# 元素嵌套与内容模型

HTML 元素不能只按显示效果任意组合。一个元素能放在哪里、内部能包含什么，由 HTML 的**内容模型**等规则约束。例如，`span` 可以放进普通段落 `p`，`div` 却不能作为 `p` 的内容；给 `div` 设置行内显示也不会改变这条规则。

判断嵌套需要看元素的含义和结构限制。页面能显示，说明浏览器处理了输入，不能据此认定源码符合标准。

## 一、元素之间的结构关系

开始标签与结束标签之间的元素，会形成嵌套关系。下面是可以放在文档 `body` 中的局部内容：

```html
<div>
  <p>一段包含<strong>强调文字</strong>的说明。</p>
  <p>另一段说明。</p>
</div>
```

只观察其中的元素，结构可以表示为：

```text
div
├── p
│   └── strong
└── p
```

外层 `div` 是两个 `p` 的**父元素**，两个 `p` 是它的**子元素**。两个 `p` 拥有相同的父元素，互为**兄弟元素**。`strong` 的父元素是第一个 `p`；`p` 与更外层的 `div` 都是 `strong` 的**祖先元素**，`strong` 则是它们的**后代元素**。

子元素只指直接下一层，后代元素可以隔着多层。这个区别会影响规则的检查范围：“不允许某种子元素”和“不允许任何这种后代元素”不是同一个限制。

文字同样属于内容。第一个 `p` 中，`strong` 前后的文字以文本节点参与文档结构，不能因为它们没有标签，就忽略它们对内容模型的影响。这里的树省略了文本节点，只用于观察元素关系。

## 二、内容类别、内容模型与上下文

### 1. 内容类别说明元素属于什么类型

**内容类别**是标准用来归纳元素性质的分组，与 `class` 属性无关。一个元素可以同时属于多个类别，类别也不是互不相交的标签清单。

判断普通正文的嵌套时，经常需要以下类别：

| 类别 | 含义与代表 |
|------|------------|
| 流式内容（flow content） | 正文中广泛使用的内容范围，包括普通文字以及 `p`、`div`、`span` 等元素 |
| 短语内容（phrasing content） | 文字与用于组织段内内容的标记，包括 `span`、`strong`、`img` 等；这类内容也属于流式内容 |
| 交互内容（interactive content） | 专门供用户操作的内容，例如带 `href` 的 `a` 和通常的 `button`；部分元素是否属于此类取决于属性 |

`span` 同时属于流式内容和短语内容。`div` 属于流式内容，但不属于短语内容。`a` 属于短语内容；带有 `href` 时，还属于交互内容。

标准还有元数据内容、分节内容等类别。判断当前结构时，只需找到相关元素的定义及其要求，不必先背下全部分类。类别的完整依据见 [HTML 标准：内容类别](https://html.spec.whatwg.org/multipage/dom.html#kinds-of-content)。

### 2. 内容模型说明内部允许什么

**内容模型**描述元素内部允许的内容以及相关限制。它可以指定一个内容类别，也可以要求特定的子元素、顺序或后代条件。

下面列出普通正文场景中几种常见要求：

| 元素 | 自身类别与内部要求的区别 |
|------|--------------------------|
| `p` | 自身属于流式内容，内部要求短语内容 |
| `span` | 自身属于短语内容，内部也要求短语内容 |
| `div` | 普通正文上下文中，自身属于流式内容，内部允许流式内容 |
| `ul` | 自身属于流式内容，但内部按列表结构要求组织，不能直接放任意流式元素 |
| `a` | 自身属于短语内容，内部采用透明内容模型，还要满足链接的额外限制 |

由此不能推出“流式元素内部都能放流式元素”，也不能由“一个元素属于短语内容”推出“它内部只能放短语内容”。**元素自身的分类与内部允许的内容，是两项分别定义的信息。**

表中的 `div` 特意限定为普通正文上下文。某些元素在特定父级或祖先中有不同的模型分支；查标准时需要阅读条件，不能把一个常见分支当作所有场景的通则。[HTML 标准：内容模型](https://html.spec.whatwg.org/multipage/dom.html#content-models)、[div 元素](https://html.spec.whatwg.org/multipage/grouping-content.html#the-div-element)分别给出了通用规则和具体定义。

### 3. 上下文说明元素可以出现在哪里

元素定义中还会列出 **Contexts in which this element can be used**，即允许使用它的上下文摘要。例如，可以用这种摘要快速了解元素适合放在需要流式内容还是短语内容的位置。

上下文摘要方便查阅，最终仍需按照父元素的内容模型和额外限制判断。不能只看到子元素属于某一类，就跳过父元素对具体结构的要求。

实际检查时，可以沿着以下关系阅读标准：父元素内部允许什么，候选子元素是否符合要求，以及当前位置还有哪些针对特定元素或后代的限制。这些信息分别记录在[元素定义](https://html.spec.whatwg.org/multipage/dom.html#element-definitions)的类别、上下文和内容模型等字段中。

## 三、逐层判断常见嵌套

### 1. 段落中的内容必须满足段落模型

`p` 要求短语内容，`span` 属于短语内容，因此下面这段局部标记符合要求：

```html
<p>请阅读<span>这段说明</span>。</p>
```

还要继续检查 `span` 内部。这里的内容是普通文字，符合 `span` 对短语内容的要求，所以两层结构都成立。

如果改成下面的写法，预期的嵌套就不符合要求：

```html
<!-- 错误示例：div 不属于 p 允许的短语内容 -->
<p>请阅读<div>这段说明</div>。</p>
```

问题不在标签是否按顺序闭合，而在 `div` 不是短语内容。浏览器处理这份 HTML 时，会在遇到 `div` 时提前结束已有段落；恢复后的实际结构与作者想写的嵌套不同。这里只需要区分两者，完整解析过程不影响对源码规则的判断。依据是 [p 的内容模型](https://html.spec.whatwg.org/multipage/grouping-content.html#the-p-element)。

### 2. 特定结构不能用一般类别替代

列表 `ul` 的内容模型要求列表项等特定结构。普通列表项使用 `li`，因此嵌套列表应放在对应的 `li` 内部：

```html
<ul>
  <li>第一项</li>
  <li>第二项
    <ul>
      <li>第二项的补充</li>
    </ul>
  </li>
</ul>
```

外层 `ul` 的普通子元素是 `li`，内层 `ul` 位于第二个列表项之中。这个位置表达“补充内容属于第二项”，而不只是通过缩进把文字画到右侧。

下面的写法则把内层列表直接放在外层列表之下：

```html
<!-- 错误示例：内层 ul 应放入对应的 li -->
<ul>
  <li>第一项</li>
  <ul><li>补充项</li></ul>
</ul>
```

内层 `ul` 虽然属于流式内容，也不能替代这里要求的列表结构。修复时应把它移动到所属的 `li` 中，再检查其内部列表项。

严格地说，`ul` 还允许规范定义的脚本支持元素；元素间空白与注释也有各自的处理规则。因此不能把本例简化成“`ul` 标签之间只能出现 `li` 字符串”。这里检查的是普通列表内容的结构位置，完整要求见 [ul 的内容模型](https://html.spec.whatwg.org/multipage/grouping-content.html#the-ul-element)。

### 3. 普通文字与空元素也有约束

流式内容和短语内容都可以包含普通文字，并不要求每段文字必须再套一个标签。但若父元素要求特定结构，就不能用任意文字或其他元素代替它要求的子元素。

**空元素**不能包含子内容。例如，`br` 可以出现在段落允许的短语内容位置，用于表达换行，但它自己没有可容纳文字的内部区域：

```html
<p>第一行<br>第二行</p>
```

“第二行”是 `p` 内的文字，不是 `br` 的子内容。写成 `<br>第二行</br>` 不能建立一个包住文字的 `br` 元素。空元素的标签限制与内容类别应分别判断，不能因为它属于段内可用内容，就认为它也能装入段内文字。[HTML 标准：元素语法](https://html.spec.whatwg.org/multipage/syntax.html#elements-2)定义了空元素的写法。

## 四、透明内容模型与后代限制

### 1. 透明模型需要沿所在位置检查

`a` 的内容模型是**透明的**：判断它的透明部分时，需要把它放回所在位置，检查该位置允许什么内容，而不是把 `a` 当成内部可任意放置的容器。

普通正文中的 `div` 允许流式内容，因此以下局部标记中的链接可以包含标题和段落：

```html
<div>
  <a href="#note">
    <h1>说明标题</h1>
    <p>查看完整说明。</p>
  </a>
</div>
<p id="note">完整说明。</p>
```

去掉透明层来检查它所在的位置时，标题和段落都是普通 `div` 允许的流式内容。这里还没有违反链接自身的额外限制，因此结构成立。

但把链接放进 `p` 后，所在位置要求的是短语内容，透明性不能让 `div` 绕过这项要求：

```html
<!-- 错误示例：透明链接没有改变 p 的内容限制 -->
<p><a href="#note"><div>说明</div></a></p>
<p id="note">完整说明。</p>
```

如果透明元素外面还有透明层，需要继续向外检查，直到得到对应位置的约束。`a` 自身属于短语内容，与它在不同上下文中能够包含不同内容并不矛盾；这是自身类别与内容模型分开的一个具体例子。依据见[透明内容模型](https://html.spec.whatwg.org/multipage/dom.html#transparent-content-models)。

### 2. 允许的类别之外还有额外限制

`a` 的透明内容还受到三项后代限制：不能包含交互内容后代、任何 `a` 后代，以及指定了 `tabindex` 的后代。这些限制检查全部后代，不只检查直接子元素。[a 的内容模型](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-a-element)给出了完整条件。

因此，以下局部标记虽然只是“链接包住一段文字”，仍然不合规：

```html
<!-- 错误示例：span 是链接中指定了 tabindex 的后代 -->
<p><a href="#note"><span tabindex="-1">查看说明</span></a></p>
<p id="note">说明文字。</p>
```

`span` 属于短语内容，但 `tabindex="-1"` 仍然是在后代上指定了 `tabindex`。这项限制不是只禁止正值，也不是只禁止能通过 Tab 键到达的后代。若这段文字不需要单独管理焦点，删除 `span` 上的 `tabindex` 即可消除这里的违规条件。

把按钮包在多层 `span` 后放入链接，也不能避开交互后代限制；嵌套另一个链接同样不允许。反过来，也不能从这个例子推导“所有交互元素都绝对禁止互相嵌套”，其他元素仍应分别查自己的具体定义。

## 五、用独立文档核对判断

### 1. 创建两个结构对照文件

在新建的空目录 `html-nesting` 中创建 `valid.html`，以 UTF-8 保存。它只包含一个段落和段内标记，不依赖脚本、外部样式或其他文章的文件。

::: details 查看 valid.html 完整内容

```html [valid.html]
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <title>合法的段内标记</title>
</head>
<body>
  <p id="text">前面的文字<span>中间的文字</span>后面的文字</p>
</body>
</html>
```

:::

同一目录再创建 `invalid.html`。这是有意保留错误结构的对照文件；`display: inline` 只要求 `div` 按行内方式显示，用来检验样式是否会改变 HTML 规则。

::: details 查看 invalid.html 完整内容

```html [invalid.html]
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <title>显示方式不能修复嵌套</title>
</head>
<body>
  <p id="text">前面的文字
    <div style="display: inline">中间的文字</div>
    后面的文字
  </p>
</body>
</html>
```

:::

### 2. 区分源码、实际结构与显示结果

分别用浏览器打开两个文件。合法版本中的三段文字位于同一段落中；错误版本的文字仍能出现，行距和换行与合法版本不同，具体外观还受浏览器默认样式影响。

在 Chrome 中按 `F12`，macOS 可按 `Option+Command+I`，打开开发者工具的 Elements 面板，找到 `p` 和中间的标记。合法版本中的 `span` 位于 `p` 内，错误版本中的 `div` 已经与原 `p` 分开。这个观察只用于核对源码与实际结构的差异，不要求先掌握完整 DOM API。

::: warning CSS 显示方式不决定 HTML 嵌套是否合法
HTML4 中常见的“块级／行内”分类，不能代替现行 HTML 的内容模型。CSS 的 `display` 控制显示与布局，不会把 `div` 变成短语内容，也不会修改 `p` 的模型。修改显示方式后文字靠在一起，不代表源码结构已经修复。
:::

还可以在 [Nu HTML Checker](https://validator.w3.org/nu/) 中上传两个文件，对照合法版本与错误版本的报告。检查器用于辅助核对具体规则；这里不要求背诵报错文案，也不能把浏览器恢复后的结构误认为作者原本写出了合法嵌套。

以上两个完整文件于 2026-11-14 在 macOS 的 Chrome 157.0.8103.52 中核对，并通过 Nu 在线检查器对照：

| 文件 | 浏览器中的结构 | Nu 检查结果 |
|------|----------------|-------------|
| `valid.html` | `span` 是 `p` 的后代 | 无错误、无警告 |
| `invalid.html` | `div` 不在原 `p` 内，虽设置了行内显示，结构仍已分开 | 报告存在没有对应开放段落的 `p` 结束标签 |

错误报告对应的是这份源码经 HTML 解析后的问题，不能反向当作“只需删除报错的结束标签，原本的嵌套就成立”。修复仍需回到内容模型，决定中间内容应属于段内还是独立区域。

### 3. 根据内容含义修改结构

如果中间文字只是段内的一部分，使用 `span` 等合适的短语元素，或直接保留为普通文字，再打开文件检查。修改后的结构应与 `valid.html` 一致。

如果中间内容确实需要独立的容器，就应调整段落边界。例如，下面的局部结构把两段文字与独立内容放在共同的外层 `div` 中：

```html
<div>
  <p>前面的文字</p>
  <div>中间的内容</div>
  <p>后面的文字</p>
</div>
```

外层 `div` 在普通正文中允许这些流式子内容，每个 `p` 内又都是短语内容。修复改变的是元素关系，而不是用显示效果掩盖不符合模型的写法。
