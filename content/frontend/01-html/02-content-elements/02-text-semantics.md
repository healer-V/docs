# 文本语义与引用

HTML 文本元素说明文字在内容中承担的角色。例如，`em` 表示语气强调，`strong` 表示重要性，`cite` 标记作品名称，`code` 标记代码文本。它们的默认外观可以相似，语义却不能按“粗体”“斜体”等视觉效果互换。

选择元素时，应先说明这段文字为什么需要单独标记，再选择能表达该含义的元素。只是需要改变字体而没有额外内容含义时，应通过 CSS 处理。

下面按强调、引文、代码文字和补充标记分组，最后用三个独立文件核对结构与显示。

::: info 本篇的范围
本篇讲基础文本语义元素的选择。`mark`、`time`、`data`、`ruby`、`bdi` 等增强文本元素归第 4 章；CSS 字体、颜色和排版规则归 CSS；完整参考文献系统和自动引文生成不是 HTML 的职责。示例中的引文和作品名称均为结构演示，不对应真实文献。
:::

## 一、强调与重要性

### 1. em 改变句子中的强调重点

`em` 表达语气上的强调，强调放在不同文字上，可以改变一句话的重心。下面是可以放在正文段落中的局部片段：

```html
<p>这句话由<em>我</em>来读。</p>
<p>这句话由我来<em>读</em>。</p>
```

第一句突出由谁来读，第二句突出执行的是“读”这个动作。浏览器常用斜体显示 `em`，但斜体不是它的定义；改变样式后，内容中的强调关系仍应成立。规则见 [HTML 标准：em](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-em-element)。

### 2. strong 表达重要、严肃或紧迫的信息

`strong` 标记内容的重要性、严肃性或紧迫性，不一定改变句子的语气重心。例如：

```html
<p><strong>不要覆盖原文件。</strong>先另存一份副本。</p>
```

这段标记说明警示内容具有更高的重要性。`em` 和 `strong` 不是两个不同字重的按钮，不能只根据希望的外观选择。两者也可以在确有不同语义时组合，但不需要为让文字“更醒目”而层层堆叠。

语义可供浏览器与辅助技术处理，却不保证每个屏幕阅读器一定以同样的音量或语调朗读。实际朗读依赖工具和设置，不能从一个标签名直接推导全部结果。[strong 的定义](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-strong-element)说明了它表达的内容关系。

### 3. b、i 与 u 也要按含义选择

现行 HTML 为这些文字级元素定义了用途，不能只把它们解释为加粗、斜体和下划线：

| 元素 | 内容含义与选择条件 | 常见误用 |
|------|--------------------|----------|
| `b` | 引起额外注意，但不声明更高重要性，例如文档中的关键词 | 把重要警告写成 `b` |
| `i` | 与普通正文不同的声音或表达惯例，例如外语短语、技术术语或分类名称 | 用 `i` 代替语气强调 |
| `u` | 明确的非文本注记，例如标注拼写错误 | 用 `u` 给普通文字加下划线 |

例如，关键词可以使用 `<b>属性</b>`，外语短语可在合适上下文中写为 `<i lang="en">in situ</i>`。如果内容实际是重要警告，应选择 `strong`，而不是因为 `b` 默认也加粗就用它代替。

`u` 常见的下划线外观还容易与链接混淆。需要导航时应使用链接；仅为装饰加线则使用 CSS。各项现行语义可查 [b](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-b-element)、[i](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-i-element)与 [u](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-u-element)。

### 4. 语义与默认外观分开判断

同一段文字可以用不同元素得到相似外观，但选择依据仍是内容角色。反过来，CSS 改变 `em` 的字重也不会把它变成 `strong`，给普通文字加粗也不会自动获得重要性语义。

::: tip 先写一句“为什么标记它”
选择元素前，用一句话说明这段文字在内容中承担什么角色：语气重点、重要警告、作品名、代码、用户输入还是普通关键词。说不清角色时，通常应该用普通文字加 CSS，而不是猜一个标签。
:::

## 二、引文、作品名称与来源地址

### 1. blockquote 与 q 表达不同范围的引文

`blockquote` 表示从其他来源引用的一部分内容，内部可按需要包含段落等流式内容。`q` 用于行文中的短引用，内部要求短语内容。它们都不只是用于缩进或画引号的样式工具。

以下是两个独立局部片段，引用文字均为说明结构而编写的演示内容，不对应真实文献原句：

```html
<blockquote>
  <p>这段文字用于展示独立引文的结构。</p>
</blockquote>
<p>她说：<q>这是一段短引用。</q></p>
```

浏览器通常会为 `blockquote` 设置边距，为 `q` 生成相应引号，但这些外观能够通过样式变化。使用 `q` 时不应只因默认已有引号，又机械重复添加相同的外层引号。判断对象仍是“这是否是一段引文”，不是它是否恰好呈现成自己想要的缩进。[blockquote](https://html.spec.whatwg.org/multipage/grouping-content.html#the-blockquote-element)和 [q](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-q-element)分别定义了这些语义。

### 2. cite 元素标记作品名称

`cite` 元素表示作品名称，例如一本书、一篇文章、一首作品或一份规范的名称。作者姓名与作品名称不同，不能因为在写参考来源，就把作者姓名一律放进 `cite`。

下面的局部片段中，作品名被单独标记，作者姓名保留为普通文字；所有名称均为结构演示：

```html
<p>来源：<cite>示例短文</cite>，示例作者。</p>
```

如果需要提供可点击的作品地址，应另外写出链接。单独使用 `cite` 元素，不会自动检索作品、生成参考文献或创建导航。[cite 的定义](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-cite-element)明确区分了作品名称与人名。

### 3. cite 属性记录来源，不自动显示来源

`blockquote` 和 `q` 还可以具有 `cite` **属性**，其值是来源地址；它与上面的 `cite` **元素**不是同一作用。下面是局部结构，片段地址 `#work` 指向同一文档中已给出的来源说明：

```html
<blockquote cite="#work">
  <p>这是一段演示引文。</p>
</blockquote>
<p id="work">来源：<cite>示例短文</cite>，示例作者。</p>
```

属性提供了机器可读取的地址信息，但浏览器不会仅因为设置它就自动显示一条来源链接。因此，阅读者需要看到的作品名称、作者和可用入口，应在页面内容中明确表达；不能把不可见属性当作完整的可见引用说明。

::: warning cite 属性不是可见来源
`cite` 属性不会在页面上画出链接，也不会自动生成参考文献。需要读者点击的来源入口，应使用可见的 `a` 元素；需要显示的作品名称，应使用 `cite` 元素。属性、元素和可见链接是三件不同的事。
:::

### 4. 引文的范围与来源要匹配

`blockquote` 可以包含多个段落，但它的边界应对应实际引用范围；不要把整节自己的评论都放进引文。`q` 适合句内短引用，不适合包住多段内容。引文后的评论、出处和解释应放在引文元素之外，避免读者误以为它们也是被引用内容。

## 三、代码、输入、输出与预格式文本

### 1. code 与 pre 各有职责

`code` 表示代码片段，例如元素写法、函数名或程序文本；`pre` 表示预先排好格式的文本。代码需要保留缩进与换行时，经常组合两者：

```html
<pre><code>&lt;p&gt;文字&lt;/p&gt;</code></pre>
```

`pre` 负责预格式文本这一内容角色，默认呈现通常保留空白；`code` 表明其中是代码。这些标记都不会让 HTML 解析停止，所以要显示的 `<p>` 仍须使用字符引用，不能把真正的 `p` 子元素放进去当作代码文字。

### 2. kbd、samp 与 var 标记不同的文本角色

这些元素可以与代码说明配合，但不负责执行它们包住的文字：

| 元素 | 表达的内容 | 局部示意 | 边界 |
|------|------------|----------|------|
| `kbd` | 用户输入，例如命令文字或按键名称 | `<kbd>Enter</kbd>` | 不会真的按键或执行命令 |
| `samp` | 程序或系统输出的示例文字 | `<samp>Ready</samp>` | 不会运行程序取得输出 |
| `var` | 数学表达式或程序中的变量名称 | `<var>x</var>` | 不会声明或计算变量 |

如果一句话在说明“输入什么”和“返回什么”，分别标记它们可以保留这种区别。`<kbd>help</kbd>` 只把 `help` 标成用户输入，不会打开终端执行命令；`samp` 内的输出也必须按来源区分实测与示意。相关定义见 [code 及相邻文字元素](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-code-element)。

### 3. 代码高亮不是 code 的自动能力

代码高亮也不是 `code` 元素自动提供的语言分析能力。需要语法着色时通常要另加样式和相应工具，不应把普通 `class` 名称当成浏览器已安装的高亮器。预格式与默认空白处理可参照 [pre 的定义](https://html.spec.whatwg.org/multipage/grouping-content.html#the-pre-element)和[注释、空白与字符引用](../01-foundation/07-comments-whitespace-references.md)。

::: warning 代码文字里的尖括号仍要转义
`<pre><code>` 不会关闭 HTML 解析。想显示 `<p>` 字样，必须写成 `&lt;p&gt;`；直接写 `<p>` 会建立真实元素，既改变页面结构，也可能违反 `code` 的内容模型。
:::

## 四、缩写、附注、上下标与编辑标记

### 1. 缩写和附注不是单纯字号选择

`abbr` 表示缩写。需要在属性中提供完整展开形式时，可以使用 `title`，例如：

```html
<p><abbr title="HyperText Markup Language">HTML</abbr> 是标记语言。</p>
```

`title` 中应是对应的完整名称，而不是混入另一段无关提示。不过，属性提示不能保证所有设备都方便访问；重要的展开说明仍应在首次使用等合适位置以可读文字提供。`abbr` 不会自动为整篇文章展开缩写。

`small` 表示附注、小字说明等内容角色，例如版权或法律附注，不等于“任何想显示得小的文字”。长篇正文仅因想缩小字号而整体放入 `small`，不能据此外推它具有附注语义。[abbr](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-abbr-element)与 [small](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-small-element)分别说明了两者的用途。

### 2. 上下标表达书写约定

`sub` 与 `sup` 用于确有上下标书写约定的内容，例如化学式或指数：

```html
<p>水的化学式为 H<sub>2</sub>O；平方可写为 x<sup>2</sup>。</p>
```

它们不只是把任意字母移动到上方或下方的布局工具。公式本身需要更复杂的结构时，应选择适合数学表达的标记方式，不能仅靠连续嵌套上下标表达全部数学关系。

### 3. s 与 del、ins 区分内容状态和编辑变化

`s` 表示不再准确或不再相关的内容；`del` 与 `ins` 分别表示文档中的删除和插入。它们默认的删除线或下划线外观相近，也不意味着可以互换：

```html
<p><s>旧说明仍然有效。</s>该说明已不再适用。</p>
<p>修订：<del>十份</del><ins>十二份</ins>。</p>
```

前一段表达一句内容失效，后一段明确记录从旧文字到新文字的编辑变化。`del` 和 `ins` 可以带修改来源、日期等信息，但不会自动建立版本历史；这里只说明文本变化的语义，不构建修订系统。规则见 [s](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-s-element)与[文档编辑标记](https://html.spec.whatwg.org/multipage/edits.html)。

`mark`、`time`、`data`、注音和双向隔离等增强元素各有独立含义，归入 HTML5 文本语义与内容说明主题，不在这里重复展开。

## 五、三个独立文件的对照

### 1. 强调与关键词

新建空目录 `html-text-semantics`。下面三个文件分别展示一种关系，都可单独打开，不共享样式、脚本或资源。先创建 `emphasis.html`，以 UTF-8 保存：

::: details 查看 emphasis.html 完整内容

```html [emphasis.html]
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <title>强调与关键词</title>
</head>
<body>
  <!-- em 改变语气重心，strong 表达重要性 -->
  <p>这句话由<em>我</em>来读。</p>
  <p><strong>不要覆盖原文件。</strong></p>

  <!-- b 只引起额外注意，不声明更高重要性 -->
  <p>检索词：<b>属性</b>、<b>元素</b>。</p>

  <!-- i 可标记与正文不同的表达惯例，并声明语言 -->
  <p>外语短语：<i lang="en">in situ</i>。</p>
</body>
</html>
```

:::

默认显示中，`strong` 与 `b` 都能呈现粗体，但前者表达重要性，后者仅给关键词额外注意。应根据文字的内容角色解释选择，不能仅从截图中相同的字重得出它们语义相同。

### 2. 引文与作品名

创建独立的 `quotation.html`。内容明确是为说明引用结构而写的演示材料，不对应真实作者或作品引文。

::: details 查看 quotation.html 完整内容

```html [quotation.html]
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <title>引文与作品名</title>
</head>
<body>
  <!-- cite 属性保存来源地址，但不会自动显示链接 -->
  <blockquote cite="#work">
    <p>这是一段演示引文。</p>
  </blockquote>

  <!-- cite 元素标记作品名称；作者姓名保留为普通文字 -->
  <p id="work">来源：<cite>示例短文</cite>，示例作者。</p>

  <!-- q 用于行内短引用 -->
  <p>她说：<q>这是一段短引用。</q></p>
</body>
</html>
```

:::

打开后能看到引文与下方的来源说明。Elements 面板可以读到 `blockquote` 的 `cite` 属性，但引文内部没有因此自动出现链接。要把来源做成可点击入口，需要另外声明链接，属性并不替作者生成页面内容。

### 3. 代码文字与错误恢复

创建 `code-text.html`。命令与输出均作为示意文本展示，不要求执行其中的命令。

::: details 查看 code-text.html 完整内容

```html [code-text.html]
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <title>代码文字与输入输出</title>
</head>
<body>
  <!-- 字符引用让尖括号成为文字，而不是新元素 -->
  <pre><code id="code">&lt;p&gt;文字&lt;/p&gt;</code></pre>

  <!-- kbd 表示用户输入，samp 表示程序输出，二者都只是文本角色 -->
  <p>输入示意：<kbd>help</kbd>；输出示意：<samp>Ready</samp>。</p>

  <!-- var 表示变量名称，不声明或计算变量 -->
  <p>变量名称：<var>x</var>。</p>
</body>
</html>
```

:::

页面第一段预格式文本显示 `<p>文字</p>`。在 Chrome Elements 中检查 `code`，其内容是包含尖括号的文字，没有一个真实的 `p` 子元素。

把文件复制成 `invalid.html`，将 `&lt;p&gt;文字&lt;/p&gt;` 改成真正的 `<p>文字</p>`。这次源码会建立实际元素，而非显示代码；同时 `p` 不满足 `code` 的短语内容模型。通过 [Nu HTML Checker](https://validator.w3.org/nu/) 查看错误，再恢复字符引用，重新打开文件即可复测。

### 4. 注入错误并恢复

| 注入的错误 | 观察 | 恢复 |
|------------|------|------|
| 把 `&lt;p&gt;` 写成 `<p>` | 产生真实 `p` 子元素，不再显示代码文字 | 恢复字符引用，检查 DOM |
| 把作者姓名放进 `cite` | 结构可能合法，但作品名与人名混淆 | 只把作品名放进 `cite`，作者用普通文字 |
| 只写 `cite` 属性期待来源链接 | 页面没有新增可见链接 | 另写可见的 `a` 元素 |
| 用 `b` 代替 `strong` 表达警告 | 外观相似，重要性语义丢失 | 按内容含义改用 `strong` |
| 用 `u` 给普通文字加下划线 | 容易与链接混淆，且没有注记含义 | 删除 `u`，装饰用 CSS |

以上三个完整文件于 2026-11-14 在 macOS 的 Chrome 157.0.8103.79 中核对，Nu 均无错误、无警告。原样插入 `p` 的错误版本产生真实 `p` 子元素，Nu 报告不允许的子内容；恢复后又显示为字面代码。

把作者姓名误写进 `cite` 则属于另一类问题：标签可以形成合法结构，仍不能准确表达作品名称。需要回到内容含义修正，不能期待所有语义选择错误都由检查器自动发现。本例也未据此断言任何屏幕阅读器的具体朗读方式。
