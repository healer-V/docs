# 进程与信号

进程是正在执行的程序实例。运维操作面对的不是磁盘上的可执行文件，而是具有 **PID、父进程、运行身份、状态和启动参数** 的具体进程。发送信号前必须先确认这些属性，否则相同程序名、过期 PID 或过宽的匹配条件都可能让操作命中错误目标。

本文在隔离的 Ubuntu Server 26.04 实验机中使用 `sleep` 创建临时进程，只演示单个 PID 的识别和终止。命令语义依据 Ubuntu 26.04 的 [ps 手册](https://manpages.ubuntu.com/manpages/resolute/man1/ps.1.html)、[kill 手册](https://manpages.ubuntu.com/manpages/resolute/man1/kill.1.html)与 [signal(7) 手册](https://manpages.ubuntu.com/manpages/resolute/man7/signal.7.html)。

::: warning 当前示例尚未在 Linux 实验机执行
当前工作区没有可用的 Linux 或 systemd 实验环境，因此 PID、运行时长和终端号均为预期格式，不是本机实测记录。实际执行时必须使用命令返回的 PID，不能照抄示例数字。
:::

## 一、进程身份

程序名只能说明进程可能在执行什么，不能唯一标识某次运行。调查或终止进程时，至少同时检查 PID、父进程、用户和完整命令行。

### 1. PID 与 PPID

PID（Process ID）是内核分配给当前进程实例的数字标识；PPID（Parent Process ID）是创建该进程的父进程 PID。进程退出后，其 PID 可以被系统重新分配给新的进程，因此保存很久的 PID 不能直接用于后续终止操作。

```bash
ps -o pid,ppid,user,stat,etime,cmd -p 1
```

`-p 1` 选择 PID 1，`-o` 明确输出字段。Ubuntu 的 PID 1 通常是 `systemd`，但容器或特殊启动环境可能不同，应以实际 `cmd` 结果为准。

### 2. 运行身份

`USER` 字段表示进程的有效用户身份。普通用户通常只能向自己的进程发送信号；root 或具备相应能力的进程权限更大，但更高权限不会消除选错目标的风险。

| 字段 | 含义 | 操作前的判断 |
|------|------|--------------|
| `PID` | 当前进程标识 | 是否仍指向本次目标进程 |
| `PPID` | 父进程标识 | 是否由预期终端、服务或管理器创建 |
| `USER` | 有效运行用户 | 当前用户是否有权发送信号 |
| `ETIME` | 已运行时长 | 是否与目标的启动时间相符 |
| `CMD` | 完整命令行 | 参数和资源对象是否匹配 |

只看 `PID` 或程序名都不足以形成安全的终止依据。

### 3. 进程状态

`ps` 的 `STAT` 字段首字母表示主要状态，后续字符是附加属性。状态是查询时刻的快照，不代表进程会一直保持该状态。

| 状态 | 含义 | 常见判断 |
|------|------|----------|
| `R` | 正在运行或等待 CPU | 进程当前可调度，不等于 CPU 持续满载 |
| `S` | 可中断睡眠 | 常见于等待定时器、网络或其他事件 |
| `D` | 不可中断睡眠 | 常见于等待内核 I/O，信号可能暂时无法生效 |
| `T` | 已停止 | 由作业控制或停止信号暂停执行 |
| `Z` | 僵尸状态 | 子进程已退出，父进程尚未回收退出信息 |

::: tip 把状态与等待对象一起解释
`S` 并不表示异常，`R` 也不证明进程健康。判断卡顿或资源问题还要结合运行时间、CPU、I/O、日志和调用链，不能只凭一个状态字母下结论。
:::

## 二、前台与后台

前台、后台描述进程与控制终端的关系，不表示进程的重要程度。一个进程是否由 systemd 管理、是否脱离终端以及是否提供业务服务，是不同维度。

### 1. 前台进程

前台进程组接收终端产生的交互信号。用户在终端按 `Ctrl+C` 时，终端通常向前台进程组发送 `SIGINT`；具体处理结果取决于程序是否捕获或忽略该信号。

本文的实验进程在终端 A 前台运行，使其创建和退出都能直接观察。终端 B 只负责定位与发送信号，不依赖 Bash 作业编号。

### 2. 后台进程

后台运行只表示进程不占用当前终端的前台位置。Shell 的 `&`、作业控制和 `nohup` 各自还有会话与信号规则；systemd 服务则由服务管理器按单元和 cgroup 追踪。

需要管理长期服务时，应优先使用对应的服务管理接口，而不是从进程列表中随意选择 PID。直接信号操作适合受控实验、明确的独立进程或服务管理器无法使用的诊断场景。

## 三、目标定位

目标定位分为候选查找与 PID 复核。`pgrep` 可以缩小范围，但它的匹配结果仍需用 `ps` 检查完整属性。

### 1. 演示进程

在终端 A 以前台方式启动只等待、不修改文件的演示进程：

```bash
sleep 317
```

终端会等待进程结束。`317` 秒是本例的识别参数；如果它在后续步骤前自然结束，重新执行命令并使用新的 PID。

### 2. 精确匹配

在终端 B 查询当前用户拥有、完整命令行恰好为 `sleep 317` 的进程：

```bash
pgrep -a -u "$(id -u)" -f '^sleep 317$'
```

预期格式如下，实际 PID 会不同：

```text
24137 sleep 317
```

`-u` 限定有效用户，`-f` 让正则匹配完整命令行，`-a` 同时显示 PID 与命令。若返回零行，进程已经退出或匹配条件不符；若返回多行，不能任选一个 PID，应先检查每个候选的父进程与终端。

### 3. PID 复核

把下列 `<PID>` 替换为上一步刚取得的数字，再获取快照：

```bash
ps -o pid,ppid,user,tty,stat,etime,cmd -p <PID>
```

只有 `USER`、`CMD`、运行时长和终端关系都符合预期时，才把该 PID 作为信号目标。操作间隔较长时，应在发送信号前重新运行这条命令，降低 PID 已退出并被复用的风险。

::: danger 禁止使用宽泛模式直接终止
不要把 `pkill sleep`、`killall sleep` 或从旧记录复制的 PID 用作本例替代。它们可能命中其他用户或其他任务的等待进程，且无法证明终止对象就是刚创建的实验进程。
:::

## 四、信号语义

信号是发送给进程或线程的异步通知。`kill` 命令名称容易让人误解：它可以发送多种信号，默认发送的是 `SIGTERM`，并不等同于立即强制杀死。

### 1. SIGTERM

`SIGTERM` 表示请求进程终止。程序可以捕获该信号，完成停止接收请求、刷新缓冲区或释放资源等清理，也可以忽略或延迟处理。

```bash
kill -TERM <PID>
```

显式写出信号名称可以让变更记录更清楚。虽然 `kill <PID>` 默认也是 `SIGTERM`，生产操作仍建议标明意图。

### 2. SIGKILL

`SIGKILL` 由内核直接执行，进程不能捕获、阻塞或忽略它。它能终止仍可被内核调度处理的目标，但不会给应用执行清理逻辑的机会。

```bash
kill -KILL <PID>
```

只有在 `SIGTERM` 未生效、等待时间符合应用停止约定、目标身份再次复核无误，并且已经评估未刷盘数据与锁状态后，才考虑 `SIGKILL`。处于 `D` 状态的进程可能要等内核操作返回后才真正退出。

### 3. 信号 0

信号 0 不向目标投递实际信号，只检查调用者是否能定位该 PID 以及是否具备发送信号的权限：

```bash
kill -0 <PID>
echo $?
```

退出状态 `0` 表示目标存在且允许发送信号；非零可能表示进程不存在，也可能表示权限不足，必须结合错误信息区分。检查成功不证明 PID 对应正确程序，因此它不能替代 `ps` 复核。

## 五、终止验证

终止操作的闭环不是“命令没有报错”，而是目标进程消失、终端恢复，并且未影响其他进程。下面只对第三节创建的单个 PID 操作。

### 1. 正常终止

在终端 B 再次复核 PID 后发送 `SIGTERM`：

```bash
ps -o pid,user,stat,etime,cmd -p <PID>
kill -TERM <PID>
```

`sleep` 使用默认信号处理，因此预期终止。终端 A 应恢复命令提示符；某些 Shell 还会显示 `Terminated`。

### 2. 结果检查

在终端 B 检查旧 PID 和精确命令行：

```bash
ps -p <PID>
pgrep -a -u "$(id -u)" -f '^sleep 317$'
```

两条查询均不应显示该实验进程，并应返回非零状态。这里的非零表示“未找到目标”，正是终止后的预期结果。

如果旧 PID 仍存在，先查看其 `STAT` 与 `CMD`。命令行已经变化说明 PID 可能被复用，不能继续向旧数字发送更强信号；命令仍匹配时，再按应用停止约定判断是否需要等待或升级处理。

### 3. 影响范围

终止前后的候选数量应该从一条变为零，且操作只针对记录下来的正数 PID。没有必要向进程组、全部用户进程或 PID `-1` 发送信号。

::: tip 记录终止链路
生产变更至少记录目标 PID、完整命令、运行用户、信号类型、发送时间和验证结果。对 systemd 服务还应记录单元名，并通过 `systemctl` 与日志验证服务状态。
:::

## 六、异常状态

信号未达到预期结果时，先区分权限、目标变化和父子进程问题，再决定后续动作。

### 1. 权限拒绝

出现 `Operation not permitted` 表示目标可能存在，但当前身份无权发送信号。先比较 `USER` 字段和当前身份，并确认是否应由服务管理器或授权管理员操作。

不要因为权限拒绝就直接使用 `sudo kill -KILL`。提权只改变发送者能力，不会验证目标 PID，也不会为被终止程序补做清理。

### 2. PID 变化

出现 `No such process` 通常表示目标已退出，或查询与发送信号之间 PID 已变化。重新按命令、用户、父进程和启动时间定位，不把旧 PID 当作长期稳定标识。

服务反复重启时，主进程 PID 会不断变化。此时应检查 systemd 单元状态与重启策略，而不是追逐每一个短命 PID。

### 3. 僵尸进程

`Z` 状态表示子进程已经结束，只剩退出信息等待父进程回收。它不再执行用户代码，向僵尸 PID 发送 `SIGKILL` 也不能完成回收。

处理方向是确认 `PPID`，调查父进程为什么没有读取子进程退出状态。父进程正常处理或退出后，僵尸条目才会消失；不要把僵尸状态与仍在消耗 CPU 的运行进程混为一谈。

本文建立的操作顺序是：**先按属性定位，再复核 PID，优先发送 `SIGTERM`，最后验证目标和影响范围**。`SIGKILL` 只是无法正常退出时的升级手段，不是默认停止方式。
