# sudo 与权限边界

`sudo` 让经过授权的用户以另一个身份执行特定命令，默认目标通常是 root。它不是“遇到权限错误就重试”的前缀，而是一次需要认证、策略匹配、命令执行和审计记录的权限转换。

Ubuntu 默认锁定 root 账号的直接密码登录，由安装时创建并加入 `sudo` 组的管理员临时提权。本文以 `operator` 为已授权管理员，只操作 `/srv/ops-lab/sudo-boundary`，不修改生产 `sudoers` 策略。

::: danger 保留第二个管理员会话
修改任何授权策略前，先保留一个已经通过验证的管理员控制台或虚拟机快照。错误的 sudoers 配置可能让所有管理员失去提权能力。
:::

## 一、sudo 执行模型

一次 sudo 调用需要同时满足调用者身份、认证状态、授权策略和目标命令约束。命令本身仍可能因为参数、资源或应用规则失败。

### 1. 调用者与目标身份

直接执行命令时，进程继承当前用户身份；执行 `sudo 命令` 时，sudo 根据策略决定是否允许切换到目标身份。

```text
operator 输入命令
        ↓
sudo 读取调用者身份与授权策略
        ↓ 允许
认证并建立目标身份环境
        ↓
以 root 或 -u 指定用户执行命令
```

`sudo` 成功只证明授权和身份转换成立，不证明目标命令达成业务结果。仍需检查命令输出、退出状态和实际资源变化。

### 2. 认证与授权

认证回答“调用者是谁”，授权回答“该调用者能以谁的身份执行哪些命令”。Ubuntu 常见配置要求管理员输入自己的密码，而不是 root 密码。

| 阶段 | 失败表现 | 调查对象 |
|------|----------|----------|
| 认证 | 密码错误、凭据过期 | 当前用户、认证方式、终端条件 |
| 授权 | `is not allowed to run sudo` | sudoers 规则、用户与组 |
| 执行 | 目标命令返回错误 | 命令参数、文件、服务或资源状态 |

把三类失败区分开，才能避免用更高权限掩盖拼写、路径或配置错误。

### 3. 策略与记录

sudoers 策略决定允许的目标用户、主机、命令及参数约束。日志位置和内容取决于 Ubuntu 的 sudo 实现与系统配置，不能假定每次调用都具有完整命令输出审计。

本篇只使用现有授权，不写入 `/etc/sudoers` 或 `/etc/sudoers.d`。生产授权应经过独立评审，并使用 `visudo` 完成语法检查。

## 二、授权状态

开始提权操作前，先确认当前身份及其现有授权。查询动作不修改策略，可以作为变更记录的一部分。

### 1. 当前身份

```bash
whoami
id
```

预期当前用户为 `operator`，组列表通常包含 `sudo`。组成员只是常见授权来源，最终允许内容仍以 `sudo -l` 的策略结果为准。

### 2. 允许命令

```bash
sudo -l
```

认证成功后，输出会列出当前用户允许执行的规则。需要重点识别：

- 可以切换到哪些目标用户；
- 允许执行全部命令还是命令白名单；
- 是否要求密码；
- 是否存在环境变量或主机限制。

不要把其他主机的 `sudo -l` 输出复制为当前授权结论。

### 3. 凭据验证

`sudo -v` 只更新或验证凭据时间戳，不执行目标管理命令：

```bash
sudo -v
echo $?
```

退出状态 `0` 表示认证成功。非交互环境可以用 `sudo -n` 禁止密码提示；需要认证时它会立即失败，而不是无限等待输入。

## 三、拒绝与允许对照

同一路径先以普通身份写入，再以经过授权的身份写入，可以分离文件权限拒绝与 sudo 授权结果。

### 1. 测试目录

创建 root 所有、普通用户只可搜索的测试目录：

```bash
sudo install -d -o root -g root -m 0755 /srv/ops-lab/sudo-boundary
ls -ld -- /srv/ops-lab/sudo-boundary
```

目录模式应为 `drwxr-xr-x`，所有者和所属组均为 `root`。普通用户能够查看目录，但没有创建文件所需的目录写权限。

### 2. 普通身份拒绝

不使用 sudo 创建文件：

```bash
touch /srv/ops-lab/sudo-boundary/denied
echo $?
```

预期出现 `Permission denied` 并返回非零状态。使用 `ls` 确认 `denied` 没有被创建；这一步证明当前普通身份权限不足。

### 3. 授权身份允许

在已经确认目标与命令后执行最小提权：

```bash
sudo touch /srv/ops-lab/sudo-boundary/allowed
sudo stat -c '%U %G %a %n' /srv/ops-lab/sudo-boundary/allowed
```

预期文件所有者与所属组为 `root`。结果证明 sudo 允许本次身份转换并完成文件创建，不表示 `operator` 应永久获得目录写权限。

::: tip 只提升需要的命令
优先执行 `sudo 具体命令`，完成后立即回到普通身份。长期 root Shell 会扩大误操作范围，也让后续命令的身份边界难以辨认。
:::

## 四、目标身份与环境

sudo 可以通过 `-u` 指定目标用户。身份改变后，环境变量、家目录和搜索路径可能按策略被保留、重置或替换。

### 1. 目标用户

比较当前身份与 root 目标身份：

```bash
id
sudo -u root -- id
```

第一条显示 `operator`，第二条的有效 UID 应为 `0(root)`。`--` 结束 sudo 选项，后续内容作为目标命令传入。

### 2. 环境差异

不要假定 sudo 命令继承交互 Shell 的全部环境。服务管理、脚本和包管理命令应使用明确的绝对路径、配置文件与工作目录。

需要目标用户登录环境时，应先确认业务要求，而不是默认使用 root Shell。`sudo -H`、`sudo -i` 和环境保留策略具有不同影响，生产操作必须根据 `sudo` 手册与本机策略选择。

### 3. 文件归属

sudo 创建的文件默认归目标身份所有。管理员在普通用户工作目录中以 root 写文件，可能造成用户后续无法修改。

```bash
sudo touch /srv/ops-lab/sudo-boundary/root-owned
sudo stat -c '%U %G %n' /srv/ops-lab/sudo-boundary/root-owned
```

因此，提权前不仅要判断“能否执行”，还要判断产物应该归谁管理。

## 五、凭据生命周期

sudo 通常会在短时间内缓存成功认证，具体时长由策略决定。缓存只减少重复认证，不扩大原有授权范围。

### 1. 缓存刷新

```bash
sudo -v
```

在交互终端中，该命令可以刷新当前凭据时间戳。自动化任务不应依赖人工缓存，应使用明确的非交互授权和失败处理。

### 2. 缓存失效

结束管理操作后使当前凭据时间戳失效：

```bash
sudo -k
```

下一次需要认证的 sudo 调用将重新请求凭据。`sudo -k` 不撤销 sudoers 授权，也不终止已经运行的 root 进程。

### 3. 非交互检查

缓存失效后执行：

```bash
sudo -n true
echo $?
```

如果策略要求密码且没有有效缓存，命令应立即失败并返回非零状态。该模式适合脚本快速发现缺少非交互授权，但不应通过把所有命令改成免密来消除失败。

## 六、最小授权

最小授权要求把主体、目标身份、命令路径、参数范围和有效场景限制到完成任务所需的最小集合。

### 1. 授权维度

| 维度 | 需要回答的问题 |
|------|----------------|
| 主体 | 哪个用户或受控组需要权限 |
| 目标身份 | 必须是 root，还是专用服务账号即可 |
| 命令 | 哪个绝对路径的程序需要执行 |
| 参数 | 哪些对象和子命令必须允许 |
| 时间 | 权限是长期、临时还是变更窗口内有效 |
| 证据 | 如何记录调用、结果和异常使用 |

只限制程序路径但允许任意参数，仍可能让调用者访问意外对象或调用程序的命令执行能力。授权评审必须理解目标程序本身。

### 2. 配置修改边界

sudoers 文件只能使用 `visudo` 或同等语法验证流程修改。语法检查命令为：

```bash
sudo visudo -c
```

该命令只检查当前配置语法，不证明规则符合最小权限，也不证明所有管理员仍能登录。本文不提供 `NOPASSWD: ALL`、通配参数或全命令授权配方。

### 3. 拒绝处理

出现 sudo 拒绝时，按以下顺序处理：

1. 用 `whoami` 与 `id` 确认调用者；
2. 用 `sudo -l` 核对实际规则；
3. 确认目标用户、命令绝对路径和参数；
4. 判断任务是否确实需要提权；
5. 由授权责任人修改最小规则并执行语法与回退验证。

不要切换到 root 或放宽目录权限来绕过未知的授权拒绝。

## 七、实验清理

清理只删除本篇创建的两个 root 文件和测试目录，并使凭据缓存失效。

### 1. 对象确认

```bash
sudo find /srv/ops-lab/sudo-boundary -mindepth 1 -maxdepth 1 -printf '%U %G %p\n'
```

结果只应包含 `allowed` 与 `root-owned`。如果出现其他对象，先调查来源，不执行整个目录删除。

### 2. 目录删除

```bash
sudo rm -- /srv/ops-lab/sudo-boundary/allowed
sudo rm -- /srv/ops-lab/sudo-boundary/root-owned
sudo rmdir -- /srv/ops-lab/sudo-boundary
```

普通身份拒绝步骤中的 `denied` 不应存在。最后使用 `test ! -e /srv/ops-lab/sudo-boundary && echo cleaned` 确认目录已删除。

### 3. 凭据失效

```bash
sudo -k
```

这一步结束当前实验的认证缓存。它不修改用户组或 sudoers，原有授权保持不变。

本文证明了普通身份拒绝、sudo 授权允许、目标身份产物和凭据生命周期之间的边界。具体生产规则还需要结合命令参数能力、审计要求和失联回退方案单独评审。
