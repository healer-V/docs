# Responses API 调用文章重构设计

## 一、重构目标

当前样板覆盖了环境、请求、响应和错误信息，但正文只有二级标题。调用对象、字段解释、程序实现和判断依据混排在较大的内容块中，右侧大纲只能定位到宏观阶段，无法承担技术导航作用。

本次重构采用分层教程结构：二级标题表达调用阶段，三级标题表达独立技术问题，正文结构负责呈现结论、机制、实现位置和判断依据。标题增加必须对应独立内容，不通过机械拆分制造层级。

| 目标 | 验收结果 |
|------|----------|
| 阅读路径清晰 | 读者能够按请求模型、环境、实现、验证、诊断和边界顺序完成阅读 |
| 大纲可以定位 | 右侧大纲能够直接定位到请求结构、凭据、异常、状态、用量和错误类别 |
| 注意力有重点 | 关键条件、危险操作、成功判据和失败证据使用匹配的内容结构承载 |
| 内容保持闭环 | 环境、代码、执行命令、真实输出、失败分支和边界全部保留 |
| 标题准确简短 | 使用技术对象或判断阶段命名，不把完整结论或操作步骤写入标题 |

## 二、文章边界

| 项目 | 设计约束 |
|------|----------|
| 唯一问题 | 如何发送一次文本请求，并正确读取 Responses API 的状态、文本和用量 |
| 主文章类型 | 接入教程 |
| 目标深度 | 使用 |
| 保留内容 | Python 3.12、SDK 3.19.2、环境变量、完整程序、真实响应、错误分类 |
| 排除内容 | 流式、后台任务、多轮状态、结构化输出、工具调用、自动重试 |
| 示例场景 | 将虚构客户反馈压缩为一句中文摘要 |

重构不改变已经验证的程序行为和版本基线，不扩大到后续模块负责的模型接入能力。

## 三、标题结构

| 层级 | 标题 | 内容职责 |
|------|------|----------|
| `##` | 一、请求模型 | 建立客户端、请求方法和 Response 之间的关系 |
| `###` | 1. 调用链 | 展示输入、SDK、API、Response 和应用判断的执行顺序 |
| `###` | 2. 请求结构 | 解释 `model`、`instructions` 和 `input` 的作用与边界 |
| `###` | 3. 响应结构 | 解释 `id`、`status`、`output_text` 和 `usage` 的职责 |
| `##` | 二、环境配置 | 建立能够独立运行示例的本地条件 |
| `###` | 1. Python 环境 | 创建并激活 Python 3.12 虚拟环境 |
| `###` | 2. SDK 安装 | 安装和核对 OpenAI Python SDK 3.19.2 |
| `###` | 3. API 凭据 | 设置 Key 与模型变量，并说明凭据保护边界 |
| `##` | 三、请求实现 | 将请求拆为客户端、参数、调用和异常四个实现责任 |
| `###` | 1. 客户端初始化 | 读取凭据并创建 `OpenAI` 客户端 |
| `###` | 2. 请求参数 | 组织模型、任务指令和客户反馈输入 |
| `###` | 3. 请求发送 | 调用 `responses.create()` 并保留 Response 对象 |
| `###` | 4. 异常捕获 | 区分连接错误与 API 状态错误，保留诊断证据 |
| `##` | 四、响应验证 | 根据状态、文本和用量判断本次调用是否完成 |
| `###` | 1. 完成状态 | 只接受 `completed`，其他状态进入失败路径 |
| `###` | 2. 文本输出 | 使用 `output_text` 并拒绝空文本 |
| `###` | 3. Token 用量 | 读取输入、输出和总 Token，不把用量当作质量证明 |
| `###` | 4. 实际响应 | 展示同一次真实请求的脱敏结果和退出码 |
| `##` | 五、错误诊断 | 根据证据定位失败所在边界 |
| `###` | 1. 配置错误 | 处理缺少 Key、模型变量和虚拟环境问题 |
| `###` | 2. 连接错误 | 识别 DNS、代理、TLS 和网络可达性问题 |
| `###` | 3. API 状态错误 | 解释 `401`、`403`、`404` 和 `429` 的处理方向 |
| `###` | 4. 响应契约错误 | 处理未完成、空文本和缺少用量的响应 |
| `##` | 六、调用边界 | 区分接口执行完成与业务结果可用 |
| `###` | 1. 成功条件 | 汇总状态、文本、用量和退出码四项条件 |
| `###` | 2. 业务校验 | 说明事实、格式和业务规则仍由应用负责 |
| `###` | 3. 未覆盖能力 | 明确本文不负责的后续能力 |
| `##` | 七、参考资料 | 保留支撑当前行为的官方资料 |

## 四、内容组织

### 1. 请求模型

先使用一张简短调用链展示参与对象，再分别解释请求和响应字段。字段表只承担同维度查询，调用过程不塞入表格单元格。

### 2. 环境配置

将原有命令组拆为环境创建、SDK 安装和凭据设置三个操作单元。每个单元先说明目的和预期观察结果，再给出 PowerShell 与 Bash 命令。

### 3. 请求实现

保留一个权威完整程序并默认折叠。折叠外按程序职责展示不超过十行的关键片段，逐一对应客户端初始化、参数组织、请求发送和异常处理。局部片段必须与完整程序一致，并明确其上下文来自同一文件。

### 4. 响应验证

将字段说明改为判断过程。每个小节先给成功条件，再解释代码如何取值、失败时使用哪个退出码。真实响应紧跟执行命令，Token 数值注明只代表该次运行。

### 5. 错误诊断

错误总表保留为入口，每类错误增加独立解释。真实验证过的缺少 Key 分支明确标注为实测；没有主动触发的 API 错误只说明 SDK 证据和处理方向，不伪造成运行结果。

### 6. 调用边界

使用成功条件清单收束全文，再通过业务校验和未覆盖能力区分“请求完成”“内容有效”和“生产可用”三个层次。

## 五、阅读重点

| 信息类型 | 表达方式 | 使用位置 |
|----------|----------|----------|
| 版本前提 | `info` 容器 | Python、SDK 和模型验证基线 |
| 凭据风险 | `danger` 容器 | 设置 API Key 之前 |
| 便捷属性边界 | `tip` 容器 | `output_text` 解释之后 |
| 重试范围 | `warning` 容器 | API 错误处理之后 |
| 调用过程 | 文本流程图 | 请求模型的调用链小节 |
| 字段比较 | 表格 | 请求结构与响应结构 |
| 操作顺序 | 有序列表 | 响应判断和成功条件 |
| 完整程序与长输出 | `details` | 请求实现和实际响应 |

内容容器不连续堆叠，不把整节正文放入容器。核心条件和结果判断始终保留在折叠内容之外。

## 六、验证要求

| 验证层次 | 检查内容 | 通过标准 |
|----------|----------|----------|
| 标题层级 | `#`、`##`、`###` 编号与顺序 | 一级标题唯一；二、三级标题连续；不使用无内容标题 |
| 小节完整性 | 每个三级标题的正文与证据 | 不存在空小节、单句骨架小节或连续定义小节 |
| 代码一致性 | 局部片段、完整程序与执行脚本 | 三者关键语句一致，完整程序可独立执行 |
| 代码折叠 | 超过十行的代码和输出 | 默认使用 `details`，折叠外保留必要解释 |
| 导航呈现 | 侧栏与右侧大纲 | 文章入口可访问；右侧大纲显示精确三级标题 |
| 页面布局 | 1920×1080 与 390×844 | 无横向页面溢出，标题、表格和代码不遮挡正文 |
| 工程检查 | 文档测试与 AI 构建 | `pnpm docs:test` 和 `pnpm docs:build:unit ai` 通过 |
