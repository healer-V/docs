# 大型知识库模块化构建与内容治理设计

当前知识库仍有大量主题需要补充，但现有单体构建已经在 630 篇 Markdown 下触及 Node.js 内存边界。本设计不通过限制文档数量解决问题，而是在保留单仓库、统一 GitHub Pages 站点和现有 URL 的前提下，将站点内部改造为多个 VitePress 构建单元，并建立统一搜索、路由兼容和分阶段内容治理流程。

## 一、现状与核心结论

### 1. 现状审计

2026-08-28 的工作区审计以磁盘中的实际文件为准，包含用户尚未提交的 Java、React 和微服务重构内容。

| 指标 | 当前结果 | 说明 |
|------|----------|------|
| `content/` 下 Markdown | 630 篇 | 不含仓库外规范文件 |
| Markdown 总体积 | 约 6.17 MiB | 平均每篇约 10 KiB |
| Markdown 总行数 | 220,879 行 | 包含 11,711 条代码围栏边界 |
| sidebar 唯一目标 | 1,334 个 | 包含尚未创建的规划页面 |
| sidebar 缺失目标 | 766 个 | 不能直接视为正式写作任务 |
| 未进入 sidebar 的实际页面 | 62 篇 | 需要逐项判断是否应公开导航 |
| 当前静态产物 | 约 268 MiB | 631 个 HTML、1,263 个 JS |

当前构建基准如下。测试使用仓库现有 VitePress 1.3.4、关闭内置本地搜索，并保持 `maxParallelFileOps: 3`。

| Node.js 堆限制 | 构建结果 | 观察结果 |
|----------------|----------|----------|
| 默认约 4.1 GiB | 失败 | 约 99.73 秒后 OOM |
| 5 GiB | 失败 | 约 113.21 秒后 OOM |
| 6 GiB | 成功 | 约 109.48 秒，进程工作集峰值约 6,108.8 MiB |
| 8 GiB | 成功 | 约 103.55 秒 |

### 2. 问题根因

VitePress 没有设置固定的文档数量上限，文件系统和两位编号也不是当前瓶颈。真正限制持续扩展的是单次构建同时加载全部 Markdown、全站 sidebar、主题组件和页面模块所形成的峰值内存，以及每篇页面对应 HTML、普通 JS 和 lean JS 等产物带来的构建成本。

现有 GitHub Actions 已通过 `NODE_OPTIONS=--max-old-space-size=8192` 暂时维持构建，但按照当前页面复杂度线性增长到 1,000～1,500 篇，会让单体构建再次接近或超过内存边界。继续单纯增加堆内存只能延后问题，不能降低故障范围和维护复杂度。

### 3. 设计结论

采用“对外统一、内部模块化”的架构：Markdown 继续保存在一个仓库和现有目录中，用户继续访问同一个 GitHub Pages 站点；GitHub Actions 按知识模块并行构建，合并所有静态产物后统一校验、生成 Pagefind 全文索引，并通过 GitHub 官方 Pages Artifact 原子发布。

## 二、已确认约束

本设计以会话中已经确认的决策为硬约束，实施阶段不得自行改变。

| 决策项 | 已确认方案 |
|--------|------------|
| 最终规模 | 建设覆盖前端、后端、运维、AI、Web3 等方向的完整知识库，目标 1,000～1,500 篇 |
| 用户体验 | 对外保持一个统一站点 |
| 仓库形态 | 继续使用当前单仓库，不按知识方向拆仓 |
| 部署平台 | 继续使用 GitHub Actions 和 GitHub Pages |
| 构建方式 | 允许多个模块并行构建，最终合并产物 |
| 搜索 | 必须提供跨模块统一全文搜索 |
| URL | 已发布页面保持原 URL，变更时提供兼容页或旧锚点 |
| 内容规划 | 先审核知识覆盖、重复项和章节边界，再形成正式建设清单 |
| 建设节奏 | 模块蓝图确认、样板确认、逐章生成、模块验收后发布 |

## 三、目标与非目标

### 1. 设计目标

| 目标 | 完成标准 |
|------|----------|
| 扩展能力 | 1,000～1,500 篇规模下不依赖单个超大 Node.js 构建进程 |
| 统一体验 | 首页、顶部导航、主题、URL、搜索和发布地址保持统一 |
| 发布可靠性 | 任一构建单元失败时不更新线上站点 |
| URL 稳定性 | 已发布页面路径和需要保留的历史锚点通过基线自动检查 |
| 导航真实性 | 正式 sidebar 只指向已经存在且通过验收的页面 |
| 搜索完整性 | 所有正式文章进入同一个中文全文搜索索引 |
| 内容完整性 | 每个模块通过知识项、职责卡和覆盖矩阵证明范围完整 |
| 可诊断性 | 构建时间、内存、页面数、产物体积、链接和索引覆盖均可观察 |

### 2. 明确非目标

- 不把知识库拆成多个用户可感知的独立网站；
- 不批量移动现有 Markdown 文件；
- 不为了模块化构建而改变现有公开 URL；
- 不把 766 个 sidebar 占位直接批量生成成空壳文章；
- 不在首次工程改造中顺带全文重写所有历史文档；
- 不以文章数量、字数或标题数量代替知识完整性判断；
- 不在未经用户明确授权时执行 `git push`、线上发布或部署设置变更。

## 四、总体架构

### 1. 构建单元

站点划分为七个构建单元。当前文档数是审计结果，规划规模仅用于容量评估，最终数量必须经过模块蓝图审核。

| 构建单元 | 当前文档 | 现有 sidebar 并集估算 | 负责范围 |
|----------|----------|-----------------------|----------|
| `portal` | 约 3 篇 | 约 3 篇 | 首页、链接页、关于页、404 和公共静态资源 |
| `frontend` | 197 篇 | 约 305 篇 | HTML、CSS、JavaScript、TypeScript、Vue、React |
| `backend` | 233 篇 | 约 369 篇 | Node.js、Express、NestJS、Java、Python、微服务、数据库 |
| `operation` | 47 篇 | 约 227 篇 | Linux、Shell、Jenkins、CI/CD、Kubernetes、Docker、Nginx |
| `ai` | 10 篇 | 约 163 篇 | 模型接入、上下文、RAG、Agent、评测、安全和成本 |
| `web3` | 30 篇 | 约 219 篇 | 区块链、Solidity、Web3.js、Ethers.js、DApp 和进阶主题 |
| `ecosystem` | 约 110 篇 | 约 110 篇 | 跨端、工程化、微前端、实践、面试、文章、项目等 |
| **合计** | **630 篇** | **约 1,396 篇** | 目标规模仍以蓝图审核结果为准 |

单元不是永久不可调整的边界。当某个单元持续超过 400 篇、构建时间超过 5 分钟或堆使用率持续高于 85% 时，应沿稳定 URL 前缀继续拆分，例如将 `backend` 拆为语言、框架与数据构建单元。拆分只改变构建配置，不改变源文件和公开路径。

### 2. 源码与配置关系

所有构建单元继续以 `content/` 为 VitePress 源目录，通过环境变量选择包含范围，并使用独立缓存和输出目录。GitHub Actions Matrix 中每个单元运行在独立 Runner，VitePress 的 `.temp` 因工作区隔离而不会冲突；本地多单元构建默认串行执行。

```text
docs/
├─ .vitepress/
│  ├─ config.mjs
│  ├─ build-units.mjs
│  ├─ theme/
│  └─ themeConfig/
├─ frontend/
├─ backend/
├─ operation/
├─ ai/
├─ web3/
└─ ...

.build/
├─ units/
│  ├─ portal/
│  ├─ frontend/
│  └─ ...
└─ assembled/
```

`build-units.mjs` 是构建边界的唯一事实来源，至少记录单元名称、负责的 URL 前缀、包含目录、排除目录、输出目录和根级产物所有权。VitePress 1.3.4 已支持 `srcExclude`、`outDir` 和 `cacheDir`，不需要复制 Markdown 或创建临时源码镜像。

### 3. 共享配置与局部配置

| 配置 | 所有单元共享 | 按单元选择 |
|------|--------------|------------|
| `base` | 固定为 `/docs/` | 否 |
| 主题和样式 | 是 | 否 |
| 顶部导航 | 是 | 否 |
| Markdown 配置 | 是 | 否 |
| sidebar | 否 | 只加载当前单元负责的条目 |
| `srcExclude` | 否 | 排除其他单元页面 |
| `cacheDir` | 否 | 每个单元独立目录 |
| `outDir` | 否 | 每个单元独立目录 |

顶部导航可以链接所有模块，但构建时不得把其他模块完整 sidebar 注入当前客户端。这样可以降低单个 bundle 的配置规模，同时保持全站入口一致。

## 五、模块构建与产物合并

### 1. 单元构建契约

每个构建任务必须输出三类产物：静态站点文件、路由清单和构建指标。路由清单记录规范 URL、源 Markdown、生成 HTML、页面标题、所属单元和页面哈希；构建指标记录页面数、耗时、峰值内存和产物体积。

```text
unit-artifact/
├─ site/
├─ routes.json
├─ file-digests.json
└─ build-metrics.json
```

构建单元只能声明自己负责的页面路径。无法归属的页面在配置校验阶段失败，不允许被多个单元同时接管，也不允许悄悄遗漏。

### 2. 根级产物所有权

多个 VitePress 构建会同时生成 `index.html`、`404.html`、`hashmap.json`、站点地图、公共资源和客户端运行资源，不能使用简单目录覆盖完成合并。

| 产物类型 | 合并规则 |
|----------|----------|
| 首页、404、公共图片 | 只允许 `portal` 生成并拥有 |
| 模块 HTML | 由负责该 URL 前缀的单元生成 |
| 带内容哈希的 JS/CSS | 按文件摘要合并；同路径同内容可去重，同路径不同内容立即失败 |
| `hashmap.json` | 汇总所有单元路由映射后重新生成 |
| sitemap | 基于完整规范路由清单统一生成 |
| 搜索索引 | 合并完成且链接校验通过后统一生成 |
| 路由基线报告 | 汇总所有单元清单后统一生成 |

合并脚本不得以“后复制覆盖先复制”的方式处理冲突。每个文件都计算 SHA-256 摘要，只有摘要一致时才允许同路径去重。

### 3. 客户端路由边界

同一构建单元内部继续使用 VitePress 客户端路由；跨单元链接必须触发完整页面加载，使目标页面加载自己的客户端运行资源和页面映射。顶部导航、跨模块 sidebar 链接和搜索结果统一标记为完整页面导航，主题路由守卫作为兜底。

合并后的 `hashmap.json` 包含所有正式页面，用于部署切换后客户端重试和路由映射刷新。该聚合是必须项，不能只保留 `portal` 或最后一个复制单元生成的文件。

### 4. 合并不变量

- 每个规范 URL 只能由一个构建单元负责；
- 每个正式 Markdown 必须出现在一个路由清单中；
- 根级非哈希文件必须具有明确所有者或统一生成器；
- 产物合并前后页面数量必须与规范路由数量一致；
- 合并结果必须能够从任一模块跳转到其他模块；
- 所有静态资源引用必须在最终产物中存在。

## 六、GitHub Actions 与发布流程

### 1. 工作流阶段

```text
validate-config
      │
      ▼
build-units(matrix: 7)
      │
      ▼
assemble
      │
      ▼
validate-site
      │
      ▼
build-search
      │
      ▼
upload-pages-artifact
      │
      ▼
deploy-pages
```

| 阶段 | 职责 | 失败影响 |
|------|------|----------|
| `validate-config` | 校验构建边界、sidebar、重复路由和配置语法 | 不启动构建矩阵 |
| `build-units` | 七个独立 Runner 并行构建 | 保留诊断产物，但禁止合并发布 |
| `assemble` | 下载所有 Artifact，执行确定性合并 | 冲突时立即失败 |
| `validate-site` | 检查路由、资源、链接、历史 URL 和页面数量 | 任一失败都禁止发布 |
| `build-search` | 对完整 HTML 生成一次 Pagefind 索引 | 索引失败时禁止发布 |
| `upload-pages-artifact` | 上传唯一完整站点 Artifact | 只接受已验收目录 |
| `deploy-pages` | 原子部署到 GitHub Pages | 仅 `main` 分支执行 |

### 2. 触发和并发策略

- Pull Request 执行配置校验、全部单元构建、合并、链接检查和搜索检查，但不发布；
- `main` 分支执行完整流水线并发布；
- `workflow_dispatch` 支持人工触发完整验证或部署；
- 同一分支出现新提交时取消尚未完成的旧流水线；
- 初期每次构建全部单元，避免共享主题、导航或依赖变化造成新旧产物不一致；
- 只有建立可靠的依赖指纹和旧产物可追溯机制后，才评估增量跳过未变化单元。

### 3. 发布权限

发布迁移到 GitHub 官方 Pages 流程，使用 `actions/configure-pages`、`actions/upload-pages-artifact` 和 `actions/deploy-pages`。部署任务只授予 `contents: read`、`pages: write` 和 `id-token: write` 所需权限，不再依赖个人 `ACCESS_TOKEN` 向 `gh-pages` 分支推送。

仓库 Pages Source 需要在实施验收时一次性切换为 `GitHub Actions`。这是外部设置变更，必须在新流程通过本地与 Pull Request 验证，并获得用户明确发布授权后执行。

GitHub 官方说明：

- [使用自定义 GitHub Actions 工作流部署 GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)
- [在 GitHub Actions 中传递 Workflow Artifact](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts)

## 七、导航、搜索与 URL 兼容

### 1. 正式导航与建设台账分离

当前 sidebar 中 766 个不存在的目标迁移为模块建设台账，正式 sidebar 只包含真实文件。关闭 `ignoreDeadLinks` 后，新增无效链接直接阻断构建。

| 数据 | 用途 | 是否发布 |
|------|------|----------|
| 模块蓝图 | 确定知识边界、版本和依赖 | 默认不发布 |
| 文章职责卡 | 约束单篇文章范围和证据 | 默认不发布 |
| 缺口台账 | 记录保留、合并、已覆盖、移除和待确认 | 默认不发布 |
| 正式 sidebar | 展示已经通过验收的文章 | 发布 |
| 路由基线 | 校验历史 URL | 构建内部使用 |

过程文档按 2026-09-28 确认的目录迁移规则保留在仓库根目录 `superpowers/`，不参与网站构建和站点搜索；原过程文档路由已从基线撤出。文档文件继续保留，其他技术文章的历史 URL 和锚点兼容要求继续生效。

### 2. Pagefind 全站搜索

全站搜索采用 Pagefind Extended，并通过锁文件固定已验证版本。VitePress 内置本地搜索保持关闭，避免每个构建单元生成相互割裂的 MiniSearch 索引。

| 项目 | 设计 |
|------|------|
| 输入 | 合并且通过链接检查的完整 HTML |
| 输出 | `/docs/pagefind/` |
| 分词 | 使用支持中文和日文的 Extended 构建 |
| 索引正文 | VitePress 正文容器标记 `data-pagefind-body` |
| 排除内容 | 导航、sidebar、页脚和交互控件标记 `data-pagefind-ignore` |
| 元数据 | 标题、摘要、标签、所属模块和规范 URL |
| 过滤 | 前端、后端、运维、AI、Web3、生态等模块 |
| 加载 | 搜索框聚焦或首次输入时延迟加载索引 |
| 跳转 | 同单元可使用客户端路由，跨单元执行完整页面导航 |

Pagefind 对正文范围和元数据的控制依据：

- [Pagefind 索引范围配置](https://pagefind.app/docs/indexing/)
- [Pagefind 搜索元数据](https://pagefind.app/docs/metadata/)
- [Pagefind CLI 配置](https://pagefind.app/docs/config-options/)

### 3. 历史 URL 基线

实施第一阶段从当前生产站点和构建产物生成 `published-routes.json`。每条记录至少包含规范路径、标题、源文件、所属单元、历史锚点和状态。

发布门禁执行以下规则：

1. 所有历史正式路径在新产物中仍能访问；
2. Markdown 保持原路径是默认策略；
3. 必须迁移时生成静态兼容页，不依赖 GitHub Pages 服务端重定向；
4. 标题变化导致锚点变化时保留旧锚点别名；
5. 兼容页不得形成循环或多跳链路；
6. 搜索只返回规范页面，不返回兼容页；
7. 新页面不得占用已有历史路径。

## 八、缺失文档与内容治理

### 1. 缺口审核

sidebar 占位、官方知识体系和现有正文需要交叉审核，不能以任一单一来源作为完整性基准。

| 审核结果 | 判断条件 | 后续动作 |
|----------|----------|----------|
| 保留 | 具有独立学习问题、可靠来源和唯一归属 | 进入模块蓝图和职责卡 |
| 合并 | 多个占位共同构成不可拆分的知识闭环 | 合并为一篇文章 |
| 已覆盖 | 现有文章已经达到要求深度和证据标准 | 删除占位，保留现有路径 |
| 重命名 | 主题有效但标题或路径不准确 | 确定规范名称并设计 URL 兼容 |
| 移除 | 重复、越界、过时或没有独立学习价值 | 不创建正文和线上链接 |
| 待确认 | 版本、边界或来源无法确认 | 阻断该知识项，不阻断无关模块 |

最终新增文章数量由审核结果决定，不预设为 766 篇。知识完整性由覆盖矩阵证明，不以填满当前 sidebar 为目标。

### 2. 建设顺序

| 顺序 | 模块范围 | 排序原因 |
|-----:|----------|----------|
| 1 | 当前重构中的 Java、React 16、React 18、微服务 | 先识别并保留用户已有大规模改动 |
| 2 | HTML、CSS、JavaScript、TypeScript、Java、Python、Node.js、Linux、Shell | 建立下游框架依赖的基础知识 |
| 3 | Vue、React、Spring Boot、NestJS、MySQL、PostgreSQL、Redis | 在稳定前置知识上完成框架与数据模块 |
| 4 | 微服务、Docker、Kubernetes、CI/CD、Nginx | 完成架构、平台、诊断和恢复能力 |
| 5 | AI、Web3、跨端、微前端 | 复用已稳定的语言、协议与工程前置知识 |
| 6 | 实践、面试、速查和综合文章 | 引用主教程，不重复完整讲解核心知识 |

同一阶段内按照依赖中心性、现有缺口、使用价值和示例验证条件排序，不按照文件创建时间或缺失数量排序。

### 3. 单模块流程

```text
现状审计
→ 主版本和官方来源
→ 知识项与依赖关系
→ 章节、职责卡和覆盖矩阵
→ 用户确认模块蓝图
→ 编写并验证一至两篇样板文章
→ 用户确认样板
→ 按章节生成正文
→ 章节验收
→ 构建单元验证
→ 合并站点验证
→ 获得授权后发布
```

默认以一个章节为最大批次。高风险测试、生产排障或需要外部服务的文章进一步缩小批次。蓝图和样板未确认前，不批量创建目标正文，也不向正式 sidebar 添加占位链接。

### 4. 首个试点

工程基础设施完成后，以 HTML 模块作为首个内容治理试点。HTML 现有 12 篇，范围相对明确，同时覆盖基础概念、元素 API、表单、可访问性、安全和性能等多种文章类型，能够验证蓝图、样板、示例和质量门禁是否具有可复制性。

HTML 试点通过不代表其他模块可以跳过蓝图。不同知识方向仍需采用仓库 `standards/documentation/knowledge-system.md` 中对应的覆盖模型。

## 九、质量门禁

### 1. 分层门禁

| 门禁 | 自动检查 | 语义检查 |
|------|----------|----------|
| 构建配置 | 单元覆盖、重复路由、配置语法 | 构建边界是否稳定且职责单一 |
| 模块蓝图 | ID、依赖存在性、循环、唯一归属 | 知识范围、版本、深度和章节边界 |
| 单篇文章 | Frontmatter、标题、代码块、链接 | 事实、闭环、证据、边界和重复归属 |
| 章节 | 文件编号、sidebar、内部链接 | 遗漏、重复、术语和场景一致性 |
| 构建单元 | 页面数量、产物和资源引用 | 模块最终能力与覆盖矩阵闭合 |
| 合并站点 | 冲突、死链接、历史 URL、搜索覆盖 | 跨模块体验和剩余风险 |

任何硬性门禁失败都不能通过其他指标得分抵消。机器检查只能发现候选问题，知识遗漏、文章粒度和语义重复仍需结合职责卡判断。

### 2. 发布前工程检查

- Frontmatter 合法，`title` 与唯一一级标题一致；
- 标题层级和编号符合仓库规范；
- 代码块具有语言标识和必要上下文；
- 新增函数、方法和回调满足代码注释规范；
- sidebar、内部链接和图片路径全部有效；
- 每个正式页面只属于一个构建单元；
- 七个构建单元全部成功；
- 合并后没有不同摘要的同路径文件；
- 历史 URL 和锚点基线完整；
- Pagefind 索引页面数与应索引页面清单一致；
- 最终 GitHub Pages Artifact 可以完整预览。

## 十、监控、失败处理与恢复

### 1. 构建指标

| 指标 | 正常 | 预警 | 阻断或治理动作 |
|------|------|------|----------------|
| Node.js 堆使用率 | 不高于 70% | 70%～85% | OOM 立即失败；持续高于 85% 评估拆分 |
| 单元构建时间 | 不高于 3 分钟 | 3～5 分钟 | 超过 5 分钟评估拆分或性能治理 |
| 单元文档数 | 不高于 350 篇 | 351～400 篇 | 超过 400 篇必须复核构建边界 |
| 历史 URL 保留率 | 100% | 无预警区间 | 少于 100% 阻断发布 |
| 内部死链接 | 0 | 无预警区间 | 大于 0 阻断发布 |
| 产物路径冲突 | 0 | 无预警区间 | 大于 0 阻断发布 |
| 搜索索引覆盖率 | 100% | 无预警区间 | 缺少正式页面时阻断发布 |
| Pages Artifact | 不高于 750 MiB | 750 MiB～1 GiB | 超过 1 GiB 暂停扩展并复核 |

文档数只用于容量预警，不能作为文章内容拆分标准。页面复杂度、代码高亮和主题依赖会使文档数量相同的构建单元产生不同资源消耗。

### 2. 失败处理

| 故障 | 自动行为 | 恢复方式 |
|------|----------|----------|
| 单元构建失败 | 其他矩阵任务可完成诊断，发布任务不执行 | 修复失败单元后重跑完整流水线 |
| 产物冲突 | 合并任务立即失败并报告双方所有者 | 修正产物所有权或共享生成逻辑 |
| 路由或资源缺失 | 链接检查失败 | 恢复文件、链接或路由清单 |
| 搜索生成失败 | 不上传 Pages Artifact | 修复索引输入或配置后重新生成 |
| 历史 URL 丢失 | URL 门禁失败 | 恢复原路径或增加静态兼容页 |
| 新版本线上异常 | 不修改源码历史 | 从最后稳定提交重新运行部署 |
| 蓝图发现漏项 | 暂停当前内容批次 | 修订蓝图、职责卡和覆盖矩阵后重新确认 |

GitHub Pages 只接收完整且已验收的单一 Artifact，因此构建失败不会产生半更新站点。上一版站点在新部署成功前继续提供服务。

## 十一、实施阶段

| 阶段 | 交付内容 | 放行条件 |
|-----:|----------|----------|
| 1 | 当前生产路由、锚点、页面和构建指标基线 | 630 篇现有页面均有明确状态 |
| 2 | 构建单元配置、独立缓存、独立输出和本地合并脚本 | 合并产物与当前单体站点路由一致 |
| 3 | GitHub Actions Matrix、Artifact 传递和合并任务 | PR 中可以完成全链路构建但不发布 |
| 4 | sidebar 真实性、死链接和历史 URL 门禁 | 可以关闭 `ignoreDeadLinks` |
| 5 | Pagefind 搜索、模块过滤和跨单元跳转 | 所有正式页面统一可搜索 |
| 6 | GitHub 官方 Pages Artifact 发布 | 获得授权后完成一次可回退发布 |
| 7 | HTML 模块蓝图与样板试点 | 完整走通内容治理和用户确认门禁 |
| 8 | 按依赖顺序逐模块补齐 | 每个模块独立通过覆盖与构建验收 |
| 9 | 1,000、1,200、1,500 篇容量复核 | 按指标决定是否继续拆分构建单元 |

阶段 1～6 解决站点承载和发布可靠性，阶段 7～9 解决内容完整性。两类工作有依赖但不能混为一次大规模提交；工程基础通过后，再逐模块补全文档。

## 十二、验证方案

### 1. 本地验证

| 验证类型 | 验证内容 |
|----------|----------|
| 配置测试 | 单元名称、前缀归属、排除规则、重复路由和根级文件所有权 |
| 单元构建 | 七个单元分别构建成功，并记录耗时、内存和产物 |
| 合并测试 | 文件摘要、路由聚合、`hashmap.json`、sitemap 和资源引用 |
| 链接测试 | 同单元跳转、跨单元跳转、直接打开深层 URL 和刷新页面 |
| 搜索测试 | 中文关键词、技术术语、模块过滤、结果 URL 和无结果状态 |
| 兼容测试 | 历史路径、旧锚点、兼容页和循环重定向检测 |
| 响应式检查 | 桌面和移动端的导航、sidebar、搜索框和搜索结果 |

### 2. GitHub Actions 验证

Pull Request 必须证明矩阵构建、Artifact 下载、确定性合并、全站校验和搜索生成均可重复。`main` 发布前还需验证 Pages Artifact 结构、权限和环境保护规则，发布后抽检首页、各构建单元至少一个深层页面、全站搜索和历史 URL。

### 3. 内容验证

每个模块分别输出知识覆盖、版本依据、示例状态、章节重复、工程验证和剩余风险。构建成功只证明工程产物有效，不能代替模块蓝图和单篇内容门禁。

## 十三、风险与控制

| 风险 | 影响 | 控制措施 |
|------|------|----------|
| 独立构建生成共享根文件 | 合并覆盖导致路由或资源失效 | 根级所有权、摘要冲突检测和统一聚合 |
| 跨单元客户端路由加载不到页面 | 点击链接显示 404 或错误页 | 跨单元完整页面导航和路由守卫 |
| 主题变更只重建部分单元 | 页面资源版本不一致 | 初期每次全量构建全部单元 |
| 搜索索引包含公共导航 | 结果重复且排序失真 | `data-pagefind-body` 与 `data-pagefind-ignore` |
| 把 sidebar 规划误当成知识体系 | 批量生成重复或空洞文章 | 官方来源、知识项、职责卡和覆盖矩阵交叉审核 |
| 历史页面迁移破坏外部链接 | 已收藏或搜索引擎链接失效 | URL 基线、静态兼容页和旧锚点别名 |
| 当前工作区大规模未提交改动重叠 | 覆盖用户重构内容 | 每阶段读取当前状态并限制修改范围 |
| GitHub Actions 成本增加 | 七个 Runner 增加总计算时间 | 先保证可靠性，稳定后再引入依赖指纹和增量构建 |

## 十四、最终验收标准

1. 用户仍通过同一个 GitHub Pages 地址访问完整知识库；
2. 现有已发布 URL 和要求保留的历史锚点 100% 可访问；
3. 七个构建单元可独立构建，合并后页面数量和规范路由一致；
4. 产物合并不存在不同内容的同路径覆盖；
5. 任一构建、链接、URL 或搜索门禁失败时不部署；
6. sidebar 只包含真实且通过验收的文章；
7. 全站搜索覆盖所有正式文章并支持模块过滤；
8. GitHub Actions 使用官方 Pages Artifact 和最小发布权限；
9. 每个技术模块具有版本基线、知识项、职责卡和覆盖矩阵；
10. 正文严格按照蓝图确认、样板确认、逐章生成和模块验收推进；
11. 达到 1,000、1,200 和 1,500 篇时分别完成容量复核；
12. 实施不覆盖用户已有改动，未经明确授权不执行远端推送和生产发布。

本设计完成后，知识库增加文档不再直接放大单体构建风险。工程系统负责让大规模内容能够稳定构建、搜索和发布，内容治理流程负责确保新增页面确实补全知识，而不是只增加文件数量。
