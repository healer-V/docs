# 运维单篇文档结构重设计

当前运维正文已经覆盖必要知识和操作，但页面主要依赖连续二级标题、表格、代码块与提示容器组织内容。不同信息使用了接近的视觉权重，读者难以快速识别核心问题、当前步骤、验证依据和失败分支。

本设计建立“公共阅读骨架 + 文档类型结构”的单篇规范。公共骨架保证文章具有一致的注意力层级，类型结构让概念、教程、机制和排障文章按照各自问题展开，避免统一模板把正文写成课程提纲。

## 一、目标与范围

### 1. 设计目标

新版规范需要同时实现以下结果：

- 初学者能够沿主线从定义进入机制或操作，不需要先理解完整知识图谱；
- 有经验的读者能够通过标题、关键判断和验证结果快速定位信息；
- 概念、操作、观察、结论和失败处理具有可辨认的层次；
- 命令、输出和解释保持相邻，形成可以独立执行的操作单元；
- 不同类型文章保留适合自身问题的结构，不机械套用固定章节名称；
- 文章在增加层次后仍遵守现有标题编号、示例验证和 VitePress 语法规则。

### 2. 首批迁移范围

首批只重构已经位于新运维目录并开放导航的六篇正文：

| 顺序 | 文档 | 类型 | 重构重点 |
|------|------|------|----------|
| 1 | `01-linux/01-system-foundation/01-linux-distribution.md` | 概念文章 | 用真实服务器需求串联内核、用户空间、发行版与 Ubuntu Server |
| 2 | `01-linux/01-system-foundation/02-install-lab.md` | 操作教程 | 按准备、安装、验证、快照和恢复建立阶段闭环 |
| 3 | `01-linux/01-system-foundation/03-terminal-help.md` | 操作教程 | 以首次登录任务串联提示符、命令结构、帮助和退出状态 |
| 4 | `01-linux/02-filesystem-operations/01-paths-filesystem.md` | 概念与操作 | 以定位同一文件为主线解释目录树和路径解析 |
| 5 | `01-linux/04-processes-systemd/02-systemd-services.md` | 机制与操作 | 以服务状态变化组织单元、启动、启用、失败和恢复 |

### 3. 范围排除

本次不调整运维模块目录、章节数量和文章知识归属，不重新设计 VitePress 主题样式，不引入新的 Markdown 组件，也不扩大到尚未生成的 342 篇规划正文。

尚未生成的文章在后续创建时直接使用新版规范，不先建立空文件或导航链接。

## 二、公共阅读骨架

公共骨架规定信息出现的顺序和职责，不规定每篇文章必须使用相同标题。

### 1. 开篇建立问题与结论

一级标题后使用二至四个短段落完成三件事：

1. 直接说明技术对象是什么或当前问题为什么发生；
2. 给出文章最终要建立的核心判断；
3. 在需要操作时说明环境、版本和安全边界。

开篇不放文章目录、学习目标、知识清单和“本篇将介绍”等元叙述。前置条件只在影响理解或执行时出现，并链接到承担完整讲解的文章。

### 2. 核心模型建立全局视角

复杂主题先提供一个足以承载后续内容的模型。模型根据问题选择关系图、状态图、时间线、决策表或具体场景，不强制使用同一种图形。

模型只保留主线对象和关系。需要多段解释的机制不能全部塞入表格单元格；表格承担同维度对照，正文负责因果和推导。

### 3. 分层知识回答连续子问题

标题层级按问题关系组织：

| 层级 | 职责 | 判断标准 |
|------|------|----------|
| `##` | 技术对象、能力域、任务阶段或机制阶段 | 能够构成文章知识骨架，并准确限定所辖内容 |
| `###` | 上级对象的组成、机制、分类、约束或独立操作 | 具有专属解释或证据，不能只写一句话 |
| `####` | 子问题中的细分机制或并列失败分支 | 只有内容无法在正文、列表或表格中清楚表达时使用 |

禁止为了“看起来有层级”机械增加标题。连续并列事实使用列表或小型表格；相互依赖的步骤使用有序列表。

### 4. 技术目录使用概念型标题

标题是知识结构的索引，不是正文摘要、讲解话术或结论句。二级标题标识技术对象、能力域或过程阶段，三级标题标识其组成、机制、分类或约束；正文负责解释对象之间的关系、结论和推导过程。

标题默认使用“技术对象 + 必要限定”的名词短语，并遵守以下边界：

- 删除“从……开始”“如何”“为什么”“先”“通常”“必须”“让”“用……判断”等讲解式措辞；
- 不把“相同内核不代表相同系统”这类完整结论直接作为目录项，改为“系统差异来源”，结论放在节首正文；
- 不把案例、反例、提示、验证动作分别提升为标题，除非它本身就是文章需要检索的故障现象或操作阶段；
- 子标题可以省略父标题已经明确的对象，但不能缩成“概述”“其他”“相关内容”等无法独立定位的信息；
- 只阅读标题时，应看到概念树或任务阶段，而不是作者对读者说话的连续句子。

### 5. 操作单元保持证据相邻

每个操作单元按以下顺序组织，但不把标签机械写成固定小标题：

```text
操作目标
→ 执行条件
→ 命令或动作
→ 预期结果
→ 结果解释
→ 失败时的下一步
```

命令与预期输出之间只保留必要解释。结果解释必须说明观察项证明了什么，不能只写“运行成功”。失败处理紧邻可能失败的步骤，不统一堆到文章末尾。

### 6. 结尾收束判断边界

文章结尾说明当前场景已经证明什么、没有证明什么，以及读者遇到条件变化时应重新检查哪个证据。结尾不重复全文知识清单，也不使用“下一篇”导航话术。

教程和排障文章可以使用验收表收束；概念和机制文章优先使用具体判断案例或反例收束。

## 三、文档类型结构

### 1. 概念文章

概念文章解决“对象是什么、为什么这样划分、怎样用于判断”，推荐结构为：

```text
真实问题或错误判断
→ 核心定义
→ 对象关系
→ 关键差异
→ 场景判断
→ 边界与反例
```

定义不能连续堆叠。每组定义后必须通过关系、场景或反例展示它如何影响实际判断。

### 2. 操作教程

操作教程解决“怎样从当前状态得到可验证结果”，推荐结构为：

```text
最终结果
→ 前置检查
→ 阶段一操作与验证
→ 阶段二操作与验证
→ 失败分支与恢复
→ 最终验收
```

较长流程按照可独立验证的阶段拆分。每个阶段都要产生观察证据，不能等到文章末尾才统一验证。

### 3. 原理与机制文章

机制文章解决“参与对象如何协作、状态如何变化、失败如何传播”，推荐结构为：

```text
现象或冲突
→ 参与对象
→ 正常执行过程
→ 状态变化
→ 失败传播
→ 观察与验证
```

核心机制优先使用状态转换、执行顺序或对象关系表达。命令只是证明机制的证据，不能代替机制解释。

### 4. 排障文章

排障文章解决“从现象怎样收集证据并定位根因”，推荐结构为：

```text
故障现象与影响
→ 先保护现场
→ 分层采集证据
→ 根据证据收敛分支
→ 修复或回退
→ 恢复复测
→ 预防与监控
```

排障步骤必须解释选择顺序，避免把命令列表伪装成诊断方法。修复后需要重放原始触发条件，证明故障已经消失。

## 四、注意力层级

### 1. 页面阅读节奏

一段正文只推进一个中心意思。超过一个屏幕的纯文字区域，应根据语义拆成子问题、步骤、对照或关键提示，而不是仅增加空行。

不同表达形式承担不同职责：

| 表达形式 | 负责内容 | 不负责内容 |
|----------|----------|------------|
| 正文 | 定义、因果、机制和结论推导 | 大量同维度数据比较 |
| 有序列表 | 有前后依赖的动作和判断 | 无顺序的概念罗列 |
| 无序列表 | 简短并列事实 | 完整机制讲解 |
| 表格 | 同维度对照、参数、状态和决策 | 长段落、连续步骤和因果叙述 |
| 代码块 | 命令、配置、代码和真实输出 | 文章目录和阅读顺序 |
| 提示容器 | 一个关键条件、判断、建议或风险 | 整个章节的主体内容 |
| `details` | 完整长代码、补充证据和次要细节 | 核心结论、必要前提和风险 |

### 2. 关键结论

关键结论先用普通正文完整说明，再根据重要性使用加粗或提示容器。不能只把一句口号放进容器，也不能连续堆叠多个容器制造虚假重点。

同一小节中应存在明确的主信息。读者只阅读标题、每节首段和提示容器时，能够还原文章的主要判断路径。

### 3. 表格约束

表格只在列之间具有稳定比较关系时使用。出现以下情况时改用正文或步骤：

- 单元格需要两段以上解释；
- 行之间存在明显先后依赖；
- 表格只是把连续句子切成多列；
- 同一页面连续出现多个大型表格且没有机制解释；
- 移动端必须横向滚动才能理解主线。

大型参考表只能作为主线讲解后的查询工具，不承担第一次解释概念的职责。

### 4. 示例与输出

命令块前说明执行位置和目的，输出块后说明观察重点。动态值使用真实输出格式并明确哪些字段会变化，不编造 PID、时间、地址和软件版本。

错误示例必须包含触发动作、错误现象、退出状态或其他证据、产生原因和正确处理。没有恢复步骤的故障注入不能进入正文。

## 五、六篇正文的重构方向

### 1. Linux 与发行版

目录按“Linux 系统架构 → Linux 发行版 → Ubuntu Server → 系统基线 → 发行版选型”组织。三级标题分别承担内核、用户空间、发行版组成、软件包与仓库、发布维护、产品定位、环境标识和选型约束等具体知识；故障案例与概念反例保留在所属正文中。

### 2. 安装隔离实验环境

目录按“环境隔离 → 安装介质 → 虚拟机配置 → Ubuntu Server 安装 → 基线验证 → 快照恢复”组织。三级标题标识每个阶段的配置对象和验证对象；启动失败、镜像不一致、磁盘异常和恢复失效等分支紧邻对应步骤，不单独建立排障目录。

### 3. 终端与命令帮助

目录按“终端与 Shell → 命令结构 → 帮助系统 → 退出状态 → 输出与错误 → 会话控制”组织。三级标题只标识终端、Bash、提示符、命令组成、帮助来源、状态分类、输出通道和退出对象；成功与失败命令作为正文对照，不提升为目录项。

### 4. 文件系统与路径

以“从三个不同当前目录定位同一个 `/etc/hostname`”为贯穿任务。目录按“Linux 目录树 → 工作目录与家目录 → 路径类型 → 文件对象类型 → 路径解析错误”组织；三级标题只标识对应对象、分类与错误类型。常见目录按照配置、用户数据、运行状态和虚拟接口分组讲解，验证过程、故障案例和最终结论保留在所属知识小节，不单独进入目录。

### 5. systemd 服务管理

以测试服务从不存在、已安装、运行、启用、失败到恢复的状态变化为主线。把 `start` 与 `enable` 的区别放入状态模型，命令按状态转换组织；安装文件、启动失败和撤销变更分别形成可验证阶段。

### 6. Bash 错误处理

以同一个脚本在普通命令、条件、管道和命令替换中的失败传播差异为主线。先给出错误假设，再用最小实验逐项证伪；显式错误处理放在机制解释之后，最后用测试矩阵验证脚本状态。

## 八、验收标准

### 1. 单篇验收

- 开篇直接建立问题、结论和必要边界；
- 二级标题能够还原主问题路径，三级标题只承担真实子问题；
- 标题使用精确的概念型短语，目录形成知识树或任务阶段，不出现讲解式问句、对话句和完整结论句；
- 案例、反例、提示与局部验证默认保留在正文，不为增加目录层级而单独设标题；
- 每个核心小节都有定义或结论，并提供必要机制、场景、示例或证据；
- 命令、预期结果、解释和失败处理保持相邻；
- 表格只用于稳定对照，没有用表格承载连续操作或长段机制；
- 提示容器数量由真实重点决定，不连续堆叠；
- 文章结尾通过验收、案例或边界判断收束，不机械复述目录；
- 不存在空标题、单句骨架小节、占位文本和虚构输出。

### 2. 批次验收

- 六篇正文路径和标题保持不变；
- 六个 `publishedLink` 继续指向真实文件；
- 仓库文档测试全部通过；
- 运维构建单元成功；
- 新规范与根 `AGENTS.md` 不冲突；
- 六篇之间没有重复主讲知识，前置关系与 Linux、Bash 蓝图一致；
- 无 Ubuntu 实验环境时明确列出未执行的运行验证，不把静态检查写成实测结果。

## 九、设计决策

本次选择“公共阅读骨架 + 文档类型结构”，不采用全篇固定模板。统一的是问题进入方式、信息权重、证据位置和完成标准，不是章节名称和标题数量。

这个设计把系统学习作为主要阅读场景，同时保留通过标题、关键判断、命令块和故障现象快速检索的能力。后续新文章先确定类型和主线场景，再设计标题层级，不能从统一标题清单直接生成正文。
