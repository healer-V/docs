# 运维、Web3 与 AI 正文重构设计

本设计将已经在 Linux 文档中确认的标题、内容结构和验证方式扩展到运维与 DevOps、Web3、AI 三个知识领域。实施顺序采用“一个领域完成后再进入下一个领域”，避免同时维护三套未闭合的版本、术语和示例体系。

当前三个目录共规划 664 篇正文，其中运维与 DevOps 已发布 13 篇，剩余 651 篇仍处于未发布规划状态。文件存在不等于正文完成；只有通过内容、示例、构建和页面检查的文章才能开放导航。

## 一、重构目标

### 1. 内容目标

重构后的文章需要同时满足系统学习与日常检索：初学者能够沿知识依赖建立完整认识，有经验的读者能够通过精确标题、关键结论和验证证据快速定位信息。

每篇文章必须解决一个明确问题，完整解释必要概念、机制、操作方法、适用边界和判断证据。禁止使用标题数量、文章字数或代码块数量代替内容完成度。

### 2. 结构目标

标题统一使用“技术对象 + 必要限定”的短语。二级标题表达技术对象、能力域、机制阶段或任务阶段，三级标题表达组成、分类、状态、约束或独立操作。

标题不得写成对话、完整问句、讲解话术或冗长结论。正文负责解释“是什么、为什么、如何使用、如何验证以及失败时怎样处理”。

### 3. 工程目标

正文通过验收后才在 Catalog 和 Sidebar 中设置正式链接。所有新增链接必须指向真实文件，构建、导航、移动端布局和控制台检查必须通过。

旧稿与旧 URL 默认保留，不因退出新导航而删除。目录迁移、历史链接兼容和旧文件清理需要独立授权。

## 四、模块门禁

### 1. 模块蓝图

每个模块进入正文前必须具有独立蓝图，至少包括：

- 教学契约、读者基线和最终能力；
- 主版本、依赖版本和官方来源；
- 当前方向基础与跨方向前置知识；
- 知识项清单和无循环依赖关系；
- 章节职责、文章职责卡和统一场景；
- 知识覆盖矩阵和能力覆盖矩阵；
- 样板文章及其验证环境。

领域级目录不能代替模块蓝图。蓝图发现当前 Catalog 存在遗漏、重复或顺序问题时，先修订设计并说明影响，不直接在正文中扩张范围。

### 2. 样板文章

每个模块默认选择一篇能够体现主要难度的样板。模块同时包含差异明显的机制文章和高风险操作文章时，可以增加第二篇样板，但必须说明必要性。

样板需要完成正文、示例验证、页面渲染和评审记录。样板未确认时，不批量生成其余文章。

### 3. 逐章生成

一个章节是默认最大批次。每篇文章通过内容与工程检查后再进入下一篇；整章通过后统一开放本章导航。

```text
读取章节与文章职责
→ 核对版本和官方来源
→ 设计文章主线与证据
→ 生成并验证单篇正文
→ 检查跨篇遗漏与重复
→ 构建与页面检查
→ 开放当前章节导航
```

高风险示例、外部服务依赖或无法建立验证环境时，批次缩小到单篇，并准确记录未验证范围。

## 五、文章结构

### 1. 公共骨架

一级标题后直接进入技术对象、问题边界和核心判断，不添加学习目标、课程目录、上一篇回顾或下一篇预告。

正文按当前问题选择核心模型、连续子问题、证据链和收束方式。统一的是信息职责，不是固定章节名称和标题数量。

### 2. 类型结构

| 文章类型 | 主线结构 |
|----------|----------|
| 概念 | 对象定义 → 关系模型 → 关键差异 → 场景判断 → 边界 |
| 操作教程 | 最终结果 → 前置检查 → 分阶段操作与验证 → 失败恢复 → 验收 |
| 原理机制 | 参与对象 → 正常过程 → 状态变化 → 失败传播 → 观察证据 |
| 排障 | 现象与影响 → 现场保护 → 分层取证 → 分支收敛 → 恢复复测 |
| 对比决策 | 约束 → 候选方案 → 比较维度 → 取舍 → 回退条件 |
| API 与接入 | 环境与依赖 → 配置 → 调用 → 返回结果 → 错误处理 |

同一篇文章可以具有一个辅助类型，但必须保留一个明确主类型和唯一学习问题。

### 3. 证据组织

命令、配置或代码前说明目标和条件，结果后立即解释观察项。错误示例必须同时包含触发方式、失败表现、原因、定位证据和恢复动作。

无法实际执行时，必须标记为预期格式或未验证结论；静态检查、编译通过和真实运行不能混写为同一种验证结果。

## 六、导航与迁移

### 1. 发布状态

Catalog 中存在标题和文件名只表示规划。正文文件通过当前文章全部适用门禁后，才增加 `publishedLink`，Sidebar 随之生成可点击入口。

不得批量创建空 Markdown 文件来满足导航测试，也不得提前添加指向不存在正文的链接。

### 2. 旧稿处理

旧目录和旧页面继续保留原路径，但不参与新目录覆盖判断。新正文根据已确认蓝图重新生成，不从旧稿复制未经验证的结论和输出。

删除、重命名或建立旧链接兼容属于独立迁移任务，不包含在本设计的逐章正文生成中。

### 3. 已发布文章

现有 13 篇运维正文已经采用当前结构，默认不重复重写。后续蓝图修订只有在知识归属、版本或事实发生实质变化时，才对受影响文章定点修订。

## 七、质量验收

### 1. 单篇验收

单篇文章至少通过以下检查：

- Frontmatter 标题与唯一 H1 一致；
- 二级、三级标题编号连续且名称精确；
- 不存在空标题、单句骨架小节和连续定义堆叠；
- 概念、机制、操作和失败边界达到职责卡要求；
- 示例链路完整，验证状态真实；
- 超过 10 行的代码块使用具名 `details`；
- 内部链接、外部来源和资源有效；
- 桌面与移动端页面没有正文造成的布局错误；
- 不覆盖用户已有无关改动。

### 2. 章节验收

整章需要核对知识项覆盖、跨篇重复、版本一致、统一场景和导航状态。章节内任一文章存在核心门禁失败时，不把该章标记为完成。

### 3. 模块验收

模块结束时对照知识覆盖矩阵和最终能力执行整体验收，并记录已运行、仅编译、静态检查与未验证项目。构建成功不能替代内容与示例验收。

## 九、设计决策

本次选择顺序式领域推进，不采用三个领域同时批量生成，也不一次性生成全部空文件。顺序式推进让版本、术语、统一场景和验证环境保持可控，并使每个模块的经验能够修正后续模块。

三大领域共享文章结构和质量门禁，但不共享固定知识清单。运维与 DevOps 使用基础设施和平台覆盖模型，Web3 使用协议、语言与应用边界，AI 使用模型接口、上下文、工作流、评测、安全和运行成本覆盖模型。
