# AI 应用开发知识目录重构设计

AI 知识域面向具备基础编程能力、但尚未系统开发过 AI 应用的读者。学习主线从模型调用开始，逐步进入上下文设计、RAG、Agent、框架编排、应用架构、质量治理和生产交付，使读者能够独立构建、验证并运行一个可维护的 AI 应用。

本文是 AI 知识域的目录与迁移基线。它确定模块边界、学习依赖、章节主题、文章职责和导航策略，不表示 158 篇正文已经完成。正文必须按模块蓝图、文章职责卡和样板文章验收后逐章生成。

## 一、设计目标与范围

| 项目 | 设计决定 |
|------|----------|
| 核心主线 | 以 AI 应用从原型到生产的开发生命周期组织知识，不按模型厂商或单一框架组织 |
| 目标读者 | 具备一门编程语言和 HTTP/JSON 基础，未系统接触 AI 应用开发 |
| 学习结果 | 能完成模型接入、上下文设计、RAG、Agent、评测、安全治理和应用部署 |
| 模块规模 | 10 个模块、60 个章节、158 篇规划文章 |
| 导航分组 | 基础与接入、知识与智能体、工程与治理 |
| 目录重建 | 删除现有 `content/ai/` 整棵目录后按新路径重建，不保留旧页面兼容入口 |
| 首批页面 | 创建领域首页和 10 个模块首页；文章正文通过验收后才加入可点击导航 |
| 历史设计 | `superpowers/specs/` 中的历史设计作为决策记录保留，不属于旧 AI 正文目录 |

### 1. 纳入范围

- 基于托管或兼容 API 的模型调用与能力接入；
- Prompt、上下文、结构化输出和工具调用；
- RAG、Agent、MCP 与工作流编排；
- AI 应用的服务架构、评测、可观测性、安全、成本和部署；
- LangChain 与 LangGraph 的必要实践，但不以框架 API 罗列替代通用原理。

### 2. 排除范围

- 机器学习数学、传统机器学习算法和深度学习基础；
- 预训练、微调算法、分布式训练和完整 MLOps 平台；
- GPU 集群、量化、张量并行和自托管推理引擎的系统教程；
- 某一模型厂商、云平台或框架的完整产品手册；
- 与 AI 应用无直接关系的通用后端、前端、数据库和运维基础。

::: info 自托管推理的边界
vLLM、量化和模型并行可以在后续单独规划“模型推理基础设施”模块。本次“性能、成本与部署”只负责 AI 应用服务，不把模型服务基础设施混入同一学习主线。
:::

## 二、方案选择

| 方案 | 组织方式 | 优点 | 主要问题 | 结论 |
|------|----------|------|----------|------|
| 生命周期主线 | 基础接入 → 能力构建 → 工程治理 | 符合应用从原型到生产的真实过程，边界清晰 | 需要严格控制跨模块重复 | 采用 |
| 技术栈主线 | SDK → LangChain → LangGraph → 向量库 | 上手路径直观 | 易被框架版本绑架，通用能力割裂 | 不采用 |
| 能力专题主线 | Prompt、RAG、Agent、评测并列 | 单点检索方便 | 初学者难以理解前置依赖和交付顺序 | 不采用 |

目录采用生命周期主线，但保留稳定的能力模块。通用机制先于框架实现，质量、安全和运行能力贯穿开发过程，并在后半段集中形成工程闭环。

| LangChain、LangGraph | [LangChain 官方文档](https://docs.langchain.com/oss/python/learn) | 先讲通用机制，再讲框架映射；明确 LangChain 与 LangGraph 的职责 |
| MCP | [Model Context Protocol 规范](https://modelcontextprotocol.io/specification/draft/server/index) | 标注规范版本；区分 Prompts、Resources、Tools 及控制边界 |
| GenAI 可观测性 | [OpenTelemetry GenAI 语义约定](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/) | 标注语义约定的稳定性，不把开发状态内容写成固定标准 |
| AI 风险治理 | [NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework) | 用于风险治理框架，不替代具体技术控制 |
| LLM 应用安全 | [OWASP GenAI Security Project](https://genai.owasp.org/llm-top-10/) | 结合真实攻击链与验证方法，不只转述风险名称 |

通用文章不得绑定单一厂商。确需使用具体 SDK 时，先确定一种主实现完成可复现闭环，再用代码组或对照表补充兼容实现；不同厂商的请求字段、功能状态和计费规则必须分别核对。

## 十、导航开放规则

| 对象 | 设计状态 | 导航行为 |
|------|----------|----------|
| `content/ai/index.md` | 首批创建 | 顶部 AI 菜单提供“AI 应用开发”入口 |
| 10 个模块首页 | 首批创建 | 顶部菜单按三组开放，模块首页展示完整规划与建设状态 |
| 未完成文章 | 仅保留在 catalog 规划数据中 | 显示标题但不生成链接，不创建空文件 |
| 已验收文章 | 文件、职责、内容和链接均通过检查 | 在模块 sidebar 中开放链接 |
| 整章完成 | 章内文章全部验收 | 章节保持展开逻辑和连续编号 |

`.vitepress/themeConfig/catalogs/ai.js` 是 AI 目录和导航的单一事实源。模块编号必须按 AI01 至 AI10 连续排列，路径与本设计一致。`.vitepress/themeConfig/sidebar/ai.js` 继续使用公共生成器，不复制一份手写目录。

::: warning 规划标题不等于正文文件
重建目录时不得一次性创建 158 个空 Markdown 文件。只有完成文章职责卡、正文和验收后才创建对应文件并开放链接，否则导航应明确保持非链接状态。
:::

## 十一、迁移范围

### 1. 删除与重建

| 操作 | 目标 | 处理方式 |
|------|------|----------|
| 删除 | `content/ai/` 当前全部内容 | 删除 37 篇 Markdown 和 3 个图片资源，以及实施前新增的其他旧 AI 文件 |

| 保留 | `.vitepress/themeConfig/sidebar/ai.js` | 保持公共 catalog 生成方式，只有接口变化时才调整 |

删除范围严格限定为 `content/ai/`。历史设计文档、其他技术模块及其资源不因本次迁移删除。

### 2. 同步更新

| 文件或区域 | 更新内容 |
|------------|----------|
| `.vitepress/themeConfig/nav.js` 或公共导航配置 | 增加领域首页入口并使用新的三组模块导航 |
| `scripts/docs/__tests__/topic-navigation.test.mjs` | 更新模块路径、顺序、分组、章节数和文章数断言 |

| `scripts/baselines/route-redirects.json` | 移除 AI 旧路径重定向，不建立新兼容映射 |
| 仓库内有效链接 | 将仍需保留的非历史引用改到新路径；历史决策记录不回写 |

旧 AI URL 在迁移后允许返回 404。这是用户确认的破坏性变更，不生成别名页、跳转页或重定向规则。

## 十二、生成与验收门禁

| 顺序 | 门禁 | 通过条件 |
|-----:|------|----------|
