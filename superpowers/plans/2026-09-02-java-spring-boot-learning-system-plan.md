## 二、工作区保护与迁移原则

当前 Java 目录和 `backend.js` 已包含用户未提交的重构内容，Spring Boot sidebar 还包含指向未创建文件的预规划条目。所有迁移按下列规则执行：

| 规则 | 执行方式 | 完成证据 |
|------|----------|----------|
| 保留已有改动 | 修改前逐篇读取旧文档；只处理当前批次涉及的文件，不还原其他工作区改动 | 当前批次 diff 不包含无关文件 |
| 内容先迁移后清理 | 新目录文章完成并通过校验后，才处理职责已被取代的旧文件 | 旧知识项在覆盖矩阵中有唯一新归属 |
| 一章一次导航切换 | 当前大章全部文章真实存在后，再将该章 sidebar 指向新目录 | sidebar 不新增死链接 |
| 旧路径先查引用 | 删除或改名之前使用 `rg` 搜索仓库内引用；有有效引用时同步修改或保留兼容说明页 | 旧路径引用为零或具有明确兼容处理 |
| 不用骨架占位 | 未进入当前批次的文章不创建空文件，不提前加入 sidebar | 所有新增文章都通过小节完整性检查 |
| 控制批次大小 | 除样板外，每个交付批次最多重写一个大章 | 每批可独立检查、评审和回退 |

## 三、内容完成标准

每篇文章必须解决蓝图职责卡中的唯一问题，并达到“计算机相关专业毕业生可以独立读懂和复现”的深度。完成度不以标题数量或篇幅判断，而以知识闭环判断。

| 文档类型 | 最低完成标准 |
|----------|--------------|
| 概念与语法 | 给出准确模型、语法或 API 规则、适用边界、正反例和可观察结果 |
| 运行机制 | 说明参与对象、执行顺序、关键状态、失败传播，并通过代码、日志、字节码、时序或调试证据验证 |
| 接入与使用 | 提供版本、依赖、配置、完整核心代码、执行命令、预期结果和至少一个失败场景 |
| 设计与实践 | 使用订单业务约束给出决策依据、实现方案、反例和回退条件，不只罗列优缺点 |
| 测试与排障 | 提供可执行测试或诊断命令、观察点、失败输出、定位证据和恢复方式 |
| 维护与迁移 | 同一能力给出 Java 8/21 或 Boot 2.7/3.5 对照、兼容边界、迁移顺序和验证结果 |

所有 Java 示例中的新增类、方法和回调都要有职责注释；多入参方法使用 JavaDoc 说明参数约束、返回值或副作用。Spring Boot 示例还必须标明相对文件路径，并保持包名、端口、字段、错误码和订单业务规则一致。

## 九、样板评审项

Java 和 Spring Boot 样板都必须单独生成评审记录。用户确认样板后，后续章节沿用已确认的内容密度和证据要求；如样板标准发生变化，先更新评审记录和本计划，再继续生成。

| 评审维度 | Java 样板观察点 | Spring Boot 样板观察点 |
|----------|-----------------|------------------------|
| 读者适配 | 不假定读者熟悉 Java 类型系统，但不回避表示、提升和精度机制 | 假定已学 Java，重点解释 MVC 绑定链路和注解语义 |
| 内容深度 | 能解释“为什么得到这个值”，不止列出八种类型 | 能解释“请求怎样进入参数对象”，不止罗列注解 |
| 示例完整性 | 源码、命令、输出、失败和结论闭合 | 依赖、配置、Controller/DTO、请求、响应、测试闭合 |
| 业务真实性 | 使用金额、数量、标识、Unicode 文本等真实选择场景 | 使用创建/查询订单请求，并覆盖前端常见输入错误 |
