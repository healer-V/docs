# 运维与 DevOps 知识目录重构实施计划

本计划执行[运维与 DevOps 知识目录重构设计](../specs/2026-09-23-operation-devops-directory-design.md)。领域级设计已经确定十四个模块、五组导航、DevOps 导读和旧稿保留原则，但**尚未替代单模块蓝图和样板确认**。计划中的文章和路径只有通过对应阶段的验收后才成为正式内容。

## 一、交付范围与状态

| 对象 | 当前状态 | 计划交付 |
|------|----------|----------|
| 领域设计 | 已评审，未提交 | 作为模块边界和目录顺序的依据 |
| 旧正文 | 除已退役的 Linux 旧目录外，其他历史文章和首页继续保留 | 保留的旧文件与 URL 不作为新目录的正文映射 |
| 旧导航 | `nav.js` 和 `sidebar/operation.js` 有用户未提交修改 | 到实施导航阶段只修改运维相关片段，并保留其他改动 |
| 规划链接 | 当前运维 sidebar 二百二十七个链接中一百八十个无正文 | 转成结构化规划标题；不将缺失路径发布为链接 |
| 新模块 | 十四个模块尚无经确认的逐篇蓝图 | 每模块独立完成版本、来源、知识项、职责卡、矩阵和样板评审 |
| 新领域首页 | `content/operation/index.md` 尚不存在 | 说明 DevOps 与各模块边界，内容有效后作为导航入口 |
| 历史兼容 | 路由基线记录仍需保留的旧页面；已退役目录从基线清除 | 保留的旧页面继续提供原路由和锚点，删除的旧首页按迁移表重定向 |

这不是一次批量复制或移动任务。新模块独立写作；除已退役的 Linux 旧目录外，其他旧稿退出新导航但保持可访问。提交、推送与部署均不属于本计划的自动操作。

## 二、实施批次与依赖

| 批次 | 模块 | 进入条件 | 主要跨模块边界 |
|-----:|------|----------|----------------|
| 1 | Linux、Bash 与 Shell、网络基础、Nginx | 领域设计已确认 | 主机命令、脚本语法、网络机制与产品配置分开 |
| 2 | Docker、Kubernetes | 批次 1 的必要前置已有可引用正文，或在当前文中补足最小上下文 | 单机容器与集群工作负载分开 |
| 3 | CI/CD、Jenkins | Git 入门责任明确，交付通用规则已归属 CI/CD | 工具无关交付与 Jenkins 产品机制分开 |
| 4 | 监控与可观测性、SRE、运维安全 | 已有可观察的运行场景 | 遥测、可靠性决策和跨系统安全控制分开 |
| 5 | Ansible、Terraform、平台工程 | 主机、交付和集群边界已明确 | 配置管理、资源状态与平台自助服务分开 |

批次用于组织评审，不授权一次生成整个批次。每个模块分别经过蓝图确认与样板确认；单章正文是默认最大写作批次。无严格依赖的模块可在其自身门禁通过后调整工作顺序，但不改变十四个模块的公开学习顺序。

## 三、任务 1：现状审计与保护

1. 在每个批次开始时重新读取目标模块的真实 Markdown、同目录文章、导航、引用与 Git 状态，不能沿用早期统计覆盖后续用户修改。
2. 核对 `scripts/baselines/published-routes.json` 中仍需保留的旧路由与锚点；检查新目录没有与旧路由冲突。
3. 对现有的七个真实模块区分“正文已存在”“内容部分覆盖”和“仅有规划链接”；旧文标题不能直接作为知识覆盖证明。
4. 记录 `nav.js`、`sidebar/operation.js`、路由基线与重定向清单的现有未提交差异；编辑前逐项核对，其他领域内容不改。
5. 搜索跨模块正文与导航引用。已退役目录的引用必须清理；其他保留页面的历史链接按有效性处理，新正文只能引用经过验收的目标。

完成条件：每个待处理模块都具备真实文件清单、旧链接影响清单和与用户改动不冲突的编辑范围。若工作区新改动改变了目标文件或路由，先更新审计再实施。

## 四、任务 2：分别形成十四个模块蓝图

按照领域设计的 `01` 至 `14` 顺序，逐模块使用仓库根目录的 `standards/documentation/templates/module-blueprint-template.md` 和 `standards/documentation/templates/article-responsibility-card-template.md`。蓝图放入 `superpowers/specs/`，文件名包含日期、运维模块名与 `blueprint`，不覆盖已有设计稿。

| 蓝图部分 | 必须落实的内容 | 评审失败时的动作 |
|----------|----------------|------------------|
| 教学契约 | 零基础起点、明确前置、最终可验证能力和范围排除 | 收紧或调整当前模块边界 |
| 版本与来源 | 一个主版本、运行环境、关键依赖及官方资料直接链接 | 无法闭合版本时暂停该模块正文 |
| 知识项与依赖 | 稳定 ID、必要前置、来源、目标深度、证据和唯一主讲文章 | 修复漏项、循环依赖或重复主讲 |
| 章节与文章 | 两位连续章节编号、章内从 `01` 编号；每篇有完整职责卡 | 合并骨架化主题或拆分独立问题 |
| 覆盖矩阵 | 知识项和最终能力均有归属、验证方式与真实状态 | 不以文章数量代替能力闭环 |
| 旧稿审计 | 旧文具体知识、拟复用事实、缺口与不再采用的内容 | 旧稿不按文件名一对一映射 |
| 样板选择 | 选能体现主要示例、机制或排障难度的文章 | 不只选最简单的概述 |

每个模块蓝图还须确定适合从空目录复现的实验环境。版本可能影响示例与目录职责时，先核对官方版本和兼容矩阵，再最终确定标题；领域设计的规划主题可在蓝图中据证据合并或拆分，但实质修改模块范围或跨模块主讲归属须重新交用户确认。

完成条件：对应模块蓝图通过仓库 D01—D10 门禁并获得用户确认。十四个模块无须等全部蓝图完成才开始首模块样板，但没有本模块蓝图的模块不得写正文或接入正式链接。

## 五、任务 3：样板校准

1. 每个模块从已确认职责卡中选择一篇代表主要内容难度的样板；若同时存在差异显著的操作和原理型文章，在蓝图中论证第二篇样板的必要性。
2. 按仓库根目录的 `standards/documentation/article-generation.md` 完成样板，独立给出环境、依赖、代码或命令、执行入口、观察结果及失败边界。
3. 从空目录按本篇内容实际执行或验证核心示例；无法验证时记录具体阻塞，不编造输出。
4. 核查术语、版本、章节粒度、代码折叠、提示容器、链接和示例安全。将具有普遍性的修正同步回模块蓝图。
5. 用户确认样板后才开始该模块的其余正文。未确认时只修样板和受影响蓝图。

Linux 的首个样板优先选择能够验证主机服务、日志与故障判断的文章，而不是纯概述；具体篇目由 Linux 蓝图确定。其他模块分别根据自己的核心实践选择，不机械套用同一示例。

## 六、任务 4：建立目录数据与导航规则

此任务在相应模块蓝图和首篇真实内容通过门禁后执行，不提前向正式导航发布不存在的页面。

| 文件或能力 | 实施动作 |
|------------|----------|
| `.vitepress/themeConfig/catalogs/operation.js` | 建立十四模块、章节、文章规划的单一结构化来源；存稳定 ID、标题、目标文件名和可选已发布链接 |
| `.vitepress/themeConfig/sidebar/operation.js` | 复用现有 `createTopicSidebar` 思路生成侧栏；无正文的文章只显示纯文本 |
| `.vitepress/themeConfig/nav.js` | 顶栏改为“运维与 DevOps”，五组模块按领域设计排序；只为真实首页提供链接 |
| `content/operation/index.md` | 撰写 DevOps 导读、能力链路、已开放范围及规划说明；不放旧稿入口或不存在的链接 |
| `scripts/docs/__tests__/topic-navigation.test.mjs` | 覆盖十四模块唯一性、顺序、编号、有效链接与规划纯文本行为 |

新目录的首页必须呈现真实内容和开放范围，不创建一行标题的空壳文件。导航切换应限于运维片段；不能覆盖其他领域在同一配置文件中的用户改动。旧平铺目录仍可由直接 URL 访问，但不出现在新 nav/sidebar。

目录数据和页面不可自行推断“规划即完成”。`publishedLink` 只在对应正文已经存在、内容与工程验收通过后加入；生成侧栏时对不存在的 `publishedLink` 抛错，不能靠导航过滤掩盖录入错误。

## 七、任务 5：逐章生成与迁移

| 顺序 | 每章动作 | 完成证据 |
|-----:|----------|----------|
| 1 | 读取本章知识项、职责卡、前置章节和现有旧稿 | 唯一主讲与输入状态清楚 |
| 2 | 每篇按职责卡写正文，示例从本篇的空目录独立复现 | 有实际命令、输出、失败边界和验证记录 |
| 3 | 检查同章及相邻模块重复、漏项、术语和版本 | 覆盖矩阵与职责卡同步更新 |
| 4 | 只为通过验收的文章补 `publishedLink` 与有效相对链接 | 新侧栏中该文章可点击，其余规划项不可点击 |
| 5 | 检查旧页面路由与锚点仍由原文件提供 | 无需重定向，历史入口保持有效 |
| 6 | 按章执行测试与运维构建单元验证 | 通过后才进入下一章 |

新正文不引用旧稿或仓库示例目录作为完成教程的必要入口；旧文仅作内容审计证据。发现领域设计中的重大漏项或跨模块主讲冲突时，暂停受影响批次，修订对应蓝图并重新确认，不边写边扩大目录。

## 八、任务 6：工程验证与历史路由检查

| 验证层次 | 执行入口 | 通过标准 |
|----------|----------|----------|
| 目录与导航单元测试 | `pnpm docs:test` | 编号、路径、规划/发布状态和有效性断言通过 |
| 运维构建单元 | `node scripts/docs/build-unit.mjs operation` | 新旧运维页面可构建，正式链接目标存在 |
| 全站产物 | `node scripts/docs/build-all-units.mjs` 后运行 `node scripts/docs/assemble-site.mjs --input .build/units --output .build/assembled` | 所有构建单元合并成功，无路由/文件冲突 |
| 历史路由 | `node scripts/docs/check-route-baseline.mjs --site .build/assembled` | 四十七个旧运维入口及要求保留的锚点仍可用 |
| 全站链接 | `node scripts/docs/validate-site.mjs --site .build/assembled` | 正式 nav、sidebar、正文与静态资源无本次新增死链 |
| 页面体验 | 按本地服务规范复用已有预览服务，必要时运行浏览器回归 | 桌面和移动端导航分组、侧栏与导读页可用 |

单章修改先执行定向测试与运维单元构建；完成一个模块、跨模块导航切换或最终验收时执行全站组装与历史路由检查。构建产物只用于验证，不修改历史基线以消除失败。启动本地服务前检查是否已有本项目可复用服务，临时服务在验证结束后关闭或明确记录端口。

## 九、停止条件与交付记录

| 停止条件 | 处理方式 |
|----------|----------|
| 模块主版本或核心官方事实无法确认 | 标记受影响知识项，暂停该模块正文，继续不受影响的审计 |
| 蓝图或样板未获用户确认 | 不进入该模块批量正文和正式导航 |
| 现有未提交改动与目标编辑无法兼容 | 停止重叠文件编辑，明确冲突和可选方案 |
| 新文章无法独立验证核心示例 | 修正文档或环境；不能宣布章节完成 |
| 旧路由或锚点消失 | 保留旧文件，定位路由冲突；不直接改历史基线 |
| 导航中出现不存在文件的链接 | 移除发布链接或先完成正文验收；规划项保留纯文本 |
| 涉及删除旧稿、提交、推送或部署 | 不在本计划内执行，需单独明确授权 |

每章交付记录应写明新增页面、知识项覆盖状态、运行验证结果、导航链接、旧路由检查和未解决风险。最终交付对照十四个模块分别汇总：蓝图/样板状态、已开放章节、内容与工程门禁、旧稿保留情况。未开放模块继续显示为规划，不以目录已设计宣称正文完成。
